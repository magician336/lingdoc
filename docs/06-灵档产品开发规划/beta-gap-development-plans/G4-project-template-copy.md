# G4. 项目级模板副本与规则编辑

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)
> 相关计划：[G1. 建项语义与草稿阶段](G1-draft-baseline.md)、[G4. 模板、规则与问题治理](G4-template-rules.md)
> 本文件把“用户可以编辑模板”限定为项目级模板副本；团队共享模板库不纳入本阶段。

## 1. 目标和边界

LingDoc 不是申报主管部门。模板是 LingDoc 或用户整理、发布的项目结构版本，不自动代表外部官方要求。用户应能按照自己的写作方式调整项目模板，但历史项目、立项基线和交付快照仍必须可解释、可回放。

本计划交付：

- 从已有模板版本复制出一个项目级模板副本；
- 在草稿期编辑副本的字段、章节和项目级规则配置；
- 在立项确认时使用当前副本生成 ProjectSpec 字段集和章节骨架；
- 已立项项目通过 `template_upgrade` ChangeSet 修改模板；
- 保存每个副本的来源、作者、版本、变更和绑定关系。

本阶段不交付：

- 跨项目共享模板库；
- 通用可视化模板市场；
- 用户编写任意代码执行规则；
- 把用户模板宣称为主管部门的正式申报要求；
- 直接改写已经被历史项目或交付快照使用的模板版本。

本阶段只讨论领域逻辑。规则能力限定为系统预定义规则的声明式配置；用户可以启用、停用、限定适用范围和调整允许范围内的参数，但不能在本阶段创建新的规则执行器或上传自定义代码。

## 2. 模板的来源和层级

模板来源必须显式记录：

| 来源 | 含义 |
|---|---|
| `lingdoc_builtin` | LingDoc 随产品提供的起始模板，仅代表产品方案 |
| `organization_input` | 组织或领域专家整理的模板要求 |
| `project_copy` | 某个项目从已有模板复制后形成的私有副本 |
| `external_reference` | 根据外部指南、通知或申报书整理的参考模板 |

已有模板版本是复制起点，不是不可修改的权威。复制后，项目拥有自己的模板编辑空间；源模板后续发布新版本不会静默改变该项目副本。

源模板的“撤回”默认只表示不再允许新项目复制；已存在的项目副本仍按自己的版本和哈希运行。若发现模板存在必须停止使用的错误或风险，必须单独标记为“强制禁用/安全召回”，并在项目侧显示原因、影响范围和可执行的迁移或恢复路径。

模板的权威范围只能描述为“谁发布、适用于什么项目、依据哪些材料”，不能只用 `official` 作为无来源的状态。

## 3. 项目级模板副本

### 3.1 绑定关系

创建项目时，用户先选择一个可用模板版本，系统同时建立：

- `Project.template_profile_id`：复制来源的稳定引用；
- `ProjectTemplateCopy`：该项目自己的模板副本；
- `base_template_version`：复制时所依据的源版本；
- `project_template_version`：副本自己的版本序号；
- `template_source`、`created_by`、`created_at` 和审计信息。

项目实际使用的字段、章节和规则配置以 `ProjectTemplateCopy` 为准。`template_profile_id` 只用于追溯复制来源，不能绕过副本读取当前内容。

每个副本版本必须保存内容哈希和规则哈希（至少包括字段、章节、术语和规则配置）。立项绑定、`template_upgrade` ChangeSet、章节骨架和 ReleaseSnapshot 都引用具体的副本版本及其哈希；哈希变化就视为新版本，历史对象不能只引用“当前模板”。

### 3.2 副本状态

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `draft` | 尚未绑定到正式项目基线的可编辑副本 | 编辑、预览、迁移、立项确认 |
| `bound` | 已随项目立项确认成为当前模板版本 | 读取；active 项目只能通过 ChangeSet 生成新版本 |
| `superseded` | 被项目的新模板版本替代 | 只读历史和回放 |
| `discarded` | 项目草稿丢弃后不再使用 | 只读审计，不可重新绑定到其他项目 |

副本没有独立的跨项目发布状态。用户要给其他项目复用，必须等后续团队模板库能力，不允许通过复制 ID 形成隐式共享。

## 4. 用户可以编辑什么

### 4.1 字段

用户可以：

- 增加项目自定义字段；
- 修改字段显示名称、说明、顺序和帮助文本；
- 调整字段是否为项目要求的必要字段；
- 设置数据类型允许的格式约束；
- 将源模板字段标记为本项目不使用，但必须保留迁移和审计记录。

用户不能：

- 修改已经存在的稳定 `field_id` 的数据类型而不经过迁移；
- 用删除字段的方式静默丢失已有 ProjectSpec 值和溯源；
- 在立项确认时隐藏仍未处理的必要字段；
- 把字段检查结果伪装成外部机构的合规结论。

### 4.2 章节

用户可以：

- 增加、删除和重排项目级章节；
- 修改章节标题、说明、顺序和是否可选；
- 将自定义字段或 ProjectSpec 字段声明为某章节的写作上下文；
- 为章节设置字数、格式和引用展示等可配置约束。

删除或停用已有章节时，系统必须显示受影响的草稿、章节引用和待交付对象。active 项目不能直接删除已有章节，必须走 `template_upgrade` ChangeSet。

### 4.3 规则

Beta 先支持声明式规则配置：必填、长度、格式、术语一致性和对象存在性等规则。用户可以选择是否启用、设置适用章节和严重度，但不能上传任意代码或改变规则执行器的安全边界。

规则的严重度受判定方式约束：只有可重复计算、判据明确的结构和格式规则才可以申请阻断；模型辅助、语义相似度或需要学术判断的规则最多产生警告或提示，不能单独阻断立项或导出。项目编辑者可以在允许范围内调整严重度，但把规则升级为阻断必须经过产品与领域专家评审并留下版本记录。

用户自定义的规则必须标记 `origin = project`；LingDoc 内置规则标记 `origin = lingdoc`。两者都要保存 `rule_id`、版本、严重度、目标对象和审计记录。项目规则不能删除源模板历史中已经产生的 ValidationIssue，只能对新版本重新求值。

## 5. 草稿期编辑流程

项目处于 `draft` 时：

1. Owner 或具备项目设置权限的 Admin 打开模板编辑器；
2. 系统建立副本编辑事务，展示来源版本和当前副本版本；
3. 用户编辑字段、章节和声明式规则；
4. 系统预览字段迁移、章节影响、必要字段缺失和规则变化；
5. 用户保存后，`project_template_version` 和 `project_version` 条件递增；
6. `current_context_revision` 仍为 `0`，不创建 ChangeSet；
7. 立项确认读取当前副本，生成对应的 ProjectSpec 字段集和章节骨架。

模板编辑保存与 ProjectSpec 保存使用同一项目版本条件。两个成员基于同一副本版本同时编辑时，一次成功、一次 `version_conflict`，不得静默覆盖。

## 6. 立项和 active 项目边界

立项确认把当前 `ProjectTemplateCopy` 绑定为项目的模板基线。此时：

- 副本状态从 `draft` 变为 `bound`；
- 项目进入 `active`，`Context Revision` 从 `0` 变为 `1`；
- 章节骨架按副本当前章节定义生成；
- ProjectSpec 按副本当前字段定义冻结；
- 立项确认不会创建 `ChangeSet`。

active 项目修改字段定义、章节结构或规则绑定，必须创建 `template_upgrade` ChangeSet。评估预览至少列出：

- 字段迁移和 orphaned/missing 结果；
- 章节新增、删除、重排和已有版本影响；
- 规则、ValidationIssue、确认和交付影响；
- 新模板版本的 `ruleset_hash`。

只有 Owner 能应用该 ChangeSet。应用成功后，新副本版本、项目模板引用和新的 Context Revision 在同一事务中写入；旧版本继续供历史章节和 ReleaseSnapshot 回放。

## 7. 权限与审计

| 动作 | 默认权限 | 必须记录 |
|---|---|---|
| 复制模板 | 项目创建者/Owner | 来源模板版本、复制者、时间 |
| 编辑草稿副本 | Owner、Project Admin | 字段/章节/规则差异、旧值、新值、版本 |
| 立项绑定副本 | Owner | 当前副本版本、确认差异、基线记录 |
| 创建 active 模板升级 | 有项目编辑能力的成员 | base_revision、影响预览 |
| 应用 active 模板升级 | Owner | ChangeSet、评估结果、新 Context Revision |
| 查看历史副本 | 项目可读成员 | 当前访问授权和读取审计 |

`owner_unavailable` 下不能编辑或绑定新的模板基线；完成所有权转让后，新 Owner 必须重新读取当前副本和影响预览。模板副本权限不能扩大资料、章节或租户权限。

## 8. 迁移和失败语义

| 场景 | 必须发生 | 不能发生 |
|---|---|---|
| 复制源模板 | 建立项目私有副本 | 项目直接共享源模板可变记录 |
| 修改字段类型 | 生成迁移预览和处理状态 | 静默转换或丢失值 |
| 删除已有字段 | 标记 orphaned 并保留溯源 | 物理删除历史值 |
| 新增必要字段 | 标记 missing 并阻断确认 | 立项时自动填空值 |
| 两人同时编辑副本 | 一次成功，一次版本冲突 | 后写入覆盖前写入 |
| 源模板发布新版本 | 项目副本保持不变 | 自动改变项目字段或章节 |
| active 模板修改 | 要求 template_upgrade ChangeSet | 普通保存直接改项目结构 |
| 规则严重度改变 | 新版本重新求值并保留旧问题历史 | 沿用旧问题裁定到新规则 |
| 项目被丢弃 | 副本不可写但可审计 | 复制记录恢复成其他项目模板 |

## 9. 交付切片

| 切片 | 交付物 | 完成判据 |
|---|---|---|
| G4P.1 模板来源与副本 | source、copy、版本和绑定关系 | 项目复制后可独立编辑，源模板更新不影响副本 |
| G4P.2 字段编辑 | field_id、类型、必要性、迁移预览 | 不静默丢值，ProjectSpec 可按副本字段集读写 |
| G4P.3 章节编辑 | 章节增删改排、骨架生成 | 立项生成的骨架与副本版本一致 |
| G4P.4 声明式规则 | 项目规则、严重度、求值输入和审计 | 项目规则可运行但不能上传任意代码 |
| G4P.5 active 升级 | template_upgrade ChangeSet、影响评估 | 旧版本可回放，新版本原子绑定 |
| G4P.6 编辑器界面 | 来源提示、预览、冲突和恢复 | 用户能看见差异、缺失、孤儿和失败原因 |

## 10. 领域验收场景

### AC-G4P-01：复制并编辑

用户从 LingDoc 内置模板复制一个项目级副本，修改字段名称、增加自定义章节并调整顺序。源模板不变，草稿项目读取到修改后的副本。

### AC-G4P-02：字段迁移

用户把一个文本字段改为枚举字段。系统先显示迁移预览；未处理的旧值进入待处理状态，未完成处理前不能立项。

### AC-G4P-03：立项使用副本

Owner 确认时，系统按项目副本的字段和章节生成 ProjectSpec 与章节骨架，不读取源模板的后来版本。

### AC-G4P-04：active 模板升级

active 项目通过 `template_upgrade` ChangeSet 增加章节。影响预览列出确认、规则和交付影响；应用失败时项目仍绑定旧副本版本。

### AC-G4P-05：并发编辑

两名成员基于同一副本版本编辑。只有一个保存成功，另一方重新读取后才能合并；不得出现半套字段迁移。

### AC-G4P-06：历史回放

项目模板经过两次升级后，旧章节版本和旧 ReleaseSnapshot 仍能读取当时绑定的模板副本和规则哈希。

## 11. 与其他能力线的交接

### 交给 G1

- 创建项目时建立的项目级模板副本；
- 草稿期模板编辑、字段迁移和当前副本版本；
- 立项确认使用副本生成字段集与章节骨架。

### 交给 G3

- active 模板升级的 `template_upgrade` ChangeSet；
- 字段、章节、规则和确认的影响预览；
- 新旧副本版本与 Context Revision 的绑定。

### 交给 G5

- 模板复制、编辑、立项绑定和升级应用的 capability；
- 项目级副本不可跨项目读取或隐式共享的边界。

### 交给 G6

- 模板副本编辑、迁移冲突、规则重算和历史回放 fixture；
- 用户完成一次“复制—编辑—立项—升级”的时间、失败和恢复记录。
