# T15-02：执行器按场景驱动，F01 结论不变

状态：2026-09-27 完成。执行器不再内置任何场景身份，规格由调用方传进来；F01 的逐条结果**与改前逐字节相同**。需要说清覆盖范围：契约 mock 上改前改后都只能走 7 步、都在第 8 步轮询超时（mock 的 `getGeneration` 样例停在 `queued` 且不推进，见 §回归证据），完整 23 步由注入 `opener` 的合成轨迹覆盖，两者相加才等于「结论不变」。机器生成的证据在 `docs/08-本轮实施方案/T15-S3-证据.json`。

对应票 #29；是 #27（T15 错误矩阵）里「把写死 F01 的那一处解开」的前半步，后面 #31（请求定义与断言求值）、#32（跨步捕获）、#33（读回式副作用断言）都挂在这个接缝上。

## 结论

`scripts/lingdoc_mock/run_f01.py` 现在只认**传进来的规格**，不再认 `"F01"` 这个字符串：

1. `F01Runner` → `ScenarioRunner`，构造参数从「一份 workflow 字典」变成 `ScenarioSpec`（`id` / `steps` / `download_sha256_variable`）。
2. 装载时校验的是**形状**（每步必须有 `operation_id`、数字 `expected_http`、`request` 对象），不是场景身份；`id != "F01"` 那条硬校验删掉了。步内 `id` 缺失时按 `F01-01` 的既有约定合成（`<场景 id>-<两位序号>`）**供报告使用**；报错则改用契约里真能查到的地址（`scenario F22 step 1`），不拿合成 id 指路。
3. 规格有两个来源，同一个装载入口 `load_spec(path, scenario_id=None)`，也同一个构造点 `spec_from_document`：
   - **步清单文档**（workflow.json）：文档自带 `id` 与 `steps`，直接驱动；
   - **scenarios.json 里按 id 点名的一条**（`--scenario F01`）：F01 条目自己不写步骤，用 `specification_file` 指向 workflow.json，装载器照着这条指针去取——这条指针是契约里写着的，不是执行器里的特例。
4. 场景条目里那句单数形式的 `assertion`（F02–F22 用的是它）在装载时归一进 `assertions`，于是既有的 `manual_assertions` 机制照常把意图文本原样列进报告、标 `not_run`。对 F01 这条是**空操作**（F01 用的是复数 `assertions`），它服务的是 #31 之后真能跑起来的场景步骤；留着是因为去掉它就等于「场景的意图文本静默消失」，而静默丢失正是这条链上反复出问题的地方。

**报告格式本票冻结**：键名与结构一字未动（含 `workflow` 这个键名——驱动场景时它的值是场景 id；改名留给 #38 的矩阵报告）。

## 回归证据（怎么复核）

**对契约 mock 跑 F01。** 契约 mock（`scripts/lingdoc_mock/server.py`）返回固定样例，`getGeneration` 的样例是 `queued` 且不会推进，所以这条流程只能走到第 7 步、第 8 步轮询超时——**这是运行环境的事实，不是回归**。改前 / 改后的比对因此是「同样的 7 步 + 同样在第 8 步失败」，两边 report（`completed_steps` / `steps` / `failed_step` / `manual_assertions`）与 stdout、stderr **逐字节相同**（`regression_mock_provider`，三轮摘要全等，含 `--scenario F01` 这条新路径）。下面是证据里实际跑的三条命令（`argv` 原文见证据；`before` 那份是 `HEAD` 的模块原文另存到仓外，副本不在仓库根，所以显式给 `--openapi` 与 `--workflow`）：

```text
python scripts/lingdoc_mock/server.py --port 4017 &
python .scratch-t15-02/run_f01_before.py --openapi docs/08-本轮实施方案/contracts/openapi.json --base-url http://127.0.0.1:4017/api/v1/lingdoc --poll-timeout 3 --report .scratch-t15-02/mock-f01-before.json --workflow docs/08-本轮实施方案/contracts/workflow.json
python scripts/lingdoc_mock/run_f01.py --openapi docs/08-本轮实施方案/contracts/openapi.json --base-url http://127.0.0.1:4017/api/v1/lingdoc --poll-timeout 3 --report .scratch-t15-02/mock-f01-after.json
python scripts/lingdoc_mock/run_f01.py --openapi docs/08-本轮实施方案/contracts/openapi.json --base-url http://127.0.0.1:4017/api/v1/lingdoc --poll-timeout 3 --report .scratch-t15-02/mock-f01-via-scenario.json --scenario F01
```

stdout 与 stderr 分开取摘要（stderr 只有那一行 `F01 FAILED: F01-08: timed out waiting for terminal state succeeded`）：拼接两股流再取摘要会得到另一个值，证据因此把两者分列，不受缓冲与合并顺序影响。

**完整 23 步。** 契约 mock 走不到底，所以整条规格的比对走执行器单测那条注入 `opener` 的接缝（不发真网络）：把改前（`HEAD` 的模块原文）与改后的模块各驱动一次，比对**报告全文 + 每步的 HTTP 方法与完整 URL**，逐字节相同（`regression_synthetic_trace`，`identical: true`，两侧 sha256 见证据）。

**F02–F22 现在确实还不可执行，原因会被明确报出**（`scenario_selection`）：

| 场景 | 退出码 | 报错 |
| --- | --- | --- |
| F22 | 1 | `F22 FAILED: scenario F22 step 1 has no request definition in the contract; only specifications that declare path, query, header and body inputs can be driven` |
| F17 | 1 | `F17 FAILED: F17 has no executable steps; its contract holds prose assertions only` |
| F99 | 1 | `F99 FAILED: scenarios.json has no scenario F99` |

三条都是**装载期拒绝**，不会发一个请求、不会写出半真半假的报告。缺的是契约里的请求定义（#31），不是执行器的省略。报错里的地址（`scenario F22 step 1`）是契约里真能查到的那一步；报告里才会出现合成的 `F22-01`。

## 边界（没验证到的，如实记下）

1. **断言仍未被求值。** 本票只把「认场景」这一步做完：报告里 `manual_assertions[].status` 依旧是 `not_run`，`provider_semantics_status` 依旧是 `not_verified`。可求值断言是 #31。
2. **`--scenario` 目前只有 F01 一条能真跑**（其余三条被如实拒绝，见上表）；README 里记录的 `--base-url` / `--report` 两个参数没变。
3. **没有对着真实服务跑。** T15-01 已证 `cmd/server` 能在本机起来并接受真实请求，但本票的回归全部在契约 mock 与注入式合成轨迹上完成，没有对着真实服务发过一个请求。
4. **模块文件名没改。** 里面的类已泛化成 `ScenarioRunner`，文件仍叫 `run_f01.py`——`.github/workflows/lingdoc-f01-runner.yml` 的触发路径、`py_compile` 清单与 job 名都挂着它，改名要连带动 CI、README 与文档里的命令（已查：`main` 目前**未开启分支保护**，所以没有「必需检查名」会被牵连）。文件名与实际职责的错位记在这里，等 #31 让 `--scenario` 真能跑起非 F01 的场景后再一并处理。
5. **白盒观察点在 #34 单独补入。** 本票完成时 F02 系那类「不调用模型、不检索全库」的「未发生」断言仍无观察点；后续 T15-07 只为 F02 增加受限白盒计数，不改变服务行为。
6. **旧参数名 `--workflow` 不保留别名。** 它只出现在代码里、未进任何文档，直接换成 `--spec`；外部若有按旧名调用的脚本会立即报 `unrecognized arguments`，而不是被悄悄忽略。这是本票唯一一处**故意的不兼容**，理由见 §审查结论 第 5 条。
7. **场景条目自己那层的断言文本没被带进来。** 装载只把**步骤**归一，条目级的 `assertion`/`assertions`（F02 那类「整体失败不得只处理已授权子集」写在条目上）本票既不读也不报错；报告里不会出现它们。这是 #31 的事，记在这里免得被当成已覆盖。
8. **装载规则和执行器 HTTP 逻辑现在同住一个文件**（`run_f01.py` 已 530+ 行，本票又加了约 60 行装载代码）。它同时为「装载契约」和「驱动 HTTP」两个理由而改，属于会随 #31/#32 继续分叉的 Divergent Change 候选。没有拆是因为 CI 的触发路径与 `py_compile` 清单都按文件名写死，拆模块要一并改门禁；等 #31 往里加断言求值时再拆更划算。
9. **两处相邻文档事实被顺带改正**（不是格式整理，是纠正已经变假的陈述）：README 的场景数 `21` → `22`（契约里实际是 22 条），`T15-真实服务启动.md` 里那条「0 字节空壳文件留待人工处理」——那个 `'` 文件已在本票期间删除、其余此前已消失，原话已成假陈述。两处都在本票的提交里，若审阅者认为该另开一票，把这两个 hunk 摘出去即可，不影响执行器改动。

## 审查结论

本票完成后跑了两轴审查（Standards / Spec，各自独立子代理，基线是 `ff3b3d2`）。逐项处置如下，均为本票内修复：

| 意见 | 轴 | 处置 |
| --- | --- | --- |
| `ScenarioSpec.mode` 是死字段，且两处契约来源的 `mode` 取值不同、装载器静默偏向场景侧 | 两轴 | 删除该字段（连同 `load_spec` 里的静默优先逻辑与两条断言）。执行器不解释 `mode`，README 已写明「怎么跑」写在契约里、由人执行 |
| `ScenarioSpec(...)` 在两处重复构造 | Standards | 合并为单一构造点 `spec_from_document`；指针场景的 id 覆盖改为显式 `spec_id` 参数 |
| 直接构造出的 spec 会让 `run()` 抛裸 `KeyError` | Spec（脆弱性） | 抽 `_request_definition`，装载与运行共用同一条拒绝语；不再有裸 `KeyError` 路径 |
| 拒绝语里的 `F22-01` 在契约里查不到（是运行器合成的） | Spec（脆弱性） | 报错改用契约里的真实地址 `scenario F22 step 1`；合成 id 只留在报告的 `steps[].id` |
| 证据里的 `stdout_sha256` 无法按文档命令复现 | Spec（证据） | 原来把 stdout 与 stderr 拼接后取摘要，文档没写这个约定；改为两股流分别落盘、分别取摘要，并把每轮 `argv` 原文与工作目录写进证据 |
| 证据的 `command_note` 低估了改前侧所需参数 | Spec（证据） | 注明改前侧除 `--workflow` 外还要显式给 `--openapi`（副本不在仓库根，ROOT 解析会偏） |
| 交付文档开头读起来像 mock 已覆盖整条 F01 | Spec（完整性） | 开头改为明写「mock 只到第 7 步、第 8 步超时；23 步由合成轨迹覆盖」，与 §回归证据 一致 |
| `main()` 里嵌套三元表达式 | Standards | 提取为具名 `failed` |
| 新交付文档没有从 README 链进来 | Standards | README 该节末加链接 |
| `--workflow` → `--spec` 改名属于范围蔓延 | Spec | 保留，但在此说明理由：本票把「执行器驱动什么」从「F01 的 workflow」改成「任意规格」，参数名跟着走到事实一边；该参数未进任何文档，改名不破坏对外契约。已在 §边界 6 宣布为故意的不兼容 |
| 场景条目层的断言文本未被带进来 | Spec（完整性） | 不改，登记为 §边界 7，归 #31 |
| 单数 `assertion` 归一会改变非 F01 规格的报告内容，而 AC4 冻结了报告内容 | Spec（范围） | 保留：AC4 冻结的是 F01 的输出与报告**格式**，两者都逐字节未变；对 F01 这条归一是空操作。理由同 §结论 4 |
| 装载与 HTTP 逻辑同文件（Divergent Change） | Standards | 本票不拆，登记为 §边界 8，说明为何等 #31 更划算 |
