# T15-03：把声明的起点状态灌进真实服务，并读回确认

状态：2026-09-27 完成。装载器 `scripts/lingdoc_mock/load_state.py` 把契约 `starting_states` 里声明的起点（项目、条件、协作者、是否立项、章节正文、绑定资料）对着**真实服务**发前置写请求造出来，再用 `getProject` / `listChapters` / `listAssets`（必要时加一次检索预检）读回，逐条比对：不一致就打 `MISMATCH …` 到 stderr 并以 1 退出。六份声明（S1–S6）各连跑两遍，全部退 0、不一致清单全空、两轮的读回事实与其摘要相同。需要说清覆盖范围：**读回只证到通道能证的那一层**——提供方对不可用资料只答「不可用」，所以声明里更细的处理状态（`pending`/`failed`/…）进报告的 `unverified` 而不是冒充已验证；template、source、candidate、confirmation、release、export 造不出来，这一点由装载器连理由一起拒绝并写进每份报告。机器生成的证据在 `docs/08-本轮实施方案/T15-S4-证据.json`。

对应票 #30；是 #27（T15 错误矩阵）里「场景要有已知起点」这一步，#28（真实服务起来）、#29（执行器按规格驱动）已完成，#31 起要在这个起点上真跑场景。

## 结论

`scripts/lingdoc_mock/load_state.py` 只做两件事：按声明发写请求，然后读回。

1. **只声明造得出来的部分。** `SUPPORTED_PARTS = project / assets / chapters`；其余六个名字进声明会被**连理由一起拒绝**（`the service ships the demo template…`、`a candidate is produced by a generation run…`），不会被静默忽略——静默丢掉一部分正是这票要防的半截状态。同一份拒绝清单写进每份报告的 `cannot_build`，也是后续票会撞上的真实约束；这些理由不全是读契约得来的：「正文引用资料」那条跑了真服务，拿到提供方自己的答复（§边界 2）。
2. **写请求按依赖顺序发**：建项目 → 存条件 → 加协作者 → 立项 → 写章节 → 绑资料。每一步的版本前置条件都取自**本次运行看到的响应**（建档答 `spec_revision=0`，存条件就必须送 0；立项要送存条件后的 `spec_revision`；写章节要用 `listChapters` 里那一节的 `current_version_id`），没有任何地方写死版本。每个写请求带 `Idempotency-Key`。
3. **绑定是独立一步**，不并进立项：提供方的 `bindAsset` 只看写权限、不看立项（`internal/lingdoc/workspace/http.go`），草稿项目也能绑资料。同票新增的 S6 声明（草稿 + 已绑可用资料）就是在真实服务上钉这条约束的。
4. **读回分三类通道**，各答一个问题：
   - `getProject`：项目名字、模板、状态、条件、成员与角色；
   - `listChapters`：每节的正文与引用，以及「空正文章节不该有版本」这条否定面；
   - `listAssets`：**只列可用资料**，所以它既证「声明可用的那条在」和它的 `processing_state`，也证「声明不可用的那条不在」；
   - `retrieveSources` 预检：只对**不可用**的那条发（可用资料由 `listAssets` 回答，不必惊动检索），它在检索前按 `asset_not_authorized` 拒绝，带 `details.denied[].reason ∈ not_authorized / not_ready / not_found`，用来把「不可用」与「无权」「提供方不认这条绑定」分开。预检用**绑定 id**（`asset_ids` 指绑定，不是指知识；绑定 id 的唯一来源是 `bindAsset` 的响应）。
5. **比对包含否定面**：多出一条没声明的可用资料、草稿项目却有章节、空正文章节却挂着版本，都会报出来。只检查「声明里写了的东西在不在」会漏掉这三类。
6. **报告分两半，各有摘要。** `snapshot` 是声明里那些**被读回确认过**的事实，`observed` 是读回本身产生的事实（`project_version`、章节是否已有版本、资料可用性），`snapshot_digest` 与 `observed_digest` 各算各的。**「同一份声明跑两遍、读回结果相同」的判据是 `observed` 及其摘要 + 两次都为空的不一致清单**：只比 `snapshot_digest` 等于拿声明跟它自己比，证不了提供方那一侧。
7. **证不到的就说证不到。** 提供方只答「不可用」，`pending`/`processing`/`failed`/`replaced` 之间没有任何通道能区分，所以声明里那句更细的话进报告的 `unverified`，连原因一起写。
8. **多给的绑定会被拒绝。** `--knowledge` / `--member` 只接受这份声明**用得到**的名字，在第一个写请求之前就拒绝（`preflight`）：多给的绑定和打错的绑定长得一样，静默忽略就是把「半截状态」放进来。
9. **脱敏与执行器一致**：报告不含令牌、不含提供方 ID（只有契约里的名字），只含 `provider_host`。报告在**任何写请求之前**先落盘 `not_started`，中途失败留下 `failed` 与死在哪个步骤。
10. **不新增依赖、不新增传输层**：装载器直接用执行器抽出来的 `ProviderClient`（`opener` 注入、重定向凭证规则、16 MiB 上限、JSON 解码都在那一处），本票顺手把它从 `ScenarioRunner` 里抽成独立类，于是装载器不必再构造一个空规格的执行器来借传输。

## 回归证据（怎么复核）

**环境起点。** 真实服务按 [T15-01 的启动配方](T15-真实服务启动.md) 在本机 8080 上跑（本机 dev 库 + postgres 5432 / redis 6379 / docreader 50051）。声明里用名字引用两种真实资料与一名真实成员，环境事实由 `.scratch-t15-03/env_facts.py` 造并**幂等**（按名字找或造）：

| 名字 | 环境事实 | 怎么来的 |
| --- | --- | --- |
| `k-demo` | `parse_status=completed` 的知识 | 在带 `lingdoc-embedding-dashscope` 的知识库里发布一条合成材料，解析完成 |
| `k-notready` | `parse_status=draft` 的知识 | 同库一条草稿材料：解析从没跑过，永远不是 ready |
| `u-member` | 租户成员（`contributor`） | 注册一个合成账号并加进租户 |

**六份声明 × 两轮。** 命令（绑定按声明生成，见下）：

```text
python scripts/lingdoc_mock/load_state.py --state <S> \
  --base-url http://127.0.0.1:8080/api/v1/lingdoc <该声明用到的 --knowledge/--member> \
  --report .scratch-t15-03/run-<S>-<轮次>.json
```

| --- | --- | --- | --- | --- |
| S1 空资料项目 | 立项，两节都无正文，无资料 | 3 写 / 4 读 | `89d64fbf…` | 是（读回摘要 `d9ee7bb9…`） |
| S2 协作者与人工正文 | 立项，一名协作者，研究问题一节有人工正文 | 5 写 / 4 读 | `1e733868…` | 是（`4828518c…`） |
| S3 绑定未就绪资料 | 立项，绑一条不可用资料 | 4 写 / 5 读（含预检 422） | `7f55ea5f…` | 是（`6a6e5f81…`） |
| S4 草稿已填条件 | 只建项目与存条件，不立项、无章节 | 2 写 / 3 读 | `4768d193…` | 是（`e9df5bf6…`） |
| S5 绑定可用资料 | 立项，绑一条可用资料 | 4 写 / 4 读 | `d6ee9068…` | 是（`f5d21486…`） |
| S6 草稿已绑资料 | 建项目、存条件、绑一条可用资料，**不立项** | 3 写 / 3 读 | `9e7311fe…` | 是（`bb0e3bd2…`） |

S3 与 S5 是**同一种声明形状**，只差绑定的资料可不可用：一个由 `listAssets` 的否定面 + 预检 `not_ready` 证成，一个由 `listAssets` 直接列出证成。两轮的摘要逐个相同即是「起点可重复构造」。原始报告、stdout/stderr 与汇总都在 `.scratch-t15-03/`（被 `.gitignore` 的 `.*` 覆盖，不入库）。

**负向对照：读回不是走过场。** 把两边的绑定对调后重跑（`.scratch-t15-03/negative_control.py`）：

```text
S5 声明可用、实际绑了不可用资料 → exit 1
MISMATCH /assets/k-demo: declared '已绑定且可用', read back 'listAssets 未列出：资料未就绪（not_ready）'
S3 声明不可用、实际绑了可用资料 → exit 1
MISMATCH /assets/k-notready: declared '不可用（pending）', read back 'listAssets 把它列为可用资料'
```

同一条声明、同一批写请求，只换绑定的资料，结论就跟着翻转——这说明读回确实在问提供方，而不是在复述声明。

**独立核对：不看接口看库。** 证据里的 `provider_check` 直接查库（`docker exec WeKnora-postgres-dev psql`），按声明的项目名聚合：每个名字下**每跑一遍就有一行**，且这些行的状态、项目版本、规格修订、章节数、章节版本数、资料数、成员数**逐行相同**（`identical: true`）。这核对的是「写请求真的落了库、形状与声明一致」，接口读回是另一条独立通道。

**测试与静态检查。**

```text
python -m unittest discover -s scripts/lingdoc_mock -p 'test_workflow*.py'   # Ran 62 tests … OK
python -X utf8 docs/08-本轮实施方案/contracts/validate_artifacts.py          # PASS，starting_states 6，22 个静态反例
```

单测不发真网络：注入式 `opener` 后面是一份薄薄的提供方替身，只回答这批操作；它按真实网关的语义实现预检（`asset_ids` 指绑定，没有绑定答 `not_found`），所以「传知识 id 去预检」这类错误在单测里就会露出来。

**抽传输层没有动到执行器。** 装载器不再借执行器的 `request`，两者共用一个 `ProviderClient`——这是碰执行器的改动，所以另跑一遍 F01 对着 mock（`scripts/lingdoc_mock/server.py`，固定样例、无库无鉴权）的回归：同一条命令、同一份 `--openapi` 与默认 `workflow.json`、同样的 `--poll-timeout 3`，产出的报告**逐字节相同**（sha256 `af7a0697…`），stdout、stderr 与退出码也逐项相同（`.scratch-t15-03/check_f01_regression.py`，结果进证据的 `runner_refactor`）。第 8 步轮询超时是 mock 的 `getGeneration` 样例停在 queued 导致的，两侧一致，不是回归。

## 边界（没验证到的，如实记下）

1. **不可用资料的细分状态证不到。** 声明里写 `pending`，通道只能证到「不可用 + `not_ready`」；`processing` / `failed` / `replaced` 互相之间没有任何通道能区分。装载器把这句话记进报告的 `unverified`（连原因），**不**把它当成被证实的事实。要真区分，得先有能读回处理状态的接口。
2. **造不出来的部分**（写进声明会被拒绝，理由进每份报告的 `cannot_build`）：`template`（服务固定提供）、`source`（检索产物）、`candidate`（要模型）、`confirmation`（要候选带的待核项）、`release`（要已确认章节）、`export`（要过检的快照）。**由此推出一条真实约束**：「有正文且有引用」的起点目前造不出来。这不是猜的——本票真跑过一条探针声明（项目立项后写一节带 `[[source:s-demo]]` 与 `source_ids: ["s-demo"]` 的正文），真实服务在 `saveChapter` 上答 **HTTP 403 `source_access_denied`**，装载器把这条错误原样报出并把 `failed_step` 记进报告（证据里的 `cannot_build_probe`）。声明里的正文标记与 `source_ids` 必须一致这条本身两处都查，但它一致了也造不出引用：source 是检索产物，没有写请求能造。（探针留下了一个无章节的空项目 `T15-03 探针：正文引用资料`，名字不在 `合成起点%` 里，不进证据的库内核对。）
3. **没有验证「造完起点后场景能跑」。** 本票只交付装载；按规格驱动场景、断言求值是 #31 起的事。报告里的 `verification_scope=declared_state_read_back_only`、`provider_semantics_status=not_verified` 就是这句话。
4. **并发与重放没验证。** 幂等键保护的是同一个键的重放，不保护两个并发运行同时建同名项目；本票的每轮都是一次一个、串行跑。同一份声明跑 N 遍就是 N 份项目（软删除，靠人清理）。
5. **重复构造只验证了「连续两轮」。** 两轮之间没有重启服务、没有清库，也没有跨天；「同一份声明在任何时候跑都一样」超出本票证据。
6. **写请求只按契约形状校验。** 每个写请求的 body 字段先对 OpenAPI 要一次（多一个字段、少一个必填都会拒），但业务规则（谁能立项、条件字段的取值域）由服务自己判；服务拒绝时报的是它的错误码，不是装载器的猜测。
7. **`k-demo` 的「可用」依赖环境。** 它靠一条已解析的知识撑着；换环境要重造（`env_facts.py` 是仓外脚本，不入库，也不属于交付）。
8. **起点规则在静态检查与装载器里各写了一遍。** `validate_artifacts.py` 的 `check_starting_state` 与 `load_state.py` 的 `state_from_declaration` 表达同一套约束。本票只把**已经分叉**的那一处统一了（`[[source:…]]` 的字符集，以提供方自己的 `sourceMarker` 为准：静态检查与运行期现在同严）。余下的重复是**有意保留**的：静态检查的职责是独立复述契约规则、在没有任何实现的情况下也能跑；让它 import 运行期模块会把「契约是源、实现跟随」倒过来，并让契约检查继承实现的错误。代价是加一条规则要改两处，记在这里。
9. **S6 是新加的声明，只有两轮证据。** 其余五份在两轮之外还有更早几轮的库内行（`provider_check` 里 S1/S2/S3/S5 各 8 行、S4 6 行、S6 2 行），行行相同；S6 的「同形状重复」目前只有这两轮。
10. **绑定与成员只增不减。** 装载器不加角色、不移除成员、不撤权（撤权族的起点是 #35 的事）。

## 审查结论

本票完成后跑了两轴审查（Standards / Spec，各自独立子代理，基线 `b32bef4`，改动即当时的工作区）。逐项处置如下，均为本票内修复：

| 意见 | 轴 | 处置 |
| --- | --- | --- |
| README 与测试里指向的交付文档不存在（唯一一处断链） | 两轴 | 本文件即那个目标，两处链接现在都成立 |
| README 的 S5 例子给了 S5 用不到的绑定，而装载器静默忽略——与「不接受半截状态」自相矛盾 | Standards | 装载器新增 `Bindings.refuse_unused`，在第一个写请求之前拒绝多给/打错的名字；README 例子改为每份声明只给自己用到的名字；补两条测试（单测 + 命令行） |
| AC3 的证据是同义反复：`snapshot` 由声明构造，两轮摘要必然相同 | Spec | 报告新增 `observed_digest`（读回事实的摘要），`repeatability` 的判据改成「两轮 `observed` 相同 + 两轮无不一致 + 每轮退 0」；README 那句话改写；证据里记录 `observed_digests` |
| 资料声明的细分状态只被验了一半（写 `failed` 也能过） | Spec | 报告新增 `unverified`（含「为什么」），逐条记下证不到的部分；README 与 §边界 1 明说；补两条单测（有缺口 / 无缺口） |
| `_non_empty_string`、`_read_json_object` 与执行器逐字重复 | Standards | 在执行器里提升为公开的 `non_empty_string` / `read_json_object`，装载器改为导入，副本删除 |
| 起点规则两处实现且已分叉（`[^\]]+` vs `[A-Za-z0-9_-]+`） | Standards | 分叉处统一到提供方自己的 `sourceMarker` 字符集；余下重复为有意保留，理由见 §边界 8 |
