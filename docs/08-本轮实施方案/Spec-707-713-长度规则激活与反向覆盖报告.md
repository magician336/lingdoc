# Spec-707-713 长度规则激活与反向覆盖报告

Issue：[#713](https://github.com/magician336/lingdoc/issues/713)（表形状守护：修正 delivery 行结构 project_id 声明宽度漂移并激活 PG 侧规则 4，范围经 #713 评论扩充：表级反向列存在性 + 文档收口）。Spec：#707（已随 PR #712 合入 main，合并提交 `5b2a4bc4`）。

## 开工卡片

- **用户可见结果**：长度规则（Spec v1 第 4 条）在 PostgreSQL 侧激活；delivery 两处真实宽度漂移修正；versioned/SQLite 链建出的**每一列**都必须被同表登记行结构并集声明（规则 1 的反向，双方言）——「产物列无人声明」这一静默盲区关闭。
- **范围内**：规则 4 机制恢复与激活（SQLite 保持文档化 no-op）；delivery 两结构体 `size:64→36`；表级反向列存在性检查（双方言）；裁定与登记随之新增；#708 文档 superseded 注记；AST 嵌入提升盲区的决策记录。
- **范围外**：各表 project_id 产物侧宽度不一致（19×varchar(36)/6×varchar(64)，票面 Out of scope）；`lingdoc_asset_revisions`（evidence 的 ProjectAssetRevision）尚不在清单——记为后续候选，不在本票扩；AST 扫描对嵌入提升 TableName 的强制（本票决策：不实施，理由见裁定表 4）。
- **前置依赖**：#712 已合入 main。
- **真实消费者**：做 LingDoc schema 变更的贡献者与评审者；执行面 = app verify job（SQLite 守护）与 integration job（`^TestPostgres`，PG 孪生 + 反向覆盖）。
- **领域不变量**：守护是纯测试侧机制；生产改动仅限与真实列形状对齐的声明 tag（本票两处）；判定规则唯一出处仍集中在守护头注；排除目标态为零（本票零排除，登记扩大为显式 diff）。
