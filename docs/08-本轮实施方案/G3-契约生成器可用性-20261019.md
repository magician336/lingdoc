# 契约可被生成器消费：#223 的 G1–G4 修正（2026-10-19）

对应 [#223](https://github.com/magician336/lingdoc/issues/223) 的 N3。该节原文写明：若结论是「不适合」，本票转为「修契约使其适合」，而不是记为已知限制。本文件记录这次修正的范围、依据与复现命令。

## 为什么要改

2026-10-19 在 head `7341aa8` 上对着真实服务做过一次生成客户端实调：用 `openapi-typescript 7.13.0` 从 `contracts/openapi.json` 生成类型（137 个 schema、四层嵌套 `$ref` 全部解析成功），再用 `openapi-fetch 0.14.0` 以生成的 `paths` 类型调用 `GET /projects/{projectId}/change-sets/{changeSetId}/impact-assessment`（HTTP 200，字段全部正确解出）。**生成与调用都成功，但过程中撞到四处契约缺口**——它们不是生成器的问题，是契约没把运行时已经要求的东西写出来。

| # | 缺口 | 运行时事实 | 生成客户端的困境 |
|---|---|---|---|
| G1 | `POST /projects/{projectId}/change-sets/{changeSetId}/assess` 未发布 | 路由存在（`internal/lingdoc/workspace/impact_routes.go:90`） | 契约里没有这个操作，客户端无从触发评估 |
| G2 | `POST /projects/{projectId}/activation-read` 未发布；`GET /activation-diff` 无响应 schema | 路由存在（`internal/lingdoc/workspace/full_workflow_http.go:65`） | 拿不到立项回执 id；回执形状只存在于前端手写类型里 |
| G3 | `ActivateProject` 只有 `expected_spec_revision` 且 `additionalProperties: false` | 运行时要求 `activation_read_id`（`workspacecore/service_facade.go:3356-3360`），并使用 `expected_project_version` / `reviewed_project_version` | 契约形状的客户端**在语法上就发不出**这三个字段；按契约发 `POST /activate` 恒定 400 `invalid_request` |
| G4 | `ResolvedImpact.action` 枚举缺 `NO_ACTION`（`DependencyEdge.action` 有） | 服务端确实会产出 `NO_ACTION` 影响（实测响应里就有） | `tsc --strict` 报 `TS2322: Type '"NO_ACTION"' is not assignable to type '"REVALIDATE_EVIDENCE" | … | "BLOCK_RELEASE"'` |

`additionalProperties: false` 本身不是问题：openapi-typescript 不把它表达成封闭类型，多一个未声明字段照样通过类型检查，客户端因此不会因服务端将来加字段而编译失败。问题在于**必需字段没有出现在契约里**。

## 改了什么

| 位置 | 改动 |
|---|---|
| `contracts/openapi.json` | 新增 `POST /projects/{projectId}/activation-read`（含 `ActivationReadRequest` / `ActivationReadReceipt` / `ActivationReadResponse`）与 `POST /projects/{projectId}/change-sets/{changeSetId}/assess`；`ActivateProject` 增加 `activation_read_id`（必填）、`expected_project_version`、`reviewed_project_version`；`GET /activation-diff` 补响应 schema（`ActivationDiff` / `ActivationDiffResponse`）；`ResolvedImpact.action` 增加 `NO_ACTION` |
| `contracts/scenarios.json` | F12 增加一步 `recordActivationRead` 并带回执编号；canonical fixture 同步 |
| `contracts/workflow.json` | F01 连续规格增加一步 `F01-03b`（`recordActivationRead`），F01-04 立项时带回执；步数 23 → 24 |
| `contracts/validate_artifacts.py` | 轨迹负控改为按步骤 id 定位（原先按位置，插入一步就会静默改测别的步骤）；`not_run` 去掉已执行的 meta-schema 与 Prism 两项，新增 `external_validation` 记录工具、版本、结果与 head |
| `internal/lingdoc/workspace/impact_routes_contract_test.go` | `impactOwnedPathSuffixes` 增加 `/assess`——正因缺了它，`assess` 路由才漏出契约覆盖 |
| `scripts/lingdoc_mock/` | 状态装载器在立项前先登记回执；测试用提供方新增 `activation-read` 路由；G6 门禁的步骤 id 白名单允许 `F01-03b`；各处步数 23 → 24 |

## 为什么 F01 轨迹的步号不重排

新步骤取 id `F01-03b`，`F01-04`–`F01-23` 保持原样。历史证据文件（`T15-S3-证据.json` 等）按步号引用过 F01 轨迹，那些是**记录**而不是规格，重排会改写历史。因此只在轨迹里插入一步，不动已有编号；`F01` 的步数由 23 变 24。

## 仍然没做的事

- 本文件只修**契约**。#223 的 N1（浏览器人工验收）另有未满足项：`assessment.objects`（确定影响对应的 required 集合）与 `impacts[].causes[].source`（来源对象）在页面上没有渲染，确定影响与可能影响也没有分成两组。那是前端改动，不在本 PR 内。
- F01 的 24 步仍然**没有对着真实服务跑过**（`mode` 仍是 `specification_not_executed_against_provider`）。本次只保证契约自洽、静态校验通过、生成器能消费。
