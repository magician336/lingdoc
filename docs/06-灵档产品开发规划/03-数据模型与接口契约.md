# 数据模型与接口契约

> **后续设计参考**：本文保留完整产品方案；本轮范围见[实施方案](../08-本轮实施方案/01-范围与任务流程.md)，领取以[任务池](../TEAM_DEVELOPMENT_TASKS.md)为准。A/B/C 仅指领域，不分配人员。完整 PCC、复杂权限等不自动成为本轮前置条件。

## 1. 设计原则

1. 每个领域只有一个写入所有者；其他领域只能持有稳定引用。
2. `WeKnora` 内部 `knowledge_id/chunk_id` 是基础设施定位信息，不是 LingDoc 跨域主键。
3. 每条会影响项目语义的记录均带 `project_id`、权限范围、创建/修改审计字段与适用 Revision。
4. 事件至少一次投递是常态；消费者以 `event_id` 和业务幂等键去重。
5. 删除与替换优先软删除/失效标记，保留可审计的谱系；真正物理清除依资料保留策略执行。

## 2. 核心实体

| B | `Chapter` / `ChapterVersion` | id、project_id、template_section、body、parent_version、revision、status | 允许差异、回退和确认绑定到具体版本 |
| B | `ChangeSet` | id、project_id、base_revision、delta_json、status、approved_by | 先评估后应用的实质变更 |
| B | `DependencyEdge` | from_ref、to_ref、relation_type、origin、confidence、active | 跨域关系图；`origin` 区分人工/规则/模型候选 |
| B | `ImpactTask` | id、revision、target_ref、action_type、owner_domain、status、idempotency_key | 变更后可追踪的待办/异步任务 |
| B | `Confirmation` | target_ref、target_version、scope、actor、decision、reason | 只对特定对象版本及核查范围有效；统一记录内容确认（B 域 `ChapterVersion`/`ResearchClaimVersion`）与证据确认（A 域 `EvidenceCard`），确认记录本身始终由 B 写入，A 只发布证据状态 |
| C | `TemplateProfile` | id、grant_category、year、version、sections、required_fields、ruleset_id、ruleset_hash、status | 模板和规则按申报类别/年度版本化；`required_fields` 决定 `ProjectSpec` 的字段集，`sections` 决定立项确认时生成的章节骨架 Ch1–ChN；领域定义与规则实现归 C，发布/生效的治理流程走 RuoYi 管理台（见 [`02-领域架构与PCC`](02-领域架构与PCC.md) 第 1 节） |
| C | `ValidationIssue` | check_level、release_snapshot_id、rule_id、kind、severity、target_ref、target_version、status | 可计算规则与人工判断问题均可呈现，但语义不同；`severity` 为阻断/警告/提示，`status` 为 `OPEN` / `RESOLVED` / `DISMISSED`（判定为误报并删除）。`kind` 区分判定方：`computed` 由规则求值、`model` 由模型判定——两类产出**同一实体、同一严重度、同一处置方式**，这是「模型判断与规则判断同等可推翻」能够成立的前提，也让更换模型不影响交付契约。`check_level` 区分同一套规则的两次求值：`content` 对项目当前内容（模板检查，不需要快照，`release_snapshot_id` 为空），`release` 对指定快照（预检，`release_snapshot_id` 必填）；两者共用规则集、严重度与处置方式，但**问题实体不同**。`target_ref` + `target_version` 标识问题落在哪个对象的哪个版本上，两级求值共享这个身份。处置权限见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 3.3、4 节 |
| C | `ReleaseSnapshot` / `ExportArtifact` | project_id、context_revision、content_version_set、template_version、status | 明确“这次文件到底由哪些版本组成” |

## 3. 版本边界

不要把所有版本都叫作 `version`：

| 名称 | 表示什么 | 例子 |
|---|---|---|
| `AssetRevision` | 项目资料/解析的版本 | PDF 被重新上传或重新解析 |
| `ContextRevision` | 项目语义的全局稳定序号 | 增加变量、改变样本范围；`0` 表示草稿期空基线 |
| `ChapterVersion` / `ResearchClaimVersion` | 章节或主张文本版本 | 人工修改章节第二段 |
| `TemplateVersion` | 申报模板和规则版本 | 2027 年度模板升级 |
| `ReleaseSnapshot` | 一次交付组合的不可变快照 | 导出的 DOCX 所依据的集合 |

`ContextRevision` 变化不必强制所有章节/主张版本重写，但会使依赖它的确认和派生结果进入待复核状态。

`Context Revision 0 → 1` 是这条序列里**唯一不改变语义的递增**：它把草稿期内容冻结为正式基线，而不是修改项目语义（见 [`07-建项阶段设计`](07-建项阶段设计.md) 第 5.3 节）。由此，基于 `Revision 0` 产生的语义相关结果——例如草稿期的调研候选池——在立项确认后**不标 `STALE`**，因为其依据的语义内容等于 `Revision 1` 的内容。第 5 节的防陈旧不变量与 [`02-领域架构与PCC`](02-领域架构与PCC.md) 第 4.2 节的机械版本比较，在此需按语义判读，不能只比数字。

## 4. 命令、事件与查询

### 4.1 命令

| 命令 | 发起方 → 处理方 | 前置条件 | 结果 |
|---|---|---|---|
| `CreateProjectDraft` | UI → B | 调用者为租户 `active` 成员且角色 ≥ `Contributor` | `Project`（`status=draft`、`Revision 0`）与创建者的 `ProjectMember`（`governance_role=owner`）；可选指定负责人，并自动发起一次所有权转让 |
| `ConfirmProjectBaseline` | UI/Owner → B | 研究条件满足所选模板必要字段的最低要求；Owner 已查看两类差异（他人改动、仍是 AI 填写且未经人工改动） | 章节骨架 Ch1–ChN、`Context Revision 1`、`status=active` |
| `CreateChangeSet` | UI → B | 用户有项目编辑权限 | 草稿 ChangeSet |
| `AssessChangeSet` | B → PCC | 基线 Revision 仍为当前 | 影响预览和候选任务 |
| `ApplyChangeSet` | UI/负责人 → B | 已评估且基线未漂移 | 新 Context Revision、领域任务 |
| `RevalidateEvidenceCard` | B → A | 引用合法、任务未被更新 Revision 取代 | 证据状态/候选结果 |
| `GenerateChapterCandidate` | B → B/A | 指定章节、上下文切片、资料范围 | 带依据的候选内容 |
| `RunTemplateCheck` | UI → C | 项目已立为 `active`，存在章节骨架 | 针对项目当前内容的问题清单；不改变交付状态，也不产生跨域事件 |
| `RunDeliveryPreflight` | B → C | ReleaseSnapshot 可构造 | 问题清单和交付状态 |
| `DismissValidationIssue` | UI → C | 该问题仍为 `OPEN`；须持 `delivery.issue.dismiss`——警告/提示级可由 `Owner`、`Admin`、`Member + Author` 或 `Member + Reviewer` 删除，阻断级仅 `Owner` 或 `Member + Reviewer` | 该问题置 `DISMISSED`，记录删除人、理由、规则与目标版本，重算该快照交付状态 |
| `ExportRelease` | 负责人 → C | 无阻断问题且指定快照稳定 | ExportArtifact |

命令在 API 层需强制项目权限、Revision 比较和幂等键。长任务返回任务 ID，不以 HTTP 超时作为失败语义。

### 4.2 事件信封

所有跨域事件使用同一信封，载荷只传稳定引用与必要摘要：

```json
{
  "event_id": "uuid",
  "event_type": "evidence.revalidated.v1",
  "occurred_at": "2026-09-19T00:00:00Z",
  "tenant_id": "t-01",
  "project_id": "p-01",
  "context_revision": 118,
  "causation_id": "changeset:CS-42",
  "correlation_id": "impact:IT-17",
  "producer": "lingdoc.evidence",
  "payload": {}
}
```

版本化事件类型不可就地破坏性变更；新增字段可选，重大语义改变升级 `.v2`。

### 4.3 最小事件目录

| 事件 | 生产者 | 消费者 | 语义 |
|---|---|---|---|
| `workspace.context_revision_applied.v1` | B | A、C | 有新项目语义，按关联范围更新 |
| `evidence.project_asset_revision_changed.v1` | A | B | ProjectAsset 替换/重解析，旧 EvidenceCard 可能不可用 |
| `evidence.project_asset_scope_revision_changed.v1` | A | B、UI | 项目有效资料范围变化（导入、撤销或授权调整），生成与重校验的输入集合随之改变；与上一条的 `AssetRevision` 不是同一个版本概念 |
| `evidence.revalidated.v1` | A | B | 返回支持、缺失或候选证据，带基于的 Revision |
| `workspace.confirmation_invalidated.v1` | B | C | 交付快照需重检/可能阻断 |
| `workspace.release_snapshot_changed.v1` | B | C | C 运行预检 |
| `delivery.issue_detected.v1` | C | B | 模板/路线图/文件问题，需要项目任务处理 |
| `delivery.release_ready.v1` | C | B/UI | 指定快照可请求导出 |

## 5. 关键不变量

- 草稿期（`status = draft`、`Context Revision 0`）不得创建 `EvidenceCard` 或 `ResearchClaim`：证据卡的意义是支撑一条主张，而主张属于已经成立的项目语义。草稿期允许上传与归档 `ProjectAsset`、对话、受控检索与 `ProjectSpec` 草拟。
- 职能 scope 为空有两种**相反**语义，不可混同：对 `Owner` 是**全集**（它不参与职能轴），对其他治理角色是**尚未指派**（对章节等对象的写权为空，默认拒绝）。草稿期授予的职能角色在立项确认后进入待指派状态。
- 「丢弃」与「归档」是两回事，不可共用一个状态：丢弃是 `draft` 项目的**软删除标记**（`discarded_at`），表示这段构想未成立；归档是 `active` 项目的 `status = archived`，表示项目已结束。**仅 `draft` 可丢弃，`active` 项目只能归档**。丢弃保留审计与可恢复入口，物理清除依资料保留策略执行（见第 1 节第 5 条）；系统既不自动丢弃也不自动归档。
- 一份 `HUMAN_CONFIRMED` 内容必须指向固定 `ChapterVersion`/`ResearchClaimVersion` 和确认范围；内容、所依证据或项目语义实质变化后不得沿用确认。
- `ReleaseSnapshot.context_revision` 必须等于导出时项目的稳定 Revision；若发生新变更，旧快照仅可作为历史文件，不可伪装为当前正式版本。
- A 无权更新 B 的 `ResearchClaim`/`Confirmation`；A 只能发布证据状态。C 无权更新 B 内容；C 只能发布交付问题/状态。
- 每个 `Project` 有且仅有一个 Owner（`owner_user_id`）；所有权转让是原子操作，项目不得处于无 Owner 状态。`Owner` 不由邀请产生，只能由转让变更。因为 `changeset.apply`、`delivery.export` 与 `project.archive` 仅 Owner 持有，失去 Owner 即等于项目无法推进变更、放行交付或归档；转让是解除该状态的路径。Owner 因租户侧停用而暂时不可用时，项目进入 `owner_unavailable`，只冻结这三项能力，见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 8.3 节。
- `STALE` 任务结果不得覆盖现行结果。允许保留给人工比较，但必须明确标注来源 Revision。
- 一个 `BLOCK_RELEASE` 未关闭时，系统不生成 `READY` 状态，正式导出也不接受阻断级豁免——阻断项只能被修复、关闭或判定为误报删除，不能被跳过。警告与提示级问题不阻断导出，但豁免必须显式记录负责人、理由和风险清单，并进入导出审计。
- **模板检查与预检是同一套规则对两类对象的两次求值**，不是两套并行的检查体系：`content` 级对项目当前内容，写作过程中随时可跑，结果只落在 UI、不产生跨域事件、不影响交付状态；`release` 级对指定 `ReleaseSnapshot`，由内容变化、模板变更或确认失效触发，是导出放行的唯一依据。只有预检，格式与字段缺口会被推迟到交付前才暴露；只有模板检查，则答不出「这一个快照到底能不能导」。两者共用严重度与处置方式，各自产生问题实体。
- **“删除”与“豁免”语义相反，不可混用**：豁免是承认问题真实存在、本次接受，只对警告/提示级开放；删除（`DISMISSED`）是判定规则或模型判断有误、这条问题本不该存在，对任一严重度开放，包括阻断级——AI 会产生幻觉，用户必须能推翻它。删除同样必须记录删除人、理由、规则 ID、判定方与目标版本并进入导出审计，且只对“该规则 + 该目标对象 + 该对象版本”生效——**这个作用域跨检查级别、也跨判定方**：在模板检查里被删除的问题，预检只要目标对象版本未变就不再报出，反之亦然；模型类判定与规则类判定在这条上无差别。模型类问题默认取较低严重度，且不得自动关闭或自行降级，只能由人工处置或内容变化触发。目标对象产生新版本后删除失效，问题在下次求值重新出现，不得成为永久静音。
- 证据、文本、模板和导出均不得跨 `tenant_id/project_id/authorization_scope` 越权读取或拼入模型上下文。

## 6. WeKnora 适配契约

LingDoc A 建立 `KnowledgeGateway`，屏蔽内部实现。最小接口为：

```text
IngestProjectAsset(assetRef, file, processingProfile) -> ProcessingRun
GetProcessingStatus(assetRef) -> AssetProcessingStatus
RetrieveEvidence(query, allowedAssetRefs, contextRevision) -> EvidenceCandidate[]
ResolveAnchor(assetRef, anchor) -> SourceExcerpt | NotFound
```

适配层负责把 WeKnora 的上传/处理/检索/引用结果映射为稳定 `ProjectAsset` 与 `SourceAnchor`。当 WeKnora 重解析导致 chunk 改变时，A 发布资料修订事件，而不是让 B/C 保存失效 chunk ID。
