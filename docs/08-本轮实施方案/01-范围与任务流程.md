# 本轮范围与任务流程

协作/任务模型版本 0.5；业务范围未因 20→16 的任务重组扩大。任务不预分给个人，不按特长分组；负责人和评审人在领取时填写。架构中的资料、工作区、交付是接口边界，不是三份固定人员工作包。

## 交出什么

**新建项目 → 填研究条件 → 选择已有资料 → AI 起草 → 采纳和人工编辑 → 确认 → 检查 → 导出可编辑 DOCX。**

先用固定演示模板、两个代表性章节和明确配置的测试成员贯通。账号、上传、知识库处理尽量复用现有能力；没有正式业务模板时必须标为演示。保留的待核内容须随内部演示文件显示。

暂缓通用模板编辑器、复杂组织权限、多人实时编辑、完整 PCC/论证图、外部学术检索、精细排版、机构管理台和微服务建设。本轮是可运行内部演示，不等同完整 Beta 或正式申报能力。

## 怎么推进

1. **先验证真实难点。** 指定资料真实检索/生成；持久化与条件写入；固定两章真实 DOCX。三项可并行，失败也形成明确结果。可维护的验证代码直接演进，避免先做后扔。
2. **把最小接口交给消费者。** 固定模板、生成上下文、候选/来源、交付输入分别给样例和小接口。消费者可先用 fake，提供方尽早交真实小切片。
3. **接通三个用户结果。** 项目→人工保存→读回；选资料→生成→服务端采纳→再编辑；两章确认→冻结检查→导出打开。不等大模块全部做完才联调。
4. **随功能验证失败路径。** 版本冲突、结果过期、资料撤权、重复请求、模型/导出失败不能丢掉用户编辑或把旧状态冒充当前。

任务顺序与领取见[任务池](../TEAM_DEVELOPMENT_TASKS.md)，合作方式见[协作约定](../06-灵档产品开发规划/05-团队分工与代码边界.md)。

## 工作量与重估

原投入口径约每天 3–4 小时、17 个可投入日，即每人约 51–68 小时、三人共 153–204 小时。这只是总容量背景，含学习、评审、联调和返工，不是承诺或逐日配额；时间窗口改变时重算。

领取时填写剩余工作量区间和未测风险，不按零估算未知。比较未完任务的剩余量与可投入量，已花掉的时间不能重复算。每人先领一个主要任务，另留评审/解除阻塞位置；不按任务数量或领域数量证明平均。

一个开发时段仍没有最小运行结果或失败定位、持续等同一依赖、一项任务同时阻塞多个消费者、剩余量超出容量时，就进行短讨论，不必等整条链完成。先缩小接口切片、补固定实现、转移完整任务或结对排障；范围取舍再集中决定。

当前可明确讨论的减量是项目列表界面切片改为固定测试项目入口（归 T07），保留创建/读取 API 与核心流程。成员管理 UI、独立检索/检查页、复杂格式已排除，不能再次算节省；权限、并发、待核保留、文件一致性不能删掉凑容量。

## 验收边界

静态契约和参考场景通过，仅说明方案内部一致。真实接口和数据库、真实模型质量、实际可打开编辑的文件分别验收。正式业务模板和可用资料仍由业务来源确认，开发者不自行编造申报要求。
