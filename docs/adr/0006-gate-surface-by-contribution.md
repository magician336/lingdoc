# 6. 门禁按贡献面判定：基线合并后只重测 PR 自己的贡献

**状态**：已采纳（2026-10-20，由 Issue #196 收口时的门禁成本讨论产生）

**后续**：[ADR 0007](0007-gate-decision-deep-module.md) 修订了本决策的**实现结构**，**不修订其语义**：判定仍然只有一处，仍然只读 Git，仍然「任何异常都回退到全量」；变的只是判定住在哪个模块、以什么形状存在。

## 背景

仓库的 CI 边界按**最后一次推送的 diff**判定（ADR 0005）。这条规则在「纯格式提交」上是对的：一个只重排版的推送不改变任何行为，不该重跑十几分钟的全量矩阵。

但同一条规则在**基线合并**上会失效。把 `main` 并进 PR 分支（或变基）之后，最后一次推送的 diff 就是 **main 带进来的全部改动**——于是：

- `go-lint`、`app`、`frontend`、`lingdoc-interface-integration` 等仓库级矩阵全部被重新排队；
- PR gate 的 provider tests 与 frontend 步骤也按这个 diff 重跑；
- 被重测的代码，**PR 自己一行都没改**，而是 main 的代码——而 main 的那些提交**已经被 main 自己的 CI 验过**。

这与仓库的规则直接冲突：`docs/agents/development-rules.md` 写着「修改公共契约、迁移、事务边界或 **base** 后，应手动 dispatch 或提交代码变更重新跑完整门禁」。于是每次基线合并都要付一次全量门禁的钱，而**要防的那件事——PR 的贡献在新 main 上不起作用——反而没有被更精确地验证**：全量矩阵测的是 main 的改动，不是 PR 的贡献在新 main 上的行为。

2026-10-20 的 #233 收口就是实例：分支落后 main 59 个提交，为了合并必须先并入 main，随即便触发了一次全量门禁；而这条分支的验收证据与 main 的改动毫无关系。

## 决策

### 一、验证单元 = (被测面内容, 基线内容)

一个 PR 要被重新验证，当且仅当下面两个事实之一变了：

1. **被测面内容**变了：PR 自己贡献的代码（Go 包、前端目录）的内容变了；
2. **基线内容**变了：基线在 PR 底下移动了（基线合并或基线前移）。

两者都没变 → 不重测。这就是「纯文档推送不重跑」的真正根据：不是「最后一次推送碰了哪些路径」，而是「**被测的东西变没变**」。

### 二、被测面来自 PR 自己的贡献

被测面 = PR 相对基线的改动（`base...head`）触及的 Go 包与前端目录。判定与执行都在**合并后的树**上进行，所以「贡献在新 main 上是否还成立」被正面覆盖：贡献涉及的包会在新 main 的代码上重跑一次。

- Go 侧缩到**包级**（`go test ./internal/lingdoc/<pkg>/...`），包边界就是 Go 的编译与契约边界。
- 前端侧无法缩（`npm test` 跑的是整个前端），因此**贡献未触及前端时跳过该步骤**，并在门禁产物里写明理由。
- 仓库级矩阵（`app`、`frontend`、`lingdoc-interface-integration` 等）只在**贡献的代码变了**时跑；基线合并不重跑它们——main 的代码由 main 自己的 CI 负责。
- **门禁自身的改动由全量门禁判定**：改了判定脚本或门禁工作流，就不能缩面。裁判必须由它自己来验，否则一个坏掉的门禁可以藏住一个坏掉的代码库。

### 三、判定集中在一个脚本

判定只有一处。（本决策落地时是 `scripts/ci/lingdoc_risk_surface.py`，工作流级的 `lingdoc_change_scope.py` 与 PR gate 的 `lingdoc_pr_scope.py` 都从它取决策；#304 按 [ADR 0007](0007-gate-decision-deep-module.md) 把判定收进 `scripts/ci/lingdoc_gate_decision.py`，那三个脚本随之删除。）两边各判一次等于门禁自相矛盾。

判定只读 Git：贡献面、树哈希、合并基点。**任何异常都回退到全量**（fail-open）：门禁的目的是不漏，不是卡人。

### 四、产物必须能解释这次测了什么

门禁产物（`result.json` 与 step summary）新增三个字段：

- `surface`：这次测了哪些包/目录；
- `reason`：为什么是这个面（贡献面变化 / 基线移动 / 未判定回退全量）；
- `base`：这次判断所依据的基线提交。

「Skipped means NOT RUN, not passed」继续成立：跳过必须带**可解释的理由**，静默跳过不可接受。

## 被否决的备选方案

**按标签或提交信息声明「这次只是合了 main」。** 与 ADR 0005 否决标签的理由相同：判定权不能交给提交者。

**开 merge queue，改为验证合并结果。** 最干净的形态（验证的是真正要进 main 的东西），但仓库当前没有开启 merge queue（`mergeQueue: null`），需要新的仓库特性与规则集配置；本决策先在现有工作流形态内把成本降下来。

**基线变了就重跑全量。** 就是现状。它把「main 的代码」当成「PR 的风险」来测，测的不是要防的那件事。

**基线移动就完全跳过。** 会让 PR 的贡献在新 main 上从未被验证过——正是本决策要防的坏结果。

## 影响

- 新增 `scripts/ci/lingdoc_risk_surface.py`（判定器）与 `scripts/ci/test_lingdoc_risk_surface.py`（单测）。（历史记录：#304 按 ADR 0007 把判定收进 `scripts/ci/lingdoc_gate_decision.py`，这两个文件随之删除。）
- `scripts/ci/lingdoc_change_scope.py` 与 `scripts/ci/lingdoc_pr_scope.py` 改为从判定器取决策；两者的**既有** diff 范围与格式快门禁语义保持不变。（历史记录：这两个脚本也已随 #304 删除。）
- PR gate 的 provider tests 目标从 provider 根目录收窄到贡献触及的包；frontend 步骤在贡献未触及前端时跳过并写明理由。
- 门禁产物新增 `surface` / `reason` / `base` 三个字段。
- ADR 0005 的格式快门禁继续存在且继续有效：一次只重排版的推送会改变被测面的内容哈希，格式快门禁正是覆盖这种情形的第二条判据。

## 风险与限制

- **语义级风险仍靠人工评审兜底。** 静态判定只能覆盖文件级与包级的影响面：基线若改了 PR 依赖的对外契约（API、迁移、规则）而文件不同，包级重叠判不出来。基线合并后，仓库级矩阵不再重跑，这类风险没有自动化兜底。
- **反向依赖不在被测面内。** 贡献改了某个包的接口、而基线里有别的包依赖它时，仓库级矩阵不在这次重跑范围内（代码没变时它按贡献是否变化决定是否跑）。main 合并后的自身 CI 是最后一道防线。
- 判定器本身是 CI 的一部分：它出错可能导致一次本该跑的测试没跑。因此判据保守，**任何异常都判为「全量」**。
- 「基线前移」在实践中通过 ruleset「Protect main」的 strict 策略转成一次基线合并推送：分支必须与 main 同步才能合并，所以判定只需处理推送这一种入口。
