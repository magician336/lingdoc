# 写作风格一致性与 StyleProfile 决策

> 决策日期：2026-10-26
> 适用范围：模板系统、正式章节编辑器、AI 辅助写作和项目级模板副本
> 关联文档：[模板与规则系统设计](11-模板与规则系统设计.md)、[G7 正式章节编辑器与 AI 辅助写作](beta-gap-development-plans/G7-formal-chapter-editor-ai.md)、[灵档术语表](16-术语表.md)

## 1. 决策结论

LingDoc 采用三层组合来改善全文逻辑和文风一致性：

1. **P0：版本化 `StyleProfile`**，作为模板和项目模板副本的一部分；
2. **P1：用户确认的参考范文**，作为受权限和章节范围约束的风格上下文；
3. **P1：非阻断 `Style Review`**，在写作期和导出前提示风格偏离，但不自动覆盖正文，也不单独授权导出。

后续再根据真实修改数据增加：

4. **P2：项目/团队风格记忆**；
5. **P2：风格统计和相似度指标**。

本决策不采用“只写一句保持风格一致”的提示词方案，也不在首期训练专用作者风格模型。

## 2. 为什么这样分层

模板能够约束结构、术语、格式和明确的写作要求，但不能自动证明论证正确、创新性成立或学术价值充分。风格一致也不能等同于内容正确。

因此，结构和可计算要求进入模板规则；参考范文只作为生成参考；语义和风格偏离首先进入人工可推翻的建议。任何模型判断都不能直接改变正式章节、确认状态或导出放行结论。

## 3. `StyleProfile` 契约

`StyleProfile` 是随 `TemplateVersion` 和 `ProjectTemplateCopy` 版本化的写作约束。服务端计算内容哈希，历史章节和 `ReleaseSnapshot` 保存使用过的版本。

首期字段：

| 字段 | 作用 |
| --- | --- |
| `tone` | 正式、客观、克制等整体语气 |
| `persona` | “本研究”“本文”“课题组”等叙述主体 |
| `terminology` | 推荐词、禁用词、需人工核查的变体；与项目术语表关联 |
| `sentence_preferences` | 句式、主动/被动表达和数字表达偏好 |
| `paragraph_preferences` | 段落长度、信息密度和过渡要求 |
| `forbidden_patterns` | 禁止套话、夸张表述和不适用表达 |
| `citation_style` | 引用、数字、单位和括号的表达约定 |
| `section_overrides` | 某一章节允许的局部风格差异 |
| `version` | 风格规则版本，供生成、检查和回放引用 |

字段必须有适用范围和来源。无法给出可核对例子的要求只能保存为说明或待核建议，不能直接成为 blocking 规则。

## 4. 参考范文

参考范文是独立的风格资产，不是事实来源，也不能替代 `EvidenceCard`、`SourceAnchor` 或 `ProjectAsset`。

每个范文片段至少记录：

- `example_id`、版本和所属项目/模板；
- 适用章节、任务类型和范围；
- 是否经过用户确认；
- 是否允许模型使用；
- 来源和授权状态；
- 创建、修改、撤回记录。

生成时只能检索当前用户有权使用、已确认、适用范围匹配且未陈旧的范文。范文可以提供句式、段落组织和过渡方式，但不得让模型把范文中的事实、数字或结论复制为当前项目事实。

## 5. Style Review

`Style Review` 与 G4 的 Template Check 共用版本和问题可追溯语义，但默认只产生 `INFO` 或 `WARNING`：

- 术语与 `StyleProfile` 或项目术语表不一致；
- 语气、叙述主体或禁止表达偏离约定；
- 章节之间存在明显的表达重复或风格突变；
- 引用、数字、单位和标题格式不一致；
- 生成文本与当前章节风格示例差异过大。

每条结果必须绑定：目标章节版本、模板/副本版本、`StyleProfile` 版本、检查运行、判定方和证据。模型判断不能自动覆盖正文、自动替换研究术语或单独阻断导出。只有可以稳定计算且误报可接受的格式问题，才可经过人工评审申请 blocking。

## 6. AI 写作上下文

每次 AI 生成、改写或审校都记录并向用户展示：

- 当前章节和 `ChapterVersion`；
- `Context Revision`；
- 模板、项目副本、规则集和 `StyleProfile` 版本；
- 允许使用的参考范文 ID；
- 实际使用的资料、证据卡和权限范围；
- 模型、任务卡/提示词版本和运行状态。

默认只使用当前章节、用户主动选择的资料和适用的风格资产。AI 候选进入 `CandidateDraft`，先比较再局部采纳；采纳不会自动确认正文或证据。

## 7. 后续风格记忆和指标

P2 阶段才建立项目/团队风格记忆。只有重复出现、被用户多次确认且适用范围稳定的修改，才可形成候选偏好；单次修改不能自动升级为团队规则。每条记忆必须可查看、撤销、限定范围并记录来源。

建议统计：

- 风格建议采纳率；
- 用户修改字符/段落比例；
- 术语冲突次数；
- 风格问题误报和关闭率；
- 跨章节风格偏离次数；
- 不同模型或任务卡的风格回归结果。

这些指标用于改进生成和规则，不作为学术质量评分，也不作为自动放行依据。

## 8. 依赖和验收顺序

推荐顺序：

1. 将 `StyleProfile` 接入模板版本和项目模板副本，完成服务端版本绑定；
2. 在 G7 上下文包中显示并记录风格版本；
3. 接入少量已确认范文并完成权限、范围和撤回处理；
4. 增加非阻断 Style Review 和问题定位；
5. 在真实章节和真实模板上测量误报、采纳和人工修改量；
6. 依据数据决定是否建设风格记忆和相似度指标。

最低验收场景：

- 同一项目生成两个章节时使用同一 `StyleProfile`；
- 模板副本升级后，旧风格检查结果变为陈旧；
- 用户撤回范文后，新的生成请求不能使用该范文；
- 范文中的事实不会未经证据授权进入正文；
- Style Review 只产生可追溯建议，不覆盖正文、不确认章节、不放行导出；
- 风格建议、用户采纳和最终章节版本可回放。

## 9. 明确不做

- 不用单一风格分数判断全文是否“写得好”；
- 不把风格一致性和学术正确性合并成一个结论；
- 不自动把历史正文全部加入风格上下文；
- 不让模型自动把建议改成 blocking；
- 不在没有样本和人工基准前训练专用作者风格模型；
- 不为了风格能力新建第二套编辑器、规则引擎或导出流程。
