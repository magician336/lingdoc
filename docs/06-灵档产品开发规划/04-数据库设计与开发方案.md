# 灵档数据库设计与开发方案

> **后续设计参考**：本文保留完整产品方案；本轮范围见[实施方案](../08-本轮实施方案/01-范围与任务流程.md)，领取以[任务池](../TEAM_DEVELOPMENT_TASKS.md)为准。A/B/C 仅指领域，不分配人员。完整 PCC、复杂权限等不自动成为本轮前置条件。

_基线：2026-09-20；以当前 Tencent WeKnora 仓库和本目录已确认的领域模型为准。_

## 1. 设计结论

灵档与 WeKnora **共用同一个业务数据库，但使用独立的 `lingdoc_` 表前缀**。灵档不复制 WeKnora 的用户、租户、知识库、知识条目或文件数据，也不直接写入 WeKnora 表。

数据库目标同时支持：

- PostgreSQL/ParadeDB 生产部署；
- SQLite Lite、本地开发与测试部署。

本方案只描述完整目标模型，不拆分 P0/P1/P2 实施阶段。所有目标表都必须同时提供 PostgreSQL 与 SQLite 迁移。

## 2. 与 WeKnora 的对齐约定

| 约定 | 灵档实现 |
|---|---|
| 灵档自有主键 | 应用层生成 UUID，数据库字段使用 `VARCHAR(36)`；SQLite 使用等价 `VARCHAR(36)` |
| 租户标识 | 沿用 WeKnora 的 `tenant_id BIGINT/uint64`，不新增 LingDoc tenant 表 |
| 外部用户标识 | 使用 WeKnora `user_id` 的稳定字符串引用，不复制 User |
| WeKnora 资源引用 | `knowledge_base_id`、`knowledge_id`、`chunk_id` 等只保存稳定引用，不建立跨域数据库外键 |
| 时间字段 | 所有持久化实体使用 `created_at`、`updated_at`；需要保留生命周期的表增加 `deleted_at` |
| JSON 字段 | PostgreSQL 使用 JSONB；SQLite 使用 TEXT，并由应用层完成序列化/反序列化 |
| ORM | 使用 GORM 映射实体和 Repository；生产数据库结构由 SQL migration 管理，不使用 AutoMigrate 建表 |
| 表命名 | 所有 LingDoc 表使用 `lingdoc_` 前缀，列名使用 snake_case |
| 状态枚举 | 数据库列存小写 snake_case；[`01-产品蓝图与范围`](01-产品蓝图与范围.md) 第 6 节与 [`16-术语表`](16-术语表.md) 第 6 节列的是同一批状态的全大写形式，凡那两处列出的对象，推进序列上的取值必须一一对应，同义不同名视为缺陷。唯一例外是 ChangeSet 的 `stale`——它是「基线已过期、不得应用」的失效标记，不是第六个推进状态，说明见第 5 节。未列入那两处的对象（影响任务、来源锚点、容器状态等）以本方案各表为准 |
| 删除策略 | 默认软删除或状态失效；版本、审计、确认、事件和导出记录不可覆盖删除 |

`tenant_id` 不是请求参数可以覆盖的字段。每次查询都必须从 `project_id` 回溯项目租户并校验调用者租户，不能只相信请求体中的租户值。

## 3. 数据库边界与一致性

### 3.1 写入所有者

| 数据 | 写入所有者 | WeKnora 可见方式 |
|---|---|---|
| 项目、成员、项目条件、章节、主张、ChangeSet、确认 | LingDoc B（Workspace） | 通过 LingDoc API/事件访问 |
| 项目资料绑定、资料修订、来源锚点、证据卡 | LingDoc A（Evidence） | 通过 `KnowledgeGateway` 读取 WeKnora 资料 |
| 模板、规则、预检问题、交付快照和导出物 | LingDoc C（Delivery） | 通过明确 API/事件访问 |
| User、TenantMember、KnowledgeBase、Knowledge、Chunk | WeKnora | LingDoc 只保存稳定引用 |

A 不更新 B 的主张或确认；C 不更新 B 的正文；跨域修改只能通过命令、API 或事件完成。

### 3.2 事务边界

以下操作必须在一个数据库事务中完成：

1. 创建项目与首个 Owner 成员；
2. Owner 转让（新 Owner、旧 Owner、`owner_user_id` 同时变更）；
3. 应用 ChangeSet、递增 `current_context_revision`、写入版本记录、创建影响任务；
4. 写入业务变化与对应 Outbox 事件；
5. 消费幂等键并提交其业务结果。

数据库事务不跨越 WeKnora 检索索引、对象存储或消息队列。外部动作使用 Outbox、任务状态和补偿重试表达最终一致性。

## 4. 完整目标表模型

### 4.1 项目与成员

#### `lingdoc_projects`

项目是 LingDoc 的主边界，不等同于租户、Workspace 或 Knowledge Base。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `tenant_id` | bigint | NOT NULL，索引 |
| `owner_user_id` | varchar(36) | NOT NULL，稳定引用 WeKnora User |
| `name` | varchar(255) | NOT NULL |
| `status` | varchar(32) | `draft` / `active` / `archived` |
| `template_profile_id` | varchar(36) | 可空，引用 `lingdoc_template_profiles` |
| `current_context_revision` | bigint | NOT NULL DEFAULT 0 |
| `asset_scope_revision` | bigint | NOT NULL DEFAULT 0；项目有效资料范围的版本，资料加入或撤出有效范围时递增 |
| `created_by` | varchar(36) | NOT NULL |
| `archived_at` | timestamp/datetime | 可空 |
| `discarded_at` | timestamp/datetime | 仅 draft 有效，软删除标记 |
| `created_at` / `updated_at` | timestamp/datetime | NOT NULL |
| `deleted_at` | timestamp/datetime | 可空，索引 |

约束：`draft` 必须保持 Revision 0；`discarded_at` 与 `status = archived` 不能混用；Owner 不可为空且必须与成员表唯一 Owner 一致。`owner_unavailable` 是根据租户成员状态派生的只读状态，不是 `status` 值。

`asset_scope_revision` 与 `current_context_revision` 是两个独立版本：前者只描述“这次任务允许用哪些资料”，后者描述项目语义；运行中的生成任务把两者一起写进输入快照，用于旧任务的防陈旧比较（见 [`02-领域架构与PCC`](02-领域架构与PCC.md) 第 9.1 节）。

#### `lingdoc_project_members`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` | varchar(36) | NOT NULL，FK → projects.id |
| `tenant_id` | bigint | NOT NULL，冗余租户键，用于隔离和索引 |
| `user_id` | varchar(36) | NOT NULL，稳定引用 WeKnora User |
| `governance_role` | varchar(32) | `owner` / `admin` / `member` |
| `status` | varchar(32) | `active` / `invited` / `suspended` / `removed` / `suspended_by_tenant` |
| `invited_by` | varchar(36) | 可空 |
| `created_at` / `updated_at` | timestamp/datetime | NOT NULL |
| `deleted_at` | timestamp/datetime | 可空 |

唯一约束：`(project_id, user_id)`。Owner 唯一性由事务和 PostgreSQL 部分唯一索引共同保证；SQLite 在 Repository 事务中显式检查。

#### `lingdoc_project_member_roles`

把职能角色从治理角色中拆开，避免将双轴权限压成数字等级。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_member_id` | varchar(36) | NOT NULL，FK |
| `function_role` | varchar(32) | `author` / `researcher` / `reviewer` / `observer` |
| `scope_json` | jsonb/text | 章节、资料、交付版本范围；非 Owner 未指派时表示空集 |
| `created_at` / `updated_at` | timestamp/datetime | NOT NULL |

唯一约束：`(project_member_id, function_role)`。治理角色为 Owner 的成员不得存在职能角色行；角色与 capability 的映射保持在领域代码中，避免把静态授权矩阵复制成可漂移的数据库配置。

#### `lingdoc_project_specs`

结构化建项条件。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` | varchar(36) | NOT NULL，FK |
| `field` | varchar(128) | NOT NULL |
| `value_json` | jsonb/text | 人工或 AI 填写的值 |
| `revision` | bigint | 草稿期为 0 |
| `status` | varchar(32) | `draft` / `pending_confirmation` / `confirmed` / `superseded`；`superseded` 是被更新的 revision 取代的历史条目 |
| `origin` | varchar(32) | `human` / `ai` / `ai_edited_by_human` |
| `source_ref` | jsonb/text | AI 填写必带会话、轮次或片段引用 |
| `created_by` | varchar(36) | NOT NULL |
| `created_at` / `updated_at` | timestamp/datetime | NOT NULL |

唯一约束：`(project_id, field, revision)`。

`status` 与 `origin` 是两个正交维度，不能合并：`origin` 说这条值**由谁写的**（人工、AI、或 AI 写完被人改过），`status` 说这条值**是否已经被人确认**（草稿、待确认、已确认）。AI 填写的值默认进入 `pending_confirmation`，必须由人确认后才能参与模板检查与交付（见 [`07-建项阶段设计`](07-建项阶段设计.md) 第 7 节、[`09-用户界面与交互规划`](09-用户界面与交互规划.md) 第 7 节）。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` / `tenant_id` | varchar(36)/bigint | NOT NULL |
| `anchor_id` | varchar(36) | NOT NULL，FK |
| `support_type` | varchar(32) | `support` / `limit` / `refute` |
| `scope_json` | jsonb/text | 适用研究条件、章节或主张范围 |
| `status` | varchar(32) | `candidate` / `needs_review` / `confirmed` / `insufficient` / `stale` |

#### `lingdoc_changesets`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` / `tenant_id` | varchar(36)/bigint | NOT NULL |
| `base_revision` | bigint | NOT NULL，乐观并发基线 |
| `delta_json` | jsonb/text | 变更意图，不直接保存跨域对象 |
| `status` | varchar(32) | `draft` / `assessed` / `applied` / `rejected` / `stabilized` / `stale` |
| `approved_by` | varchar(36) | 可空 |
| `applied_revision` | bigint | 可空 |
| `created_by` | varchar(36) | NOT NULL |
| `created_at` / `updated_at` | timestamp/datetime | NOT NULL |

### 4.4 确认、模板与交付

#### `lingdoc_confirmations`

统一记录内容确认与证据确认，但不混淆其业务语义。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` / `tenant_id` | varchar(36)/bigint | NOT NULL |

#### `lingdoc_issue_dismissals`

误报删除：判定问题**不存在**。

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` / `tenant_id` | varchar(36)/bigint | NOT NULL |

#### `lingdoc_issue_waivers`

豁免：承认问题**存在**，但接受本次风险。

| 字段 | 类型 | 约束/说明 |
|---|---|---|

| `actor_id` | varchar(36) | NOT NULL |
| `reason` | text | NOT NULL |
| `risk_json` | jsonb/text | 接受的风险清单 |
| `created_at` | timestamp/datetime | NOT NULL |

`severity = blocking` 的问题不得写入本表：阻断级只能被修复、关闭或判定为误报删除，不存在豁免。删除与豁免语义相反，所以是两张表、两条命令——不得用同一个字段区分，也不得相互转换。

#### `lingdoc_release_snapshots`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | varchar(36) | PK |
| `project_id` / `tenant_id` | varchar(36)/bigint | NOT NULL |

| `content_version_set` | jsonb/text | 章节/主张版本集合，不可变 |

`context_revision` 必须等于创建快照时项目的稳定 Revision；新变更不会修改旧快照。

`draft` 是预览阶段的快照：仍可随内容变化重建，也可以被丢弃；阻断问题全部关闭、负责人请求导出时，才固定为不可变快照（见 [`09-用户界面与交互规划`](09-用户界面与交互规划.md) 第 12.1 节）。`preflighting` / `blocked` / `ready` / `exported` 依次对应 [`16-术语表`](16-术语表.md) 第 6 节的 `PREFLIGHT_RUNNING` / `BLOCKED` / `READY` / `EXPORTED`；`superseded` 表示已被更晚快照取代，仅作历史保留。

[`01-产品蓝图与范围`](01-产品蓝图与范围.md) 第 6 节与 16 号「交付」行的状态是**项目级汇总**，不是本表的行状态：它包含「尚无交付对象」的 `NOT_READY`（草稿项目没有交付对象；[`13-端到端课题申报模拟`](13-端到端课题申报模拟.md) 第 12 节账本里记作「无对象」），由最新快照与确认状态派生。

> **本轮（T13/T14）落地差异** —— 上面这张是目标模型，落地建表见 [`migrations/versioned/000103_lingdoc_delivery_stores.up.sql`](../../migrations/versioned/000103_lingdoc_delivery_stores.up.sql)（SQLite 侧 [`000024`](../../migrations/sqlite/000024_lingdoc_delivery_stores.up.sql)）。差别不是「目标模型改成这样」，逐条列出是为了让下一个人看得出还没做的是什么：
>
> - 冻结输入**整份落在 `frozen_input_json`** 上，不拆成 `context_revision` / `content_version_set` / `template_profile_id`：`content_version_set` 是它的规范化投影，本轮先存投影的来源；拆列只会让「读回来的那份与冻结的那份不是同一个东西」多出若干个发生的机会。
> - **不落 `status`**：本轮只有「冻结即不可变」一种生命周期；`draft` / `preflighting` 属于预览阶段，而预览阶段在本轮还没有交付对象。
> - `id` 是**带前缀的不透明串**（`snapshot-<32 位十六进制>`，41 字符），不是 `varchar(36)`；列宽按 `varchar(64)` 建。
> - 未落 `created_by` / `tenant_id`：动作记录落在 `action_actor_id` 上，租户由 `project_id` 的归属决定。
>
> 幂等记录（`action_actor_id` / `action_key` / `action_request_hash`）与快照**同表同列**，而不是另立一张 `lingdoc_idempotency_keys`：索引与实体在同一行上，「索引在、实体不在」的半截状态于是结构上不可能存在。三列可空，因为 `Save` 落下的快照不属于任何一次动作——NULL 在唯一索引里互不相等（SQLite 与 PostgreSQL 同一条），这些行不会互相撞车。

> **本轮（T13/T14）落地差异** —— 同上：目标模型在上，落地建表见 [`000103`](../../migrations/versioned/000103_lingdoc_delivery_stores.up.sql)。逐条列出差别：
>
> - **文件本体落在 `file_blob` 上，没有 `storage_ref`**：对象存储不在本轮范围，而「文件已校验通过」与「文件读得回来」必须是同一件事——把字节放到盘上的另一处，就多出一个「库里有记录、盘上没文件」的状态，而 `downloadExport` 只能把它答成一句不可解释的失败。列表接口走**不带 `file_blob` 的投影**，一页 50 份产物不会把整页文件拉进内存。
> - `snapshot_id` 与目标模型的 `release_snapshot_id` 是**同一个引用**（外键就指向 `lingdoc_release_snapshots.id`），本轮沿用短名。
> - `status` 只有 `verified` / `failed`，没有 `queued` / `generating` / `expired`：本轮导出是同步完成的，没有排队与过期回收。
> - 新增 `failure_code` 列：`render_failed` / `empty_file` / `validation_failed` 三种失败的恢复动作不同（换一个新动作重渲 vs 回去改输入），目标模型的 `failed` 一个状态说不出是哪一种。
> - 未落 `format`：本轮只产 docx，等出现第二种格式时再加列并回填。
> - `id` 同样是带前缀的不透明串（`export-<32 位十六进制>`，41 字符），列宽 `varchar(64)`。
>
> 幂等记录同样与产物同表同列，理由与快照表逐字相同。

## 5. 索引与约束规则

1. 所有项目域表至少建立 `(tenant_id, project_id)` 或等价项目定位索引；列表查询不能只按自增/UUID 扫描。
2. 所有状态、Revision、版本号和 Outbox 状态建立与主要查询路径匹配的组合索引。
3. 软删除表的查询必须显式排除 `deleted_at IS NOT NULL`；PostgreSQL 可使用部分索引，SQLite 使用普通组合索引兼容。
4. `project_members` 的 Owner 唯一性、`owner_user_id` 同步、ChangeSet Revision 比较和角色 scope 规则必须在服务事务中再次校验，不能只依赖前端或单一数据库约束。
5. 跨域引用不建 FK；LingDoc 自有表的父子关系建 FK，并按领域语义选择 `RESTRICT`、`SET NULL` 或软删除，不能使用级联删除历史版本、确认和审计。
6. PostgreSQL 使用 CHECK 约束限制状态枚举；SQLite migration 同步等价 CHECK，应用层保留状态解析以兼容未来新增值。

## 6. 迁移与开发实现

### 6.1 迁移目录

- PostgreSQL/ParadeDB：`WeKnora/migrations/versioned/`，每次变更创建递增版本号的 `.up.sql` 与 `.down.sql`；
- SQLite：将目标表合并到 `migrations/sqlite/000000_init.up.sql`，已有数据库再追加对应增量 `.up.sql`/`.down.sql`；
- 不修改既有已发布迁移的语义，不复用已经占用的版本号；合并分支前重新检查最大版本号；
- 迁移 SQL 只负责结构、索引、约束和必要的默认值，不在迁移中写业务数据复制逻辑。

### 6.2 GORM 与 Repository

建议新增：

- `WeKnora/internal/types/lingdoc_*.go`：目标实体、状态常量、JSON Value/Scan 与创建默认值；
- `WeKnora/internal/application/repository/lingdoc_*.go`：按聚合边界提供 Repository，不允许 Handler 直接拼接跨域 SQL；
- `WeKnora/internal/application/access/project`：项目解析、租户交集、capability 和 scope 检查；
- `WeKnora/internal/application/service/lingdoc`：事务编排、Revision 比较、Outbox 写入与幂等处理；
- `WeKnora/internal/database`：仅接入已有迁移加载和数据库连接，不在启动时调用 AutoMigrate。

Repository 的写入方法必须接收 `context.Context`，使用共享 GORM 连接和显式事务；查询方法默认注入 `tenant_id`、`project_id` 与软删除条件。

### 6.3 双数据库验证

每个新增表必须验证：

1. PostgreSQL `migrate-up → migrate-down → migrate-up` 可逆；
2. SQLite 全新初始化与已有库增量升级均成功；
3. JSON 字段在 JSONB/TEXT 两种实现间可往返；
4. 时间、布尔、BIGINT、唯一索引和部分索引均有方言兼容测试；
5. 并发应用 ChangeSet、Owner 转让、幂等重试和 Outbox 重投不会破坏不变量。

## 7. 必须保持的不变量

- 草稿项目为 `status = draft` 且 `current_context_revision = 0`，不得创建 `EvidenceCard` 或 `ResearchClaim`。
- 每个项目有且只有一个 Owner；Owner 转让不能出现零 Owner 或双 Owner 中间态。
- Owner 的职能角色为空；非 Owner 未指派 scope 表示空集，不是全集。
- `ChapterVersion`、`ResearchClaimVersion`、`AssetRevision`、`ReleaseSnapshot` 和 Confirmation 都绑定明确 Revision/版本。
- STALE 任务结果不得覆盖现行结果。
- 阻断级 ValidationIssue 未关闭或正确标记为 dismissed 时，不得生成 READY 快照或导出；阻断级问题不得被豁免，`lingdoc_issue_waivers` 中不得出现指向 `severity = blocking` 问题的行。
- 误报删除与豁免是两种相反语义，分表存储、分命令写入，不得用同一字段区分或相互转换；删除的作用域是 `rule_id + target_ref + target_version + ruleset_hash`，跨检查级别、跨判定方，但不跨规则集版本与目标版本。
- 同一问题身份在任一求值结果中最多一条 `open` 行；`target_version` 或 `ruleset_hash` 变化后，对应的删除记录立即失效。
- 旧版本、确认、审计和 Outbox 记录不可被当前态更新覆盖。
- 任一租户、项目、成员或资源检查失败都默认拒绝，不得因为数据库查询异常降级为允许。

## 8. 验收清单

- 能在共库中创建、查询、归档和软删除项目，且不能跨租户枚举；
- 能原子创建 Owner、邀请成员、转让 Owner，并验证租户停用后的 `owner_unavailable` 派生行为；
- 能保存完整的资料修订、来源锚点、证据卡、主张/章节版本与确认记录；
- 旧 Revision 的 ChangeSet 会被拒绝，STALE 任务不能覆盖新结果；
- 同一规则在写作期检查与交付预检中产生同一问题身份：在一级删除的误报，另一级只要目标对象版本未变就不再报出；目标对象换版本或规则集内容变化后问题重新出现；
- 阻断级问题可被判误报删除、但不能被豁免，且删除阻断级问题仅 `Owner` / `Reviewer` 可执行；
- 规则集哈希可由内容复现：同一套规则多次计算结果一致，字段顺序变化不影响结果；
- ReleaseSnapshot 能精确重建导出所使用的内容版本、模板版本和 Context Revision；
- 审计同时记录 allow/deny、操作者、角色、scope、资源和理由；
- 事务回滚时业务表和 Outbox 同时回滚；重复命令返回幂等结果而不重复写入；
- PostgreSQL/ParadeDB 与 SQLite 的迁移、CRUD、索引、JSON、软删除和并发测试均通过；
- 方案不新增 LingDoc User/Tenant/KnowledgeBase 表，不直接修改 WeKnora 业务表。
