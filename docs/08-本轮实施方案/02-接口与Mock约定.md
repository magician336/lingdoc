# 接口与 Mock 约定

协作说明版本 0.5；HTTP / schema 契约未因 20→16 的任务重组改变。接口提供方表示服务职责，不预分人员。供接口提供方和消费者查阅。所有新增 API 都是设计提案，不表示现有后端已实现。成员先读任务稿，接接口时再看本文件。

## 1. 用最少的共同约定，让任务独立推进

共用 `contracts/openapi.json` 描述 HTTP，`contracts/scenarios.json` 描述行为，`contracts/workflow.json` 描述一次连续交付。每个提供方维护本域内容；消费者提出缺失的输入/输出，不另抄一套字段。

OpenAPI 有 25 个操作，其中 22 个标为 core。这个数量是请求入口数，不是 22 个独立任务或必须一次冻结的范围。`saveMembers`、`retrieveSources`、`checkCurrent` 标为 optional：成员先配置固定测试组，检索包含在生成中，检查包含在准备交付中；内部权限/检索/检查逻辑仍要实现。

本轮方案文件位于 `docs/08-本轮实施方案/contracts/`；Go 内部共享 DTO/小接口和合成测试资料的实际目录在 T01 接入现有仓库时确定。以最小模块接入，不新建微服务、第二套账号系统或通用工作流平台。

## 2. 后端交接边界

| 提供方 | 小接口 | 消费方需要的结果 |
|---|---|---|
| 交付服务 | `TemplateReader.Get(id, version)` | 资料服务/工作区服务：固定模板章节、必要条件、规则及版本 |
| 工作区服务 | `ProjectAccess.Authorize(actor, projectID, capability)` | 资料服务/交付服务：租户和项目成员的基础操作权限；不在这里递归检查来源 |
| 工作区服务 | `WorkspaceReader.GenerationContext(projectID, chapterID)` | 资料服务：一次一致读的研究条件、当前章、版本和模板引用 |
| 资料服务 | `AssetGateway.ResolveAllowed(projectID, actor, assetIDs)` | 生成：绑定、就绪、当前可访问的资料及版本 |
| 资料服务 | `CandidateReader.Get(projectID, candidateID)` | 工作区服务：正文、引用、待核项、输入版本；只读，不写章节 |
| 资料服务 | `SourcePolicy.Validate(projectID, actor, sourceRefs)` | 工作区服务/交付服务：当前授权、引用存在性、定位及资料版本 |
| 工作区服务 | `WorkspaceWriter.AcceptCandidate(...)` | UI：核查候选和预期版本后写出新章节；前端只提交候选 ID |
| 工作区服务 | `WorkspaceReader.DeliveryInput(projectID)` | 交付服务：一次一致读的项目、研究条件值、全部章节、确认和模板引用；允许未完成章节 |
| 交付服务 | `DeliveryService.Prepare/Export(...)` | UI：冻结输入、检查、生成和验证文件 |

内部优先 Go 小接口直接调用，HTTP 是前端边界。前端与业务模块不知道当前注入的是固定实现还是真实提供方。

调用顺序由应用操作组合：**工作区服务基础授权 → 资料服务来源授权 → 本次领域动作**。工作区服务的基础授权不调用资料服务；资料服务校验资料不能再调用已经包含来源检查的总入口，避免循环。

各域写自己的数据。资料服务不能替工作区服务写章节，交付服务不能替工作区服务更改确认。工作区服务提供原子写入和一致读；交付服务对工作区服务/资料服务的读结果进行前后版本复核，不声称跨域远程查询天然处于一个事务。

## 3. 公共请求与错误约定

- 前缀 `/api/v1/lingdoc`，复用现有认证。租户和操作者从服务端认证上下文取得。
- 成功：`{data, request_id, meta: {replayed, refresh_required}}`；失败：`{error: {code, message, retryable}, request_id}`。新增接口使用薄适配层适应现有请求拦截器，不重构全仓响应格式。
- ID 是不透明字符串；来源 ID 使用可安全嵌入引用标记的服务端格式。状态为小写 snake_case，时间为 UTC RFC3339，界面负责中文显示。
- `null` 章节版本表示尚未写过正文；空资料集合表示没有资料，禁止解释成全部知识库。
- 请求和响应先按共享 schema 严格检查。新增可选字段也必须更新契约及样例；兼容性和部署顺序另行确认，不能依赖消费者自动忽略一切变化。
- 列表面向演示规模；不引入通用搜索/分页平台。若设上限，必须显式提示截断。

| 状态 | 含义 | 界面动作 |
|---|---|---|
| 401 | 未登录 | 复用登录恢复，不自动重新发起模型调用 |
| 403 / 404 | 可见项目内能力不足 / 不应暴露的资源 | 停止读取受限内容，使用安全恢复入口 |
| 409 `version_conflict` / `stale_input` | 当前输入已变化 | 保留本地编辑，重新读取后由用户决定 |
| 409 `idempotency_conflict` | 同键对应不同请求 | 修复客户端操作键，不自动覆盖原记录 |
| 409 `request_in_progress` | 同键操作尚未提交 | 按 `Retry-After` 用原请求和原键再查/重试 |
| 422 | 缺资料、未就绪、状态不符、交付阻断 | 展示可执行原因；不报笼统服务器故障 |
| 429 / 503 | 限流 / 依赖不可用 | 保留任务 ID 和用户输入，按明确恢复动作处理 |

## 4. 版本分别管什么

| 字段 | 维护服务 | 更新规则 |
|---|---|---|
| `project_version` | 工作区服务 | 工作区服务域研究条件、阶段、章节、确认等实际写入递增；快照创建/任务轮询不递增 |
| `spec_revision` | 工作区服务 | 研究条件实质保存递增，包括草稿期 |
| `chapter_version_id` | 工作区服务 | 每次正文/引用写入产生不可变版本，旧版本不覆盖 |
| `asset_revision` | 资料服务 | 内容或解析定位改变时变化；授权是否仍有效另查当前状态 |
| `template_version` / `ruleset_hash` | 交付服务 | 固定模板和规则版本，本轮项目不在线切模板 |
| `snapshot_id` / `snapshot_digest` | 交付服务 | 一次冻结输入的身份及内容摘要 |

Candidate 的 `basis` 由服务器记录生成时研究条件、章版本、模板/规则、资料版本。任务执行成功不保证候选仍有效，`succeeded` 和 `fresh/stale` 分开。

确认绑定章版本、研究条件版本、该章资料版本、模板版本。编辑该章会使其确认失效；研究条件改变使全部章确认失效。本轮采取明确保守规则，不宣称有精确影响图。资料服务的资料变动不靠工作区服务的 project_version 检测，由资料服务的版本/当前权限检查兜住。

若底座没有稳定解析版本标识，先固定演示资料和解析方式；检测到重解析则要求重新选择资料，不能假定旧定位仍有效。

## 5. 不能在采纳和编辑时丢失待核事项

Candidate、Chapter、SnapshotChapter 都包含 `review_items`，每项有稳定 ID、原文和来源候选 ID。**采纳固定为整章替换，不做增量合并。** 工作区服务从候选复制全部正文、引用和待核项；当前章已有版本时，界面先明确提示替换范围、取得用户确认，再携带 `replace_existing=true` 和预期章版本。空章首次采纳传 false；已有版本却未确认替换返回 422 invalid_state，版本不一致返回 409，均不写入。

再次采纳保留旧章版本及其旧待核/处置记录，新版的待核集合取新候选，并必须重新确认；旧记录不被清空或偷偷标为已解决。取消替换不发请求。普通手动编辑仍由后端继承当前版本全部待核项，前端不能省略清空。本轮不支持将部分旧正文合入新候选的采纳操作；若以后支持，先定义对应待核项的继承规则。F20 覆盖已有人工正文再次采纳的正反例。

确认时提交 `review_decisions`，必须恰好覆盖当前章的全部待核项，拒绝重复或未知 ID。处置为 `resolved` 或 `retained_warning`，均须理由。`resolved` 是人工处置记录，不是系统证明研究结论正确；编辑后新版本需要重新复核。

本轮交付类型固定 `internal_demo`。保留警示可以通过内部演示检查，但导出文件必须列出待核原文、处理结论和理由，并显示内部演示属性。以后若做正式申报，需另定更严格放行规则，不能直接沿用。

正文引用统一为 `[[source:来源ID]]`。解析出的 ID 集合必须等于 `source_ids` 集合；每个来源在同一项目内、当前可用且能定位。检查只能证明来源存在和结构一致，内容是否支持研究结论仍需人工核查。

保存章节只复核**本次提交**的 `source_ids`：上面那条不变量不变，空集不复核。边界要说清：用户把正文里的 `[[source:来源ID]]` 删干净再保存，那条引用就从新版本消失了，而被引用的原话仍留在正文里。这条窄路不是本轮引入的（T13 的 `source_invalid` 判的是章节**仍引用**的失效来源），也不能算作 F17 断言 4 的覆盖——那一条关心的是删掉资料绑定，而 `/assets` 本轮没有删除入口。不要把「删掉引用标记」当成已被覆盖。

## 6. 幂等和异步：先处理授权，再判断是不是已经做过

有副作用的请求带 `Idempotency-Key`。记录范围含租户、操作者、操作、目标资源路径和键，保存规范化请求体 hash。创建项目时目标是项目集合，不能等项目 ID 生成才记录。

处理顺序：

1. 检查当前身份、项目能力和所涉资料授权，避免从历史缓存泄露撤权内容。
2. 查询该范围的操作键。已完成且同请求，返回原业务结果；同键不同请求返回冲突。
3. 尚未完成提交则返回 `request_in_progress`；已提交异步任务则返回原任务 ID，任务仍运行不等于请求没提交。
4. 只有新操作才检查当前预期版本并执行条件写入；操作结果与领域写入在同一事务中提交，唯一约束防并发重复。

重放完成结果必须先于首次写入的旧版本比较，否则“保存已成功但响应丢失”会被误报冲突。重放响应 `meta.replayed=true, refresh_required=true`，界面先取当前状态再决定能否继续，不能把缓存旧结果当成当前状态。

生成/导出先落任务记录再返回 202。任务轮询复用 ID，不重新 POST。任务进入失败或中断时保留原因；重试新任务是明确的新动作。复用分布式执行器时，不能在本进程启动时把别的 worker 的任务一律判成中断。完整 Outbox 和 exactly-once 不列为本轮已具备能力。

## 7. 冻结输入与导出

`ReleaseSnapshot.frozen_input` 必须保存完整权威输入：项目名、研究条件值与版本、固定模板章节及规则、按顺序排列的章节正文/引用/待核项/确认记录、来源标题/定位/摘录/hash、资料版本和权限关联集合。不能只存当前可变表的 ID，然后导出时重新拼正文。

空章可以进入 **blocked 快照**：`chapter_version_id=null`，无确认字段。只有通过检查且版本完整的快照才可导出。不为缺失版本造假 ID，不为了拿到一次阻断结果强迫用户先写完所有章。

passed 快照逐章校验：确认中的 chapter_id、章版本、spec_revision、template_version 与冻结章/项目/模板一致；确认的资料版本集合必须恰好等于该章 source_ids 对应的资料版本集合。待核 ID、处置 ID 各自唯一且完整对应；相同 ID 配不同理由也算重复。冻结确认须对应实际确认操作返回的记录，不能现场拼一个形式正确的新记录。重算 digest 不会使错误关联合法化；静态反例和真实提供方均验证这些不变量。

准备交付：

1. 工作区服务一致读返回输入及版本，交付服务读固定模板，资料服务校验当前来源。
2. 复核工作区服务版本与资料服务资料指纹未变，冻结输入。发生竞争变更返回 409，重新读取。
3. 对冻结内容计算检查结果，失败也保存明确原因；修订内容后准备新的快照。
4. 请求导出时重查授权、当前输入版本和确认有效性；只渲染该快照的冻结内容。
5. 真实生成临时 DOCX，校验结构、正文顺序、关键数字、引用和待核附录；通过后才提供下载。
6. 下载再次检查权限。当前正文改变后，已生成文件标历史版本；来源撤权后，旧文件也不可绕过授权下载。

T14 的交付界面切片读取 ExportArtifact 后，必须按 snapshot_id 调用 getRelease，依据其 is_current 显示“当前内容”或“历史版本”。页面刷新、重新打开、本地编辑成功及展示下载入口时更新该状态；尚未读取或读取失败显示“当前性未知”，不能只凭 verified 显示当前。F21 覆盖“导出完成→编辑正文→刷新交付页”：文件及 hash 不变，旧快照 is_current=false。该字段仅代表查询时状态，无法消除之后的并发修改，下载仍单独鉴权；动态标签不加入 digest。

`snapshot_digest` 只对 `frozen_input` 计算，动态 `is_current` 不参与。配套 canonical 文件和 sha256 是跨语言对照样例：UTF-8、无 BOM、无末尾换行、对象键排序、数组顺序保留、无无意义空白。本轮只使用整数/字符串/布尔/null 等已约束值，额外补转义、中文和边界整数用例后固定序列化实现；不能宣称 Python 的一种默认输出就是通用 JSON 标准。来源摘录 hash 对存下来的 `quoted_text` 精确 UTF-8 字节计算。

只支持标题、段落和简单引用。列表、表格、公式、精细分页等不支持项在输入/导出前明确提示，不静默吞掉。文件自动检查不能代替另一人用 Word/WPS 打开和编辑。

## 8. 撤权后怎么恢复

首版使用固定测试成员和共同资料范围。成员配置由测试初始化明确设置，不给所有租户用户自动加成员，也不以隐藏成员界面代替后端鉴权。

读取派生内容先检查所需共同资料权限；不能仅在检索时检查。上游权限过滤可能只返回允许的子集，资料服务必须比较请求 ID 与返回 ID，不能把“返回无错误”当成全部授权成功。

被撤权成员可读最小 `GET /projects/{projectId}/access-status`：访问状态、是否可新建项目、可执行恢复动作。它不返回旧正文、研究条件、资料标题。非成员仍隐藏项目存在性。

恢复动作只有两种：合法恢复原资料权限，或新建干净项目重新输入允许使用的内容。本轮不做旧派生正文自动迁移，也不通过“解除资料绑定”给旧内容放行。更细的安全迁移另立任务，不能作为一个按钮附带实现。

上面「读取派生内容先检查所需共同资料权限」这条，本轮只落在 `access-status` 一处。差额记在这里：F07 要求撤权后 `listChapters`、`getCandidate`、`downloadExport` 返 403，而本轮这几个端点在成员仍然有效时依然 200——它们只做项目/成员门禁（`Authorize` 的注释已写明资料授权不在它这一层）。各自读路径补资料层判定属 T15 的另一刀，本轮不做。所以 `access-status` 答 `restricted` 是**提示**而不是拦截：它把恢复入口递到用户面前，并不改变其它端点此刻仍在放行的事实。

## 9. Mock 怎样接真

**界面用固定 HTTP 样例；后端用可注入的小接口固定实现；完整流程用真实服务和测试数据库。** 三者不要混成一个“Mock 全绿”。

- T06 只搭最小启动/选择样例入口，资料服务/工作区服务/交付服务各维护本域样例。可以采用 Prism，先验证与现有请求层兼容并锁版本；不为使用某工具重构全仓。
- 固定样例适合成功/错误界面，不天然具有连续状态。涉及两次保存、采纳、重试、确认的测试，必须检查真实数据库副作用，或使用明确维护状态的测试替身。
- 每个真实提供方重放自己的约定，消费者对同一组样例验证请求/响应适配。新增一个真实接口就切换对应场景，失败不暗中回退 Mock。
- 联调运行模式显式标为 `mock`、`real_api_fake_model`、`real`。假模型可用来稳定检查状态流转，真实模型另检质量；正式演示不能把假模型输出标为真实生成。
- 契约变更更新 schema、固定样例、行为场景和受影响消费者；不是要求一次合入全部未来接口。

当前 F01 是 23 步连续规格：创建→条件保存→立项→两章骨架→绑定资料→生成→采纳/重放→编辑/重放→另一章保存→逐章确认→冻结/重放→导出→下载。动态 ID 和版本由前一步捕获；示例导出 hash 明确为占位，真实测试必须换成文件字节的实际 hash。

F02–F21 是提供方待实现的行为场景，包含权限、并发、过期、幂等、待核保留、空章阻断、冻结不变、再次采纳及历史标签。JSON 中写了断言不代表测试已经跑过。

## 10. 开工时才需要定下来的少数实现选择

T01 定开发数据库/运行方式和现有请求层接入；T05 定真实 DOCX 库与支持格式；T09 定资料版本的可信取得方式。这些先做最小验证，各负责人把结果带回当前任务卡。

本稿未新增 Pact Broker、复杂分支治理、完整自动代码生成或企业级监控系统。短分支、提供方/消费者测试、固定场景和尽早联调足够作为三人团队的起点。
