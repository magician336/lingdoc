# G3-208.5 裁定依据（供 #210 使用）

本文件把 #209 核实出的四项「单侧存在条件」整理成可执行的事实，供 #210 实施者裁定，**不代替裁定**。

裁定必须由实施者显式写下「并入（带参数）」或「记为有意差异（带理由）」，并在代码注释与代码评审证据中可见。

---

## 1. 模板副本绑定检查

| | 现状 |
|---|---|
| Owner 稳定化 | 产出 `template_unbound` blocker，带可机读 code |
| 只读闸门 | **无同名 blocker**；通过 preflight 基线读取间接以通用 `ErrInvalidState` 失败 |

**语义**：闸门把「模板未绑定」折叠成了通用错误，丢失了可机读分类。
**影响面**：只影响错误可读性，不影响是否阻断——两侧都拒绝。
**可选裁定**：并入并让闸门也产出 `template_unbound`（**会改变闸门的错误标识**）；或记为有意差异。

> 注意：并入会让 `ErrInvalidState` 变成一个带 code 的结果，属于**可观察行为变化**。若选择并入，必须在报告中声明这超出了「纯重构」范围，并说明为何值得。

---

## 2. 规则检查器可用性

| | 现状 |
|---|---|
| Owner 稳定化 | 产出 `rules_checker_unavailable` **blocker**（200 响应的一部分） |
| 只读闸门 | 返回**错误** `ErrImpactObjectUnavailable` |

**语义**：同一情形，两条路径的返回**类型**不同（blocker vs error）。
**影响面**：只读闸门因此以错误而非结构化结果表达「治理能力缺失」。
**可选裁定**：统一为 blocker，或统一为错误，或记为有意差异。

---

## 3. 受影响对象当前确认重读 ← **语义差异最严重**

| | 现状 |
|---|---|
| Owner 稳定化 | 有 `impactConfirmationBlockers`：重读评估中每个受影响对象的当前确认 |
| 只读闸门 | **完全没有该调用** |

**语义**：一个任务被判 STALE 后，其影响对象不再有任何义务覆盖（STALE 非阻断）。Owner 路径靠这个重读补上义务；闸门不重读，于是**受影响章节可能未确认而闸门仍然放行**。

**这不是风格差异，是两条路径对同一状态给出不同答案。**
**可选裁定**：闸门补上同样的重读（**会改变闸门行为，可能导致此前能导出的项目现在被拒**）；或记为有意差异并说明为何闸门可以不查。

> 这一项最需要人工判断。#209 的证据文档第八节记录了该条件的当前守护用例。

---

## 4. 来源授权复检 ← **方向相反，闸门更严**

| | 现状 |
|---|---|
| Owner 稳定化 | **无全量复检**。`checkedImpactWrite` 只对传入的闭环证据 refs 调 `checkSources` |
| 只读闸门 | 对 `basis.SourceIDs` **全量** `checkSources` |

**语义**：来源被全面撤销时，闸门会拒绝，Owner 稳定化却可能通过。
**影响面**：Owner 路径相对宽松。
**可选裁定**：Owner 补上全量复检（**会让稳定化变严**）；或记为有意差异并说明理由。

> 与 #206 的关系：`source_revoked` 触发 STALE 的路径目前是死代码，因为写事务前的来源复检先行失败。本项裁定若选「Owner 补全量复检」，需确认不会与 #206 的后续修复产生冲突——**#206 尚未决策**。

## 裁定的硬性约束

1. **不得默认对齐**。四项各有影响面不同的后果，按「两条路径应该等价」的假设合并，会同时造成一处变严、一处变松。
2. **凡选择「并入」并因此改变可观察结果的，必须在报告中显式声明**，不得以「纯重构」名义夹带行为变更。
3. **每项裁定都要落成代码注释**，说明为什么这样处理，防止后来者再次盲目对齐。
4. 无论裁定为何，`#212` 建立的 16 条守护与本轮新增的投影守护都必须仍然变红（说明它们没被绕过），且全套件通过。

## 补充裁定：闸门 fail-fast 保真（父会话复核 #210 时发现）

四项单侧条件裁定之外，父会话在复核 #210 实现时发现第五处**不可夹带**的差异，已修复并补守护。

**差异**：重构前 `AssertRevisionStabilized` 在任务循环内部直接 `return`，失败任务之后的条件**根本不会被求值**。重构后共享求值先收集全部条件、由消费方取第一条 gate 错误——返回值相同，但求值过程不同，后果有二：

1. **错误身份可能位移**。若任务条件失败后，`RouteStabilizationBlockers` 或规则检查器再抛出基础设施错误，重构后返回的是后者，闸门对外的错误身份与重构前不同。
2. **多余读取**。闸门会读到它原本不会读的对象。

**裁定**：闸门一侧必须保持 fail-fast（`stabilizationScope.GateFailFast`），Owner 一侧保持全量收集。二者都需要完整条件列表，差别只在「是否在失败处停止」。

**守护**：`TestStabilizationConditionsGateFailFastStopsAtFirstFailingTask` 直接钉住求值契约——因为 `AssertRevisionStabilized` 对两种实现返回同一个错误，任何针对它本身的断言都**无法**分辨，必须断言 `stabilizationConditions` 的求值边界。抑制实验（短路恒假）已验证变红，且红的原因正是「多评估了一个条件」。

> 教训：重构保真不只包括「返回什么」，还包括「在哪里停止」与「读了多少」。这两项在只断言返回值时不可见。

## 补充裁定二：结果类任务的落穿与授权集合（父会话复核 #210 时发现，**闸门被放宽**）

四项单侧条件清单里没有这一项，`稳定化测试捕获能力证明` 第五节把它记为「双侧存在，形态一致」——那份记录只比较了**回执校验本身**，没有比较校验之后的行为。

**差异**：重构前

- Owner 循环：`RECOMPUTE`/`RETRIEVE_CANDIDATES` 校验完回执即 `continue`；
- 闸门循环：校验通过后**继续落入**闭环证据循环，没有 `continue`。

落穿不是死代码。`currentImpactObject` 会把 `ComputationReceipt` 解析成回执**自带的 SourceIDs**，而闸门正是把这些 ID 并入 `checkSources` 的复检集合。重构统一成 Owner 形态（`continue`）后，**结果类回执背后的来源不再进入闸门授权集合**——闸门被悄悄放宽。

**风险场景**：章节改写后不再引用某来源，而闭环证据只剩一张回执。此时 `basis.SourceIDs` 已不含该来源，闸门不再复检它，被撤销的来源可随闸门放行。

**裁定**：保留既有的单侧形态，用 `stabilizationScope.ClosureSourcesOfResultTasks` 显式表达，并把理由写进代码注释。**这仍然是待裁决的语义缺口**（闸门更严这一侧），只是本轮不得以重构之名单方面放弃。

**守护**：**未建，如实记录**。该差异只能通过闸门实际复检的来源集合观察，而回执要携带非空来源必须是真的 chunk（`ImpactSourceDigest` 会逐个解析 id），本包无此夹具；伪造 id 会让回执校验先失败，在该接缝上与落穿不可分辨。解除条件已写进 `stabilization_guard_test.go` 的 NOT BUILT 注释：种一个真实来源，断言 gate 形态的 `ClosureSourceIDs` 含回执来源而 Owner 形态不含。

> 教训：比较两条路径的同一条件时，要比较**该条件之后**的行为。只比较条件本身，会把「形态一致」判成一致。
