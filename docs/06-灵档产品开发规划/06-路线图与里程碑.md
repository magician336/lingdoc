# 到 Beta 的路线图与里程碑

## 1. 路线图原则

按风险和可验证闭环排序，而不是按页面数量或模型数量排序。每一阶段结束必须证明上一阶段的业务不变量仍成立，才扩大模板、资料类型或自动化程度。

**本路线图的目标是 Beta**——第一个对外交付的版本，其能力范围即本目录其余文档描述的完整设计。P0–P5 是执行编号：P0–P3 是通往 Beta 的构建阶段，P4 交付 Beta，P5 是 Beta 之后的生产增强，只在 Beta 的运行证据充分后才启动。阶段编号不是当前实现状态。

## 2. 阶段计划

| 阶段           | 目标            | 主要交付                                                        | 退出门槛                         |
| ------------ | ------------- | ----------------------------------------------------------- | ---------------------------- |
| P0：基线与契约     | 固定语言和隔离边界     | 领域词汇、schema、事件信封、测试资料、feature flags                         | 任何开发者均能描述对象所有者、版本和跨域路径       |
| P1：证据—项目最小链路 | 创建项目并可用资料支撑主张 | Project（含草稿态与 Revision 0）、ProjectMember、双轴角色模型与 capability 映射、职能 scope、项目—知识库绑定、统一鉴权链路、所有权转让、草稿阶段的团队协作与 AI 填写、受控检索最小闭环（对话 + 检索 + 候选池）、ProjectAsset Gateway、Anchor、EvidenceCard、ResearchClaim | 一个主张能回到原文；越权和锚点失效被拒绝/提示；scope 确实收紧到指定章节/材料/交付版本；**发现层不漏水**（草稿期联网与检索结果不进入正式证据，层级标记在立项前后一致）；**草稿期授权不被重置**（草稿期上传的资料在立项确认后仍受同一 `authorization_scope` 约束）      |
| P2：PCC 与来源沉淀 | 让一次实质修改可局部处理，并让检索到的来源与对话可追溯地沉淀为项目资料  | ChangeSet、ContextRevision、DependencyEdge、ImpactTask、确认失效、来源导入确认与来源谱系、对话片段导入    | 改变研究对象后旧结果不能覆盖新状态；新来源可选择性导入并可追溯 |
| P3：协作写作与交付   | 从章节候选稿到可编辑材料包 | 章节版本、任务/批注、路线图、TemplateProfile、模板检查、预检、DOCX 导出                   | 固定样例完成完整闭环且无阻断问题导出           |
| P4：**Beta**（首个对外交付版本） | 在真实约束下验证价值并对外交付 | 审计、指标、回退、恢复、试点 runbook、反馈闭环、RuoYi 管理台接入                    | 试点团队可独立完成任务；失败可诊断/恢复         |
| P5：生产增强      | 在 Beta 之上扩展模板、检索与机构能力 | 新模板验证流程、新来源接入、配额与运营深化                                      | 每项扩展有独立样例、规则版本和支持成本评估        |

> 机构管理台（组织、模板发布、用量、审计）落在 P4 而非 P5：顶层计划的第二阶段交付范围、团队计划的阶段 4（PR-404/405）都把它放在对外交付之前，本路线图与两者对齐。P5 的“配额与运营深化”指在已接入的管理台上扩展配置项，不是首次接入。

## 3. P0：基线与契约

### 必须完成

- 定义 `Project` 与 WeKnora tenant/knowledge base 的关系，画出权限和数据流。
- 通过迁移创建 LingDoc 新表；不修改 WeKnora 既有领域表的语义。
- 固化状态枚举、版本命名、事件信封、错误码和审计字段。
- 建立三个脱敏测试项目：证据充分、证据不足、材料重解析/变更。
- 建立最小的 feature flag、开发环境和本地演示数据装载脚本。

### 不应开始

- 在未定 `ProjectAssetRef` 前把 WeKnora chunk ID 写进主张表。
- 在未定 Revision 前并发开发自动生成、预检和导出。
- 在未定草稿态与正式基线的边界（`Revision 0` 与 `Revision 1` 的语义差异，见 [`07-建项阶段设计`](07-建项阶段设计.md) 第 5.3 节）前，并发开发草稿期功能与 `ChangeSet` 相关功能——两者对“什么算变更”的判定不同。
- 直接接入未批准的外部学术数据库或采购付费服务。

## 4. P1：证据—项目最小链路

### 用户路径

创建记录 →（可选）草稿阶段：团队协作草拟研究条件、上传资料、受控检索 → 立项确认 → 关联一份 ProjectAsset → 看到处理状态 → 选择原文片段 → 创建 EvidenceCard → 将其关联到一个 ResearchClaim → 负责人确认/标记待核。

### 技术重点

- A 通过适配层调用 WeKnora 文档处理；不得复制其分块/索引管道。
- EvidenceCard 保存稳定锚点和原文摘要/hash，以检测资料重解析后是否仍能定位。
- B 建立项目角色、职能 scope、资料范围和主张版本；A 的检索只收到经授权的材料集合。项目角色、capability 与 scope 必须与鉴权链路同阶段交付（见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 11 节）：没有 scope 输入源，鉴权链路第 5 步恒为全集、等于空转。
- 所有权转让（原子性、受让人确认、`owner_unavailable` 下的旁路发起）在本阶段可用：缺少它，Owner 的租户身份一旦不可恢复，项目就永久卡死。
- UI 显示“支持范围”和“待核实”，区分资料存在、资料相关与资料支持。
- 建项按三步结构落地（见 [`07-建项阶段设计`](07-建项阶段设计.md)）：`Revision 0` 空基线、草稿期可邀请成员协作且立即生效、草稿期不产生 `EvidenceCard`/`ResearchClaim`、立项确认时生成章节骨架与 `Revision 1`。创建记录时的“指定负责人”复用既有转让机制，不新增机制。
- 草稿阶段**不做专用权限集**：同一张 capability 矩阵跑在 `Revision 0` 上，无对象的条目自然空转；草稿期的研究条件草拟权复用 `changeset.create` 的持有者，确认权仍在 `Owner`。
- 草稿期的受控检索复用 WeKnora 的 `web_search` / `web_fetch`，不复制第二套搜索引擎；联网开关只有租户级，LingDoc 不维护搜索提供方。

### 退出门槛

- 一个主张能回到原文；越权和锚点失效被拒绝/提示；scope 确实收紧到指定章节/材料/交付版本。
- **发现层不漏水**：草稿期的联网与检索结果不进入正式证据，层级标记在立项确认前后保持一致。
- **草稿期授权不被重置**：草稿期上传的资料在立项确认后仍受同一 `authorization_scope` 约束，不因立项而变宽或变窄。

## 5. P2：PCC 与来源沉淀

### 最小可行变更类型

仅先支持三类结构化变更：研究对象范围、核心变量/目标、材料替换。每类预置显式依赖和影响规则，语义辅助只生成候选，不直接自动改状态。

### 所需流程

```text
草稿 ChangeSet
→ 影响预览
→ 负责人 Apply
→ Context Revision + ImpactTask
→ A 重校验证据 / B 标记内容待复核 / C 预检阻断
→ 人工处置
→ 新稳定 Revision
```

### 退出门槛

- 在任务运行期间连续应用第二次 ChangeSet，第一次的异步结果被准确标为 `STALE`。
- 受影响图只重跑相关节点，不对无关章节/材料触发全量重算。
- 确认状态绑定版本；实质变更后旧确认不可继续作为导出依据。

## 6. P3：协作、预检与导出

只为一类申报书模板实施端到端能力。`TemplateProfile` 至少包含章节结构、必要字段、可计算的格式/字数规则和规则版本。

导出由不可变 `ReleaseSnapshot` 驱动，包含：Context Revision、各章节 `ChapterVersion`、ResearchClaim/EvidenceCard/Confirmation 汇总、TemplateVersion、预检问题和用户豁免/误报删除记录。导出后立即用独立解析/渲染步骤验证关键数值、表格、图形、引用及分页，保留可恢复的原始快照。

## 7. P4（Beta）与 P5 的决策门

### 进入 Beta 前必须具备

- 项目级权限、资料授权范围、操作审计与导出审计；
- 异步任务的取消、重试、陈旧结果隔离和可观测日志；
- 已知失败情形的明确 UI：解析失败、证据不足、影响不确定、预检阻断；
- 数据导出/删除和本地部署/升级说明。

### 扩展触发条件

只有在核心闭环的漏改、误报、人工投入和导出损失有真实数据后，才扩大到更多申报类别、更多已批准学术来源、学生简化版或机构级协作。每个新模板须有样例、规则版本、人工复核和回退路径；新增或收紧检查规则须明确判定方（可复算归 `computed`、语义判断归 `model`）与严重度，并附误报评估——阻断级规则的误报会让整个团队停摆，模型类检查项默认从较低严重度起步；每个新来源须有授权、字段、速率、引用和停用策略。

## 8. 建议的里程碑评审问题

每一阶段评审只问以下可证伪问题：

1. 用户能否完成这一阶段承诺的动作，而非仅看到页面？
2. 每个关键结果能否说明其项目、版本、来源和责任人？
3. 发生一次真实变化时，系统是否局部失效且没有旧结果覆盖新状态？
4. 未能可靠自动判断的部分，是否清楚转交给人？
5. 是否有自动测试/fixture 证明以上结论，而不只是人工演示？
