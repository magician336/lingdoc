# 权限管理操作模拟

> 本文是依据 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 制作的权限演练案例，不是已经完成的功能演示，也不表示当前 WeKnora 已具备文中行为。角色、capability、检查顺序的定义以 11 号文档为准；本文只演示它们在实际操作中如何组合、在哪里被拒绝、拒绝时用户看到什么。
>
> 本文与 [`13-端到端课题申报模拟`](13-端到端课题申报模拟.md) 使用同一课题与同一团队，可对照阅读：08 演示业务闭环，本文演示支撑它的权限闭环。

## 1. 模拟场景

### 1.1 课题与团队

课题沿用 08 号的「数字化平台赋能高校创新创业教育对本科生创业意向的影响机制研究」，团队四人，外加一位不进入项目的租户 Owner，以及一位尚未进入租户的校外评审。

| 人员 | 治理角色 | 职能角色 | scope | 在租户内 |
|---|---|---|---|---|
| 李老师 | Owner | —（顶点，自动含全部职能） | 全部 | 是，租户 Owner |
| 王同学 | Member | Author | Ch1、Ch2 | 是，contributor |
| 陈同学 | Member | Researcher | — | 是，contributor |
| 赵老师 | Admin | Author | Ch6 | 是，admin |
| 周老师 | —（不进入项目） | — | — | 是，租户 Owner |
| 张教授 | Member | Reviewer | Ch3、Ch4 | **否**，待邀请 |

赵老师在本演练中是 `Admin + Author`——她能管理项目配置、分派任务，也能协作 Chapter 6，但不做学术确认（见 2.3）；周老师只负责租户层操作，不持有任何项目角色。

### 1.2 本次演练要回答的问题

1. 一次邀请如何同时处理“加入租户”和“授权到项目”；
2. 预设之外的组合（科研秘书）如何在不新增核心角色的前提下表达；
3. 三层相交检查在允许与拒绝时分别展开成什么样；
4. 租户侧的单方面操作（停用成员）如何传导到项目，Owner 失效时冻结哪些能力、有无自救路径；
5. 拒绝发生时，用户看到的提示是否足以自行纠正。

## 2. 第一幕：建项与成员授权

### 2.1 创建记录与立项确认

创建记录是一次轻量写入，立项确认才是闸门，中间可以停留任意时长。

```text
① 创建记录
操作   项目列表 → 新建项目 → 填写项目名 → 指定负责人（可跳过）
检查   ① 租户成员是否 active          → 是
       ② 租户角色是否 ≥ Contributor    → 李老师是租户 Owner
结果   写 Project（owner_user_id = 李老师，status = draft，current_context_revision = 0）
       自动写 ProjectMember（李老师，governance_role = owner）
       李老师不需要勾选职能角色——Owner 是全集，不参与职能轴选择

② 草稿阶段（可选，可停留任意时长）
       李老师与王同学一起草拟研究条件；陈同学上传资料、围绕想法检索
       （两人在此阶段被邀请进来，一经接受立即生效；带章节 scope 的授权在 ③ 之后补充，见 2.2）
       期间研究条件的修改不产生 Context Revision，也不需要 ChangeSet
       ——草稿期没有需要保护的基线

③ 立项确认
操作   确认页 → 查看两类差异（他人改动 / 仍是 AI 填写且未经人工改动） → 确认
结果   按所选模板生成章节骨架 Ch1–Ch6，后续成员 scope 以这些章节为对象
       生成 Context Revision 1
       Project.status：draft → active
```

若创建记录时指定了负责人，系统自动发起一次所有权转让，受让人确认后原子生效；确认之前创建者临时持有 Owner，项目不出现零 Owner 状态。同一界面同时确定创建者自己的职能角色——否则他在转让后按“未指定职能”处理，会变成只读。

### 2.2 邀请已在租户的成员

成员授权分两段：**草稿期即可邀请，且一经接受立即生效**（治理角色 + 不带章节 scope 的职能角色）；**带章节 scope 的授权必须等立项确认之后**，因为章节那时才生成。在此之前，被授职能角色对章节对象的写权为**空（待指派）**，而不是全集——`function_scopes` 为空对 `Owner` 是全集，对其他治理角色是尚未指派，两者不可混同。

下面两小节是**立项确认之后**的授权示例。

**王同学**——走预设组合“章节负责人”。

```text
操作   邀请弹窗 → 选预设「章节负责人」→ 限定 scope 为 Ch1、Ch2 → 发送
检查   ① 操作者具备 project.members.manage → Owner 具备
       ② 被邀请人是本租户 active 成员      → 是
结果   ProjectMember（王同学, member, [author], scope={author:[Ch1,Ch2]}, status=invited）
       王同学接受后 status 变为 active
```

**陈同学**——同样走预设“研究助理”（`Member + Researcher`），无章节 scope。

### 2.3 邀请自定义组合的成员

赵老师要做的事是：管理模板、分派任务、检查材料完整性、协作 Chapter 6，**但不做学术确认**。这四项职责对应的组合是 `Admin + Author`——`Member + Author` 不含治理权，纯 `Admin` 不含内容编辑与确认能力，两者都不够。预设之外的组合直接在邀请弹窗里表达，不需要新增第六种核心项目角色。

```text
操作   邀请弹窗 → 治理角色选 Admin → 职能角色勾选 Author → 限定 scope 为 Ch6 → 发送
检查   ① 操作者具备 project.members.manage → Owner 具备
       ② 被邀请人是本租户 active 成员      → 是
结果   ProjectMember（赵老师, admin, [author], scope={author:[Ch6]}）
       治理权与职能权一次授予：她能管理项目配置、分派任务，也能协作 Chapter 6
```

四项职责逐项对应：

| 她要做的 | 由哪个角色提供 |
|---|---|
| 管理模板、项目配置 | `Admin` → `project.settings.edit` |
| 分派任务 | `Admin` → `task.assign` / `task.manage` |
| 检查材料完整性 | `Admin` → `asset.read`（管理动作另有 `asset.delete`，本演练未用到） |
| 协作 Chapter 6 | `Author` → `content.edit`（受 scope 限制） |

她仍然拿不到的四项，与阶段无关，是设计边界本身：

| 她不做的 | 因为缺 |
|---|---|
| 确认证据或内容 | `evidence.confirm`、`content.confirm` |
| 批准 ChangeSet | `changeset.apply` |
| 放行导出 | `delivery.export` |
| 归档项目、丢弃草稿 | `project.archive` |

> **治理角色 `Owner` 是唯一不能这样授予的角色**：邀请弹窗的治理下拉只到 `Admin`，新任 `Owner` 必须走转让流程（见 5.3）。否则邀请一次就会同时存在两个 Owner，与“有且只有一个 Owner”的不变量冲突。

### 2.4 邀请不在租户内的成员

张教授已注册 WeKnora 账号，但不属于本租户。这是管理面结合的关键路径。

```text
操作   邀请弹窗 → 输入邮箱 → 系统检出「该用户不在本租户」
       弹窗展开第二步：租户角色选 viewer，项目侧选 Member + Reviewer，scope 为 Ch3、Ch4
检查   操作者是否同时具备①租户管理权、②project.members.manage？
       → 李老师是租户 Owner，两项都具备
结果   一次操作内完成两件事：
         ① 调用 WeKnora API  POST /tenants/:id/members { email, role: viewer }
         ② 创建 ProjectMember（张教授, member, [reviewer], scope={reviewer:[Ch3,Ch4]},
            status=invited）
       两边的真相源各归其主：租户成员记录在 WeKnora，项目成员记录在 LingDoc
       两条邀请各自独立流转：租户邀请被接受后 TenantMember 转为 active，
       项目邀请被接受后 ProjectMember 转为 active——不是同一次事务
       两者都 active 之前，3.1 的链路会在第 ② 步或第 ④ 步拦下
```

**反例**——操作者具备 `project.members.manage` 但不具备租户管理权。本项目里赵老师就是这一类：她是项目 `Admin`，租户侧虽然也是 `admin`，但租户成员 API 要求租户 `Owner`+（见 11 号文档 8.2）——治理轴与租户轴不可互推。

```text
操作   赵老师（项目 Admin）尝试合并邀请张教授
结果   拒绝，提示「加入租户需要租户管理员权限」
       LingDoc 生成待办：「需租户管理员邀请 张教授 进入租户」
       待办指派给租户管理员，而不是静默失败
```

这条分支的意义在于：LingDoc **可以发起**租户层操作，但**不持有**租户层真相，也不绕过租户层权限。项目内是 `Admin` 不代表租户侧有管理权，反之亦然。

### 2.5 绑定知识库

```text
操作   项目资料页 → 绑定知识库（本项目资料将接入其中）
检查   ① project.settings.edit              → Owner 具备
       ② ResolveKB / KBAccess 知识库共享级别 → 同租户，通过
结果   建立项目—知识库绑定；对已有 WeKnora 资料只建立 ProjectAsset 关联，
       不复制原始文件、不重建索引；M-01 ~ M-04 在后续资料接入时进入该绑定
```

## 3. 第二幕：日常操作的权限检查

### 3.1 允许的路径：八步链路完整展开

王同学在 Chapter 2 生成候选稿：

```text
① 认证        JWT 有效
② 租户        active TenantMember，租户角色 contributor
③ 项目        project.tenant_id == 王同学所属租户
④ 项目成员    ProjectMember.status == active
⑤ 能力        content.edit 存在；scope 检查：目标 Ch2 ∈ [Ch1, Ch2]
⑥ 资源        ProjectAsset 边界：M-01、M-03 均已绑定到本项目 → 通过
               再对其所在的知识库逐个 ResolveKB / KBAccess → 通过
⑦ Agent       本次走章节生成链路（检索 + 生成），未调用 Research Agent；
               若经 Agent，还须校验 Agent 来源租户、调用者身份与工具 scope
⑧ 审计        记录 allow、actor、capability、资源、Revision
结果          生成候选稿，写入 ChapterVersion
```

关键点：**第 ⑤ 步的 scope 检查与第 ⑥ 步的资源检查是两次独立判断**。王同学对 Ch2 有写作权，不代表他对某个知识库有读取权；任一失败都不放行。第 ⑥ 步内部本身也是两道：先看这份资料是否绑定到本项目（`ProjectAsset` 边界，LingDoc 侧），再看调用者对该知识库是否有分享权限（`ResolveKB` / `KBAccess`，WeKnora 侧）。

### 3.2 被拒绝的路径与用户看到的提示

拒绝提示必须可执行——用户应当知道“缺什么、找谁要”。

| 场景 | 失败步骤 | 原因码 | 用户看到的提示 |
|---|---|---|---|
| 任何人访问其他租户的项目 | ③ 项目 | `NOT_FOUND` | 项目不存在（对不可见项目统一返回 404，减少 ID 枚举） |
| 王同学改 Chapter 4 | ⑤ 能力 scope | `SCOPE_DENIED` | 你的写作授权限于 Ch1、Ch2；Ch4 的负责人是李老师 |
| 陈同学确认证据 | ⑤ 能力缺失 | `CAPABILITY_MISSING` | 确认证据需要 Reviewer 职能，请联系项目负责人（李老师） |
| 赵老师确认证据 | ⑤ 能力缺失 | `CAPABILITY_MISSING` | 你未被授予 Reviewer 职能，请联系项目负责人（李老师） |
| 张教授确认 Chapter 1 | ⑤ 能力 scope | `SCOPE_DENIED` | 你的审阅授权限于 Ch3、Ch4；如需审阅 Ch1，请联系项目负责人（李老师） |
| 成员读取未绑定本项目、或未共享给本人的知识库 | ⑥ 资源 | `RESOURCE_DENIED` | 该知识库未共享给本项目，需要知识库管理员调整共享级别 |

上表末行需要交代前提：2.5 绑定的知识库在绑定时已通过共享检查，因此对**已绑定且仍保持共享**的知识库读取不会触发这一行；它覆盖的是未绑定到本项目的知识库，或绑定后共享级别被下调的情形。

四条设计意图：

- **`CAPABILITY_MISSING` 与 `SCOPE_DENIED` 分开**：前者是“没有这个职能”，后者是“有这个职能但不在范围”，补救方式完全不同。
- **读操作不会因 scope 被拒**：scope 只约束写操作。王同学可以自由阅读 Ch3–Ch6，张教授也可以阅读全部章节，只是不能改、不能确认。上表里的读拒绝只有两条：项目层的 `NOT_FOUND`（首行）与资源层的 `RESOURCE_DENIED`（末行），都不来自职能 scope——读取边界由知识库共享级别和资料授权范围管辖，不由职能 scope 管辖。
- **治理与学术分离可见**：治理轴与职能轴互不推出——持有 `Admin` 的人拿得到 `task.assign`，却拿不到 `content.confirm`，这在确认证据时被拒不是权限配置错误，而是设计本身要表达的边界。本项目里赵老师（`Admin + Author`）就是这条边界的实例（见 2.3）。
- **项目不可见返回 404 而非 403**：403 会泄露项目存在性。

### 3.3 同一动作，不同结果

以“确认内容”（`content.confirm`）为例，同样是项目成员，结果取决于职能与 scope：

| 人员  | 治理 + 职能                    | 确认 Ch3 | 确认 Ch6 | 原因                   |
| --- | -------------------------- | ------ | ------ | -------------------- |
| 李老师 | Owner（顶点）                  | 允许     | 允许     | 全集，不受职能 scope 限制     |
| 赵老师 | Admin + Author             | 拒绝     | 拒绝     | 无 `content.confirm`  |
| 张教授 | Member + Reviewer（Ch3/Ch4） | 允许     | 拒绝     | 有职能，scope 不覆盖        |
| 王同学 | Member + Author            | 拒绝     | 拒绝     | 无 `content.confirm`  |

“确认证据”（`evidence.confirm`）是另一个能力，对象是 `EvidenceCard` 而不是章节文本：它确认“这段原文确实支持该主张”，scope 按证据卡所服务的主张与章节判定。张教授的 `{reviewer: [Ch3, Ch4]}` 对两者同样生效——他能确认 Ch3、Ch4 的正文，也能确认服务于这两章的证据；赵老师则因为没有 Reviewer 职能，对两者同样被拒。两个能力的定义与依赖见 11 号文档第 3.3 节。

## 4. 第三幕：权限调整

### 4.1 追加职能

李老师给王同学追加 Reviewer 职能，scope 仍为 Ch1、Ch2：

```text
操作   项目成员页 → 王同学行 → 职能角色勾选 Reviewer → 确认
结果   function_roles = [author, reviewer]
       Author    → content.edit      （Ch1、Ch2）
       Reviewer  → content.confirm   （Ch1、Ch2）
       Reviewer  → evidence.confirm  （服务于 Ch1、Ch2 的证据）
       两个职能的 scope 各自独立记录
```

### 4.2 自写自审是允许的

此时王同学可以**确认自己刚写的章节**。这是设计明确允许的：内容确认不设职责分离要求，`Author + Reviewer` 是其负责章节的正常配置。可追溯性由“确认记录绑定对象版本、核查范围与理由”保证，而不是靠强制换人点确认（见 11 号文档第 3.2 节规则 5）。同理，他也可以确认自己提交的、服务于 Ch1、Ch2 的证据候选——自写自审对证据确认与内容确认是同一原则。

### 4.3 撤销调整

撤销与追加同样简单：取消勾选即回收能力，**下一个请求立即生效**。`ProjectPermissions` 只在单个请求内缓存，不跨请求，因此不需要等 token 过期。

## 5. 第四幕：异常与恢复

### 5.1 普通成员被租户停用

假设陈同学离开课题组，租户 Owner 李老师在 WeKnora Settings 中停用了他。

```text
时序   ① 租户侧：TenantMember.status → suspended
       ② 陈同学下次请求：链路第 ② 步即被拦下，无法进入项目
       ③ 若事件订阅可用：LingDoc 主动将 ProjectMember.status
          标记为 suspended_by_tenant
       ④ 李老师在项目成员页看到「陈同学 — 租户身份已失效」并高亮，
          等待项目侧处置（移除操作见 5.4）
```

注意两件事：

- **方向是单向的**：租户状态影响项目，项目操作不回写租户。移除项目成员 ≠ 移出租户。
- **不依赖事件**：即便事件丢失，第 ② 步的请求时检查仍能拦住他，只是提示会稍晚出现。

### 5.2 Owner 被租户停用（最严重的异常）

李老师本人被**另一位租户 Owner（周老师）**停用——租户成员管理要求 Owner+ 权限（见 11 号文档 8.2），团队中只有周老师具备；李老师自己是租户 Owner，不能停用自己，且租户层的 last-owner 保护也不允许移除最后一个 Owner。项目此时没有可执行的 Owner。

本幕演示的是**租户侧未先转让就直接停用**的情形：11 号文档第 4 节要求租户层 suspended 前应先触发项目所有权转让，但该要求依赖租户侧主动配合；未遵守时项目进入 `owner_unavailable`，只能走下面的兜底解除路径。

```text
时序   ① 租户侧：李老师的 TenantMember → suspended（由周老师操作）
       ② ResolveProject 请求时检查发现：owner_user_id 指向的人租户身份已失效
       ③ 项目进入 owner_unavailable
            ├ changeset.apply 入口置灰，说明「需先恢复 Owner 的租户身份，或转让所有权」
            ├ delivery.export 入口置灰，说明同上
            ├ project.archive 入口置灰，说明同上
            ├ 项目首页与成员页显示阻断提示，并给出两条解除路径
            └ 通知租户 Owner（周老师）与项目 Admin（赵老师）
       ④ 项目内其余成员看到提示，但**任何人都不能自行取得所有权**
       ⑤ 解除路径一：周老师恢复李老师的租户身份 → 项目自动恢复
       ⑥ 解除路径二：转让所有权（见 5.3）
```

**约束范围是本场景的重点**：只冻结 Owner 独有的三项能力——`changeset.apply`、`delivery.export` 与 `project.archive`。编辑、调研、审阅等日常协作**不受影响**——它们不需要 Owner 参与，冻结它们只会让项目无谓停摆。真正被卡住的是“改变项目语义”、“放行交付”和“归档项目”。

值得注意的是，**李老师本人此刻发不起转让**——他被停用后连项目都进不去。所以解除路径二必须有一条旁路，见 5.3。

### 5.3 转让所有权：owner_unavailable 的第二条解除路径

承接 5.2，周老师选择不恢复李老师的租户身份，而是促成转让。

```text
前提   转让规则见 11 号文档第 4 节
操作   ① 周老师（租户 Owner，持旁路发起权）在项目成员页指定受让人 → 赵老师
       ② 赵老师确认接受——未确认前所有权保持原状，不把最终责任强加给未同意的人
       ③ 一次事务内完成：赵老师 governance_role 升为 owner，李老师降为 Member
结果   Project.owner_user_id = 赵老师；ProjectMember 中不存在第二行 owner
       赵老师的 Author(Ch6) 职能在同一次事务内被清空——Owner 不携带职能轴，
       她的能力改由 Owner 全集提供，不再受 Ch6 这个 scope 约束（见 11 号文档 3.2 规则 1）
       李老师降级后职能轴为空（Owner 本不参与职能轴选择），按"未指定职能"处理即 Observer；
       其租户身份仍为 suspended，因此项目内仍处于失效态
       项目退出 owner_unavailable，changeset.apply / delivery.export / project.archive 恢复可用
```

三条不能省的约束：

- **原子**：新 Owner 上任与旧 Owner 降级在同一次事务内完成，不允许出现“零 Owner”或“双 Owner”的中间态；
- **受让人确认**：未确认前不生效，避免把最终责任强加给尚未同意的人；
- **旁路发起 ≠ 可自行取得所有权**：`owner_unavailable` 下由租户 `Owner` 或平台管理员**指定受让人并发起**，接不接受由受让人决定；项目内成员仍然无法自行接管。

由此也确定一条边界：**`Owner` 不由邀请产生**——邀请弹窗的治理角色只到 `Admin`（见 2.3），新任 `Owner` 只能走这条转让流程。

### 5.4 移除成员

承接 5.1 与 5.3：陈同学的租户身份已失效，赵老师接管项目后完成项目侧的清理。

```text
操作   赵老师（Owner）→ 移除陈同学
检查   project.members.manage → Owner 具备
结果   ProjectMember.status → removed（项目侧清退，与租户侧传导来的 suspended_by_tenant 区分）
       移除在下一次请求立即生效（每次请求重新解析，不依赖 token 过期）
       陈同学此前已因租户身份失效无法进入项目，本步是项目侧的最终清理
       陈同学的租户身份不受影响
       他创建的 EvidenceCard、ChangeSet 全部保留，作者信息保留在审计中
```

## 6. 第五幕：审计查看

```text
准入   audit.read —— 全部项目成员具备（含 Observer）；审计页只读
显示   确认、导出、权限变更、模型调用、管理员操作
       权限变更条目示例（括号内为变更生效时的项目 Context Revision；
       权限变更本身不推进 Revision，本次演练全程为 Revision 1）：
         「赵老师 于 Ch6 的写作授权 由 李老师 授予（基于 Revision 1）」
         「王同学 的 Reviewer 职能 由 李老师 追加（基于 Revision 1）」
         「项目所有权 由 李老师 转让给 赵老师，周老师 发起、受让人已确认（基于 Revision 1）」
默认   不展示研究原文
归属   租户级操作（成员增删、角色变更）在项目审计页聚合显示其对项目的影响，
```

审计事件不允许由前端伪造；权限拒绝与越权尝试同样入审计。

## 7. 本次演练确认的权限规则

演练过程中明确的四条边界，均已回写 11 号文档：

1. **scope 只约束写操作，不限制读。**
   王同学能读 Ch3–Ch6，但只能写 Ch1–Ch2；张教授能读全部章节，但只能确认 Ch3–Ch4。读取边界由知识库共享级别和资料授权范围管辖，不由职能 scope 管辖——章节之间高度关联，限制读会让协作无法进行。敏感内容另按 11 号文档第 11 节的生产增强项处理。

2. **允许自写自审。**
   王同学追加 `Reviewer` 后可确认自己撰写的章节，`Author + Reviewer` 是其负责章节的正常配置。内容确认不设职责分离要求，可追溯性由确认记录绑定的对象版本与核查范围保证。

3. **双轴角色可自由组合，但治理角色 `Owner` 例外。**
   预设之外的组合（`Admin + Author` 等）与五种预设同为界面可达，不再有“模型支持、界面表达不出”的角色。例外是 `Owner`，有两处：其一，邀请弹窗的治理角色只到 `Admin`，新任 `Owner` 必须走转让流程（见 5.3）——否则会同时存在两个 Owner，与“有且只有一个 Owner”的不变量冲突；其二，`Owner` 不携带职能轴，`governance_role = owner` 的行 `function_roles` / `function_scopes` 恒为空，转让会清空受让人原有的受限授权（见 5.3、11 号文档 3.2 规则 1），其能力一律来自 Owner 全集，不受任何章节/材料/交付版本 scope 约束。

4. **`evidence.confirm` 与 `content.confirm` 是两件事。**
   前者确认“这段原文确实支持该主张”，对象是 `EvidenceCard`（A 域来源真相），scope 按证据卡所服务的主张与章节判定；后者确认“这段文字表述准确、未超出其所引证据能支持的范围”，对象是章节/主张版本（B 域项目真相），scope 按章节本身判定。两者在映射矩阵中恰好同列（`Owner` 与 `Member + Reviewer`），但不可互相替代，也不能由一方推断出另一方。

## 8. 常见操作速查

|---|---|---|
| 创建记录（拿到草稿项目） | 租户角色 ≥ Contributor | LingDoc 项目列表 / 建项向导 |

| 改项目治理/职能角色 | `project.members.manage` | LingDoc 项目成员页 |

| 改 KB 共享级别 | KB 所有者 / 管理员 | WeKnora 知识库设置 |

---

**一句话回顾**：WeKnora 决定“谁属于哪个租户、能否访问哪个知识库”；LingDoc 决定“这个人在当前课题中能对哪些项目对象执行什么操作”；租户侧的状态变化只向项目单向传导，而任何一层拒绝，最终请求都必须拒绝。
