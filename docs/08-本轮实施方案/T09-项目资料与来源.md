## 3. 设计

### 3.1 资料版本：从可观测信号自维护（契约 §10）

契约 §4 要求 `asset_revision` 在「内容或解析定位改变时」变化。底座没有版本号，只有下列可观测信号：

| 信号 | 底座位置 | 说明 |
|---|---|---|
| `FileHash` | `types.Knowledge.FileHash` | 内容指纹，**最强信号** |
| `FileSize` | `types.Knowledge.FileSize` | 缺失（0）与空文件在这里不可区分，取更保守的一侧 |
| `ProcessedAt` | `types.Knowledge.ProcessedAt` | 该次解析完成时刻；重解析会变 |
| `ParseStatus` | `types.Knowledge.ParseStatus` | **不进指纹**，只映射 `processing_state`（理由见下） |

`FingerprintOf` 把**可得**的信号做规范化拼接后取 sha256，并**记录依据**（`basis`，落地在 `lingdoc_asset_revisions.metadata_json`），使得「这次用了哪几个信号」可被报告与人工复核，而不是一个看不出成分的哈希。

- **刻意不吃 `ParseStatus`**：它翻转只是处理进度，把它算进内容指纹会造出契约没要求的版本递增（`processing→completed` 会让 `asset_revision` 平白 +1）。
- **刻意不吃 `UpdatedAt`**：底座任何一次行更新（含状态翻转）都会改它，同上。
- 一个内容信号都拿不到时，指纹落在**固定哨兵** `no_content_signal`，而不是每次现算：现算会让每次观测都判成「变了」，版本自己往上跑；空串更不行——空串在存储里表示「还没观测过」。此路径由 `TestFingerprintWithoutContentSignalsIsStableSentinel` 钉住（§6.4 登记其区分度风险）。
- **退化不改变判据方向**：指纹只用来回答「与上次观测是否相同」。同输入必同输出，所以信号缺失**不会**导致每次都判定为变化。
- 观测到指纹变化 → `asset_revision + 1`，旧修订行标 `superseded`，并新建一条修订行。这正是契约 §4 末行「检测到重解析则要求重新选择资料」的落地：消费者按版本比较发现自己持有的 `asset_revision` 已过期。
- **首次观测只建立基线、不递增**（`Observe` 在 `prev.Fingerprint` 为空时直接返回）：还没有任何东西基于旧版本产出，递增只会平白作废消费者的工作。

`processing_state` 由 `ParseStatus` 映射，**只有 `completed` 映射为 `ready`**（fail-closed）：

| ParseStatus | processing_state | 说明 |
|---|---|---|
| `pending` | `pending` | |
| `processing` / `finalizing` | `processing` | 主解析完成但富化未完成，仍不算就绪 |
| `completed` | `ready` | 唯一可进入允许集合的值 |
| `failed` | `failed` | |
| `cancelled` | `failed` | 契约枚举里没有 `cancelled`；取消后既无可用产物、也不会自行恢复，故并入 `failed`（提示需重解析），而不是 `pending`（会暗示还在排队） |
| `deleting` | `replaced` | 资料正在被删除，绑定不再指向可用内容 |
| `unprocessed` / `""` / 未知值 | `pending` | DDL 默认值里有 `unprocessed` 而 Go 常量里没有；不认识就不当就绪，不给它放行 |

映射表由 `TestProcessingStateOfIsFailClosed` 逐值钉住（含 `cancelled`、`unprocessed`、未知值），断言「恰好一个值映射成 `ready`」。

### 3.2 原文落点：本轮的可诚实上限（T03 §6.5 的缺口）

T03 §3.3 的强档要求「原始资料可直读」。全量解析产物没有落库，`Knowledge.FilePath` 指向原始文件。T09 交出 `NewOriginReader`（`origin.go`），判据是**可证明的字节同一性**，不是「看起来像文本」。

**先查清楚了真链路**（这是本节与初稿最大的差别，初稿的两条结论是错的）：

| 环节 | 实际行为 | 出处 |
|---|---|---|
| Go 侧简单格式读取 | `md`/`markdown`/`txt`/`text` **原样返回文件字节**，不过 Python 解析服务 | `docparser/builtin_converter.go:57-60` |
| 同处的转换格式 | `csv`→`csvToMarkdown`、`json`→`jsonToMarkdown` **明确改写** | 同文件 `:61-72` |
| 切分前的清洗 | `CleanInvalidUTF8` 丢掉非法 UTF-8 字节与 NUL | `common/tools.go:189-210` |
| 切分前的归一 | `NormalizeLineEndings` 把 `\r\n` 与 `\r` 统一成 `\n` | `infra/chunker/strategy.go:207-213` |
| 切分前的图片处理 | 图片引用被改写成对象存储地址 | `docparser/image_resolver.go` |

**所以强档的成立条件被精确化成**：读到的字节经过上述几步改写之后**没有变化**。逐条排除：

| 情况 | 结论 | 理由 |
|---|---|---|
| `txt`/`text`/`md`/`markdown` 且文件干净 | **强档 `ok=true`** | 字节同一，rune 偏移可比对 |
| `csv`/`json` | 降弱档 | 解析侧明确改写，偏移不可证 |
| PDF/DOCX/HTML/图片等 | 降弱档 | 走 Python 解析，产物与文件无逐字关系 |
| 文件含 `\r`（CRLF 或裸 CR） | 降弱档 | 切分用的是归一后的文本，硬claim会产出**假的 `stale`** |
| 文件含 NUL、或非法 UTF-8 | 降弱档 | `CleanInvalidUTF8` 会丢字节 |
| 文件含图片引用（`![`/`<img`/`data:image/`） | 降弱档 | 图片解析会改写这串字节 |
| 带 UTF-8 BOM | **仍算强档** | U+FEFF 是合法 rune、不是 NUL，上面两步都不动它，两侧一致（初稿判错，已由 `TestOriginAcceptsBOMBecausePipelineKeepsIt` 钉住） |
| 文件缺失/目录/空文件/超 8 MiB | 降弱档 | 读不出可比对的正文；**不是错误**——底座真故障才报错（`TestOriginSeparatesWeakTierFromFailure`） |
| 该文件类型被 KB 规则改派给别的引擎 | 降弱档 | 见下「第二道前提」 |

**第二道前提：没有别的引擎经手**（代码评审补上的一处假强档）。上面那句「`md`/`txt` 原样返回字节」只在**默认路由**下成立：`eff.ChunkingConfig.ResolveParserEngine(fileType)`（`knowledge_process.go:3771`）允许 KB 级 `parser_engine_rules` 把 txt/md 改派出去，那时切分吃的是引擎产出的 markdown，与文件字节不再逐字相等，而 `origin.go` 仍会发强档 → 又是一批假的 `stale`。空串即内置路由（`types/knowledgebase.go:305`）。

判据因此要求调用方回答一个事实：`KnowledgeReader.UsesBuiltinConverter(ctx, knowledgeID)`。实现方在接线处取上面那个函数，**判不定返回 false**——保守一侧是降档，不是失败。`TestOriginDeclinesWhenAnotherEngineParsesTheContent` 钉住三条：改派降档、判定故障如实报错、手工资料不受引擎路由影响（它走另一条链路，直接进 Go 分块器）。

**手工资料的强档同样要按链路走，不能靠「手工写的」这个身份**（代码评审补上的另一处假强档）。它的正文在 `metadata.content` 里（`types.ManualKnowledgeMetadata`，见 `types/knowledge.go:322`），但进切分前有**四步改写**（`knowledge_create.go:1237-1274`），而分块器切的是改写之后的文本——chunk 的 rune 偏移是相对改写结果，不是相对 metadata 里的原文：

| 步骤 | 处理 | 出处 |
|---|---|---|
| 1. `clean := strings.TrimSpace(content)` | **纯函数——这里照样做一遍**，取回的字串就与切分输入对齐 | `:1237` |
| 2. data-URI 图片解析成存储地址 | **排除**：读文件系统/存储，重建不出同结果 | `:1241` |
| 3. 远程 http(s) 图片解析成存储地址 | **排除**：要联网 | `:1249` |
| 4. `chunker.NormalizeLineEndings(clean)` | **排除**：手工输入的 CRLF 是常态（该行注释自认） | `:1274` |

镜像第 1 步比降档更对：首尾空白是最常见的情况，而分块器看到的就是 `TrimSpace` 之后的那一串，取回它偏移才对齐（否则块尾的偏移会越界）。后三步只能排除。`TestOriginDeclinesManualContentThePipelineRewrites` 两边都钉：CRLF/图片降档，首尾空白取回对齐后的字串。

- 降弱档不是失败：调用方落到 T03 已有的 `quoteBySelfConsistency`，引用仍可用，只是强度不同。
- **不新增解析产物落点**：那是底座（docreader/解析链路）的职责，且「重解析」会引入新的失效面（解析器版本、模型版本）而本轮无法验证。本轮如实声明上限，把「解析产物落库」登记为欠账（§6.3）。
- 维护提示：上面几处改写只要有一处变了（例如新增加一道清洗），`verbatimOrigin` 的判据就必须跟着改。这是**有意写死的耦合**——判据依赖的是底座的实现细节，而它没有稳定的公开契约。

### 3.3 授权接缝：消费既有权限体系，不自建（B2）

`evidence.Authorizer` 是 T03 留下的消费点。T09 交出 `NewFixedAuthorizer`（`authz.go`），它**只回答资料级当前授权**：

```
FixedAuthorizer.CanAccessAsset = ScopeReader.AssetScope(projectID, assetID) → KBReadChecker.CanReadKB(actor, kbID, ownerTenant)
```

- `ScopeReader` 由 `Bindings` 直接满足：判权要知道「这份资料属于哪个知识库、那个库属于哪个租户」，而契约的 `Asset` 是 `additionalProperties: false`，加不了这两个字段；回存储取是对的落点。
- **`AssetScope` 按（项目, 资料）双键收敛**（代码评审修正）：早先只按 `assetID` 查，注释却声称「与 `ObserveAsset` 一样按 projectID 收敛」——承诺由调用方保证，而不是本方法保证，于是它成了一个跨项目探测的口子。现在项目不对就返回 `ErrAssetNotFound`，与「不存在」不可分辨（`TestBindingsAssetScope` 钉住）。`CanAccessAsset` 的参数 `projectID` 早先是 `_`，现在真的用上了。
- `KBReadChecker` 是**缝**：实现在应用层（`internal/application/access` 的 `KBPermissions.Check(kbID, ownerTenantID, OrgRoleViewer)`），由接线处注入。本包不反向依赖应用层——那会把 `types.Caller` 这类运行上下文语义带进资料域。**该适配器随 S4 一起落**（S4 才有 ctx 里的 `types.Caller`）。
- 判权**每次现查、不缓存、不落库**（B5，`TestFixedAuthorizerAsksEveryTime` / `TestGatewayDeniesAfterRevocation`）。**不写** `lingdoc_asset_revisions.status = 'revoked'`：那是把授权状态存成标志位，撤权后再授权就会留下一个过期的 `revoked`。授权是「此刻能不能读」的问答，不是资料自身的属性。

**初稿在这里判错了一半**，修正如下：项目可见性**不放在** `Authorizer` 里。

- 端口只能回 true/false，而「不可见」在 HTTP 上必须与「不存在」收敛成同一个答案（`02-接口与Mock约定.md` §8 末句）。若由这里把不可见答成 `not_authorized`，就变成「403 说明这个项目存在」——**泄露存在性**。
- 且 `02-接口与Mock约定.md` §2 要求资料服务「校验资料不能再调用已经包含来源检查的总入口」：项目可见性是工作区服务（T07 的 ProjectAccess）的事。
- 所以它是 **S4 接线时的前置条件**，由 HTTP 层先判、不可见即 404，且必须现查。这一点在 `NewFixedAuthorizer` 的文档注释里写死，避免接线的人漏掉。

### 3.4 拒绝原因与「请求 ID 集合 vs 返回 ID 集合」

契约 §8 要求资料服务比较请求 ID 与返回 ID，不能把「返回无错误」当成全部授权成功。T03 的 `ResolveResult{Requested, Allowed, Denied}` 已承载这个语义，T09 的责任是：**用真实存储与真实授权把三条路径都跑到**（未就绪/未授权/不存在），并断言 `Requested` 逐项出现在 `Allowed ∪ Denied` 中——缺项即失败。

跨项目 ID 与不存在的 ID 收敛为同一个 `not_found`（不泄露存在性）。

### 3.5 仓储与迁移

- `Bindings`（`binding.go`）是绑定存储，GORM 模型 `ProjectAsset` / `ProjectAssetRevision` 对应设计表 `lingdoc_project_assets` / `lingdoc_asset_revisions`；`Asset`（契约形状）仍由 T03 的 `asset.go` 承载，**序列化边界不变**。
- 迁移：`migrations/versioned/000098_lingdoc_evidence_assets.*.sql` + `migrations/sqlite/000019_lingdoc_evidence_assets.*.sql`。
  **版本号取 98/19 而不是 97/18**：PR #4（未合入）已占用 `000097_lingdoc_workspace` / `000018_lingdoc_workspace`。设计文档 §6.1 要求「不复用已经占用的版本号；合并分支前重新检查最大版本号」——本条即为那一步的结论。
- 迁移只建结构/索引/约束，不写业务数据（设计文档 §6.1）。`internal/database` 的双库对照测试已登记新表并把 `expectedSQLiteMigrationVersion` 提到 19。

**与设计表 §4.2 逐条的差别（不是遗漏，是决定）**：

| 设计列 | 本轮处理 | 理由 |

| `processing_run_ref`（修订表） | **不落** | 同上 |
| 修订表 `status` 的 `failed`/`revoked` | CHECK 里保留，**只写 `active`/`superseded`** | `revoked` 会与 B5 冲突（见 §3.3）；CHECK 取设计表的全集，免得为别人的取值再改一次表 |
| 至少一个 `knowledge_id`/`external_ref` | 收紧为 `knowledge_id NOT NULL` | 本轮只有 `weknora` 来源，`external_ref` 不存在，收紧后的不变量更简单也更强 |

**模型与迁移必须逐列一致**，这条由 `TestSQLiteMigrationSchemaSupportsBindings` 守住：它把 `000019` 的 DDL 原样执行，再在真实表上跑绑定/观测/唯一约束/CHECK。`AutoMigrate` 建的表只能证明模型自洽，证明不了 `migrations/` 里的那一份，而线上跑的是后者。

**该测试在本轮补了一段：索引也要对齐**（代码评审发现的漏洞）。早先它只看表名与 CHECK，于是漏掉过一类漂移——模型上的 `gorm:"index"` 与迁移里的 `CREATE INDEX` 是两处独立声明，谁多一条少一条都不会让上面那些断言变红，而测试库（AutoMigrate）与线上 DDL 就此分叉。现在它用 `PRAGMA index_list` + `index_info` 比**索引形状**（唯一与否 + 列序列，排序后比较），刻意不比名字：迁移里用表级 `UNIQUE` 声明的那两条，SQLite 建出来叫 `sqlite_autoindex_*`，而 `uniqueIndex` 建出来是带名字的索引，比名字只会造出假的红。

这一段补上当天就抓出两处真实漂移：

| 漂移 | 谁对 | 处理 |
|---|---|---|
| 模型把 `idx_lingdoc_project_assets_scope` 只声明在 `tenant_id` 一列上，迁移是 `(tenant_id, project_id)` | 迁移 | 模型给 `ProjectID` 补上 `index:...,priority:2` |
| 迁移多一条 `idx_lingdoc_asset_revisions_asset (asset_id, revision_no DESC)` | 模型 | 删掉这条冗余索引：同列的 `UNIQUE (asset_id, revision_no)` 就是 btree，本域的查询（精确查某一版、按 `asset_id` 取全部修订）都走它，`DESC` 只对谁都没做的「最新优先扫描」有用 |

另外 `ProjectAsset.DeletedAt` 去掉了 `gorm:"index"`：本域没有一个查询按 `deleted_at` 过滤，建一条用不上的索引只会多一处可以漂移的地方。`migrations/versioned/000098` 与 `migrations/sqlite/000019` 两份对称，两份都在真实 Postgres 容器上实跑过（见 §7）。

### 6.4 未测风险

- `FileHash` 在部分资料类型上可能为空；退化到只剩 `FileSize` 时指纹区分度低（同大小改内容检测不出来），只剩 `no_content_signal` 时**完全不检测**。这条路径有测试钉住行为，但**没有真实资料样本可验证它的实际发生率**——不知道线上有多少资料落在这一档。
