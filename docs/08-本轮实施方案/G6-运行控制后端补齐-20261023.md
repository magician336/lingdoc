## 4. 口径与不可变契约

### 4.1 #382-A 告警规则可读回

- `Service.ListRuntimeAlertRules(ctx, actor, projectID) ([]RuntimeAlertRule, error)`：
  只读事务 + 项目 read 授权 + `ListRuntimeRecords(tenant, projectID, "alert_rule")`，逐条反序列化。
- HTTP：`GET /api/v1/lingdoc/projects/:projectId/runtime/alert-rules`（`impactRouteRead`）。
- 返回的规则必须带出**状态**与**版本**。

### 4.2 #382-B 告警规则可停用 / 可更新

- `RuntimeAlertRule` 增加 `Version int64`（json `version`）与 `Status string`
  （json `status`，取值 `ACTIVE` / `DISABLED`）；新建时 `Status=ACTIVE`、`Version=1`。
- 新增 `RuntimeAlertRuleActionInput{ExpectedVersion, Operation, Reason, Signal?, Severity?, Disposition?, ResponsibleID?, Scope?}`。
  `Operation` ∈ `disable` | `enable` | `update`。**处置动作字段叫 `disposition` 而不是 `action`**——
  规则的 `Action` 是处置动作，语义会撞车。
- `disable` → `DISABLED`；已停用再 `disable` → `ErrInvalidState`。`enable` → `ACTIVE`；
  已启用再 `enable` → `ErrInvalidState`。`update` 改 `signal/severity/disposition/responsible_id/scope`，
  **未提供的字段保持原值**。
- `reason` 非空否则 `ErrInvalidRequest`；`expected_version` 不符 → `ErrVersionConflict`。
- `signal` / `severity` / `disposition` / `responsible_id` 的合法值**复用 `SaveRuntimeAlertRule` 的同一套校验**
  （`runtime_alert_rule.go` 的 `validRuntimeAlertSignal` / `validRuntimeAlertSeverity` /
  `validRuntimeAlertDisposition` / `validRuntimeAlertRule`），不复制第二份规则表。
- `responsible_id` 仍须对项目有 manage 权。
- CAS 用 `CompareAndSwapRuntimeRecord(tenant, projectID, "alert_rule", ruleID, expectedVersion, next)`，
  `next.Version = expectedVersion + 1`。
- HTTP：`POST /api/v1/lingdoc/projects/:projectId/runtime/alert-rules/:ruleId/actions`
  （`impactRouteWrite(h, true, ...)`）。
- **`applyRuntimeAlerts` 必须跳过 `Status == "DISABLED"` 的规则**——这是本规格的核心行为，
  必须有测试证明。

### 4.3 #382-C 授权判定可观测

- **只记拒绝（deny），不记放行（allow）**。理由：放行是常态且每次读请求都会发生，记下来会淹没运行事件流、
  让 `GET /runtime/events` 的全量返回变成性能问题；拒绝才是需要值班响应的信号。放行侧由既有的
  `request/success` 事件覆盖。
- **判定结果必须在不会被回滚的事务上下文里写**。operation 路径的授权拒绝会让写事务回滚
  ⇒ 写在同事务里的事件会一起消失；而 operation 写路径恰恰是最需要观测的。
- **不能在 `authorizeProject` / `authorizeTenant` 里另开事务写事件**：SQLite 单连接下写事务进行中另开
  store 会死锁。
- ⇒ **上下文 holder 方案**：`workspacecore` 导出 `RuntimeObservationHolder` 与 ctx 存取函数
  （holder 是可变指针）；`authorizeProject` / `authorizeTenant` 在拒绝时往 holder 写
  `{capability, decision:"deny", reason}`；判定结果由 **holder 携带**，在**事务结束后**由一个
  **独立事务**写成运行事件（`category="permission"`, `status="deny"`,
  `error_code=<拒绝错误码>`，另带 `capability` 字段）。事件写入失败必须被忽略（`_ =`）。
- **holder 装在哪**：装在**服务方法**上（G6 运行时方法、读类访问路径、`runOperation`），
  而不是 HTTP 适配层。这样覆盖的是**所有经过 WorkspaceCore 事务的授权判定**，
  包含 G6 端点组，也包含内部调用；HTTP 层因此不需要改动。
- **覆盖面如实声明**：覆盖**经 WorkspaceCore 事务发起的 capability 判定**（G6 端点组在内）；
  **不覆盖 `projectOwner()` 一族 Owner-only 业务前置条件**（在 `authorizeProject` 之外）；
  **不覆盖**未经 `authorizeProject` / `authorizeTenant` 的判定。
- **拒绝事件不带 project revision**（判定失败时 `Project{}` 零值，且读项目行会削弱 404 的存在性隐藏语义）。
- 观测里只有 allow/deny 二值 + `error_code`，**没有细因**（拒绝原因被刻意抹平为 `ErrNotFound`）；
  「拒了什么能力」由 `authorizationDecisionError` 带上（它只加能力名，不改变拒绝本身）。
- **授权拒绝只进事件流，不触发告警规则**。这是**有意的**：告警规则的 `pause` 动作会直接暂停整个课题，
  一次被拒的调用不该造成这种后果。值班请看运行事件流。若要「拒绝可告警」，需另开票并限定
  告警动作不含 `pause` / `block_export`。

### 4.4 #383 运行控制的回退端点

- **回退经既有领域入口执行**，不新造回退领域逻辑：`reverseChangeSet`
  （`change_inverse_operation.go`，HTTP `POST /projects/:projectId/change-sets/:changeSetId/reverse`）。
- `RuntimeControlInput.Action` 加 `"rollback"`；加 `Rollback *RuntimeRollbackInput{ChangeSetID, TemplateVersion, RulesetHash}`；
  `RuntimeControl` 加 `RollbackTo *RuntimeRollbackTarget`。
- `rollback` 语义：① 与 `pause` 完全相同的范围校验与授权（project scope 要求 owner，其它 scope 要求
  tenant-manage，跨范围 → `ErrNotFound`）；② 通过领域入口执行逆向 ChangeSet
  （**不直接改 revision 指针、数据库指针或发布文件**）；③ 新写入停止（状态 `PAUSED`），记录目标配置；
  ④ 写审计 `runtime.rollback`。
- **范围校验与授权在逆向之前完成**：未授权的调用者不能「先让领域变更发生，再被拒绝」。
- 逆向 ChangeSet 有自己的事务，不能跑在控制写的事务里（SQLite 单连接会死锁），所以
  `prepareRuntimeRollback` 先跑一次只读的范围/授权校验，再跑逆向，最后才写控制记录。
- `resume` 仍要求既有复验（`snapshot_id` + `export_id` + `runtimeRecovery.Recheck`），
  并校验目标配置仍可读（不匹配 → `ErrRuntimeRecoveryRequired`）。
- ⚠️ **「切回已验证配置」这一半本轮不完整实现**：让后续新写入真正使用旧模板/旧规则需要领域写路径支持，
  不在本面范围。本轮实现的是「停止新版本写入 + 记录回退目标 + 复验后恢复」。
  **这一条必须如实写进票面与 PR，不得让它看起来像已经切过去了。**
