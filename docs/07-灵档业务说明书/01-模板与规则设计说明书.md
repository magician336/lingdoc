# 灵档模板与规则设计说明书

_本文是写给**申报领域专家**的工作手册，不是技术文档。不需要任何计算机背景也能完整使用。_

## 1. 这份文档要你做什么

灵档要在写作过程中提醒团队"材料还缺什么、哪里不合规"。这些提醒是否靠谱，取决于**规则写得对不对**——而规则对不对，只有懂申报的人能判断。

所以我们需要你做的事是：**把你判断一份申报书合不合格时用的标准，写成我们双方都能核对的规则说明书。**

你在日常评审中一眼就能看出的问题（缺样本范围、术语前后不一、创新点和研究问题对不上），正是我们想固化的对象。系统不会替你判断学术价值，它只负责在你写的过程中把你自己的标准反复提醒到位。

### 1.1 分工

| 谁 | 负责什么 |
|---|---|
| **领域专家（你）** | 章节结构、必要字段、术语表、规则说明书，以及每条规则的正例与反例 |
| **产品** | 与专家共同确认规则的严重度；评估误报风险；决定上线节奏 |
| **开发** | 把规则说明书实现为系统行为；对每条规则跑通正反例 |
| **机构管理员** | 规则上线后的发布、版本管理与废止 |

**你不需要考虑技术如何实现**，只需要保证：你说的标准准确，且举得出例子。

### 1.2 你要交付的五份东西

| # | 交付物 | 用途 | 本文对应章节 |
|---|---|---|---|
| 1 | 章节结构表 | 决定作者看到的章节骨架 | 第 3 节 |
| 2 | 必要字段表 | 决定建项时必须填清楚哪些研究条件 | 第 4 节 |
| 3 | 术语表 | 决定"术语一致性"检查以什么为准 | 第 5 节 |
| 4 | **规则说明书** | 决定系统在写作与交付时检查什么 | 第 6 节 |
| 5 | 正例与反例 | 决定规则是否被正确实现 | 第 6、8 节 |

## 2. 三条你必须知道的约束

这决定你的设计能不能被系统执行。

### 2.1 规则要么能被算出来，要么能被举出例子

| 规则类型 | 特征 | 能否自动化 |
|---|---|---|
| **能算出来** | 标准明确，任何人用同样的方法算都得到同样结果 | 系统自动检查 |
| **能举出例子** | 标准依赖文字含义，但你举得出明确的正面和反面例子 | 系统提示，人来判断 |
| **举不出例子** | 你自己也说不清什么算合格、什么算不合格 | 不写成规则 |

最后一种不是你的失职，而是这类要求本就该由评审会裁量。把它写成规则，只会产生大量无意义的提醒，反而让团队不再信任系统的提示。

> **一个很好用的自检方法**
>
> 写下一条规则后，问自己：**我能立刻举出一个"这条肯定不合格"的例子吗？**
> 举不出来 → 这条先别写。
> 举得出来但标准模糊（"要有创新性"）→ 换一种说法，把它变成能举出例子的具体问题（"创新点是否明确说明了与已有研究的区别"）。

### 2.2 严重度决定这条规则会不会卡住整个团队

| 严重度 | 含义 | 后果 |
|---|---|---|
| **阻断** | 材料不合格，不能提交 | 问题不解决就**不能导出**，团队无法提交 |
| **警告** | 应该改，但不改也能交 | 可以带理由放行 |
| **提示** | 建议性内容 | 可以带理由放行 |

**阻断级要慎用。** 一条阻断规则如果判断错了（把合格的材料判成不合格），整个课题组都会被卡住，必须由人逐条推翻才能继续。所以：

- 只有当"95% 以上情况确实不合格"时才设阻断；
- 你自己在判断时也要犹豫的情况，设警告；
- 给新规则定严重度时，**默认从警告起步**，运行一段时间确认误报很少后再升级为阻断。

### 2.3 系统能改格式，但不能替你决定学术问题

| 系统会做什么 | 系统不会做什么 |
|---|---|
| 指出"第五章缺少样本范围" | 替你决定样本范围该写什么 |
| 指出"这里字数超了 200 字" | 替你删减内容 |
| 指出"第三章的术语和第二章不一致" | 替你统一（往哪边统一是研究决策） |
| 指出"这个论断只有背景材料支撑" | 替你补证据或改写论断 |

**格式类问题系统可以一键修复，内容类问题只给建议。** 这一条会影响你写规则时的措辞——你要写的是"提醒什么问题"，不是"要求系统怎么改"。

## 3. 任务一：设计章节结构

章节结构决定作者打开项目时看到的骨架。请按申报通知的要求，把完整章节列出来。

| 顺序 | 章节名称 | 是否必需 | 说明（这一章要写清什么） |
|---|---|---|---|
| 1 | 选题依据 | 必需 | 研究背景、研究问题、研究价值 |
| 2 | 国内外研究现状 | 必需 | 理论脉络、已有研究的不足 |
| … | … | | |

**几点注意**：

- **必需 / 可选的区分会影响检查**。标为"必需"的章节缺失时会报问题，标为"可选"的不会。
- **顺序就是作者看到的顺序**，和申报通知保持一致。
- **章节名称用申报通知的原文**。如果通知里叫"研究基础与条件"，不要简写成"研究基础"——作者和评审都按通知对材料。
- 如果某一章内部还分固定小节（如"研究现状"下分"国内"和"国外"），在说明栏里写清楚，这会影响后续检查的粒度。

---

## 4. 任务二：确定必要字段

必要字段是建项时必须填清楚的研究条件。它们不只是表单——后续所有检查都拿这些字段当基准。

| 字段名 | 填写说明 | 是否必需 | 这一项会影响哪些检查 |
|---|---|---|---|
| 研究对象 | 研究针对的具体人群/现象/材料 | 必需 | 方法章节是否与对象匹配、样本说明是否完整 |
| 研究目标 | 要回答的核心问题 | 必需 | 预期成果是否与研究目标呼应 |
| 拟用方法 | 主要研究方法 | 必需 | 方法章节完整性、样本量依据 |
| 核心变量 | 关键变量及其关系 | 必需 | 各章是否一致地使用这些变量 |
| 资源条件 | 数据/设备/经费/时间 | 可选 | 可行性说明 |
| 研究限制 | 已知约束 | 可选 | 是否有相应的应对说明 |

**设计要点**：

- **字段不是越多越好**。填不出来的字段会变成形式主义，作者随便填两笔，反而污染后续检查（系统会拿它当基准去比对正文）。只保留真正会被引用的字段。
- **字段名要与正文用词一致**。如果你把字段定名为"研究对象"，正文里却常说"研究群体"，术语一致性检查就会一直误报。
- **每个字段都要能说清"谁来用"**。如果一个字段填完之后，没有任何检查或任何章节会用到它，它就不该出现在必要字段里。

---

## 5. 任务三：维护术语表

术语表是"术语一致性"检查的唯一依据。系统会检查正文用词是否与这里一致。

| 应采用 | 不应使用 | 说明 |
|---|---|---|
| 创业意向 | 创业意愿、创业倾向、创业动机 | 指同一概念，全文统一 |
| 创新创业教育 | 双创教育、创业教育 | 含创新与创业两重含义，不可简写 |
| … | | |

**设计要点**：

- **只收真正会被混用的词**。语言中所有近义词都收进来，检查会变得极其啰嗦，作者会关掉提示。
- **"不应使用"栏里的词，如果本身有独立含义，不要列入**。例如"创业动机"如果在本研究中是另一个独立变量，它就不是"创业意向"的误用，不应收进同一行。
- **术语表和必要字段要互相对齐**。字段定名"核心变量"、术语表写"创业意向"，两者应指向同一个写法。

---

## 6. 任务四：编写规则说明书（核心工作）

这是你交付物里最重要的部分，也是耗时最多的部分。每条规则填写以下六项。

### 6.1 规则说明书的填写格式

| 填写项 | 说明 |
|---|---|
| **① 规则编号** | 如 R-01，便于后续引用和追踪 |
| **② 规则名称** | 一句话说明它检查什么 |
| **③ 判定方式** | 能算出来 / 需例判断（见下） |
| **④ 严重度** | 阻断 / 警告 / 提示 |
| **⑤ 适用对象** | 这条规则检查哪些章节或字段。**限定范围能大幅降低误报** |
| **⑥ 正例与反例** | 一个"这条不合格"的例子，一个"这条合格"的例子。**反例可省略，正例必填** |
| ⑦ 触发场景 | 你希望作者什么时候被提醒（写作中 / 交付前） |

### 6.2 ③ 判定方式怎么选

依次问自己两个问题：

```text
问题一：这条标准，换个人来判断，会不会得出不同结论？
   不会 → 能算出来（例如字数、标题层级、章节是否缺失、是否引用了未列出的文献）
   会   → 继续问问题二

问题二：你能举出一个"肯定不合格"的具体例子吗？
   能   → 需例判断（例如术语不一致、论断缺少支撑）
   不能 → 先不要写成规则
```

| 判定方式 | 系统的行为 | 例子 |
|---|---|---|
| **能算出来** | 系统直接判定，可提供一键修复 | 字数、章节完整性、编号格式、章节标题层级 |
| **需例判断** | 系统给出提示，由作者判断是否属实 | 术语一致性、论断是否有证据支撑、各章是否互相呼应 |

> **"需例判断"的规则一定要给正例**
>
> 因为这类规则最终由系统提示、由人接受或推翻，**你的正例就是系统学习"什么算不合格"的唯一依据**。正例写得含糊，规则上线后会产生大量误报，作者会开始无视所有提示。

### 6.3 规则说明书示例

**示例一：能算出来的规则**

| 填写项 | 内容 |
|---|---|
| ① 规则编号 | R-01 |
| ② 规则名称 | 选题依据章节正文不少于 800 字 |
| ③ 判定方式 | 能算出来 |
| ④ 严重度 | 警告 |
| ⑤ 适用对象 | 第一章"选题依据" |
| ⑥ 正例（不合格） | "本章正文约 500 字，未达到 800 字要求。" |
| ⑦ 触发场景 | 写作中与交付前都检查 |

**示例二：需例判断的规则**

| 填写项 | 内容 |
|---|---|
| ① 规则编号 | R-07 |
| ② 规则名称 | 术语与项目研究条件不一致 |
| ③ 判定方式 | 需例判断 |
| ④ 严重度 | 警告 |
| ⑤ 适用对象 | 全部章节 |
| ⑥ 正例（不合格） | "项目研究条件中写作'创业意向'，第二章第 3 段写作'创业意愿'，属同一概念的不同表述。" |
| ⑦ 触发场景 | 写作中随时可查 |

**示例三：一条不该写的规则（反面示例）**

| 填写项 | 内容 |
|---|---|
| ② 规则名称 | 创新点应具有创新性 |
| 问题 | 举不出明确的反例——"这条创新点不够创新"没有客观界线，不同评审给不同答案 |
| 改写成 | R-12「创新点是否明确说明了与已有研究的区别」——这个能举出例子：合格的做法会说清"已有研究做到了 X，本研究进一步做到 Y"；不合格的只写"本研究具有重要的创新意义"而不说区别在哪 |

## 7. 任务五：确定上线节奏

规则不是一次全上。推荐分三批：

| 批次 | 内容 | 上线方式 |
|---|---|---|
| **第一批** | 章节完整性、必要字段完整性、字数等"能算出来"的规则 | 直接上线，先设为警告级 |
| **第二批** | 术语一致性等"需例判断"但例子清晰的规则 | 先内部试跑，统计误报，误报低于约定比例后上线 |
| **第三批** | 论证一致性等判断较难的规则 | 仅以提示级上线；观察一个申报周期后再评估 |
| **之后** | 第一批中运行良好、确认极少误报的规则 | 经评审后升级为阻断级 |

**升级为阻断级需要一个明确的决定**，不是自动发生的：由产品与专家共同确认"这条规则在过去一个申报周期内没有产生过误报"，并留下记录。

## 8. 交付与评审

### 8.1 你会拿到什么反馈

提交规则说明书后，开发团队会做两件事并把结果给你：

1. **正例能否触发**——你写的每条"不合格"例子，系统是否都能正确识别；
2. **反例是否误报**——你写的合格例子，系统是否误判为不合格。

这两项通不过，规则不会被上线，会退回给你调整措辞或补充例子。**这是正常的迭代，不是你的交付质量问题。**

### 8.2 上线后你会看到什么

系统会统计每条规则的**误报率**——即"系统提示了，但作者判断不需要处理"的比例。

| 误报率 | 建议动作 |
|---|---|
| 低于约定阈值 | 维持现状；表现良好的可考虑升级严重度 |
| 明显偏高 | 检查规则措辞是否需要收窄适用对象，或补充更清晰的正例 |
| 长期偏高 | 考虑降级为提示级，或暂时下线 |

### 8.3 规则会随申报要求变化

申报通知每年调整，规则也需要跟着改。规则**不是一次交付就固定**的：

- **修改措辞或适用范围** → 需要重新过 8.1 的评审；
- **新增规则** → 从警告级起步；
- **废止规则** → 机构管理员处理，历史记录保留。

## 9. 待确定事项

以下事项需要在本说明书定稿前确认：

| 事项 | 说明 |
|---|---|
| **首批目标申报类别** | 本文全部结构与示例为占位内容，需替换为实际申报类别的真实要求 |
| **规则数量目标** | 建议首批 15–25 条，需结合实际申报要求调整 |
| **推荐专家名单** | 由谁担任规则设计的领域专家，及其可投入的时间 |
| **误报率阈值** | "低于约定阈值"的具体数值，需由产品与专家共同确定 |
| **可参照的既有材料** | 申报通知原文、历年申报书、评审意见等可作为规则来源的材料 |

## 附：与开发文档的关系

本文是**业务侧的设计输入**；开发团队据此实现的具体计划见 [`12-模板与规则系统开发计划`](../06-灵档产品开发规划/12-模板与规则系统开发计划.md)。两份文档的分工：

| 本文（业务侧） | 开发计划（技术侧） |
|---|---|
| 章节结构该包含什么 | 章节骨架如何生成与存储 |
| 规则该检查什么、举例 | 规则如何被系统求值 |
| 严重度如何影响团队 | 严重度如何阻断导出 |
| 专家何时介入、评审什么 | 规则版本如何管理与回滚 |
