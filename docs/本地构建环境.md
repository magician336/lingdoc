# 构建环境与 CGO 前置条件

本文件说明本仓库在本地构建 Go 后端所需的环境，以及每个平台遇到的具体问题。

## 为什么需要 CGO

后端依赖两条原生链路，都必须启用 `CGO_ENABLED=1`：

- `github.com/duckdb/duckdb-go/v2` — 分析型查询引擎
- `github.com/asg017/sqlite-vec-go-bindings/cgo` — SQLite 向量扩展

也就是说，即使运行时选择 PostgreSQL，构建阶段仍会编译并链接 DuckDB 与 sqlite-vec。

## sqlite-vec 需要 SQLite 开发头文件

`sqlite-vec-go-bindings` 的 cgo 版本用 `#include "sqlite3.h"` 编译自己的 C 代码，因此 C 编译器必须能找到该头文件。缺少时构建会停在：

```
sqlite-vec.h:7:10: fatal error: sqlite3.h: No such file or directory
```

Linux CI 镜像自带该头文件（Ubuntu 上由 `libsqlite3-dev` 提供），所以 CI 从不报这个错；裸的 Windows / macOS 工具链通常没有对应的 SQLite 开发包，只有编译器。

### 仓库脚本如何处理

`scripts/ensure-sqlite-header.sh` 处理这个依赖：

1. 先探测编译器能否直接找到 `sqlite3.h`。能找到就直接退出，不做任何改动。
2. 找不到则从 `github.com/mattn/go-sqlite3`（项目已依赖、且 gorm 实际使用的驱动）取它随包携带的 SQLite amalgamation 头文件，拷到一个临时目录，并通过 `CGO_CFLAGS=-I<目录>` 交给编译器。

这样构建不再依赖系统包管理器，Linux、macOS、Windows 通用，也不会影响已经装好开发包的环境。

`make build`、`scripts/dev.sh` 与 `scripts/package-lite.sh` 都会自动调用它。手动构建时：

```bash
source scripts/ensure-sqlite-header.sh
go build ./cmd/server
```

脚本在需要介入时会在 stderr 打一行说明；系统已有该头文件时它保持静默。

> `make build` 的 recipe 显式走 `bash -c`，因为 Windows 上的 `make` 默认用 cmd.exe 执行 recipe 行，那里没有 `source` 内建命令。

### 仍然需要的工具链

头文件只是其中一环。CGO 还需要一套 C 编译器：

| 平台 | 要求 |
| --- | --- |
| Linux | `gcc`，以及 `libsqlite3-dev`（可选，有它脚本就不介入） |
| macOS | Xcode Command Line Tools：`xcode-select --install` |
| Windows | 支持 CGO 的 GCC。推荐 UCRT 工具链（MSYS2 UCRT64 或 WinLibs），并确认 `gcc` 在 PATH 中 |

Windows 上还有两点已知限制：

- DuckDB 的预编译静态库依赖 GCC 的 libstdc++，**不要**用 LLVM-MinGW（它用 libc++），也不要用过旧的 MinGW 8.1。
- 路径尽量用 ASCII，避免中文路径带来的工具链问题。
