# G3. PCC、ChangeSet、依赖图与技术路线图

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)  
> 对照设计：[领域架构与 PCC](../02-领域架构与PCC.md)、[数据模型与接口契约](../03-数据模型与接口契约.md)  
> 前置假设：T01–T16 已完成并通过各自验收。本文件描述领域逻辑和交接契约，不表示功能当前已实现。

## 1. 目标和问题定义

G3 解决 active 项目建立正式基线之后的“改了一个地方，其他地方怎么办”问题。研究条件、项目资料范围、证据主张、章节结论、模板规则和技术路线之间存在明确依赖；任何一个正式变化都必须能够回答：

1. 这次变化修改了哪个正式版本，是否仍基于当前基线？
2. 哪些对象因显式依赖而受到影响，哪些对象明确不受影响？
3. 谁负责复核、重新确认或重新生成，什么结果才算处置完成？
4. 在全部阻断问题解决前，为什么项目不能稳定或导出？

PCC（Project Change Coordination）只协调变更、依赖、任务和稳定化。它不判断研究结论是否正确，不替用户自动改写全文，也不宣称可以发现全部隐含依赖。

为降低用户理解 G3 的门槛，项目可以提供一个受限的 **G3 影响助手**。它负责把结构化变更、依赖图、影响任务和阻断原因翻译成用户能看懂的说明，并提醒用户检查可能遗漏的影响。助手的输出只能是建议和待确认项；版本条件、任务创建、确认失效、稳定化和导出闸门仍由确定性规则负责。

## 2. 范围、边界和术语

### 2.1 G3 负责的对象

| 对象                        | 领域含义                       | 权威写入方             |
| ------------------------- | -------------------------- | ----------------- |
| `ChangeSet`               | 针对已确认项目基线的一组拟议语义变化         | B/PCC             |
| `ContextRevision`         | 已应用的项目语义基线版本               | B/PCC             |
| `DependencyEdge`          | 两个版本化业务对象之间的显式依赖           | 关系所属域，经 PCC 登记    |
| `ImpactTask`              | 对受影响对象的可分派处置要求             | B/PCC 创建，所属域处置    |
| `ValidationIssue`         | G4/C 对当前版本计算出的规则问题         | 规则所属域             |
| `RouteNode` / `RouteEdge` | 技术路线图的版本化节点和关系             | B 保存项目语义，C 负责交付表示 |
| `Stabilization`           | 对目标 revision 是否达到稳定基线的聚合判定 | B/PCC             |

### 2.2 不属于 G3 的判断

- 证据是否支持主张由 G2/A 的证据流程和人工确认决定；
- 章节语言是否流畅、是否有创新由用户和对应规则决定；
- 模板规则的具体表达和求值由 G4/C 决定；
- WeKnora 的解析、检索和 OCR 处理由适配层完成；
- 隐含依赖可以被模型建议，但未被人工或规则确认的建议不能直接成为阻断事实。

### 2.3 实质变更与普通内容编辑

下列变化必须创建 `ChangeSet`：修改研究对象、研究问题、目标、方法、变量、纳入排除条件、正式资料范围、已确认主张、已确认证据关联、模板版本、规则绑定、必需路线图结构，或改变已确认章节结论所依据的项目语义。

只修改未确认章节草稿的措辞、排序、排版或评论，不改变项目语义时，可以创建新的 `ChapterVersion`，不自动创建 `ChangeSet`。无法由声明式规则判断是否改变语义时，进入人工选择：用户可以将其升级为 `ChangeSet`；系统不能默默把它当作普通编辑。

### 2.4 G3 影响助手的职责边界

| 助手可以做什么 | 助手不能做什么 |
|---|---|
| 将用户的自然语言修改整理成 ChangeSet 草稿 | 直接应用 ChangeSet |
| 用当前依赖图解释受影响对象和影响原因 | 凭语义相似度直接标记对象失效 |
| 提示可能漏登记的依赖关系 | 把“可能依赖”写成已确认依赖 |
| 汇总 ImpactTask、责任人和阻断原因 | 自动关闭人工任务 |
| 提醒旧版本结果、待复核证据和未满足规则 | 替用户确认主张、章节或路线图 |
| 建议下一步操作和需要询问的成员 | 绕过 Owner、权限或稳定化闸门 |

助手必须引用它所依据的 ChangeSet、DependencyEdge、RuleSet、ImpactTask 或版本信息。无法指出依据时，只能显示为“待人工确认的可能影响”。

## 3. PCC 总流程和不变量

```text
捕获变化 → 形成 Semantic Delta → 绑定 base_revision
      → 评估依赖和影响 → Owner 决定应用
      → 原子写入新 revision → 生成 ImpactTask
      → 各域处置、重新确认、重算规则
      → 稳定化聚合 → STABILIZED / BLOCKED
```

所有跨域写入必须携带 `project_id`、`change_set_id`、`base_revision`、`target_revision`、`correlation_id` 和 `causation_id`。异步结果还必须携带 `based_on_revision` 与幂等键。

必须保持以下不变量：

1. `base_revision` 不是当前 `current_context_revision` 时，ChangeSet 不能应用；
2. 应用 ChangeSet、创建新 ContextRevision、绑定变更后的正式项目语义和写入审计记录是同一领域事务；
3. 影响解析只沿当前有效的显式依赖边传播；没有依赖边的对象不能被全量标记失效；
4. 旧 revision 的异步结果、任务处置和确认不能覆盖新 revision；
5. 任何未关闭的 `BLOCKING` 任务或当前版本的阻断规则问题，都不能进入 `STABILIZED`、`READY` 或导出；
6. 历史 revision、旧确认和旧交付快照可读但不可被当作当前版本继续写入。

## 4. Context Revision 与 ChangeSet 状态

### 4.1 Context Revision

`Context Revision` 是项目语义基线的单调递增整数。G1 的 `0 → 1` 只表示草稿冻结，不是一次实质变更；从 `1` 开始，每次应用 ChangeSet 只增加 1。资料本身的版本、模板副本版本、章节版本和证据卡版本仍保留各自谱系，不能用 Context Revision 替代。

### 4.2 ChangeSet 状态

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| `DRAFT` | 仍在编辑拟议变化，尚未形成评估结果 | 修改 delta、取消 |
| `ASSESSED` | 已基于指定基线生成影响预览 | 查看预览、申请应用、重新评估 |
| `APPLIED` | 已原子产生目标 revision，等待影响处置 | 处置任务、重新确认、稳定化 |
| `STABILIZED` | 目标 revision 的当前检查全部通过 | 创建冻结交付快照、导出 |
| `REJECTED` | Owner 明确拒绝，正式项目不变 | 只读历史 |
| `STALE` | 基线被其他变更推进，不能再评估或应用 | 复制 delta 到当前基线后重新创建 |

`STALE` 是基线失效标记，不是成功推进状态。`APPROVED` 不是独立状态；批准和应用在同一次条件写入中完成，避免出现“已批准但没有应用”的假象。

### 4.3 ChangeSet 的最小内容

每个 ChangeSet 至少记录：`id`、项目、创建者、变更类型、`base_revision`、结构化 delta、变更理由、目标对象版本、评估结果、决定人、决定时间、目标 revision、状态和审计关联。

delta 必须表达字段级或对象级变化，不能只有一段不可解析的自然语言。用户补充说明可以保留，但不能代替系统识别变化对象。

## 5. ChangeSet 生命周期

### 5.1 创建和评估

有 `changeset.create` 权限的成员可以创建草稿，但创建不等于应用。评估前检查项目为 active、Owner 可用、基线存在、delta 可解析、对象版本仍存在且资料授权范围可读取。

评估输出至少包含：

- 变更前后摘要和目标对象版本；
- 沿依赖图找到的直接和间接受影响对象；
- 每个对象的建议动作、严重级别、理由和所属领域；
- 预计失效的确认、章节、路线图节点、模板检查和交付项；
- 无法确定的关系和需要人工判断的项目；
- 不受影响的代表性对象及其原因；
- 评估使用的依赖图、规则版本和资料范围快照。

评估是预览，不会改变正式项目。依赖图、规则或目标对象版本在应用前发生变化时，评估结果过期，必须重新评估。

### 5.2 应用和拒绝

只有当前 Owner 能应用 ChangeSet；Admin 可以查看、分派和审计，不能替 Owner 做项目语义确认。应用时再次读取当前 revision、Owner 状态、对象版本和权限，不复用旧预览作为最终条件。

应用成功在一次事务中完成：

1. 条件检查 `base_revision == current_context_revision`；
2. 将 ChangeSet 状态写为 `APPLIED`，生成 `target_revision = base_revision + 1`；
3. 写入新的项目语义、模板引用或资料范围版本；
4. 保留旧基线和旧确认，不覆盖历史；
5. 为直接受影响对象创建幂等的 ImpactTask；
6. 写入变更应用事件和审计记录。

任一条件失败，项目仍保持原 revision，不能产生半个新 revision、半组任务或已改模板引用。

拒绝只关闭 ChangeSet，不删除其评估和历史。撤销已经应用的变化不能通过把指针静默改回旧版本完成，必须创建一个新的、以当前 revision 为基线的逆向 ChangeSet。

### 5.3 并发和过期

两个 ChangeSet 可以同时基于同一 revision 创建和评估，但只能有一个先应用成功。后应用者收到 `STALE`，不能自动合并或覆盖前一个变化。用户可以查看 delta 并以当前 revision 复制为新的 ChangeSet。

重复提交同一个幂等键返回第一次应用结果；不同幂等键即使 delta 相同，也必须经过当前基线检查，不能靠内容相等跳过审计。

## 6. DependencyRegistry 与 DependencyEdge

### 6.1 依赖边的语义

依赖边表达“源对象变化可能要求目标对象采取什么动作”，不复制源对象正文。边至少包含：源引用及版本范围、目标引用及版本范围、`relation_type`、建立来源（人工/规则/模型建议）、理由、置信度、创建者、创建时间、有效起止、当前是否被确认。

示例：

```text
ProjectSpec.population@rev3
  ├─depends_on→ ResearchClaim.C3@v2
  ├─depends_on→ Chapter.method@v5
  └─depends_on→ RouteNode.R7@v1

ProjectAsset.A1@v4 → SourceAnchor.S2@v1 → EvidenceCard.E12@v3
EvidenceCard.E12@v3 → ResearchClaim.C3@v2 → Chapter.2@v5 → ReleaseItem.X8@v1
```

### 6.2 边的建立和确认

- 用户在证据卡、主张、章节或路线图中建立关联时，可以直接产生已确认边；
- G2、G4 或模型发现的可能关系先作为 `suggested` 边；
- `suggested` 边可用于影响预览中的“待人工确认”提示，不能单独使目标失效或阻断导出；
- 目标对象删除或版本替换时，旧边关闭并保留历史，不能改写成指向新对象；
- 同一源、目标、关系类型和版本范围的重复边合并为一条逻辑边，但保留多次建立记录。

### 6.3 AI 辅助导入依赖关系

用户不必手工建立全部依赖边。AI 可以读取当前用户有权限访问的项目对象，批量提出依赖候选，例如：

- 研究条件字段与章节、主张、RouteNode 的可能关系；
- EvidenceCard 与 ResearchClaim、章节结论的可能支撑关系；
- RouteNode 的输入、输出和前置关系；
- 模板字段、规则和交付项之间的可能映射。

AI 导入必须经过以下流程：

```text
选择范围 → AI 提出候选边 → 显示依据和置信说明
        → 用户逐条或批量确认/拒绝/修改
        → 写入已确认边或保留为 suggested
```

每条 AI 候选边至少显示：源对象、目标对象、关系类型、对象版本、触发它的文本或字段、建议理由、模型运行标识和生成时间。用户可以修改关系类型、限定版本范围或补充说明。

AI 不得跨越项目权限读取对象，不得只凭名称相似建立正式边，也不得因为候选边数量多就自动扩大影响范围。用户确认后才写入 `confirmed` 依赖；用户拒绝的候选保留拒绝记录，避免同一版本被反复推荐。模型、规则或对象版本发生变化时，旧候选可以重新生成，但不能覆盖已经确认或拒绝的人工决定。

### 6.4 传播规则

ImpactResolver 从 ChangeSet 的变更对象出发，只沿有效边传播，并按关系类型转换为动作：`REVALIDATE_EVIDENCE`、`RETRIEVE_CANDIDATES`、`REVIEW_REQUIRED`、`REGENERATE`、`RECOMPUTE`、`INVALIDATE_CONFIRMATION` 或 `BLOCK_RELEASE`。

同一对象收到多个上游影响时合并任务，但保留所有原因和上游引用。纯排版编辑、未确认候选和没有版本依赖的对象不应被传播影响。

## 7. ImpactTask：生成、分派和关闭

### 7.1 任务模型

ImpactTask 是对某个目标版本的明确处置要求，不是异步计算日志。逻辑身份为：

```text
(change_set_id, target_ref, target_revision, action_type)
```

任务至少包含目标对象和版本、动作、严重级别、来源边、责任域、责任人、状态、处置说明、创建/更新时间和关闭依据。

推荐状态：`OPEN`、`IN_PROGRESS`、`WAITING_USER`、`DONE`、`DISMISSED`、`STALE`、`CANCELLED`。`DONE` 只表示责任人按动作完成了处置，不代表整条变更链已经稳定。

### 7.2 分派规则

| 动作 | 默认责任域 | 典型处置 |
|---|---|---|
| `REVALIDATE_EVIDENCE` | A/G2 | 重查证据、更新卡片或标记不足 |
| `RETRIEVE_CANDIDATES` | A/G2 | 检索候选，交给用户选择 |
| `REVIEW_REQUIRED` | B/项目成员 | 人工查看并重新确认主张或章节 |
| `REGENERATE` | B 或 C | 以目标 revision 的快照生成新候选 |
| `RECOMPUTE` | 所属规则域 | 在当前版本重算派生结果 |
| `INVALIDATE_CONFIRMATION` | B | 使旧确认失效，要求绑定新版本 |
| `BLOCK_RELEASE` | C | 在预检中阻止正式导出 |

系统可以建议责任人，但没有责任人的任务不能因为异步作业成功而自动关闭。跨域任务必须记录交接事件和接收结果。

### 7.3 关闭条件

关闭任务时，责任人必须说明实际动作和依据对象版本。系统重新读取目标对象检查：

- 目标版本仍是任务要求的版本；
- 所需确认、证据、资料授权和规则计算已经更新；
- 若动作是 `REGENERATE`，新候选明确标注生成快照；
- 若动作是 `INVALIDATE_CONFIRMATION`，旧确认保留历史且当前确认已进入待复核；
- 若动作是 `BLOCK_RELEASE`，只能由 C 在当前冻结输入上重新预检后解除。

旧 revision 的任务结果只能写为 `STALE`，不能关闭新 revision 的同类任务。重新投递必须命中同一逻辑身份，不能生成重复副作用。

## 8. A/B/C 事件和陈旧保护

### 8.1 领域职责

| 领域 | 拥有的真相 | 典型事件 |
|---|---|---|
| A Evidence | 资料、SourceAnchor、EvidenceCard、证据状态 | `evidence.revalidation_required`、`evidence.version_changed` |
| B Workspace/PCC | 项目条件、主张、章节确认、ChangeSet、Context Revision、ImpactTask | `changeset.applied`、`context_revision.changed`、`confirmation.invalidated` |
| C Delivery | 模板规则、RouteNode 的交付表示、预检、ReleaseSnapshot、导出 | `delivery.issue_detected`、`release.preflight_blocked` |

事件是通知和交接，不是跨域直接写表的授权。消费方必须根据事件中的项目、目标版本和当前权限重新读取；事件重复或乱序不能造成旧结果覆盖新结果。

### 8.2 异步结果

任何检索、证据重校验、章节生成、路线图重绘或预检任务返回时：

```text
based_on_revision == current_context_revision
且输入资料范围、模板/规则版本仍匹配 → 可进入当前候选或待核状态
否则 → 保存为历史/STALE，不得覆盖当前确认、章节或快照
```

`0 → 1` 仍遵循 G1 的语义例外：草稿候选继续保留，但不会自动成为正式证据。其他 revision 变化没有此例外。

## 9. RouteNode 技术路线图

### 9.1 对象定义

RouteNode 表示研究过程中的一个可检查步骤，例如研究对象定义、数据采集、分析方法、验证或交付成果。它不是流程引擎任务，也不是一段自由文本。

RouteNode 至少有稳定标识、版本、标题、目的、输入、输出、方法/工具、前置节点、关联章节、关联主张或变量、负责人、状态、来源和审计记录。RouteEdge 表达顺序、依赖或支撑关系，并同样随路线图版本保存。

路线图版本必须可编辑、可比较、可恢复。一次节点文字编辑可以形成新 RouteNode 版本；新增、删除、改变前置关系、改变产出或改变与研究条件的关联，通常属于项目语义变化，应通过 ChangeSet 或由当前 ChangeSet 一并应用。

### 9.2 必需性和交付关系

模板规则声明某个 RouteNode 或路线图交付项是否必需：

- 必需节点缺失、待复核、版本落后或没有进入冻结输入，产生 `BLOCKING` ValidationIssue；
- 可选节点缺失按模板规则产生 warning/info，不自动阻止稳定；
- 路线图被修改后，引用旧节点版本的章节、证据或交付项进入影响任务；
- 导出只使用冻结的当前 RouteNode 版本，不能读“当前编辑中”的未冻结图。

G3 不替用户判断路线是否科学可行，只保证路线图结构、版本、依赖和交付关系可追溯。

## 10. 稳定化和 READY 闸门

### 10.1 稳定化聚合器

`StabilizeRevision` 按同一个目标 revision 重新读取全部条件，不相信旧的预览或任务计数。至少检查：

1. 没有未关闭的 `BLOCKING` ImpactTask；
2. 没有当前版本的 OPEN blocking ValidationIssue；
3. 受影响 EvidenceCard、ResearchClaim、Chapter 和 RouteNode 已复核，确认绑定当前版本；
4. 资料授权、ProjectAsset/SourceAnchor 版本仍有效；
5. 重新生成和预检结果的 revision、模板版本、规则版本与当前快照匹配；
6. Owner 或有相应权限的人完成了要求的人工确认；
7. ReleaseSnapshot 使用的所有输入均为冻结版本。

任一条件失败，ChangeSet 保持 `APPLIED`，并记录稳定化结果为 `BLOCKED` 以及具体对象、版本和原因。全部通过后才写入 `STABILIZED`，随后 C 才能把交付状态推进为 `READY`。

### 10.2 与 ValidationIssue 的关系

G4 的 `DISMISSED` 只表示当前规则版本、目标版本下的问题不再作为同一个问题阻断；它不能自动关闭 ImpactTask，也不能替代对象重新确认。规则集、目标 revision 或路线图版本变化后，问题必须重新求值。

## 11. 影响中心最小交互

影响中心至少提供：

- ChangeSet 状态、基线和目标 revision；
- 变更前后摘要；
- 影响树或按领域分组的对象列表；
- 每个 ImpactTask 的动作、严重级别、责任人、版本和关闭理由；
- “为什么受影响”和“为什么未受影响”的来源边；
- 过期任务、失效确认、阻断规则和授权问题；
- 重新评估、重投、复制到当前 revision、查看历史的入口。

### 11.1 G3 影响助手交互

助手作为影响中心中的解释和监控入口，不单独拥有项目写权限。用户提交修改后，助手可以用以下方式工作：

1. **变更摘要**：用一句话说明“你改了什么”；
2. **影响说明**：按“确定受影响 / 可能受影响 / 当前未发现影响”分组，并显示依据；
3. **风险提醒**：指出陈旧结果、未确认依赖、未关闭阻断任务和可能漏登记的关系；
4. **下一步建议**：提示用户先复核证据、确认章节、补充路线节点或联系责任人；
5. **状态播报**：当异步任务返回或稳定化条件变化时，更新待处理事项。

用户可以接受、忽略或改写助手的建议。接受建议只会创建明确的人工操作或待确认依赖，不会直接改变正式项目状态。助手使用的上下文必须限制在当前项目、当前用户有权访问的对象和当前目标 revision 内。

路线图页面至少支持按版本查看节点/边、显示受影响标记、编辑未冻结版本、比较前后版本和跳转对应章节/主张/任务。界面不应把候选、待复核、已确认和稳定混成一个颜色或一个按钮。

## 12. 交付切片

| 切片 | 交付物 | 完成判据 |
|---|---|---|
| G3.1 ChangeSet | 创建、评估、应用、拒绝、过期和 revision 条件写入 | 旧基线不能应用；应用无半完成写入 |
| G3.2 依赖图 | DependencyRegistry、版本化边、AI 候选导入、传播查询和审计 | 每条影响可追溯到来源边；重复边、建议边和人工确认边有明确语义 |
| G3.3 影响解析 | ImpactResolver、预览、动作映射和任务幂等 | 只生成受影响任务；无关对象保持原状态 |
| G3.4 任务协调 | 分派、处置、关闭、STALE 和跨域事件 | 旧任务不能关闭新版本；异步成功不等于人工关闭 |
| G3.5 RouteNode | 节点/边版本、章节/主张关联、必需性 | 路线图可比较、可恢复；必需项缺失可阻断 |
| G3.6 稳定化 | 聚合器、确认复核、冻结输入和 READY 闸门 | 未关闭阻断项不能 STABILIZED 或导出 |
| G3.7 影响中心 | 变更、影响树、任务、路线图最小 UI | 用户能看见影响理由、责任人和下一步动作 |

## 13. 领域验收场景

### AC-G3-01：基线上的研究条件修改

用户将研究对象从“普通本科生”改为“接受过创业教育的本科生”。系统创建 ChangeSet，预览受影响的 EvidenceCard、ResearchClaim、方法章节和 RouteNode；Owner 应用后生成新 revision，旧确认保留历史并进入待复核。

### AC-G3-02：旧基线拒绝应用

CS-01 和 CS-02 都基于 revision 3。CS-01 先应用到 revision 4；CS-02 应用失败并标记 STALE，不产生新 revision、任务或模板写入。

### AC-G3-03：应用原子性

应用过程中任务写入失败或权限失效。项目仍保持原 revision 和旧模板引用，不能出现新 revision 已存在但 ImpactTask 不完整的状态。

### AC-G3-04：局部影响

变更只依赖 Ch2 和 RouteNode.R7。Ch1、无关 EvidenceCard 和无关路线节点不产生失效或复核任务，并能在预览中显示未受影响理由。

### AC-G3-05：多上游任务合并

同一个章节同时受研究条件和证据版本变化影响。系统生成一条逻辑 ImpactTask，保留两个来源和动作原因；重复重投不产生第二条任务。

### AC-G3-06：旧异步结果

revision 4 的章节生成运行期间，ChangeSet 产生 revision 5。revision 4 的结果可以保存为历史候选，但不能覆盖 revision 5 的章节、确认或 ReleaseSnapshot。

### AC-G3-07：证据复核不能自动确认

A 完成证据重检并返回新候选。任务仍需责任人查看和确认；模型或异步作业成功不能直接把 ResearchClaim 标为 confirmed 或关闭人工复核任务。

### AC-G3-08：RouteNode 必需项

模板声明 RouteNode.R7 为必需。R7 缺失、待复核或版本落后时，C 产生 blocking ValidationIssue；即使其他任务已完成，revision 也不能 STABILIZED 或 READY。

### AC-G3-09：规则问题与任务分离

Owner dismiss 当前规则问题后，ValidationIssue 不再阻断该次求值，但对应 ImpactTask 仍为 OPEN，项目不能稳定；新目标 revision 重新求值后问题可以再次出现。

### AC-G3-10：模板升级

active 项目尝试直接改模板字段或章节，普通保存被拒。通过 `template_upgrade` ChangeSet 评估字段迁移、规则、章节、RouteNode、确认和快照影响；应用后旧快照仍绑定旧模板版本。

### AC-G3-11：撤销变化

用户想恢复旧研究对象。系统不把项目指针静默改回 revision 3，而是要求基于当前 revision 创建逆向 ChangeSet，并重新进行影响评估和确认。

### AC-G3-12：稳定化重新读取

所有任务页面显示已完成，但其中一个目标对象后来被新版本替换。稳定化聚合器重新读取后发现版本不匹配，保持 BLOCKED 并创建/重投对应任务。

### AC-G3-13：建议依赖边

模型提出某章节可能依赖某证据，但用户未确认该关系。系统可以在预览中提示“待确认关系”，不能单独使章节失效或阻断导出。

### AC-G3-14：G3 影响助手

用户用自然语言提出修改。助手生成 ChangeSet 草稿，并用“确定受影响”和“可能受影响”两组说明解释原因；用户确认后才进入正式评估。助手不能直接应用变更、关闭任务或放行导出。

### AC-G3-15：AI 批量导入依赖

用户选择“研究条件、证据卡和第 2–4 章”作为范围。AI 提出若干候选依赖，并显示对象版本、依据片段和建议理由；用户确认其中一部分、修改一部分、拒绝一部分。只有确认的关系进入正式依赖图，拒绝记录不会在同一版本中反复推荐。

### AC-G3-16：路线图版本恢复

用户编辑未冻结路线图后取消编辑。系统恢复到上一个 RouteNode/RouteEdge 版本，关联任务和章节引用不指向被取消的临时版本。

## 14. 与其他能力线交接

### 交给 G1

- 当前 active 项目和 `current_context_revision`；
- 基线确认记录、字段版本和 Owner 状态；
- active 后禁止普通 ProjectSpec 保存的边界。

### 交给 G2

- ChangeSet 影响的 ResearchClaim、EvidenceCard、SourceAnchor 和 ProjectAsset 版本；
- `REVALIDATE_EVIDENCE` / `RETRIEVE_CANDIDATES` 任务及其 based_on_revision；
- 证据重检完成后的人工确认入口。

### 交给 G4

- `template_upgrade` 的新旧 TemplateVersion、规则版本和字段迁移结果；
- 当前目标 revision 的规则重算请求和 ValidationIssue；
- RouteNode 必需性和导出前置条件。

### 交给 G5

- 创建、评估、应用、分派、关闭和稳定化各动作的权限要求；
- Owner 失效时冻结 ChangeSet 应用和导出的条件；
- 任务、确认和审计对象的项目范围。

### 交给 G6

- 旧基线、乱序异步、重复投递、局部影响、模板升级、路线图缺失和撤销变化 fixture；
- 影响漏报数、误报数、任务重复率、陈旧结果覆盖率和稳定化阻断原因等指标；
- 从 ChangeSet 应用到 READY 的完整回归路径。

## 15. 不纳入 G3

- 宣称 PCC 能发现所有隐含影响；
- 自动替用户覆盖全文、确认主张或判断创新性；
- 一个可以任意写入 A/B/C 的“超级 Agent”；G3 影响助手只能解释、提醒和提出建议；
- 分布式工作流平台、复杂组织审批流和实时多人编辑；
- 把模型相似度直接当作不可撤销的依赖事实；
- 通过删除绑定、静默改指针或放宽权限来绕过复核和稳定化。

G3 完成的标准不是“变更按钮可以点击”，而是任何正式变化都能被绑定到一个明确基线，沿显式关系生成可解释任务，在当前版本完成责任人处置和重新确认，并由稳定化聚合器证明项目确实可以继续交付。
