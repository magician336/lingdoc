# G3-208.5 裁定依据（供 #210 使用）

本文件把 #209 核实出的四项「单侧存在条件」整理成可执行的事实，供 #210 实施者裁定，**不代替裁定**。

裁定必须由实施者显式写下「并入（带参数）」或「记为有意差异（带理由）」，并在代码注释与代码评审证据中可见。

---

## 1. 模板副本绑定检查

| | 现状 |
|---|---|
| Owner 稳定化 | 产出 `template_unbound` blocker，带可机读 code |
| 只读闸门 | **无同名 blocker**；通过 preflight 基线读取间接以通用 `ErrInvalidState` 失败 |

**语义**：闸门把「模板未绑定」折叠成了通用错误，丢失了可机读分类。
**影响面**：只影响错误可读性，不影响是否阻断——两侧都拒绝。
**可选裁定**：并入并让闸门也产出 `template_unbound`（**会改变闸门的错误标识**）；或记为有意差异。

> 注意：并入会让 `ErrInvalidState` 变成一个带 code 的结果，属于**可观察行为变化**。若选择并入，必须在报告中声明这超出了「纯重构」范围，并说明为何值得。

---

## 2. 规则检查器可用性

| | 现状 |
|---|---|
| Owner 稳定化 | 产出 `rules_checker_unavailable` **blocker**（200 响应的一部分） |
| 只读闸门 | 返回**错误** `ErrImpactObjectUnavailable` |

**语义**：同一情形，两条路径的返回**类型**不同（blocker vs error）。
**影响面**：只读闸门因此以错误而非结构化结果表达「治理能力缺失」。
**可选裁定**：统一为 blocker，或统一为错误，或记为有意差异。

---

## 3. 受影响对象当前确认重读 ← **语义差异最严重**

| | 现状 |
|---|---|
| Owner 稳定化 | 有 `impactConfirmationBlockers`：重读评估中每个受影响对象的当前确认 |
| 只读闸门 | **完全没有该调用** |

**语义**：一个任务被判 STALE 后，其影响对象不再有任何义务覆盖（STALE 非阻断）。Owner 路径靠这个重读补上义务；闸门不重读，于是**受影响章节可能未确认而闸门仍然放行**。

**这不是风格差异，是两条路径对同一状态给出不同答案。**
**可选裁定**：闸门补上同样的重读（**会改变闸门行为，可能导致此前能导出的项目现在被拒**）；或记为有意差异并说明为何闸门可以不查。

> 这一项最需要人工判断。#209 的证据文档第八节记录了该条件的当前守护用例。

---

## 4. 来源授权复检 ← **方向相反，闸门更严**

| | 现状 |
|---|---|
| Owner 稳定化 | **无全量复检**。`checkedImpactWrite` 只对传入的闭环证据 refs 调 `checkSources` |
| 只读闸门 | 对 `basis.SourceIDs` **全量** `checkSources` |

**语义**：来源被全面撤销时，闸门会拒绝，Owner 稳定化却可能通过。
**影响面**：Owner 路径相对宽松。
**可选裁定**：Owner 补上全量复检（**会让稳定化变严**）；或记为有意差异并说明理由。

> 与 #206 的关系：`source_revoked` 触发 STALE 的路径目前是死代码，因为写事务前的来源复检先行失败。本项裁定若选「Owner 补全量复检」，需确认不会与 #206 的后续修复产生冲突——**#206 尚未决策**。

---

## 裁定的硬性约束

1. **不得默认对齐**。四项各有影响面不同的后果，按「两条路径应该等价」的假设合并，会同时造成一处变严、一处变松。
2. **凡选择「并入」并因此改变可观察结果的，必须在报告中显式声明**，不得以「纯重构」名义夹带行为变更。
3. **每项裁定都要落成代码注释**，说明为什么这样处理，防止后来者再次盲目对齐。
4. 无论裁定为何，`#212` 建立的 16 条守护与本轮新增的投影守护都必须仍然变红（说明它们没被绕过），且全套件通过。
