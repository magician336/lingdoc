> **口径版本**：v1.1（2026-10-23 增补，在 v1 上**只加不改**）。**裁决票**：[#439](https://github.com/magician336/lingdoc/issues/439)（wayfinder 地图 [#436](https://github.com/magician336/lingdoc/issues/436) 的决策票）。**本次增补的授权票**：[#523](https://github.com/magician336/lingdoc/issues/523)（人工前置项的承接状态）。

## 0. 为什么要有一份口径

#437 同一张票被两个会话同时处理，两份独立盘点**事实层一致**（19 张票的 US 总数 294、19 行未关闭原生 blocker 逐条相同、4 个合并提交一致、六个面的 Spec 归属一致），**口径层不一致**（一份按 US+IMPL+TEST=600，一份按 US+TD=400）。两份都不是「算错」——是**「验收点」这个单位本身没有被定义**。

没有定义的后果有三个：① 「这张 Spec 还剩 30 点」这句话没有意义（分母不明）；② 下一批面按点数估工会算错；③ 机器没法判，因为机器需要一个可判的谓词。

⇒ 本口径把「验收点」定死为一个**原子可核验要求**，并把判定表、谓词、证据落点、签收规则一次写清。

## 1. 验收点是什么（一行 = 一个原子可核验要求）

### 1.1 定义

> **验收点 = 一个可以被单独核验、并且能单独判 PASS / FAIL / NOT RUN 的要求。**

它不是票面的编号，也不是段落的条目数。`US-xx` / `TD-xx` / `IMPL-xx` 是**定位坐标**，用来指回票面原文；**它们不是计数单位**。

### 1.2 切分规则（可脚本复现）

| 来源段 | 怎么算 | 计入点数 |
| --- | --- | --- |
| `## User Stories` | 每一条 User Story = 1 个验收点 | ✅ |
| `## Testing Decisions` | 每一条 = 1 个验收点 | ✅ |
| `## Testing Decisions` 里的**聚合条目** | 先按**顿号 / 逗号**切分成子项，每个子项 = 1 个验收点 | ✅ |
| `## Implementation Decisions` | 每条是一条**实现决策**（如「五项动作是具体五项」），不是验收条款 | ❌ 只作约束引用 |

**聚合条目的识别**：条目以「必验成功：」「必验失败：」「Must pass:」「Must fail:」开头，后面跟一个顿号分隔的清单。

**切分时「和 / 或 / 及 / 斜杠」连接的成分不拆**：它们是**同一个要求的不同面**。

- ✅ 拆：`创建档案、保存草稿、发布` ⇒ 3 个验收点
- ❌ 不拆：`历史读取、召回记录和旧副本隔离` ⇒ **1** 个验收点（「和」连接的三面）
- ❌ 不拆：`激活和章节骨架` ⇒ **1** 个验收点

拆开会产出**看似更多、实则不可分别核验**的假原子（「激活」和「章节骨架」不是两个能各自判 PASS 的要求）。

### 1.3 两代票的粒度差

19 张票分两代，两代的 `Testing Decisions` 写法不同：

| 代 | 票 | 写法 | 按条计的后果 |
| --- | --- | --- | --- |
| 一 | #123 #124 #125 #126 #127 #128 #129 #130 #133（9 张） | 每条 = 一个单独可核验的要求 | 不低估 |
| 二 | #135 #136 #137 #138 #139 #141 #142 #143 #145 #146（10 张） | 含「必验成功 / 必验失败」聚合条目 | **按条计会低估这 10 张** |

⇒ 本口径用 §1.2 的规则把两代统一到同一粒度。

### 1.4 实测总数（2026-10-23）

按本口径对 19 张票正文实测：

| 口径 | 总数 |
| --- | --- |
| US 逐条 | **294** |
| TD 逐条（不展开聚合条目） | 106 |
| TD 按 §1.2 展开后的原子数 | **222** |

## 2. 交付分类：「未交付」与「未记录验收」是两件事

判定表用**独立的一列**表达交付分类，不与判定状态混在一起：

| 分类 | 含义 | 清零条件 |
| --- | --- | --- |
| **已交付** | 有交付记录（PR 合并提交 / 执行票关闭记录 / 验收报告）**且**能指到具体验收点 | — |
| **证据缺失** | 相关能力**已在 `main` 上**（文件级可查），但**没有任何针对该 Spec 的验收记录** | **该 Spec 的判定表里，每一条验收点都齐备了 §4.2 的三件套** ⇒ **不需要补实现** |
| **未交付** | 明确没做（所属面未认领/未开工，或有残留票明写） | 完成实现 + 齐备三件套 |

**为什么必须分**：仓里至少 8 张 Spec 的主体能力其实已经在 `main` 上（#123 #129 #133 #136 #137 #139 #141 #142 #143 的静态存在性判定），只是没有任何针对该 Spec 的验收记录。若把两者混进一个「剩余 N 点」，下一批面会**重复建设已有能力**。⇒ 分了之后，下一批面的工作是**补证据**还是**重建**，一眼可见。

> 「已在 main 上」只由**文件级可查**支撑（路径 + 行号），**不等于验收通过**。

## 3. 判定表的形状

### 3.1 六列

| 列 | 填什么 | 规则 |
| --- | --- | --- |
| **定位坐标** | `US-06` / `TD-03` / `IMPL-02` | 必须能指回票面原文的**段与条**；IMPL 只作约束引用，**不计入点数** |
| **验收点原文** | 逐字引自票面 | **不转述** —— 转述会把「要求」悄悄改写成「好做的事」 |
| **判定状态** | `PASS` / `FAIL` / `NOT RUN` / `DEFERRED_MANUAL` | **四值**。不设「部分通过」：部分通过就是 `FAIL`，差在哪写进备注。`DEFERRED_MANUAL` 是**未完成的承接项**（§5.3），不是第四种「通过」 |
| **交付分类** | 已交付 / 证据缺失 / 未交付 | 见 §2 |
| **证据** | 用例名 + 可复现命令 + 落证 head | 三件套，见 §4.2 |
| **备注** | 判定边界、残留、解除条件 | 见 §5 |

**状态与分类是两个维度**：状态说「机器判成什么样」，分类说「这件事欠的是什么」。一张表就能同时回答「哪些过了」与「下一批面要干多少」。

### 3.2 模板

```markdown
| 定位坐标 | 验收点原文 | 判定状态 | 交付分类 | 证据 | 备注 |
| --- | --- | --- | --- | --- | --- |
| US-06 | 「As a 项目成员, I want the project to remain usable for ordinary collaboration when the Owner's tenant identity is unavailable, so that work does not stop unnecessarily.」 | PASS | 已交付 | `TestOwnerUnavailableDoesNotFreezeOrdinaryCollaboration`；`go test ./internal/router/ -run TestOwnerUnavailableDoesNotFreezeOrdinaryCollaboration`；head `2b1b098c` | — |
| TD-03 | 「Test owner tenant suspension and restoration, including ordinary collaboration during owner_unavailable and frozen Owner-only actions.」 | PASS | 已交付 | 同上三件套 | — |
| US-12 | 「…tenant restoration to clear `owner_unavailable`…」 | NOT RUN | 证据缺失 | — | 解除条件：PR #360 合入后 PG 侧迁移演练可跑（见 §5.2） |
| US-13 | 「…the real browser chain over the template catalogue…」 | DEFERRED_MANUAL | 已交付 | 代码侧证据：`go test -count=1 ./internal/lingdoc/templategovernance/ -run TestTemplateCatalog…`；落证 head `1f195def` | 解除条件：按 #523 的验收步骤在真实浏览器跑完该链，并把证据绑到当前 head（跟进票 #523） |
```

`DEFERRED_MANUAL` 那一行的两个必带件（**解除条件** ＋ **跟进票号**）必须写在**同一格**里——这是守护测试能机械判定的那一格（§5.3、§10）。

### 3.3 填写规则

1. 一行 = 一个验收点（§1），**不合并、不省略**。
2. 验收点原文**逐字引**；要转述就另起一行并在备注里说明。
3. `PASS` 只在 §4.2 的三件套**全部齐备且命令在当前 head 跑通**时才能写。
4. `NOT RUN` 必须在同目录 `T*-验证报告.json` 的 `not_run[]` 里有对应条目（§5）。
5. 判定状态与交付分类**分别填**；`PASS` 也可以是「交付分类=证据缺失」（能力在、证据刚补齐）。
6. `DEFERRED_MANUAL` 只在 §5.3 的两个必带件（**解除条件** ＋ **跟进票号 `#NNN`**）**同时**写在该行时才能写；缺任一项 ⇒ 守护测试判失败（该行无效）。

## 4. 判定：纯机器

### 4.1 谁判

**判定结果由机器给出，脚本全权。**

- 机器判：证据是否齐备、是否绑当前 head、命令是否真跑绿。
- **机器不判**：这条验收点的**语义**是否真被那个测试覆盖。**纯机器方案下，语义覆盖只能靠「用例名与验收点文本的对应关系」来近似，不能被证明。**
- 判定结果**不可由人改写**。

### 4.2 PASS 的谓词（三件套）

一条验收点判 `PASS` ⇔ **三件套齐备**：

1. **一个具名的可 grep 用例名** —— Go 侧是 `TestXxx`（`go test -run <名>`）；前端侧是测试标题。
2. **一条可复现命令** —— 完整到别人复制粘贴能跑。
3. **绑当前 head** —— 证据的落证 head 与判定所依据的 head 一致。

**且**：该命令在**当前 head** 上**跑通**。

> 机器可复用的既有件：`go test -run`（可 grep 用例名）、`scripts/ci/check_lingdoc_routes.py`（路由双向核对）、`contracts/validate_artifacts.py`（契约校验）、`scripts/lingdoc_parallel_surfaces.py`（登记处自检）、命名登记表（`scripts/lingdoc_naming_registry.py` + `scripts/ci/test_lingdoc_naming_registry.py`）。
> 判定器的退出码必须分三态：**通过 / 发现问题 / 未比对**（拿不到基线时退出码 2 且输出「未比对」）。**「拿不到基线」绝不能被当成「没问题」。**

### 4.3 失败条件

| 情形 | 判 |
| --- | --- |
| 三件套缺任一件 | `FAIL` |
| 命令在当前 head 上跑红 | `FAIL` |
| 证据 head ≠ 判定 head | `FAIL`（硬要求第 2 条：数字不得沿用旧 head） |
| **静默 SKIP**（作业被跳过、命令实际没跑） | **`FAIL`**，不判 `NOT RUN` |
| 显式登记在 `not_run[]` 的未运行 | `NOT RUN` |
| **PG 相关验收点，且 #360 的修法尚未落地** | **`NOT RUN`，不得 `PASS`** |
| **人工前置项未完成**，但代码侧条件已满足，且已有跟进票与解除条件 | `DEFERRED_MANUAL`（**不是 `PASS`**；见 §5.3） |

**「静默 SKIP 一律 FAIL」的理由**：只有**显式登记**的未运行才允许记 `NOT RUN`。按路径缩面而 skip 的作业**也算 SKIP**，必须登记并写解除条件 —— 否则「其实没跑」会被看成「跑过了」。

**PG 特例的理由**：现在 PG 侧**根本没有能跑那几条用例的位置**（`app.yml` 跑 `internal/database` 但没有 PG service；带 PG service 的 `lingdoc-interface-integration.yml` 又不跑 `internal/database`）。机器若只看到「用例存在」就判 PASS，等于**把没验当已验**。⇒ 在 #360 的修法落地前，那几条一律 `NOT RUN`。

**人工前置项的理由**：真人浏览器完整链、外部真实 KB 检索、多账号人工操作、负责人最终审批**不是机器能判的**。机器若把它们记 `PASS`，等于**把没验当已验**；若一律记 `NOT RUN`（无票、无解除条件），又会把「有人承接着」和「没人管」混成一团。⇒ 单独一个状态（§5.3）。

## 5. NOT RUN 与解除条件

### 5.1 登记在哪

**`NOT RUN` 与「按路径缩面而 skip 的作业」统一登记在同一份 `T*-验证报告.json` 的 `not_run[]`**，不另出清单。

```json
"not_run": [
  {
    "id": "AC-49-09 PG 侧迁移可升可降",
    "status": "not_run",
    "reason": "CI 里没有能跑 PG 迁移演练的位置：app.yml 无 PG service，lingdoc-interface-integration.yml 不跑 internal/database（票 #360）",
    "unblock": "PR #360 合入后，go test ./internal/database/... 在带 postgres:17 service 的 job 里执行"
  }
]
```

### 5.2 解除条件必须机器可读

每条 `not_run[]` 必带两个字段：

- **`reason`**：为什么没跑。
- **`unblock`**：变成可跑需要什么，**写成机器可读的一行** —— 「PR #360 合入」「作业 X 出现在带 PG service 的 job 里」「用例名 Y 存在于 head Z」。

判定器据此能判「这条是否已解除」；**解除条件被满足时，该条自动退出 `NOT RUN`**（不是靠人记得改）。

> 既有体例已经有这个形状：`T327-验证报告.json` 与 `T49-验证报告.json` 的 `not_run[]` 每条都写了「为什么没跑 + 为什么跑不了」；本口径只是把**按路径 skip 的作业**也纳入，并要求 `unblock` 机器可读。

### 5.3 `DEFERRED_MANUAL`：人工前置项的承接状态

**一句话**：**人工前置事项尚未完成，但代码侧条件已满足，且已有独立跟进票与写明的解除条件。**

典型场景：真人浏览器完整链、外部真实 KB 检索、多账号人工操作、负责人最终审批。

#### 与相邻状态的区别（**不许混**）

| 判定状态词 | 人工验收做没做 | 有没有承接它的载体 | 阻塞代码合并 | 阻塞 Beta 放行 |
| --- | --- | --- | --- | --- |
| `PASS` | 做了，且证据齐备 | — | 否 | 否 |
| `NOT RUN` | 没做 | **没有**（没有票、没有解除条件载体） | **是** | **是** |
| `DEFERRED_MANUAL` | **没做** | **有**：解除条件 ＋ 跟进票号 | **否** | **是** |
| `BLOCKED` | 没做，且现在做不了 | — | **是** | **是** |

⇒ `DEFERRED_MANUAL` **不是** `PASS`（人工验收确实没做），也**不是** `NOT RUN` 的同义词；它比 `NOT RUN` 多的是「**有人接住了它**」。

#### 两个必带件（**缺一即无效**）

1. **解除条件**：写成机器可读的一行——「按 #523 的验收步骤在真实浏览器跑完该链并把证据绑到当前 head」。
2. **跟进票号**（`#NNN`）：独立跟进票；票号与解除条件写在**同一格**（矩阵行）或**同一对象**（JSON 条目）里。

**缺任一项 ⇒ 守护测试判失败。** 这是防止有人拿新状态把未完成项洗成「看起来通过」的关键：新状态是**唯一**一个能让未完成项不阻塞合并的状态，因此它的门槛必须由机器守住，而不是靠人自觉。

#### 门禁效果（**两层，不许只看一层**）

- **代码合并层**：`DEFERRED_MANUAL` **不阻塞**独立开发与满足其他条件的代码合并（门禁定义 §2）。
- **Beta 放行层**：`DEFERRED_MANUAL` **阻塞** Beta 首版放行（验收协议 §6，与 `FAIL` / `BLOCKED` / `NOT RUN` 同列）。⇒ **代码合并不等于 Beta 验收通过**；完整 Beta 验收的放行判定仍依据正式验收标准。

#### 机器可校验的落点

- **词表与两个门禁谓词**：`scripts/lingdoc_acceptance_status.py`（`DEFERRED_MANUAL`、`MERGE_BLOCKING`、`BETA_RELEASE_BLOCKING`、`deferred_manual_problems`）。
- **守护测试**：`scripts/ci/test_lingdoc_acceptance_status.py` —— 扫仓内全部 `docs/**/*.md` 与 `docs/**/*.json` 的 `DEFERRED_MANUAL` 条目，逐条核对两个必带件；并**故意注入**缺解除条件、缺票号的条目，确认守护会红。
- **四个定义点必须一致**：验收协议、判定口径（本文件）、门禁定义、进度源 `docs/BETA_STATUS.md` —— 守护测试逐一核对它们与词表模块说的是同一批词。

## 6. 产物与权威

### 6.1 落点

| 产物 | 位置 | 内容 |
| --- | --- | --- |
| **判定矩阵** | `docs/08-本轮实施方案/`，**一 Spec 一份** | §3 的六列表，按 §1 逐条填 |
| **证据 JSON** | **同一目录**的 `T*-验证报告.json` | 沿用既有体例：`mode / note / head / base / head_note / base_note / passed[](id,status,evidence) / not_run[] / known_limits[]` |
| **横向汇总** | **由脚本从各 Spec 的 JSON 生成** | 哪些 Spec 还剩多少、哪些在 PG 条件下 |
| **票面** | tracker | **只放结论与指针** |

### 6.2 为什么不是一张总表

19 张票 × 数百行 = 单文件巨物，且**并行面各自改它必然冲突**（本仓已因「同一事实的多份副本互相矛盾」吃过亏：登记处、路径图、开发计划页首三处都写过同一个状态）。⇒ **一 Spec 一份**，各改各的；需要横向比较时**由脚本汇总**，不手写第二份。

### 6.3 冲突时以谁为准

> **JSON 证据 > 判定矩阵文档 > 票面**

理由：JSON 是机器可读的那一份，矩阵是人读的那一份，票面是摘要。摘要与明细冲突时以明细为准，明细与机器产物冲突时以机器产物为准。

### 6.4 与既有体例的对照

| 既有件 | 与本口径的关系 |
| --- | --- |
| `T*-验证报告.json`（T327 / T49） | **沿用其形状**，本口径只加严：`not_run[]` 必带 `unblock`；`passed[]` 的 `evidence` 必须含三件套 |
| `contracts/validation-result.json` | 静态契约校验的产物，**是机器可复用的判定件之一**（§4.2），不与判定表并列 |
| `scripts/lingdoc_parallel_surfaces.py` + `lingdoc_manifest_baseline.py` + `lingdoc_ticket_ownership.py` + `test_lingdoc_parallel_consistency.py` | **本口径 §6 的先例**：一份权威 + 说明副本 + 两个方向的一致性检测器 + 钉住失败方向的守护测试。判定表也应照此配检测器 |
| `AGENTS.md`「Development gates」 | 已有「每条矩阵行必须有当前 head 的证据」「区分 PASS / NOT RUN / 环境限制」——本口径把它**具体化为可执行的谓词** |

## 7. 签收：机器判定不可改写，关票即完成

- **判定结果由机器给出，不可由人改写。**
- **机器不能关票** —— 既有体例是「PR 合入 → 人关票」。所以「判定通过」与「票被关闭」是两个动作：前者是机器的，后者是流程动作。
- **关票不需要任何人工确认。** 流程动作 = 把票关掉；不做语义复核、不做独立审批、不写残留接受声明。

### 7.1 与 PR #336 既有处置的差异（显式声明）

PR #336 的既有处置是：「**AI 评审在作者账号下不算独立审批**」，由真人评审并**显式接受残留风险**。

**本口径不沿用那一条边界。** 理由：

1. 本口径**不设人工审批层** —— 判定是纯机器的，没有「审批」这个环节可供 AI 参与或被排除。
2. 签收环节是**流程动作**（关票），不是判定。
3. 既然没有人工确认，**残留风险不在签收环节声明，而在 `known_limits[]` 里**（§5 与本节第 4 点）——由口径本身保证「没验的不会被记成验过的」。

**代价（明写）**：语义覆盖**无人背书**。机器只能证明「有对应且跑得通的测试」，不能证明「该测试真的覆盖了这条验收点」。本口径接受这个代价，用**机器谓词的严格性**（三件套 + 跑通 + 绑 head + SKIP 即 FAIL）来补偿。

**若将来要恢复人工签收**：改本口径的版本号（v2），并同步 §7 与 §3.3 的填写规则；**不得**在不改版本号的情况下临时加人工环节。

## 8. 引用纪律

**任何盘点表、判定表、汇总数字在被引用时，必须同时写清三件事**：

1. **口径版本**（本文件 v1.1）+ **本口径的 commit** —— 查法：`git log --diff-filter=A --format=%H -- docs/08-本轮实施方案/验收判定口径.md`（引用方也可以直接写本文件所在分支的 head）。**v1.1 是加法**：按 v1 作出的判定结论**继续有效**，已写的「v1」行**不必**改写；新写的表引 v1.1。
2. **指向哪一份**（哪个文件、哪个分支、哪个 commit）—— 盘点表尤其要说清是**哪一份盘点**，因为 #437 存在两份事实层一致、口径层不同的盘点。
3. **数字的口径**（是「原子验收点」还是「US 条数」）—— 同一件事在不同口径下数字不同（516 / 400 / 294），**不带口径的数字是错的**。

**每张 Spec 的判定矩阵文档头部必须写一行**：

> 本表按《验收判定口径》v1 判定；口径 commit = `<sha>`；本表验收点总数 = N（原子验收点口径）。

**盘点表不是定论**：#437 的两份盘点都是**底稿**，不是判定结果。引用它们时必须写「这是盘点，不是判定」。

## 9. 四条硬要求 → 规则的落法

| 硬要求 | 落在哪 | 机器怎么判 |
| --- | --- | --- |
| 1. 每条验收点有可 grep 的用例名 + 可复现命令 + 落证 head | §4.2 三件套 | 三件套缺一 ⇒ `FAIL` |
| 2. 证据绑当前 head，数字不得沿用旧 head | §4.2 第 3 项 + §4.3 | 证据 head ≠ 判定 head ⇒ `FAIL` |
| 3. 不得有静默 SKIP；PG 迁移演练必须在带 PG service 的 job 里真跑 | §4.3 静默 SKIP ⇒ `FAIL`；§4.3 PG 特例 | PG 验收点在 #360 落地前 ⇒ `NOT RUN` |
| 4. NOT RUN 与按路径缩面而 skip 的作业显式登记 + 写解除条件 | §5 | 判定器读 `not_run[]`；缺登记的 SKIP ⇒ `FAIL` |
| 5. 人工前置项未完成时不得记 `PASS`；承接它的条目必须带解除条件与跟进票号 | §5.3 + §4.3 | `DEFERRED_MANUAL` 缺解除条件或缺 `#NNN` ⇒ **守护测试判失败**；`DEFERRED_MANUAL` 阻塞 Beta 放行（验收协议 §6），不阻塞代码合并（门禁定义 §2） |

## 10. 判定器应长什么样

本口径只定规则，**判定器本身是施工**（另走票）。但规则已经把它逼到一个形状，记账在此免得下张票重推：

- **输入**：一张判定矩阵（§3）+ 该 Spec 的 `T*-验证报告.json`。
- **逐条判**：三件套齐备？（§4.2）→ 命令在当前 head 跑通？（§4.2）→ head 一致？（§4.3）→ 是不是 SKIP？（§4.3）⇒ `PASS` / `FAIL` / `NOT RUN` / `DEFERRED_MANUAL`（§5.3）。
- **三态退出码**：通过 / 发现问题 / **未比对**（拿不到基线时退出码 2 且输出「未比对」）。
- **必须有守护测试钉住失败方向**：像 `test_lingdoc_parallel_consistency.py` 那样，**故意注入违规、确认守护变红**。守护全绿只证明机制自洽，不证明它抓得住真问题。
- **横向汇总**：从各 Spec 的 JSON 生成，不手写。
- **v1.1 已经落地的最小件**（不是完整判定器）：词表与两个门禁谓词在 `scripts/lingdoc_acceptance_status.py`，守护在 `scripts/ci/test_lingdoc_acceptance_status.py`。**完整判定器仍是另走票的施工**（§11）。

## 11. 本口径不回答什么 / 下一步

- **不回答**：19 张 Spec 的判定表逐张填满（那是本口径的施工）。**下一张票**应包含：为 19 张 Spec 各建一份判定矩阵 + 各配一份 `T*-验证报告.json` + 判定器 + 守护测试。
- **不回答**：某一张 Spec 的具体验收点该绑哪个用例（那是填表时逐条落证的事）。
- **会过期**：本口径依赖票面正文的形状（`## User Stories` / `## Testing Decisions` / `## Implementation Decisions` 三段）。若将来 Spec 票改用 `AC-xx` 清单，§1.2 的切分规则要跟着改 —— **改的时候升版本号**。
- **已知的上游过期**：仓内路径图自述它的依赖快照已过期（票 #413），因此本口径 §2 里「主体能力已在 main」的判断要随 `main` 变化重核，不能一次写死。
