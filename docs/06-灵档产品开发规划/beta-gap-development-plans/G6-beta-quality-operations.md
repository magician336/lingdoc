# G6. Beta 质量、运行与效果评估

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)  
> 相关能力线：G1–G5  
> 前置假设：T01–T16 已完成并通过各自验收。本文件是后续开发计划，不表示功能当前已实现。

## 1. 目标和基本判断

G6 把“流程可以演示”升级为“Beta 可被验证、观测、灰度、回退和评估”。一次成功演示不能证明产品稳定；每个关键用户结果都必须有可复现 fixture、真实依赖状态、关联运行证据和失败后的恢复路径。

G6 要回答：

1. G1–G5 的不变量是否在单域和端到端流程中成立？
2. 当前结果来自 mock、真实 API 假模型，还是完整真实依赖？
3. 请求、异步任务、ImpactTask、Preflight 和导出文件能否串联追踪？
4. 新模板、规则、迁移或接口出问题时能否暂停并回退？
5. 人工投入、证据支撑率、漏改、误报和导出损失是否允许扩大范围？
6. 失败来自领域逻辑、权限、模型、WeKnora、文件格式还是运行环境？

结论必须区分 PASS、FAIL、NOT RUN、BLOCKED。没有真实依赖、样本不足或证据缺失时，不能用“暂未发现问题”代替通过。

## 2. 范围和边界

### 2.1 本轮交付

- 六条能力线的验收矩阵、脱敏 fixture 和版本化测试数据；
- 单元、契约、集成、E2E、安全、回归和真实依赖验证分层；
- mock、real_api_fake_model、real 三种运行模式；
- 请求/任务关联 ID、结构化日志、指标、告警和运行查询；
- 数据迁移兼容、feature flag、灰度、暂停和回退；
- 真实模型、资料、DOCX/WPS、WeKnora 权限和下载环境验证；
- Beta 用户试用协议、指标采集、失败复盘和下一阶段决策；
- 运行手册、故障分级、回退演练和证据归档。

### 2.2 不负责

G6 不重新定义 G1–G5 的领域对象、权限或规则语义；不以生成字数、中标概率或一次成功演示作为质量指标；不把未经脱敏的研究数据放入测试；不把 mock 通过写成真实能力通过；不在 Beta 主路径引入 P5 的临时授权、服务账号、水印或组织审批流。

## 3. 质量证据模型

每项验证必须绑定：

- fixture_id、脱敏 project_id；
- template_version、ruleset_hash、context_revision、target_version；
- permission_snapshot、runtime_mode；
- model/provider version、WeKnora/config version；
- input_hash、output_hash、开始/结束时间；
- result、evidence_refs、owner、reviewer。

mock 只证明领域契约和失败语义；real_api_fake_model 证明真实服务、权限和文件接口可接入；real 才能进入产品效果汇总。

每个失败标记主要归因：domain_logic、permission、external_service、model_quality、file_fidelity、runtime 或 fixture_or_test，并指定责任人和下一步。

## 4. 验收基线和 Fixture

### 4.1 Fixture 分类

| 类别 | 代表内容 |
|---|---|
| project_lifecycle | 创建、草稿、模板副本、立项、丢弃、恢复 |
| evidence | PDF/书籍、OCR、多个 SourceAnchor、证据候选、矛盾证据 |
| pcc | ProjectSpec 变化、依赖边、局部影响、陈旧异步、稳定化 |
| template_rule | 字段/章节编辑、声明式规则、误报处置、Preflight |
| permission | 跨租户、跨项目、scope、撤权、Owner 停用、并发转让 |
| delivery | ReleaseSnapshot、DOCX、路线图、表格、分页、下载 |
| failure | 超时、重复投递、上游部分返回、权限变化、数据库回滚 |

每个 fixture 必须有脱敏输入、预期状态转移、允许/禁止副作用、关键审计事件和可复现步骤。涉及版本的 fixture 绑定模板、规则、Context Revision、对象版本和权限快照。Fixture 修改必须版本化，并说明是产品变化、规则变化、外部接口变化还是测试修正。

### 4.2 主路径和反向路径

主路径为：

创建项目 → 复制并编辑模板副本 → 草稿协作 → 导入资料/建立证据候选 → 立项确认 → 写作与 Template Check → 修改研究条件 → G3 ChangeSet/ImpactTask → 复核并稳定化 → Preflight → DOCX 导出 → 当前权限下载。

必须覆盖证据来源失效、多个 SourceAnchor、矛盾证据、模板升级、Owner 停用、撤权下载、异步乱序、旧快照回放和导出格式损失。

## 5. 测试分层

### 5.1 单元和契约

单元测试验证状态机、规则求值、scope 交集、权限矩阵、哈希、幂等、版本比较、Issue 去重和回退判定。契约测试验证 G1–G5 的输入/输出、事件字段、错误码、幂等响应、版本和关联 ID。契约通过不代表真实服务通过。

### 5.2 集成和 E2E

集成测试使用可控数据库、队列、WeKnora fake、模型 fake 和文件服务，验证跨域读写、乱序、重复投递、回滚、重新鉴权和审计完整性；必须断言失败时没有半套正式写入。

E2E 在干净租户和真实界面路径完成创建到导出，验证加载、空状态、错误、冲突、拒绝、恢复和历史回放；保存脱敏截图/响应摘要、fixture、运行模式和环境版本。

### 5.3 安全和回归

覆盖跨租户 ID 替换、跨项目访问、未指派 scope、撤权缓存、预签名 URL、下载重放、API Key scope、共享 Agent、异步权限变化和审计查询越权。存在性泄露、正文泄露或旧文件绕过授权均为阻断缺陷。

每次模板/规则、权限、依赖图、导出器或 WeKnora adapter 变化，重新运行受影响 fixture；回归结果按版本和模式保存。

## 6. 真实依赖验证

| 模式 | 证明什么 | 是否进入效果汇总 |
|---|---|---|
| mock | 领域状态、契约、失败语义 | 否 |
| real_api_fake_model | 真实 API、权限、文件和队列接入 | 否，仅集成证据 |
| real | 真实模型、资料、WeKnora、DOCX/WPS、权限环境 | 是，前提是样本合格 |

WeKnora 至少验证租户切换、知识库 share、KB viewer 与项目成员分离、ResolveKB/KBAccess、API Key scope、Agent 只读、上游部分返回、撤权后重新读取和资料解析/重解析。权限不确定时结果为 BLOCKED。

模型验证记录模型、提示词/结构化输出版本、输入范围、耗时、失败率和人工裁定，覆盖 G1 草稿候选、G2 证据候选、G3 影响/依赖候选、G4 规则解释。模型不能绕过人工确认和确定性闸门。

真实 DOCX 必须在 Word 或 WPS 中打开、编辑、保存并重开，检查章节、标题、表格、图形、路线图可编辑性、来源展示、分页、字体替换、空内容和损坏文件。无法支持的内容必须明确报告，不得静默省略。

## 7. 观测、日志和关联

每个请求和异步结果携带 tenant_id（脱敏）、project_id、context_revision、target_revision、template_version、ruleset_hash、correlation_id、causation_id、request_id、task_id、changeset_id、release_snapshot_id 和 runtime_mode。

关联链应能追踪：

用户操作 → 领域写入 → 事件 → 异步任务 → ImpactTask/ValidationIssue → Stabilize/Preflight → ReleaseSnapshot → ExportArtifact/下载审计。

日志记录状态、版本、耗时、错误码、资源类别和脱敏 ID；不记录研究正文、SourceAnchor 原文、API Key、访问令牌和不必要的模型输入。

最小运行指标包括请求成功/拒绝/冲突率、P95/P99 延迟、异步排队/失败/重试/陈旧/重复副作用率、ChangeSet/ImpactTask/稳定化结果、Template Check/Preflight 问题与处置、G5 allow/deny、撤权拦截、下载再鉴权、DOCX 损失和外部依赖可用性。告警必须绑定暂停、重试、回退、阻止导出或通知责任人的行动。

## 8. 故障分级与运行手册

| 等级 | 示例 | 处置 |
|---|---|---|
| P0 | 跨项目/跨租户泄露、撤权后下载、历史文件覆盖 | 立即停止相关流量/导出，保护证据并回退 |
| P1 | 错误正式状态、Preflight 放行不完整快照、数据半写入 | 暂停能力线，隔离影响项目，恢复上一验证版本 |
| P2 | 模型建议下降、DOCX 局部损失、可修复的任务重复 | 限制灰度，建立人工补救和修复任务 |
| P3 | 文案、统计延迟或非关键 UI 问题 | 记录并正常迭代 |

每个可灰度能力必须有健康检查、依赖检查、版本/flag 查看、暂停、回退、数据影响判断、重试规则、责任人、沟通模板和恢复后验证步骤。不能通过直接改数据库指针绕过领域入口。

## 9. 灰度、迁移和回退

建议顺序：内部 fixture/mock → 真实 API + fake model → 脱敏 real 试点 → 少量真实团队 → 满足退出条件后扩大。灰度按租户、项目、模板版本、规则版本和运行模式记录。

回退只停止新版本写入或切回已验证配置，不修改已发布模板、已冻结快照、历史文件和已确认审计。旧 hash 必须可读；代码回退不能让新数据不可读；数据库迁移必须有向后兼容窗口。已应用 ChangeSet 的恢复必须创建逆向 ChangeSet，不能静默改回 revision 指针。

进入真实试用前，至少演练新模板规则暂停、模型不可用、WeKnora 授权变化、队列乱序、DOCX 失败、Owner 停用和权限回退，并记录耗时、影响和未覆盖风险。

## 10. 数据迁移兼容

迁移必须说明旧版本读取、新版本写入、回退窗口和失败清理。新增字段默认值不能伪造“已确认”；缺少版本、权限或溯源的旧对象进入待迁移或 UNKNOWN。跨域事件新增字段时旧消费者应可忽略，删除字段前先完成兼容窗口。

模板、规则、ProjectAsset、EvidenceCard、DependencyEdge、ImpactTask、ProjectMember 和 ExportArtifact 的历史版本都要按当前权限读取；迁移不得让撤权对象重新可见。

## 11. Beta 用户试用

试用前锁定窗口起止、纳入项目/用户、目标样本量、最低可报告样本量、模板/规则版本、运行模式、人工支持、脱敏方式和退出条件。用户应知道哪些输出是 AI 候选、哪些结果需要确认，不能将问题提示宣传成官方合规结论。

流程为：招募与授权 → 建立脱敏项目 → 完成一次创建到导出 → 记录人工投入和失败点 → 复盘未确认项/误报/漏改 → 修复或回退 → 再跑关键场景 → 做扩大或暂停决策。不能只记录最终成功结果。

### 11.1 指标字典

指标以一次有记录的试用窗口为单位。产品与 QA 共同锁定窗口、样本量和最低可报告样本量；不足时只报告个案和原始计数，不做总体率或扩大结论。每个样本绑定脱敏 project_id、模板/规则版本和运行模式，仅 real 样本进入效果汇总。

| 指标 | 分子/计数 | 分母/观察单位 | 采集与判定 | 责任人 |
|---|---|---|---|---|
| 人工投入时间 | 建项、核证、改稿、处置、导出的主动时长总和 | 每份完成交付项目 | 活动时间戳 + 抽样核对，排除空闲/模型等待 | 产品 |
| 来源支撑率 | 人工确认有充分证据的关键 ResearchClaim 数 | 窗口内全部关键 ResearchClaim 数 | 证据确认/不足处置；仅引用不算支持 | 产品 + QA |
| 漏改数 | 复盘确认受影响却未进入 ImpactTask 的对象数 | 每个 ChangeSet，并报告复盘对象数 | 盲审影响清单与依赖图对照 | QA |
| 规则/模型误报率 | 被裁定 DISMISSED 的问题数 | 实际展示并复核的问题数 | ValidationIssue 创建、展示、裁定 | QA |
| 未确认项数 | 快照仍未关闭的待核项数 | 每份准备交付的 ReleaseSnapshot | Preflight 冻结清单 | 产品 |
| 导出损失数 | 数字、表格、路线图、引用、分页、可编辑性不一致项数 | 每份 DOCX 及检查项数 | 文件校验 + 第二人 Word/WPS 记录 | QA |

所有指标先报告分子、分母、缺失数据和模板/规则版本，再计算比例。原始正文不写入日志，审计只存脱敏 ID、分类和判定依据。

## 12. 质量门和扩大决策

进入真实试用前必须满足：G1–G5 静态契约、核心单域测试和关键失败 fixture 通过；真实 WeKnora、模型、文件和权限环境完成验证；P0/P1 未关闭问题为 0，P2 有人工补救；日志、关联 ID、审计、告警、暂停和回退入口可用；试用数据已脱敏且指标分母已锁定。

扩大或暂停由产品、QA 和安全责任人共同记录，引用真实样本数、失败样例、P0/P1/P2、人工投入、来源支撑率、漏改、误报、未确认项、导出损失和回退结果。样本不足、分母缺失、真实依赖未运行或存在无法解释的权限/数据完整性风险时，结论为 NOT READY 或 BLOCKED。

## 14. 与其他能力线交接

- **G1**：创建—草稿—立项—丢弃/恢复 fixture，Owner 条件写入、Context Revision 和 AI 候选边界证据。
- **G2**：PDF/书籍、OCR、多个 SourceAnchor、矛盾证据、授权撤回、重解析和调研助手 fixture；来源支撑率、核证时间和重检失败指标。
- **G3**：ChangeSet、DependencyEdge、AI 候选依赖、ImpactTask 幂等、陈旧结果和稳定化 fixture；漏改、重复、影响误报/漏报指标。
- **G4**：模板复制/编辑、声明式规则、ValidationIssue、误报处置、模板升级和 Preflight fixture；规则误报、回放和导出损失指标。
- **G5**：跨租户、跨项目、scope、Owner 停用/转让、撤权缓存/下载和审计 fixture；allow/deny、越权、审计完整性指标。

## 15. 验收场景

### AC-G6-01：干净环境主路径

在干净租户中从创建项目走到导出和下载，保存每步 fixture、版本、关联 ID、权限决策和输出 hash。

### AC-G6-02：三种运行模式隔离

同一场景分别以 mock、real_api_fake_model、real 运行，报告明确区分契约、接入和真实效果，不能合并为一个 PASS。

### AC-G6-03：真实权限撤回

导出前撤回资料或文件权限。正文/来源和下载被拒，审计元数据仍可查询；旧预签名 URL 和缓存不能旁路获取。

### AC-G6-04：ChangeSet 乱序和回退

revision 4 的异步任务晚于 revision 5 返回。旧结果保存为历史/STALE，不能覆盖当前对象；回退不改 revision 指针。

### AC-G6-05：模板和规则回放

模板/规则升级后，旧 ReleaseSnapshot 仍使用旧 hash，新快照使用新版本，旧问题处置不自动套用到新版本。

### AC-G6-06：DOCX/WPS 往返

真实 DOCX 在 Word/WPS 中打开、编辑、保存、重开；路线图、表格、分页或可编辑性损失按严重度阻断或降级。

### AC-G6-07：上游部分返回

WeKnora 只返回部分允许资料。系统记录过滤/未授权对象，不生成越权 EvidenceCard 或错误的“全部成功”。

### AC-G6-08：Owner 停用和恢复

Owner 租户身份失效，项目进入 owner_unavailable 派生限制，专属操作冻结；转让成功后重新运行关键主路径和权限回归。

### AC-G6-09：指标样本不足

试用窗口未达到最低样本量或缺少分母。报告原始计数并标记不可比较，不输出总体率或扩大结论。

### AC-G6-10：P0 回退

发现跨项目下载或撤权后正文泄露。立即停止相关流量和导出，切回已验证版本，保存审计和影响范围，完成恢复后验证再决定是否恢复灰度。

## 16. 不纳入 G6

本阶段不把一次 demo、生成字数、中标概率或单一满意度分数当作 Beta 质量证明；不把 mock/fake 结果混入真实效果；不把未经脱敏的研究资料写入日志或测试；不引入 P5 生产治理。G6 的完成标准是：关键领域流程有可复现证据，真实依赖状态透明，失败可定位、可暂停、可回退，历史和权限不被破坏，用户试用结果足以支持“扩大、继续试用或暂停”的明确决策。
