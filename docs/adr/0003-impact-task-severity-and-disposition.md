# 3. ImpactTask 的严重度、处置与来源失效语义

**状态**：已采纳（2026-10-19，由 #205 与 #206 的产品语义裁定产生）

## 背景

G3 交付后，`ImpactTask.Severity` 在生产提交路径被硬编码为 `blocking`，而 dismiss 动作拒绝 blocking 任务。结果是「责任人明确表示不处理」这个产品动作在真实路径上不可达，而现有可达性测试靠手工插入一个生产路径永远不会产出的严重度取值来覆盖，因此看起来是覆盖了的。

同时存在三处不一致：严重度从未定义取值域（模型是裸字符串，契约与客户端类型都不约束）；`source_revoked` 被声明为失效原因但实现不可达；`CANCELLED` 与 `DISMISSED` 在实际使用中语义重合。

这不是一个可以就地打补丁的缺陷。产品文档早已在**校验问题**上定义了完整的「严重度 + 处置」模型——豁免只适用于警告/提示级，误报删除适用于任一严重度——但那套模型从未长到影响任务上。影响任务反而复用了 `DISMISSED` 这个在术语表里属于校验问题、含义为「误报」的状态词。

## 决策

### 一、严重度采用三档，与校验问题同词表

取值域为 `blocking`、`warning`、`info`。`ImpactTask.Severity` 此前存储的字面量 `blocking` 本就借自模板规则严重度常量，统一到同一套词表是更小的改动，而不是引入新词汇。

严重度**由影响动作推导**，不接受调用方指定。推导规则集中在一个函数内。

责任域不参与推导：严重度描述后果，责任域描述归属，两者正交。G3 计划文档对两个动作的域归属有更宽的表述（章节再生成「B 或 C」、派生重算「所属领域」），代码按现有行为取值，该差异记录在案。

### 二、豁免权限是「是否阻断」的否定，而不是第二条规则

「能否被责任人接受」与「是否阻断稳定化」在产品上是同一件事的两面：可被接受的影响，本来就从未阻断。把它写成两条独立规则，就等于给同一条产品约束开两个可以各自漂移的出口。

因此只存在一条规则：**blocking 一律不可接受**。

### 三、把 BLOCK_RELEASE 的严重度写成推导函数里的常量

这是本决策中最关键的一处。

`BLOCK_RELEASE` 恒为 `blocking`。此前没有任何东西把「阻断发布」和「blocking」绑定在一起——只是恰好所有任务都是 blocking 而已。若它将来可以推导为更低的严重度，一条被接受的 `BLOCK_RELEASE` 任务将不再阻断闸门，而且**静默**地不再阻断：BLOCK_RELEASE 的预检复验只检查 DONE 任务，被接受的任务根本走不到那里。

而钉住这条保证的测试会继续变绿——它的夹具显式写死了严重度，会继续断言一个生产路径已无法产生的场景。

写成常量加上「blocking 不可接受」这条不变量之后，这条保证不再依赖任何字面量的巧合。闸门评估和动作处理都只调用 `impactSeverityBlocks`，没有第二处可以漂移。

### 四、删除 CANCELLED

接受与取消在实践中的含义相同（都是「不处理」）。保留两个词只会让审计出现两个同义词。「这件事本身不再成立」的场景应由生成阶段消化，而不是事后取消。

### 五、来源授权被撤销不是失效原因，而是操作被拒绝

原实现声称的三类失效原因中，`source_revoked` 从不可达：操作级来源复检在写事务之前执行，其检查集合是该分支的严格超集，来源被撤销时撤销必然先失败并返回错误。

我们**没有**通过放宽前置检查让它变得可达，理由是：

- 让它可达意味着允许读取一个调用方已被拒绝访问的任务，这是把一处 fail-closed 改成 fail-open。
- 转成 STALE 会断言「这项义务已经作废」，而事实相反——它作废不了，只是没人能处理了。而 STALE 既不算闭环也不阻断，任务会永远悬在那里。
- 任务保持原状且每次操作都被拒绝，是诚实的表达：这件事确实没被处理。

因此契约改写为两类失效原因，并在代码注释中写明这是**决定**而非未完成的实现，以免日后再次被当作缺陷提出。

### 六、错误自带对外形态

来源失效时，原先会命中共享映射里的 409 文案「快照基于的输入已变化，请重新准备。」——对一个影响任务动作而言是误导：那里根本没有快照。

最小改动是给映射表加一个分支，但那是类炎：每新增一个业务错误就要在同一个大 `switch` 里加一条。

改为：错误在定义处同时声明状态码、错误码与文案，映射器只做兜底。新增业务错误不再改动映射器。现有错误暂不迁移，以免把一次语义补全扩大成全域重构；但迁移方向从此处开始就成立。

## 被否决的备选方案

**按责任域推导严重度**。责任域表已存在，推导成本几乎为零。否决理由是责任域描述归属而非后果——同一个动作在不同域下的后果并不相同，用域当唯一严重度轴会得出荒谬结论。

**保留 CANCELLED 并与 DISMISSED 区分**。需要为两者找到真实区分场景。找不到：它们在当前流程中表达同一个决定。

**为来源失效新增任务状态留痕**。成本是放宽 fail-closed 检查，收益是一个既不闭环也不阻断的终态。

### 七、NO_ACTION 的影响解析语义（#216）

`NO_ACTION` 是影响解析结果，不是影响任务处置状态。系统保留它在 `ImpactAssessment.Impacts` 中，并保留依赖边的因果理由，让影响预览和审计能够回答“为什么判断本次不改变该对象”。它不会创建 `ImpactTask` 或 handoff，也不会把目标加入稳定化必需对象；因此不会进入任务处置队列或产生稳定化阻断。传播在该边停止，避免一个明确不受影响的目标继续把影响传给下游对象。

人工创建、确认或修改依赖时，审计详情同时记录最终 `action` 和 `reason`。未知动作仍拒绝写入，`NO_ACTION` 只通过影响解析层进入预览，不可被调用方伪造为任务处置结果。

## 影响

- 严重度取值域、任务状态集合、失效原因枚举在模型、契约、客户端类型三处同步。
- 界面开始展示严重度，并补齐终态中文文案（此前 STALE 与 DISMISSED 直接显示英文常量）。
- 界面新增「接受本次不处理」入口。阻断级任务上不隐藏该入口而是给出说明——隐藏会让用户以为功能不存在。
- 严重度取值不需要数据库迁移。
- `NO_ACTION`（有依赖但本次差异不改变该对象）由影响解析层保留为可审计预览结果，不生成任务；后续若需要更复杂的语义判定来源，另开 Spec。

### 八、未知动作按阻断处理（fail closed）

本决策落地时，`DeriveImpactSeverity` 的函数注释声明「词表之外的动作推导为 blocking」，而实现里的兜底分支返回的是 `warning`。这是注释与实现的漂移：注释描述的是设计意图，代码描述的是实际行为，两者不一致时，读注释的人会按 blocking 去推理后果，读代码的人会按 warning 去推理后果。

本次把推导改成显式的闭集映射：blocking 对应 `BLOCK_RELEASE`、`REVIEW_REQUIRED`、`INVALIDATE_CONFIRMATION`；info 对应 `RECOMPUTE`、`NO_ACTION`；warning 对应 `REVALIDATE_EVIDENCE`、`RETRIEVE_CANDIDATES`、`REGENERATE`；其余一律落到 blocking。

选择 blocking 而不是 warning，理由是：

- 严重度描述的是「放着不处理的后果」。一个产品尚未定义的动作没有已知后果，因此不能被断言为「轻微」。
- 豁免权限是「是否阻断」的否定（见第二节）。把它降级成 warning，等于默认送给调用方一条可以被责任人直接接受掉、且不需要任何闭环证据的任务。这与本模块「无法识别的取值不得被读成可以跳过工作」的原则相反。
- 这与 `impactSeverityBlocks` 对**未知严重度**的处置是同一条原则：那里已经是 fail closed，词表之外的动作如果落到 warning，两侧就会朝相反方向失败。

影响面：生产路径上只有任务创建一处写入严重度，其动作一定取自 `validImpactAction` 的闭集，因此现有生产行为完全不变，变化只针对闭集之外的动作。推导表本身由 `TestImpactTaskSeverityFollowsTheProductRules` 逐条钉住，另有测试断言推导映射与动作词表一一对应，避免新增动作时再次出现「新增了动作却忘了给严重度分支」的漂移。
