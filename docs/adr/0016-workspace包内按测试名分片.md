# 16. workspace 维持单一 Go 包：gate 按测试名分区分片，不拆包

**状态**：已采纳（2026-10-26，由治理票 #736 产生；ADR 先行于实施）。决策对象是 #724 验收报告 §2.2/§6 显形并「另行立票」的那条决策：**provider 分片的最大分片被 workspace 单一 Go 包钉在 660s**（job 墙 642–660s，dispatch 40451195877；`go test` 本体 590–600s，M12 评审已把 `-timeout` 放大到 15m 止血），而包是 `go test` 的最小调度单元。

**修订关系**：本决策**不修订** [ADR 0014](0014-gate-evidence-sharding-frontend-delegation-red-lines.md) 的任何一节的结构，只做两处**显式修订**：第一节「每个分片跑同一条测试命令」的**字面**（分片命令此后允许携带判定模块发布的 `-run` 过滤器；`-race -count=1` 的红线二字面与意图原样），与「分片是包清单的编组」的**形状**（分片条目此后可选携带一个测试名过滤器）。0014 的四条红线里，一、三、四逐字不动；第二条的意图（不降 race 与缓存语义）原样且被守护测试继续钉住。#724 报告 §2.2 的顾虑在本文第三节正面裁决。

## 背景

provider 分片（#724）落地后，全量 gate 的 wall 地板 = workspace 分片 ≈ 660s（占 55%+）。地板的结构原因是**包粒度**：`internal/lingdoc/workspace` 是单一 Go 包（起点 `cb57f5c9` 实测：51 个产品文件、116 个测试文件、495 个 `func Test`，无子目录、无 `TestMain`、无 testify suite、无 build tag、无 `t.Parallel()`），`go test` 以包为最小单元，包内不可再分。要降地板只有三条路：拆包、包内用 `-run` 正则把一个包的测试拆到多个 job、或接受地板。

拆包的成本不是猜测，是可数的：

1. **未导出耦合**：产品文件含 233 个未导出顶层声明；116 个测试文件中 **73 个**引用其中 **63 个**。Go 的外部测试包（`package workspace_test`，测试文件必须与被测包同目录——搬到子目录即是另一个包）拿不到未导出标识：要么把这 63 个标识导出（连带 51 个产品文件的 API 面重画、`internal/container` 等真实消费者重新审阅），要么造桥——而 `export_test.go` 式的桥**只在本包测试构建里编译**，跨目录的子包根本看不见。
2. **共享 testhelper**：测试文件内有 282 个小写 helper，其中 **96 个被多于一个测试文件使用**（最大 `testRuntime` 被 20 个文件使用）；**87/116** 个测试文件至少依赖一个跨文件 helper。这些 helper 构造未导出产品类型——把它们提升成可导出的测试支持包，同样撞上第 1 条的导出面爆炸。
3. **按主题拆产品代码**（http/wiring/selected_rewrite/…）理论上消除第 1、2 条，但那是重画仓库最大包的架构：主题间共享类型（routes→service→gorm adapter 同包互引），拆开要么引入分层核心包、要么成环；为省 CI 秒数去动 233 个未导出声明的归属，是把「设计给领域的边界」外包给「CI 的墙钟」，方向反了——Ousterhout 的账上，被迫导出内部类型得到的是**更浅**的模块（面变大、深不变），纯负值。

`-run` 分片的真实顾虑也被 #724 报告如实登记了：它改变「每个分片跑同一条测试命令」的语义（ADR 0014 红线二的邻接面）。这个顾虑的实质是什么、代价几许，本文第三节正面算这笔账。

## 决策

### 一、workspace 维持单一 Go 包

不拆包，不为 CI 墙钟拆产品代码或导出内部标识。理由是上面三条量化事实：**拆包的每一个可行形态都把包的内部面变成导出面**，而包内并没有现成的结构边界（无子目录、主题与文件不同构）。「拆子包」若有一天该做，驱动它应当是领域架构（CONTEXT.md 的单一上下文、模块深浅），不是 gate 秒数；到那一天，本决策的分片机制**不受影响**——分片数据随包结构自然演进（见第五节）。

### 二、gate 按「测试名分区」把 workspace 包的测试分给多个分片 job

判定模块在决策时**枚举** workspace 包的全部顶层测试名（读 `<主根>/workspace/*_test.go` 的 `^func Test\w+\(`），按**确定性哈希桶**（`md5(测试名) mod N`，N=3）分成恰好覆盖、两两不交、各自非空的 N 片，为每片生成一个锚定的 `-run` 模式（`^(TestA|TestB|…)$`）。分片输出（`provider_shards`）的条目从「分片名 + 包清单」扩展为「分片名 + 包清单 + 可选 `go_test_filter`」；工作流 matrix 逐片消费，`-run` 过滤器只作为数据流经工作流——**工作流文件里没有、也不允许出现任何测试名**（红线四原样）。

- **枚举即分区，登记税为零**：分区由枚举派生，不靠人往清单里登记名字。新增一个测试，它自动落入恰一片——gate **结构上不可能**静默漏跑一个测试；这是对 §2.2 顾虑（改名分片后「漏测」风险）的机制性回答，而不仅是守护。
- **守护测试双向钉住**（fail-closed）：一个守护用例独立按源码枚举测试名，断言模块发布的各片模式对真实仓库构成精确分区（并集=全名集、两两不交、各片非空、模式锚定）；枚举逻辑与守护枚举是两份独立实现，谁坏了谁红。
- **降级安全**：枚举不可用（找不到测试文件、树形态变化）时，workspace 退化为**单片不过滤**——恰是 #724 的现状形态。降级只慢、不漏。
- **分片数 N=3 的依据**：Phase 0 的 17 次 race 全量 run 总长 556–934s（方差 ±27%）。两片的最坏值 934/2≈467s 加 job 固定开销会顶穿 450s 目标；三片最坏 934/3≈311s 加开销后仍有余量。runner 计费分钟相应增加（3 个小 job 各自承担 checkout/setup 与一次编译），按 0014 第五节同口径记为**观察项，不是红线**。
- **确定性**：哈希对插入稳定（新测试不打乱既有测试的归属）；同一 head 的枚举与分桶逐字节确定，判定输出可复现。

### 三、对 #724 报告 §2.2「同一条命令」顾虑的正面裁决

**变了的**：一个包的测试集合被名字分区到多个 job——「每片同一条命令」的字面不再成立。**没变的**：每个测试仍在 `-race -count=1 -timeout 15m` 下运行，竞争检测与禁缓存逐测试等值；失败归因不变（测试名 + 分片名都在 `-json` 日志与必需检查里）；分区覆盖由守护钉死，不存在「某片忘了带哪些测试」的自由度。红线二的意图——**提速不得来自稀释验证强度**——原样成立；修订的只是它的字面（「同一条命令」→「同一条命令骨架，包内分片可携带判定模块发布的 `-run` 过滤器」）。

如实登记的**新增代价**，三项：

1. **每片重复支付包级固定成本**：每片各自编译链接同一个巨型测试二进制、各自跑一遍 `go vet` 全包与包级初始化（实测该包无 `TestMain`、无重型包级 init，固定成本主要是编译）。这是「片数 × 固定成本」换「wall 除以片数」的直接账，N=3 时计费分钟约 +40%，wall 约 660s→300s 量级。
2. **not-empty 断言的假红面**：某片若恰好全是被环境跳过的测试（如未设 DSN 的 Postgres 门控测试）会触发「零通过」红。该风险被分区的不交覆盖与片规模（~165 个测试/片）压到可忽略，且真发生时是**红灯不是假绿**——方向安全。
3. **测试改名/删除的漂移**：名字变了，归属随之变。守护测试在每个 head 上重验分区，漂移即红；不存在需要人维护的静态名单，也就没有名单腐烂。

### 四、「维持现状」被否决的量化代价

接受 660s 地板意味着：每一笔触及 workspace 族的全量 gate（workspace 是域内主包族，占 provider 测试时长 63.4%）多等约 4 分钟（对三片 300s 量级而言）；且 `-timeout 15m` 的余量随包继续生长而变薄——包从 #724 报告的 114 个测试文件长到本票起点的 116 个，侵蚀速度慢但方向单一。现状的唯一优势是零机制、零维护；本文第二节的机制是**零登记税**的（枚举即分区），现状省下的维护成本接近于零，多付的是每 PR 4 分钟与超时余量的单调侵蚀。**复核条件**：若分区守护在真实使用中频繁误红（枚举实现缺陷）、或某片实测持续超过 450s（时长方差超出 Phase 0 区间），回退路径是删掉过滤器数据——一处分片条目改动，回到 #724 形态，不牵动工作流。

### 五、与 #724 分片机制的关系

本决策**不新增第二个分片机制**：还是 0014 第一节那条「判定模块输出分片数据、工作流 matrix 哑消费」的缝，`provider_shards` 输出键不变、消费方式不变，条目多一个可选字段。族计划表 `LINGDOC_FAMILY_SHARDS` 随之演进：workspace 族从一行（单分片）变为三行（同族、各带一片过滤器），其余族原样（过滤器为空 = 整族跑）。将来若 workspace 真的拆了子包，族计划把子包登记为新族即可，本决策的测试名分区对尚存的包内测试照常工作；若某天族拆细到每族时长低于片目标，删掉对应过滤器行即回到纯包分片。**分片策略只写在判定模块这一处**的教条（0014 第一节）逐字不变；GLOSSARY「分片」条目随本决策扩展。

## 被否决的备选方案

**拆 Go 子包（测试文件按主题搬入子目录）。** 73/116 的测试文件引用未导出产品标识、87/116 依赖跨文件 helper（96 个共享 helper，最大者覆盖 20 个文件）——测试出包即编译失败；补齐访问权只有导出 63 个内部标识一条路，得到的是更浅的模块与更大的 API 面。按主题拆产品代码可免导出，但那是为了 CI 秒数重画仓库最大包的归属边界，主题间共享类型还会逼迫分层核心包或成环；成本以周计、风险以架构计，收益（每 PR 约 4 分钟）与本决策重合。**不排除将来以领域理由重提**——届时本决策第二节的数据（耦合事实）仍是它的第一块拦路石，也是它必须先搬掉的石头。

**维持现状，接受 660s 地板。** 见第四节：登记税为零的机制摆在眼前时，「零维护」的优势不复存在；多付的是每全量 gate 约 4 分钟与 15m 超时余量的单调侵蚀。回退到现状的成本被刻意压到一处分片数据改动，现状随时可退——这正是它不值得现在选的原因。

**人工策划的主题前缀 `-run` 正则（如 `^Test(Delivery|Export|…)`）。** 495 个测试有 104 个名字前缀，名字与主题不同构（`The`×15、`Handler`×14）；人工分组意味着每个新测试都要登记，漏登记要么守护红（烦）、要么静默漏测（不可接受）——而守护要红得能防漏测，就必须做枚举核对，既然枚举核对都做了，直接枚举分桶严格优于人工策划（零税、同样 fail-closed）。人工策划唯一可能的优势是按时长手工平衡分片；实测若出现超出目标的失衡， correct 的做法是在模块内对已知的重量级测试做少量显式桶覆盖（数据 + 守护照旧），而不是回到人工前缀表。

**把 `-run` 模式写进工作流。** 红线四直接挡下：工作流长出测试名知识即是第二份归属副本。模式只作为判定输出流经 matrix。

## 影响

- 本决策由 #736 同票实施：判定模块（枚举 + 分桶 + 输出扩展 + 分区数据）、工作流（filter 环境变量与 `-run` 接线）、守护测试（接线断言更新 + 新增真实仓库分区守护）、GLOSSARY「分片」条目扩展。
- 验收目标：WSL 逐片 `go test -race -count=1 -timeout 15m` 实测，最大片 <450s；全套守护（967 项基线）与 `go build ./...`、`go vet` 全绿；`internal/lingdoc/workspace` 的产品代码与测试文件**零改动**（测试零删减，只重新编组）。
- runner 计费分钟上升（观察项）；gate 必需检查名、require-coverage、委托机制（#723/#734）一概不变；coverage 表的 `verified_by` 记新分片 job 名（`lingdoc-workspace-a/b/c`），读者从覆盖表看到的验证单元从「一个包」细到「包的一个名字分区」。
