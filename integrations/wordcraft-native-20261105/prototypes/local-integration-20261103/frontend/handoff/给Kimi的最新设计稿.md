# LingDoc 最新前端设计稿

设计基线：LD-V1-20261103-R1。日期：2026 年 11 月 3 日。接收方：Kimi 前端设计与开发。配套：后端接口与联调计划、统一演示场景、CURRENT.json。

## 先读这一段

请围绕一份科研申报稿，重新设计“继续写作、落实审核意见、应对条件变化、复核交付”的完整体验。可以激进调整页面结构、组件和流程，不需要兼容旧版四页结构、双模式导航或想法库形态。保留的不是旧页面，而是用户对真实编辑、可靠保存、依据可查和自主决定的需要。WordCraft 原生菜单、功能区、输入、选区、格式、撤销和文档能力必须真实保留，不再制作仿 Word 工具栏或 contentEditable 替代品。

本稿是新的工作设计基线，替代旧《LingDoc前后端交接计划》和旧四页原型对新界面的约束。它不是所有功能已经实现或上线的声明。前后端以 CURRENT.json 指向的同一版本工作；未接通状态明确标为演示。任何端发现合同不能支持设计，应提出一项共同变更，而不是各自静默改成不同产品。

## 一 产品承诺

让已有研究材料和初稿的用户，完成一次可追溯的科研申报审阅。用户能知道这段话依据什么、老师要求改什么、自己决定了什么、修改是否保存、条件变化后哪里需要再看。

第一版必须打通三件事：可靠写作与重开；一次按位置意见处理；一次显式关联的变化回看。资料与 AI 不是独立卖点，服务于这条任务。可编辑技术路线图作为并行验证；匿名活页和字段映射依首个实际模板决定，不把所有需求同时塞进首版。

## 二 新的信息架构

采用项目级任务结构，不默认沿用资料库、想法库、写作、待回看四个平级页面。

| 主空间 | 首要内容 | 主要动作 |
| --- | --- | --- |
| 项目概览 | 当前文稿、上次工作位置、已保存版本、待处理意见与变化 | 继续上次工作 |
| 写作工作台 | 完整原生 WordCraft，当前任务和可按需打开的资料、意见、助手 | 写作或处理一项意见 |
| 审阅与交付 | 意见、变化回看、来源核验与输出要求，展示覆盖范围 | 处理下一项；导出审阅稿 |

资料、研究方案、图表、历史是项目资产，可以用抽屉或独立资产页承载。不要为了这四类资产再制造四套永久占位的侧栏。研究方案先呈现目标、对象、方法、周期等关键判断；是否需要独立“想法库”，由跨任务复用需求决定。

项目启动支持直接打开已有 DOCX；不能要求用户先建好库、确认完想法或使用 AI 才能写。构思和写作可以是助手的任务上下文，不必强制成为两个互斥页面；若保留模式，会话与上下文隔离必须清楚。

## 三 桌面布局与视觉方向

```text
项目名称    项目概览 | 写作 | 审阅与交付       真实保存状态   交付
当前任务：处理导师对样本选择的意见     上一项 / 下一项     专注写作
┌────────────┬───────────────────────────┬──────────────┐
│ 资料及原文 │ 真实 WordCraft 原生宿主    │ 当前意见详情 │
│ 版本、片段 │ 菜单、功能区、正文、标尺   │ 或 AI 助手   │
│ 展开阅读   │ 由原生引擎管理全部编辑操作 │ 明确切换入口 │
└────────────┴───────────────────────────┴──────────────┘
```

这是信息组织线框，不是要求重画原生菜单。真实界面参考见 `原生界面参考.png`；该图来自此前真实运行截图，只用于认识必须保留的原生区域，不要求保留截图外围旧导航。

视觉上更像认真工作的科研文稿桌面：正文是重心，使用克制的中性色与一个主要强调色；状态不用大面积绿色包装完成感。默认安静，不把 AI 长对话、所有资料和所有意见一起铺开。必要状态可见，技术参数进入详情，不把 revision、hash、接口名堆在日常操作里。

资料和右侧辅助区独立开关。资料可与 AI 同时看，打开一个不得自动关另一个。右侧内部可切换意见与助手，切换保留原任务、输入草稿和滚动位置。正文最小可用宽度先用真实原生界面验证；空间不足时提示用户选择展开阅读或覆盖辅助区，不悄悄压缩到无法编辑。

专注写作只隐藏外围区域，退出后恢复布局；面板布局按项目记忆。展开资料时明确提供“返回刚才的文稿位置”；查看原文不改变任务、模式、已选意见或模型上下文。移动端本轮以阅读与意见处理为目标，不承诺完整原生桌面编辑体验。

## 四 必须交付的交互状态

| 编号 | 画面与交互 | 真实依赖与失败反馈 |
| --- | --- | --- |
| S01 | 打开已有项目：突出继续写作、最近位置、一条待处理意见 | 区分服务器已保存稿与当前未保存编辑；加载失败仍给重试和已有草稿入口 |
| S02 | 专注写作：原生界面完整，资料和助手只留入口 | 页面与面板切换不销毁宿主，不丢选区、撤销和未保存内容 |
| S03 | 正文与依据并排：具体版本、段落及关联理由；可扩大阅读再返回 | 无法打开、版本已变化、解析失败分别提示；不是只打开整份文件 |
| S04 | 导师意见：显示意见原文、指向的正文及旧摘录 | 定位有效可查看；失效时要求重新定位，不猜位置；看过不等于完成 |
| S05 | 请求 AI 局部帮助：发送前可展开实际上下文，添加和移除有反馈 | 展示实际聊天历史、片段及资料版本；未授权内容不得隐式发送 |
| S06 | 建议与原稿对照：用户可采用、自己改或放弃 | 采用前校验正文版本；版本变化要求重新比较；失败不部分静默覆盖 |
| S07 | 保存中继续输入、保存失败、版本冲突三个分支 | 旧请求成功不清除新编辑的未保存状态；重试不重复写入，不自动覆盖冲突 |
| S08 | 条件由四社区改为两社区：展示新旧值、原因及关联章节 | 系统提示需要检查，不能自动推断样本量减半或修改研究方法 |
| S09 | 回看决定与处理：决定修改、记录实际修改、复核完成分开 | 完成记录关联真实保存版本，或保留无需调整理由；暂缓仍可找回 |
| S10 | 交付预览：本次文稿版本、未完成事项、已核验范围 | 输出可编辑 DOCX；是否附意见记录由用户选，不自动打包内部资料 |

空项目、无资料、无 AI、无待处理项也要成立。网络失败、来源失效、请求结果未知、定位失效不能共用一个“出错了”弹窗。

## 五 状态与动作的共同语言

“草稿已生成”“已采用建议”“已保存”“意见已完成”“已导出”是五件不同的事，不允许一条操作自动把它们全部标绿。

- 意见决定：修改正文、更新研究方案、两者调整、无需调整、暂不判断。
- 处理进度：待判断、待处理、暂缓、已完成。决定和进度分别记录；决定修改后仍待处理。
- 来源核验：可访问、书目信息匹配、引文一致、是否支持主张分别呈现。前三级不能替用户完成第四级学术判断。
- 保存反馈：未保存、保存中、已保存、保存失败、版本冲突；底层部分成功或回执未知时解释实际事实，不能用前端计时器变成成功。
- 定位：可定位、已失效、尚未接入。旧摘录始终是参考，不能冒充当前正文。

无需调整需要用户理由；“系统未发现直接关联”只说明检查范围，不等于用户确认不受影响。刷新后哪些数据恢复由真实持久化决定，mock 页面必须提示刷新会清空。

## 六 统一演示场景

全部材料虚构，仅模拟科研申报，不对应实际基金规则。

项目为《社区老年人数字公共服务使用障碍研究》。研究者已有初稿与联系记录，计划进入四个社区。导师在“样本选择”段提出：“说明社区选择标准，不要据此概括全市情况。”用户打开原依据，查看建议，手工或确认后修改并保存。

随后联系记录从 v1 更新到 v2：其中两个社区本期不能配合，进入场地由四个变为两个。预置的显式关系关联样本范围、进度和路线图。系统提醒回看，不自动把样本量减半。用户调整范围和进度，决定保留访谈方法并说明理由。图表如尚未接入则显示待人工更新；接入后由用户主动替换文稿中的旧图。最终复核、保存、关闭重开并导出导师审阅稿。

数据文件为 `统一演示场景.json`。不得把不同页面的数据改成互不相干的占位文案；历史快照必须仍能看到当时的四社区依据。所有新意见和新想法有自己的历史，不套用其他对象的形成记录。

## 七 AI 和图表允许重新设计

此前暂停的选区上下文等入口不再构成设计禁令。可以设计新的显式选区和资料添加流程，但必须包含查看实际发送内容、移除、来源版本变化、模式切换及历史附件处理。新模型调用尚未联调时标为演示，不以旧功能名自动继承授权。

AI 建议可以积极，但学术方向与正文写入由用户决定。首版无需自动生成整份申报书，不把多智能体数量作为卖点。AI 上下文显示是实际请求的可见窗口，不是一组与请求无关的标签。

路线图先画一种可编辑研究流程图的完整状态：节点和连线编辑、图源保存、当前文稿中旧图对照、主动更新文稿。DOCX 内一张图片不等于保留了可编辑图源。手绘识别与任意复杂图生成不在首个验证承诺内。

## 八 前后端并行分工

Kimi 负责目标界面、交互状态、组件边界和前端 Adapter 接口使用。后端负责现有 API 核对、持久化、幂等与版本检查、意见对象和影响任务适配。原生适配负责真实文档身份、定位、编辑与保存回执，不允许页面绕过保存协调器。

现有端点以 `后端接口与联调计划.md` 为准，不能照旧稿另造 `/conversations` 等接口。设计可以提出新的意见操作，但写明“待实现合同”，不得声称已有。前端演示数据与真实 API 实现分开；各交互都标明接入状态，真实与演示数据按环境及项目身份隔离；切换时不得混合实体、继承 mock 完成状态或覆盖历史快照和未保存正文。

第一批两端共同交付：打开一个真实 DOCX，保存后重开；同时完成项目概览、专注写作及保存分支设计。第二批接来源查看及位置意见；第三批接显式条件变化后的回看。每批都交一条端到端证据，不以“接口返回 200”或“页面能点”替代完整验收。

## 九 最新基线如何同步

唯一入口为 `CURRENT.json`，里面列设计基线、文件 SHA256、已核验源码版本、待同步端和当前能力边界。文件名叫“最新”不构成同步证明。共享基线文件可打包交付，但离线 ZIP 只是这个版本的快照，不会自动更新。

Kimi 开工回报读取的 baselineId、设计稿哈希及工作分支；后端回报同一 baselineId、接口映射哈希和代码提交；联调回报实际运行的前端与后端提交。任一项不一致，先对齐差异，不进行无提示的半升级。代码未提交时记为未提交，不填虚构 SHA。

本轮只读核对远端与本地，不自动把最新上游合并到当前工作树。采用新提交前评估保存、模型上下文和原生接口差异。对用户保持安静，在开发信息或交接记录显示完整版本；接口不兼容时用户界面保留编辑内容并明确提示操作暂不可用。

1. 项目概览、真实 WordCraft 工作台、审阅交付三组主要画面，以及 S01—S10 状态与图表试验状态。
2. 一份可点击前端，按统一场景串联；无法运行原生宿主时使用明确标注的原生参考截图占位，不自行重造编辑器。
3. 接口映射表：每个动作对应已有接口、待适配、待新增或 mock，附错误与版本冲突处理。
4. 本轮变更清单与验收证据，回报 baselineId；源码交付保留原生接入点，不把设计包中的“待同步”自己改成“全端完成”。

验收重点：正文仍是主位；按意见找到上下文；查看动作不改变用户任务；保存反馈可信；变化能解释；用户知道下一步做什么。可以推翻旧页面，但不能牺牲这些结果。

## 十一 产品内部也要明确最新

“最新资料”“最新确认的研究方案”“这份正文使用的依据”“当前未保存稿”不是同一个版本。界面应告诉用户差异：例如“正文仍依据四社区方案；最新确认方案为两社区，三处待回看”，而不是用一个 v2 标签让用户猜。

服务器确认后的资料版本和处理状态是跨端同步依据；当前编辑器中的未保存正文仍由原生引擎维护。发现新版本时，刷新导航计数和资料摘要，并提示可查看变化；不能用服务器新稿直接覆盖未保存正文，也不能把历史快照自动改指向最新资料。

请求提交时携带用户操作所依据的具体版本。若后端发现已变化，返回冲突并要求重新比较；不能重新读取 latest 后静默重放写入。前端忽略不属于当前项目、文档或已过期请求的响应。事件推送尚未接通时可在进入页面、窗口重新聚焦及写操作前查询校准，不能画出不存在的实时同步能力。

设计应包含“发现更新但尚未应用”“当前离线，最后同步时间”“写入冲突，保留本地稿”三个状态。真正接通实时事件后仍要断线校准。不同端跟随同一最新已确认状态，不意味着把用户尚未确认的草稿自动传播或采纳。
