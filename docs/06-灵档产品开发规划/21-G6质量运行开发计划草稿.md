# G6 Beta 质量、运行与效果评估开发计划（草稿）

状态：草稿，基于 `main` `4902d0ffbb5451dc8493e9370716ca13c81db025`；不表示 G6 已实现或已完成 Beta 验收。

## Problem Statement

当前 LingDoc 已有领域契约、场景执行器和部分 G7 持续写作能力，但一次契约通过或单次演示仍不能证明从建项、依据、变更、模板检查、权限判定到导出下载的真实链路可靠。验证结果还需要明确区分 mock、真实 API 加假模型和完整真实依赖；失败需要能够归因、复现、暂停和恢复；历史快照与撤权后的数据不能因回退或缓存而重新暴露。

Beta 试用还缺少统一的脱敏 fixture、运行证据格式、关联 ID、失败分级、回退演练和指标分母。没有这些边界，团队容易把静态契约当成真实能力，把样本不足的个案写成效果结论，或在修复一个领域时破坏另一个领域的版本、权限和导出不变量。

## Solution

建立一条以场景驱动的质量证据入口：同一套版本化、脱敏 fixture 由场景执行器在三种运行模式下运行，并输出可审计的 PASS、FAIL、NOT RUN 或 BLOCKED 报告。报告绑定 fixture、模板/规则版本、对象版本、权限快照、运行模式、依赖版本、输入输出摘要和责任归因，禁止写入正文、原文摘录、令牌或其他敏感内容。

首版按六个交付切片推进：验收基准、自动化分层、真实依赖验证、观测与告警、灰度/迁移/回退、Beta 试用评估。各领域功能作者负责随切片交付成功和失败证据，G6 提供统一证据格式、运行手册和质量门，不重新定义 G1–G5 的对象、权限或业务规则。

最高层测试接缝是“场景声明 → 提供方请求 → 脱敏验证报告”。单域单元/契约测试作为该接缝的输入，真实依赖和人工 Word/WPS 检查作为报告的外部证据；不为每个领域另建一套质量框架。

## User Stories

1. 作为领域开发者，我想用脱敏 fixture 重现成功和关键失败路径，以便在提交切片时同时交付可复核证据。
2. 作为测试人员，我想在同一场景下区分 mock、real_api_fake_model 和 real，以便不把接入通过误报为真实效果通过。
3. 作为评审人，我想看到 fixture、版本、权限快照、运行模式和输入输出摘要，以便判断报告是否可复现且没有跨版本混淆。
4. 作为运行负责人，我想用关联 ID 串起用户操作、领域写入、异步任务、检查、冻结、导出和下载，以便定位失败归属。
5. 作为安全负责人，我想验证撤权、跨租户、跨项目、缓存和预签名 URL 场景，以便阻断正文、来源和历史文件泄露。
6. 作为数据库维护者，我想验证迁移前后的读取、回退窗口和未知状态处理，以便旧快照可读且新字段默认值不伪造确认状态。
7. 作为产品负责人，我想知道失败来自领域逻辑、权限、外部服务、模型、文件格式、运行环境还是 fixture，以便安排修复责任人。
8. 作为运行负责人，我想暂停新版本写入、切回已验证配置并保留历史快照，以便 P0/P1 故障可控恢复。
9. 作为试用组织者，我想锁定试用窗口、纳入项目、模板/规则版本、运行模式和最低样本量，以便效果结论可解释。
10. 作为 QA，我想记录人工投入、来源支撑、漏改、误报、未确认项和导出损失的分子、分母及缺失值，以便样本不足时只报告个案。
11. 作为第二位复现者，我想按仓库中的命令、fixture 和环境说明独立运行主路径，以便作者自测不被误认为独立验收。
12. 作为内容作者，我想在真实 Word/WPS 往返后检查章节、表格、路线图、引用、分页和可编辑性，以便导出损失不会静默进入交付。
13. 作为权限管理员，我想验证 Owner 停用、转让和重新授权后的关键路径，以便恢复行为不会绕过当前权限。
14. 作为模型接入负责人，我想记录模型、提示词/结构化输出版本、范围、耗时和失败率，以便模型质量与领域逻辑分开归因。
15. 作为领域消费者，我想在上游只返回部分资料或异步结果乱序时看到明确的过滤、陈旧和阻断状态，以便系统不会伪造“全部成功”。
16. 作为发布负责人，我想根据 P0/P1/P2、真实样本和回退结果决定扩大、继续试用或暂停，以便 Beta 进入下一阶段有明确依据。

## Implementation Decisions

- **证据模型**：每份报告必须包含 fixture_id、脱敏 project_id、template_version、ruleset_hash、对象版本/修订、permission_snapshot、runtime_mode、依赖版本、输入输出摘要、时间、结果、证据引用、owner 和 reviewer。
- **运行模式**：`mock` 只证明契约和失败语义；`real_api_fake_model` 证明真实 API、权限、队列和文件接口接入；`real` 才可进入效果汇总。三者不得合并成单一 PASS。
- **fixture 版本化**：覆盖项目生命周期、依据、PCC/ChangeSet、模板规则、权限、交付和故障类别；每个 fixture 声明输入、状态转移、允许/禁止副作用、审计事件和复现步骤。修改须说明是产品、规则、外部接口还是测试修正。
- **测试分层**：保留现有单元、契约、集成和场景执行器，在其上补充 E2E、安全、真实依赖和回归分层。失败报告必须指出领域、依赖或 fixture 的主要归因，不把测试框架异常伪装成产品通过。
- **关联链**：请求、异步任务、ChangeSet/ImpactTask、ValidationIssue、Preflight、ReleaseSnapshot、ExportArtifact 和下载审计使用可关联但脱敏的 ID；日志只写状态、版本、耗时、错误码和资源类别，不写正文、原文摘录、API Key、访问令牌或不必要的模型输入。
- **观测与告警**：至少记录请求成功/拒绝/冲突、P95/P99、异步失败/重试/陈旧/重复副作用、检查阻断、权限拒绝、撤权拦截、下载再鉴权、DOCX 损失和外部依赖可用性；每个告警必须绑定暂停、重试、回退、阻止导出或通知动作。
- **灰度与回退**：按租户、项目、模板版本、规则版本和运行模式记录灰度。回退停止新版本写入或切回已验证配置，不修改已发布模板、冻结快照、历史文件和审计；已应用变更通过逆向 ChangeSet 恢复，不能直接改 revision 指针。
- **迁移兼容**：明确旧版本读取、新版本写入、回退窗口和失败清理；缺少版本、权限或溯源的旧对象进入待迁移/UNKNOWN，不以默认值表示已确认；旧消费者可忽略新增事件字段。
- **真实依赖**：WeKnora 验证租户/知识库分享、viewer 与项目成员分离、scope、Agent 只读、部分返回和撤权重读；模型验证记录版本和范围；DOCX 必须由第二人使用 Word 或 WPS 打开、编辑、保存和重开。
- **质量门**：进入真实试用前，静态契约、核心单域测试、关键失败 fixture、真实依赖接入、日志/审计/告警/暂停/回退入口必须可用；P0/P1 未关闭问题为零，P2 有人工补救。缺真实依赖、样本不足或分母缺失时只能是 NOT RUN 或 BLOCKED。
- **试用指标**：以锁定的试用窗口为单位报告人工投入时间、来源支撑率、漏改数、规则/模型误报率、未确认项数和导出损失数；先报告分子、分母、缺失值和版本，样本不足不计算总体率或扩大结论。
- **交付边界**：G6 不重新定义 G1–G5 领域对象、权限和规则，不新建集中质量平台，不把生成字数、中标概率或一次满意度当质量证明，不把未经脱敏资料写入测试或日志，不引入 P5 生产治理。

## Testing Decisions

- 测试只断言外部行为：状态、版本、权限、响应、审计、副作用、文件摘要和恢复结果；不把内部函数调用或日志文本细节作为唯一通过条件。
- 最高层复现入口为场景驱动报告；每个场景必须有成功路径和至少一个关键失败路径。重点场景包括干净环境主路径、三种运行模式、真实撤权、ChangeSet 乱序、模板/规则回放、DOCX/WPS 往返、上游部分返回、Owner 停用恢复、样本不足和 P0 回退。
- 集成测试使用可控数据库、队列、WeKnora fake、模型 fake 和文件服务，断言重复投递、乱序、回滚、重新鉴权和失败时无半套正式写入。
- 安全回归覆盖跨租户/跨项目 ID 替换、scope 缺失、撤权缓存、预签名 URL、下载重放、共享 Agent、异步权限变化和审计查询越权；正文、来源或旧文件泄露均为阻断缺陷。
- 真实依赖测试必须保存运行模式、环境版本、脱敏响应摘要和人工检查记录；mock 或 fake 结果不得进入真实效果汇总。
- 测试先在干净环境运行，再由第二位开发者按复现配方运行；报告明确记录 PASS、FAIL、NOT RUN、BLOCKED 和未覆盖风险。
- 既有场景执行器、契约校验脚本、T15/T16 验证报告和 G7 合同检查作为 prior art；G6 增量应复用其报告和脱敏约定，不另造平行报告格式。

## Out of Scope

- 不实现 G1–G5 尚未确定的业务对象、完整 PCC/稳定化引擎、通用规则平台、模板市场或组织审批流。
- 不建设实时协同、OT/CRDT、全量离线缓存或第二套编辑器。
- 不在没有真实样本和锁定分母时发布效率提升、质量百分比或扩大结论。
- 不把未经脱敏的研究正文、来源原文、访问令牌或模型私密输入放入 fixture、日志、报告或 CI 输出。
- 不以直接数据库改指针、永久临时授权、服务账号或水印绕过领域入口和权限边界。

## Further Notes

本草稿建议以一个质量证据报告接缝承接各领域交付，再按 G6.1–G6.6 小切片实施。首张实现 PR 应先冻结报告 schema、一个脱敏主路径 fixture、一个撤权/乱序失败 fixture 及运行模式字段；随后再接观测、回退和真实试用指标。功能作者仍对自身切片的失败证据负责，G6 不成为“最后统一修所有问题”的兜底团队。

需由产品、QA 和实际消费者确认的 seam 是：场景执行器是否作为唯一跨域质量入口，以及报告是否以当前仓库既有 JSON 报告和脱敏规则为兼容基线。确认后再把本草稿拆成可领取的 issue/PR；在确认前不宣称 G6 开工或完成。
