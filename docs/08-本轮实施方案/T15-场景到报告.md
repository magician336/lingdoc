# T15-04：一条场景从契约跑到报告

状态：2026-09-27 完成。`scripts/lingdoc_mock/run_scenario.py` 把**一条**场景从契约里的声明一路跑到报告：按声明把起点状态灌进**真实服务**并读回核对 → 按步骤声明的 actor 发出那一步 → 逐条求值断言 → 写出报告。F22「部分授权不静默成功」对着真实服务跑通，**连跑三遍报告的字节完全相同**（16994 字节）。这一票的目的不是多跑几条场景，是**定下三件事的形态**——请求定义怎么表达、可求值断言怎么表达、报告长什么样落在哪里——后面的票复用它们。机器生成的证据在 `docs/08-本轮实施方案/T15-S5-证据.json`。

对应票 #31；是 #27（T15 错误矩阵）里的第一条端到端。#29（执行器按规格驱动）、#30（起点状态装载）已完成，本票把两者接起来。

## 结论

`scripts/lingdoc_mock/run_scenario.py` 组合已有的两个工具，不重新实现任何一个：起点走装载器，步骤走执行器，HTTP 走同一个 `ProviderClient`。

1. **请求定义：`request` 三件套 + `actor`。** 契约里的步骤带 `request`（`path_params` / `headers` / `json`），值可以是字面量也可以是 `{{变量}}`。变量只有三个命名空间：`{{project.id}}` 是本次运行建出来的项目，`{{asset.<声明名>}}` 是**绑定 id**（不是知识 id——检索预检按绑定寻址，而绑定 id 的唯一来源是 `bindAsset` 的响应），`{{chapter.<节 id>}}` 是章节版本。真实值由环境注入（`--knowledge k-notready=<真实知识 id>`），**契约文件里只出现契约自己的名字**，于是契约可以公开、运行事实留在环境。每条请求带 `Idempotency-Key`。
2. **身份写进契约，凭证从外面给。** 步骤声明 `actor: u-owner`，运行用 `--identity u-owner=<令牌>` 给。预检规则：一次运行里步骤声明的 actor 多于一个时，**每一个都必须给**——缺一个就不是「部分授权」，是两个不同的调用者被悄悄当成同一个人，那样跑出来的通过没有意义。只声明一个 actor 的规格允许退回 `--token`，F01 的 23 步全是一个 actor，既有命令行不受影响。
3. **可求值断言：一条 check = 一个 `path` + 一个算子 + 一句 `intent`。** 四个算子：`equals` / `length` / `keys` / `one_of`。`path` 是 JSON 指针，读的是响应里那个位置的真实值。中文一个字没丢：`intent` 是这条断言的意图，步骤的 `assertion` 是这一步的意图，都在报告里，但**都不参与求值**——报告另有一列写实际读到什么。
4. **期望值从契约已发布的响应例子里来，不从实现里抄。** 静态校验逐条把 check 绑到该步骤声明的 `response_example` 上：这条 `path` 在那个例子里必须存在、值必须一致。F22 的 6 条里 5 条这样绑住，第 6 条读的是本次运行捕获的绑定 id（例子给不出运行时的值），校验器把它记作「留给运行」而不是假装绑上了。这样期望值是从契约里来的，实现跑歪了是**发现**，不是**改期望**。
5. **报告：逐项判定，落在 `docs/08-本轮实施方案/T15-验证报告.json`。** 三个判定，各自说清自己那一层：`passed`；`failed` 带 `why`（先「期望 HTTP X，实际 HTTP Y」，再逐条「`<指针>`：`<期望…>`，实际 `<观察值>`」，读不到的位置写 `<该位置在响应里不存在>`）；`not_run` **带原因**，逐条给出是「没有请求定义」还是「没有步骤」。22 条场景在报告里全部出现，没有一条是留空的。
6. **同一输入两次 → 同样的字节。** 报告里没有任何时间戳、时长、随机值；序列化只有一处（`render_report`），**写盘和比对走的是它同一个函数**（否则「两次相同」可能只是两条不同的序列化路径碰巧一致）。实跑跑了三遍，都是 17829 字节。
7. **起点先于步骤：起点读不回来，那一步就不发。** 报告 `steps: []`、`verdict: failed`，并指出是哪个指针不一致。在一个不是声明起点的环境上跑出来的通过是假通过，所以宁可一步不发。
8. **失败路径是测出来的，不是设计出来的。** 三个用例：状态码不符（**每个**期望都被回答，不是只报第一个）；状态码对而拒绝码不对（正是下面那个缺口换到别处的形状）；起点不符短路（场景那一步根本没发出去）。
9. **F22 改指 `retrieveSources`，把 `startGeneration` 的差异登记成缺口，而不是把断言迁就实现。** 审查把这条分歧查清了：不是「拒绝形状不一致」，而是契约给 `startGeneration` 声明的**整条 422 分支在实现里不存在**——`grep -rn 422 internal/lingdoc/generation/` 零命中，那 5 个 422 例子（含 `asset_not_ready`）一条都发不出来；对已绑定但不可用的资料它答 403 `source_access_denied`，没有逐项原因。把断言改成 `source_access_denied` 会让契约失去发现问题的能力，所以改指能证的那条操作，把发现登记为 `T15-04-R1`——受影响的不止 F22：契约里 F03 的第 2 步同样落在一条不存在的分支上。**登记在报告里，不在提交信息里**——下一个读者要能看见它。
10. **F22 的授权维在本构建不可达，本票驱动的是可用性那一维。** 论证：绑定与读取用同一判定（`bindAsset` 与 evidence 网关都走 `kbReadChecker.CanReadKB`）；同租户读取无条件放行；跨租户的差异只来自租户级分享，而分享的有效权限按租户算、下限是 viewer——同一租户的两名成员不可能一放一拒；跨租户绑定答 404。所以 S7 是单参与者起点，**不需要第二个身份**。撤权族（移除分享、把租户移出组织）落地后 `not_authorized` 才有可达路径，#27 把它分给了 #35。
11. **契约 0.4.0 → 0.5.0。** F22 补上 `request` / `actor` / `checks`，新增起点 S7（一条可用 + 一条不可用资料），校验器新增 16 条反例（现共 38 条，全部被拒）。22 条场景仍全部通过静态校验。
12. **不新增依赖、不新增传输层。** 只用标准库；驱动、装载器、执行器共用同一个 `ProviderClient` 与同一条注入式 HTTP 路径。

## 边界（没验证到的，如实记下）

1. **F22 的授权维在本构建不可达**，本票驱动的是可用性那一维。论证见 §结论 10。这不是「没跑」，是「这条路径当前不存在」；证据是代码核对加实跑（同租户协作者在业主租户下读到 200，跨租户读取 403、绑定该知识 404）。等撤权族（#35）落地，`not_authorized` 才有可达路径。
2. **报告只到「HTTP 通道 + 契约里可求值的形状」这一层。** 模型质量、数据库副作用、DOCX 可编辑性不在任何通道能证的范围内，所以它们既不出现在通过里，也不出现在失败里。报告的 `verification_scope=http_smoke_only`、`provider_semantics_status=not_verified` 就是这句。
3. **只驱动了一条场景。** 另外 21 条在报告里逐条给出未跑的原因，但**未跑就是未跑**——本票不为它们作任何结论。补请求定义是后续票的事，写进契约不是省略。
4. **单环境、单身份。** 本机 build 出来的二进制、本机 dev 库、一个 owner 身份。云端环境、跨租户、多身份都没有跑过。
5. **起点里「不可用」的细分状态仍不可区分**（沿用 T15-03）：提供方对不可用资料只答 `not_ready`，`pending` / `processing` / `failed` / `replaced` 之间没有任何通道能区分，所以声明里那句更细的话进报告的 `unverified` 而不是冒充已验证。
6. **算子是四个**（`equals` / `length` / `keys` / `one_of`）。够表达 F22 这一条，也够表达「形状 + 词表」这一类断言；更复杂的断言（比如「集合无序相等」「把所有元素映射一遍」）要新增算子，本票不预造。
7. **「两次运行内容一致」不等于「环境没变」**：起点每次都新建项目，**项目 id 每次都不一样**，报告之所以逐字节相同，是因为动态 id 全部被换成了声明名。这是脱敏与可复现的交汇点，也是这条判据的适用范围——它证的是「同样的输入、同样的契约得到同样的结论」，不是「服务是幂等的」。这一点有专门的用例钉着（两次运行的替身 id 起始不同，断言 id **确实**不同且报告仍逐字节相同）：只比两次运行、而替身恰好发出同样的 id，是证明不了脱敏的。
8. **换行符随平台。** `render` 产出 LF，`write_report` 以文本模式写、在 Windows 上落成 CRLF；归一化后逐字符相同，进 git 的是 LF 那份。所以跨平台比字节要先归一化，比文本则直接相同。两个摘要都记在证据里，省得下一个读者拿错的那个去核对。
9. **`load_state.py` 里有一处沿用下来的未脱敏分支**：`compare()` 报「多出一条可用资料」时把那条例外的**真实知识 id** 写进 mismatch 的 `actual`（§证据与残留）。经由本票的驱动跑时，整份状态报告都过一遍 `redact`，不会漏；但**直接用装载器 CLI** 跑时，这句话会连着真实 id 打到 stderr 与报告里。触发条件是用一个已经有别的可用资料的项目重跑声明，本票跑的是新建项目，没有触发。属 T15-03 的范围，这里登记不改。
