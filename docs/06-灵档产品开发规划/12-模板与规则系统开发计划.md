# 模板与规则系统开发计划

> 面向对象：承接模板与规则系统实现的开发、产品与测试。  
> 系统契约依据：[模板与规则系统设计](11-模板与规则系统设计.md)。本文只讲**怎么实现、按什么顺序做、什么算完成**，不重新定义设计。  
> 业务输入来源：[模板与规则设计说明书](../07-灵档业务说明书/01-模板与规则设计说明书.md)（领域专家交付的章节结构、必要字段、术语表、规则说明书）。  
> 阅读前提：本文假设读者已知晓 `TemplateProfile`、`ValidationIssue` 的身份定义（`rule_id + target_ref + target_version`）与两级求值。

> **本文最关键的一条实施约束**
>
> **领域专家的规则说明书是求值引擎的输入契约，不是参考建议。** 开发不得在实现时自行增删规则、改变判定方或调整严重度——这些都属于业务决定。开发只实现"如何求值"，不决定"求值什么"。

## 1. 目标、边界与依赖

### 1.1 本计划要交付什么

| 交付物 | 判据 |
|---|---|
| 模板域 | 模板可版本化、可发布、可绑定到项目；规则集独立版本化并记录哈希 |
| 规则求值引擎 | 同一套规则集可对"项目当前内容"与"交付快照"两个对象求值，产出统一问题实体 |
| 规则求值器实现 | 规则说明书里全部 `computed` 规则可被求值；全部 `model` 规则可被调用 |
| 问题处置 | 误报删除与豁免两种语义、跨检查级别与判定方的作用域、完整审计 |
| 两级检查入口 | 写作期检查（随时可跑，不影响交付状态）与导出前检查（交付放行唯一依据） |
| 误报率统计 | 按规则统计误报比例，为严重度升级提供数据依据 |

### 1.2 不在本计划内

| 不交付 | 归属 |
|---|---|
| 新增或修改任何一条规则的内容 | 领域专家（经评审后交付） |
| 规则的可视化编辑器 | Beta 不做；专家交付结构化表格，开发实现（见 8.2） |
| 模板的多类别扩展 | 首批只做一类；扩展触发条件见 [顶层计划](../PROJECT_TOP_LEVEL_DEVELOPMENT_PLAN.md) |
| 章节正文的编辑与版本 | 已由 PR-302 / PR-303 覆盖 |
| 模型的选型与提示词工程细节 | [技术实施附件](../DEVELOPMENT_PLAN.md)；本文只约束输入输出契约 |

### 1.3 依赖关系

```text
业务侧（可并行）                 技术侧
────────────────────────────────────────────────
专家设计章节结构 ─┐
专家确定必要字段 ─┤
专家维护术语表   ─┼─→ 规则说明书 ─→ 规则实现（T3）
专家编写规则     ─┘                    ↑
                                      │
            T1 模板域 ─────────────────┤
            T2 求值引擎 ───────────────┤
                          T4 问题处置 ──┘
                                │
                          T5 两级检查入口
                                │
                          T6 误报统计
```

**关键路径判断**：T1、T2、T4 不依赖专家的规则内容，只依赖 `TEMPLATE_RULE_SYSTEM_DESIGN` 定义的契约，**可以立即开工**。T3 中 `computed` 类规则依赖专家先给出阈值与适用范围，`model` 类规则依赖专家给出正例。因此正确的并行方式是：**开发先建骨架（T1→T2→T4），专家同步产出规则说明书，节奏匹配点见第 7 节。**

## 2. 数据与契约

实体定义以 [设计文档](11-模板与规则系统设计.md) 第 4、5 节为准，此处只列实现所需的字段与约束。

### 2.1 模板域

```text
template_profile
  id
  grant_category      申报类别
  year
  version             模板版本
  sections            章节结构（有序数组）
  required_fields     必要字段（有序数组）
  ruleset_id          指向规则集（外键，不是内联）
  ruleset_hash        该规则集的内容哈希（发布时冗余一份，供导出审计与回放）
  status              draft | published | retired
  published_at / published_by

template_ruleset
  id
  ruleset_hash        规则集内容哈希（对外契约的一部分）
  version
  status
  created_at / created_by
```

**两个必须守住的约束**：

1. **规则集是独立实体，不是模板的内联字段。** `TemplateProfile` 只持有 `ruleset_id` 加一份发布时复制的 `ruleset_hash`，不内联规则本身。理由：设计文档 2.2 要求规则集可独立于模板结构演进，内联会让两者强行绑定。
2. **`ruleset_hash` 的计算范围必须稳定且可复现。** 建议对规则的规范化序列化（按 `rule_id` 排序，固定字段顺序）取哈希，不得包含时间戳、作者等非判定内容——否则同一套规则会算出不同哈希，回放与审计全部失效。

### 2.2 规则

```text
rule
  ruleset_id
  rule_id             跨版本稳定，问题身份的一部分
  name
  kind                computed | model
  severity            blocking | warning | info
  target_selector     按章节 / 字段 / 交付项选择作用对象
  evaluator_ref       kind=computed → 实现标识；kind=model → 检查项声明
  params              阈值、术语表引用、允许值域
```

**实现约束**：

| 约束 | 说明 |
|---|---|
| `rule_id` 跨版本稳定 | 模板升级后同一条规则必须保持同一 `rule_id`，否则用户此前对该误报的删除记录会丢失，问题会重新出现 |
| `params` 与 `evaluator_ref` 分离 | 阈值（如"不少于 800 字"）是 `params`，不是写死在实现里——否则专家调整阈值就要改代码 |
| `kind` 决定执行路径 | 不得在实现里靠 `evaluator_ref` 的前缀或类型判断隐式区分；`kind` 是显式契约 |

### 2.3 问题与处置

```text
validation_issue
  id
  rule_id              ┐
  target_ref           ├─ 三者共同构成问题身份
  target_version       ┘
  kind                 求值时的判定方快照（便于统计与审计，不作为身份的一部分）
  severity
  target_ref_type / check_level
  status               OPEN | RESOLVED | DISMISSED
  evidence             触发理由、建议动作、规则说明

issue_dismissal       （误报删除的有效记录）
  rule_id
  target_ref
  target_version
  ruleset_hash         删除生效时的规则集指纹 —— 见下方说明
  actor / reason / created_at

issue_waiver          （豁免记录，仅 warning / info）
  issue_id
  actor / reason / risk_list / created_at
```

> **删除记录为何要绑定 `ruleset_hash`**
>
> 设计文档 5.3 规定删除"只对当前规则与目标版本生效"。若规则本身改了（同一 `rule_id`，但判定条件变化），旧删除不应继续生效——**判定标准已变，用户需要在新标准下重新判断**。不绑定规则集版本，会导致"规则收紧了，但历史删除仍然静音"这一危险状态。

**不变量**：

- 同一问题身份在任一求值结果中最多一条 `OPEN` 记录；
- `target_version` 变化后，对应身份的所有删除记录失效；
- `severity = blocking` 的问题不得写入 `issue_waiver`（阻断级不可豁免）。

## 3. 任务分解

### T1 模板域

| 项 | 内容 |
|---|---|
| 交付 | 上述实体、仓储、发布接口、项目绑定 |
| 关键实现点 | 规则集独立存取；`ruleset_hash` 的规范化计算；模板版本切换时不允许已开工项目静默换模板 |
| 验证 | 规则集哈希回放稳定（同内容多次计算一致、字段顺序变化不影响哈希）；`rule_id` 跨版本稳定性测试；换模板时同名字段按名保留、不静默清空的测试 |
| 依赖 | 无（可立即开工） |

### T2 求值引擎

| 项 | 内容 |
|---|---|
| 交付 | `RunTemplateCheck(对象, ruleset, level) -> ValidationIssue[]` |
| 关键实现点 | 两级共用同一求值流程，仅对象不同；`computed` 与 `model` 走统一调度；规则求值不得依赖模型可用 |
| 验证 | 同一套规则对两类对象求值；模型不可用时 `computed` 仍完整产出、`model` 标为未求值 |
| 依赖 | T1 |

**必须显式处理的一个状态**：模型调用失败时，`model` 类规则**不得默认为通过**，必须标记为"未求值"。否则一次模型超时就会表现为"所有模型类问题都已解决"，是静默失效。

### T3 规则求值器与检查项

| 项 | 内容 |
|---|---|
| 交付 | 规则说明书中每条规则的实现 |
| 关键实现点 | 逐条实现，**每条规则必须通过专家提供的正例**；`model` 类规则的检查项声明需能表达正例所描述的情形 |
| 验证 | 正例触发测试 + 反例不误报测试，逐条通过 |
| 依赖 | T2 + 专家交付的规则说明书 |

**交付节奏建议**：不必等全部规则写齐。按严重度与类型分批——`computed` 类先行（它们不依赖长尾语义判断），`model` 类分批交付并逐批评估误报。

### T4 问题处置

| 项 | 内容 |
|---|---|
| 交付 | 误报删除、豁免、作用域判定、审计 |
| 关键实现点 | 删除的跨检查级别与跨判定方匹配（见 2.3）；阻断级拒绝豁免；删除需理由与权限校验 |
| 验证 | 见第 6 节 F3 组 |
| 依赖 | T2（需要问题实体） |

### T5 两级检查入口

| 项 | 内容 |
|---|---|
| 交付 | 写作期检查（随时可跑，不改变交付状态）与导出前检查（阻断交付） |
| 关键实现点 | 写作期检查**不得改写交付状态**；导出前检查是放行的唯一依据，不得另写一套规则 |
| 验证 | 见第 6 节 F4 组 |
| 依赖 | T4 |

### T6 误报率统计

| 项 | 内容 |
|---|---|
| 交付 | 按规则统计：触发次数、被删除数、被豁免数、误报比例 |
| 关键实现点 | 这条数据是设计说明书第 8.2 节"升级严重度"的依据，必须可导出给专家评审使用 |
| 验证 | 统计与实际处置记录一致；能按规则与时间段导出 |
| 依赖 | T4 |

## 4. 接口契约

### 4.1 求值入口

```text
RunTemplateCheck(target, ruleset, level) -> ValidationIssue[]

target   : Project（项目当前内容） | ReleaseSnapshot（冻结快照）
ruleset  : 版本化的规则集
level    : content | release

返回：问题清单。同一身份最多一条 OPEN。
      level=content 时不得产生任何跨域事件、不得改写交付状态。
```

### 4.2 处置入口

```text
DismissValidationIssue(issue_identity, actor, reason) -> ValidationIssue
   前置：问题为 OPEN；调用者持相应权限（阻断级仅 Owner / Reviewer）
   效果：写入 issue_dismissal，问题置 DISMISSED
   范围：rule_id + target_ref + target_version + ruleset_hash

WaiveValidationIssue(issue_id, actor, reason, risk_list) -> ValidationIssue
   前置：severity 为 warning 或 info（阻断级拒绝）
   效果：写入 issue_waiver，记录负责人、理由与风险清单
```

### 4.3 与专家交付物的对接

开发从 `TEMPLATE_RULE_DESIGN_GUIDE` 第 6.4 节的规则清单读取，逐行映射：

| 说明书填写项 | 落到哪 |
|---|---|
| ① 规则编号 | `rule.rule_id` |
| ② 规则名称 | `rule.name` |
| ③ 判定方式（能算出来 / 需例判断） | `rule.kind` = `computed` / `model` |
| ④ 严重度 | `rule.severity` |
| ⑤ 适用对象 | `rule.target_selector` |
| ⑥ 正例与反例 | 测试用例（**必测**，不是可选） |
| ⑦ 触发场景 | 该规则是否进入 `content` / `release` 求值集合 |

**除 `params` 中的阈值外，开发不得填写或修改以上任何一列。**

## 6. 验证清单

### F1 组：模板与规则集

- [ ] 同一规则集内容多次计算哈希一致；字段顺序变化不影响结果
- [ ] 模板版本升级后，未改动的规则保持同一 `rule_id`
- [ ] 换模板时同名字段按名保留，原模板独有字段标为"模板不再需要"，新增字段标为"待填"；**无任何已填内容被清空**
- [ ] 规则集内容改变时 `ruleset_hash` 变化，且该变化被记录进交付审计

### F2 组：求值

- [ ] 专家提供的每条正例都能触发对应问题
- [ ] 专家提供的反例不产生误报
- [ ] 模型不可用时，`computed` 规则完整产出，`model` 规则标为未求值（**不得默认通过**）
- [ ] 同一套规则对项目当前内容与交付快照求值，结论一致（对象内容相同时）

### F3 组：处置作用域

- [ ] 在写作期删除的问题，导出前不重复报出（目标对象版本未变）
- [ ] 目标对象产生新版本后，被删除的问题重新出现
- [ ] 规则集内容变化后，基于旧规则集的删除记录失效
- [ ] 阻断级问题不可豁免，但可被判误报删除
- [ ] 删除阻断级问题的权限仅 `Owner` / `Reviewer`
- [ ] 每次处置均记录行为人、理由、规则、判定方、目标版本并进入审计

### F4 组：两级检查

- [ ] 写作期检查不产生跨域事件、不改变交付状态
- [ ] 导出前存在未关闭阻断问题时，系统不生成可导出状态
- [ ] 导出前检查复用同一求值器（代码层面无第二套规则实现）

### F5 组：审计与统计

- [ ] 导出记录包含 `TemplateVersion` 与 `ruleset_hash`
- [ ] 误报率统计与实际处置记录一致，可按规则与时间段导出

## 7. 与专家工作的节奏匹配

```text
时间  专家（业务侧）                    开发（技术侧）
──────────────────────────────────────────────────────────
 1    设计章节结构、必要字段、术语表      T1 模板域、T2 求值引擎骨架
 2    编写首批 computed 类规则（阈值）    T4 问题处置
 3    编写 model 类规则 + 正例            F2 首批规则实现与联调
 4    参与正例/反例验证评审               F3 两级检查
 5    基于误报统计调整规则措辞            F4 误报统计
```

**两个必须存在的对接点**：

1. **第 3 步末尾的验证评审**——专家给的正例必须逐条跑通才算该规则交付完成。这是唯一的验收关口，不能用"看起来差不多"代替。
2. **第 5 步的误报复盘**——误报率数据必须回到专家手里，否则规则的严重度永远不会被正确调整。这一条容易在交付后被忽略，需要在流程上固定。

## 8. 风险与决策

### 8.1 已识别风险

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 专家交付的规则无法实现 | 规则写成了"举不出例子"的表述（如"论证是否充分"） | 在验证评审时退回，按设计说明书 2.1 的要求重新表述。**这是流程问题不是技术问题**，开发不得自行解释规则意图 |
| `model` 类规则误报率高 | 检查项声明过于宽泛，或正例不够具体 | 默认从 warning 起步；按 T6 统计迭代；长期误报的降为 info 或下线 |
| 规则集版本与模板版本漂移 | 两者独立变更未联动 | 严格执行 2.1：规则集变更必须使模板版本升级；导出同时记录两者 |
| 两级求值结论不一致 | 问题身份未包含版本 | 严格实现 2.3 的身份定义；`target_version` 必填，禁止空值 |
| 规则维护成本失控 | 多类别并行 | 首批只做一类；扩展须先有单类别的完整运行数据（见 [顶层计划](../PROJECT_TOP_LEVEL_DEVELOPMENT_PLAN.md) 扩展触发条件） |

### 8.2 待确认决策

| 决策 | 说明 | 建议 |
|---|---|---|
| 规则编辑器的形态 | 当前设计是"专家交付表格、开发实现"。若未来规则数量大、调整频繁，需要提供配置界面 | Beta 不做。先看实际调整频次——若一个申报周期内规则改动超过 5 次，再评估配置化 |
| 规则的存储形态 | 规则集存数据库还是存代码仓库的声明文件 | 建议声明文件（便于评审与 diff），运行时加载入数据库；具体形态在 F1 确定 |
| `model` 类规则的求值时机 | 写作期检查是否每次都跑模型类规则（成本） | 建议写作期对 `model` 类规则做节流（按内容变化或按用户主动触发），导出前必须全量跑 |
| 规则集哈希的算法与范围 | 影响回放与审计的准确性 | 建议对规范化序列化取 SHA-256；范围只含判定相关内容。在 F1 固化 |
