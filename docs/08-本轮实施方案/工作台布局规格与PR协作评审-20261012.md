# 工作台布局规格与 PR 协作评审

状态：**设计提案，未选定正式布局、未接真实接口、不得据此自动合并或发布。**

本提案把 #105 的三套合成交互原型与 Kimi·LingDoc 专职分支的独立建议收敛为可评审、可接线的规格。Codex·LingDoc 专属分支负责修订与验证；Kimi·LingDoc 专职分支负责独立复核。最终产品选择由 gong 决定，仓库合并仍由团队按既有流程审查。

## 1. 用户结果与范围

用户不再沿一根长竖列寻找研究条件、来源、AI、确认和导出按钮。进入项目后能立即找到章节和正文；查证和写作互不打断；改写比较有足够宽度；保存失败、版本冲突、待核阻断与下载入口可见。

推荐一个研究工作台，共用一份正文和工作状态：

| 工作状态 | 结构与入口 | 不变的状态 |
| --- | --- | --- |
| 研究（默认候选） | 章节目录 / 正文 / 来源、AI、待核辅助标签 | 项目、章节、草稿、保存结果、引用、候选 |
| 专注 | 收起辅助区，按需收起目录；明确返回工作台入口 | 当前章节、保存状态、待核数量持续可见 |
| 审阅 | 从候选摘要打开宽对照，原文与候选并排；结束返回原编辑位置 | 同一个候选与原文基线，不复制正文，不自动采纳 |

不维护三套 API、三个编辑器或三个独立 Workspace。这里的 A/B/C 是布局评审名称，不是 T01–T16 的领域/人员分组。现有 B 是修改审阅，C 是专注写作；选择布局不等于已有富文本、文献库、公式或引文样式。首版沿用 textarea、引用标记及现有接口，不新增编辑器依赖。

## 2. 用户路径与信息归属

```text
进入项目 → 选章节 → 写作/保存
                    ↔ 来源回看、用途与限制
                    → AI 候选 → 展开对照 → 采纳/放弃
                    → 逐项待核理由 → 提交必要版本 → 确认
顶部交付入口 → 检查 → 冻结 → 生成 DOCX → 下载/交付历史
```

顶部保留项目名称、当前章节、保存状态、待核数量以及写作/资料/核查/交付入口。独立的“创建/选择项目”入口不长期占去正文旁半屏。

- 左侧：章节目录、章节状态、研究条件/模板入口；研究条件与模板编辑用明确面板，不堆在正文上方。
- 中间：正文、引用用途、选段工具、必要的提交/确认动作及具体阻断说明。长正文只有明确的编辑滚动区；页面有可发现的辅助区滚动，避免一项高度错误锁死全页。
- 右侧：来源、AI、待核标签。同一时间通常显示一个标签，不声称三者全部“零切换”。来源回看不把正文带离当前章节；候选摘要提供“展开对照”。
- 交付：沿用 DeliveryPanel 的检查/处置/冻结/导出/历史语义。生成中、失败、成功可区分；成功后下载可见，不能让用户自行猜测还要刷新哪一块。

“研究为默认”是设计判断，不是已证明来源核对为最高频动作。真实试用允许把专注设为个人偏好，不改变数据和任务状态。

## 3. 尺寸、缩放与可操作性

尺寸判断使用**工作区实际可用宽度**，扣除 WeKnora 外层导航；不能只根据屏幕宽度认定正文足够宽。以下是首版待测约束，不是已验证像素规格：

- 默认章节栏约 180–220px，辅助栏约 300–360px；正文获得剩余宽度。正文实际可读区域不足约 560px 时，收起辅助区，再按需收起目录，不把字号压小补偿。
- 三栏所需空间不足时，辅助区按需展开并可关闭；折叠后仍有来源/AI/待核入口与状态。手机和网页放大时不可出现横向拖动才能找到动作的情况。
- 原文/候选真正双栏比较需要展开主区域；约 300px 的辅助栏只能承载摘要，不能再次硬分两栏。比较空间不足时用单栏原文/候选切换与差异标注，保留完整原文入口。
- 专注状态不把正文无限横向拉长。保留适宜阅读宽度；不靠巨量留白和不可见导航制造“专注”。
- 抽屉/浮层必须有可见关闭入口、键盘可操作、焦点进入与返回；打开/关闭不能丢输入或使页面永久不能滚动。基本交互列首版必做，装饰动画和密度微调可后做。
- 原型现状为 1100px 缩栏、800px 转浮层；它不是正式产品验收，也不是本规格断点已实现。

## 4. 状态和组件责任

Workspace 或同一会话级 composable 持有项目/章节选择、正文草稿、研究条件/模板草稿、待核理由、工作副本基线、幂等键、保存定时器和任务状态。展示组件用 props/emits；模式只改变可见性和尺寸，不自行复制请求或重新初始化草稿。

| 状态 | 布局切换必须保证 | 验证反例 |
| --- | --- | --- |
| 未保存、保存中、保存失败 | 保留输入、未保存保护与可见保存结果 | 900ms 内切状态；保存失败后回到写作 |
| 已保存工作副本但未提交 | 区分已保存与正式版本，不制造错误离页警告 | 已保存草稿进入交付再返回 |
| 未确认待核理由 | 切标签/章节不丢理由，不把默认空白当已填写 | 写理由未确认、切标签、尝试离页 |
| 版本冲突 | 保留本地输入，不暗中覆盖，不以重新读取覆盖本地草稿 | 双窗口读取旧基线，第二次保存 409 |
| 候选过期 | 继续按原文基线/来源规则拒绝，不因重建 UI 变成可采纳 | 生成后人工修改原文再打开对照 |
| 采纳成功而读回失败 | 已采纳状态持续存在，重试仅读取 | 写入成功后 GET 失败，再切模式返回 |
| 导出/冻结已成功而列表读回失败 | 不误报原动作失败，不自动重复写入 | 成功响应之后模拟历史读取失败 |

**只把草稿 ref 留在父级不足以证明安全。**采纳弹窗/交付面板也持有操作状态。不要因辅助区的 v-if 卸载而重置“已采纳、只重读”的状态；需要保持相应组件或将操作结果提升到合适的状态持有者，并覆盖上述失败反例。对焦点、选段、光标和滚动位置也要验证；保留文字不等于保留编辑上下文。

generation 与 selected-rewrite 的已有持久化键保持兼容；若需要迁移，单独写迁移说明并验证旧数据读取。存储中存在 runId 不能当作任务已成功或最新权限证明。布局不降低当前来源授权、版本、确认与下载核验。

## 5. 接线切片与基线

| 切片 | 交付 | 完成条件 |
| --- | --- | --- |
| 一：信息结构 | 外壳、目录、正文、辅助标签、交付入口、基本响应式 | 现有功能可发现；缩放/滚动/关闭可用；未保存输入不丢 |
| 二：共享状态 | 当前保存、候选、引用、待核、确认和交付状态接入 | 第 4 节失败反例有组件/浏览器证据，不能只跑正常路径 |
| 三：对照与专注 | 展开对照、专注偏好、退出后返回编辑上下文 | 不复制正文/请求，采纳/放弃及失败恢复正确 |

## 6. 在 PR 上协作

评审以提交 SHA 为准，Kimi·LingDoc 专职分支在 PR 的 Conversation 或行内评论中具名提交：观察事实、文件/位置、复现或推断依据、阻断/非阻断、建议修改。一次集中评审；作者逐项回复“已改及对应提交/证据”或“保留及理由”，不为凑回执重复审查。

双方当前可能共用 Lees-42 GitHub 登录。不得把同账号的 COMMENTED 包装成人类批准或独立 GitHub 身份；评论正文区分 Kimi·LingDoc 专职分支与 Codex·LingDoc 专属分支。不请求 Kimi 以作者账号 APPROVE 自己的 PR。团队成员的正式批准、gong 的选型和实际 merge 是另三件事。

若 Kimi 无法写 GitHub，但已产生可核验的新评审，可由作者原样代贴，标明代贴、真实出具方、所审 SHA 与来源；不得替 Kimi 编写意见。本提案来源中的历史 Kimi 报告不等于新 PR 已审。

门铃只用于传达 PR 链接、SHA 和边界，评审与改动结果优先留在 PR。发布请求/评论不等于具名已读，GitHub 活动也不会自动唤醒本地智能体。若通道未接受，只记录实际阻塞；不冒称双方正在持续协作，不换号重复催办。

## 7. 验收及本提案证据

用户最终集中验收六步：进项目找到入口；写作切专注仍保留编辑上下文；正文旁回看来源且放大时能关闭/滚动；展开原文/候选后采纳或放弃；直接看到确认阻断原因并处理；进入交付生成、下载、打开 DOCX。

施工浏览器检查至少覆盖：宽屏、笔记本和窄屏（例如 1440/1280/390px）；浏览器 125%/150% 放大；键盘开关辅助区；保存中/失败与 409；已采纳读回失败再切模式；来源受限/候选过期；交付历史读取失败与下载入口。测试要记录实际工作区宽度，不只截图整个屏幕。
