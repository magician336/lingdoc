## 0. 一句话结论

受控执行路径已经落地并且**在离线测试里真实生效**：Qwen 专用 profile 用 token 与调用次数做闸门，闸门真的走在生成调用路径上，账本记 provider 实测 token、没有 usage 就记 `unavailable`（**不可核实**）、费用列记「不适用」而不是 0，失败即停不重试。

**现场实测已消解三项**（管理会话的只读探针）：① 真实库存量值是**明文**（`SYSTEM_AES_KEY` 长度 0 ⇒ 写入端不加密）⇒ 明文行照常可用，最小可行路径 = 隔离库加密行 + 进程内注入同一把 key、**主仓零改动**（§2.4/§2.5）；② 主库有一行 `qwen3.8-flash` 但 **`provider` 存的是 `generic`** ⇒ **这是配置口径问题、不是代码缺陷**，受控执行前须由部署侧在**隔离库**把 `provider` **字面**写为 `aliyun`，**主库一律只读**（§1.5）；③ 隔离库**没有** Qwen KnowledgeQA 行 ⇒ 选择器会 fail closed（安全但跑不通）。

### 1.2 判定规则（Qwen 独立，不复用 DeepSeek 的任何一条）

`qwenModelApproved` 依次要求：

1. `model.Type == types.ModelTypeKnowledgeQA`（**按类型判定，不按名字**）；
2. `model.Source == remote` 且 `model.Status == active`；
3. `model.Name == acceptancebudget.QwenChatModel`（`qwen3.8-flash`，获准清单见 `internal/models/acceptancebudget/qwen_token_budget.go:31`）；
4. `model.Parameters.Provider == "aliyun"`（**显式字段校验**）；
5. `base_url` 在获准百炼端点白名单内（`internal/models/acceptancebudget/qwen_token_budget.go:157` `IsApprovedQwenBaseURL`，白名单 `:90`）。

**不复用 DeepSeek 的部分（有意为之）**：

- 不要求 DeepSeek 的 provider 白名单（`provider == "generic"`）；
- 不要求 DeepSeek 的端点（`api.deepseek.com`）；
- **不要求** `thinking_control = thinking_type`（那是 DeepSeek 的请求形态，不是 Qwen 的）；
- 两条路径各有各的判定函数，Qwen 获准**不依赖** DeepSeek 规则。

**为什么 provider 必须显式校验**：`provider.DetectProvider`（`internal/models/provider/provider.go:225`）只认 `dashscope.aliyuncs.com`，区域 MaaS 工作空间端点（`*.cn-beijing.maas.aliyuncs.com`）会被判成 `generic` ⇒ 用探测结果当规则会批准错的 provider。

### 1.5 ⚠️ 显式前置条件：获准行的 `parameters.provider` 必须**字面**为 `aliyun`

**实测事实（管理会话的只读探针，主库 `WeKnora` 与隔离库 `weknora_iso`，仅 SELECT、零写入）：**

⇒ **只在隔离库新增行时由部署侧直接写 `aliyun`；主库 `WeKnora` 一律只读**，**不得为本次受控执行修改主库任何行**。

#### 清单 B —— **响应后才能核实**（只能对账与标记，**不能阻止**已经发生的调用）

| # | 指标 | 取得方式 | 缺失/超限时的表现 |

| B2 | **`finish_reason`** | `response.FinishReason` | `length` ⇒ 记 `incomplete`、运行失败、**不自动续写**（`TestGenerationHostModelMarksLengthFinishReasonIncomplete`） |
| B3 | **实际发生的请求数** | provider 侧请求记录 ＋ 服务端出站日志 ＋ 账本行数，**三方交叉** | 任一方多出一次 ⇒ 立即停止并报告（§12） |

| B5 | **费用** | —— | Qwen 口径**不适用/未核算**（`cost_basis=not_applicable`）；DB 行的 0 **不得单独引用**（§10 第 1b 条） |
| B6 | 实际输出 token 是否超限、合计是否超限 | `completeUsage` 的检查 | **只是记账与标记**（`limit_violation` + 冻结账本），**不能阻止已发生的调用** |

⚠️ **明确声明**：**响应后的检查不能阻止已经发生的超额调用。** 响应后能做的只有两件事：把记录标成 `limit_violation`、冻结账本。真正的拦截全部发生在**请求发出之前**（清单 A），证据是「provider 请求数 = 0 / 仍为 1」的断言，而不是「事后拒绝记账」。

⚠️ **输入上界的量纲与偏差方向（不是精确 token 计数）**：

- **量纲是 UTF-8 字节**，不是 token。`acceptanceInputUpperBound` = `len(json.Marshal(messages)) + 1024`（`generation_acceptance_budget.go`）。
- **不变式**：UTF-8 下一个 token 至少占 1 字节 ⇒ **字节数 ≥ token 数**，恒成立。所以这个上界**永远不会低估** token 数 ⇒ 请求前闸门**不可能放行一个超限请求**；代价是它**可能拒掉一个其实装得下的请求**。
- **偏差方向按语言**（以 16,000 的上限为例）：
  - **中文**：1 字 ≈ 3 字节，token 数 ≈ 字数 ⇒ 字节上界约为 token 数的 **3 倍** ⇒ 实际允许的输入约 **5,300 字**（比「16,000 token」严）。
  - **英文**：1 token ≈ 4 字符 ≈ 4 字节 ⇒ 字节上界约为 token 数的 **4 倍** ⇒ 实际允许的输入约 **4,000 token**（比「16,000 token」严）。
  - ⇒ **两种语言都偏严（保守），不存在「偏松」的方向**：用字节数当 token 上界只会把闸门收紧。⚠️ 若把「16,000」理解为「16,000 **token**」，当前实现的实际允许量明显更小；这是**口径声明**问题，不是安全漏洞（安全侧）。**请裁定「16,000」到底指 token 还是字节**（见 §11.3 第 6 条）。
- **替代口径与代价（若要精确 token）**：本仓**没有** Qwen 分词器；引入本地 tokenizer 需要 ① 新增依赖（如 `tiktoken`，但它**不是** Qwen 的分词器，对 `qwen3.8-flash` 的计数只是近似）② 附带模型分词器文件（数 MB）③ 进程启动/首次调用的一次性加载成本 ⇒ **本轮不引入**（不报告就加依赖是不允许的）。当前选择的理由：**请求前用保守上界拦、请求后用 provider 回报的真实 usage 对账**（`usage_status=reported`），两头互补。
- **provider 侧看不见的部分**：字节数看不到 provider 自己加的 chat template 与控制 token，由固定的 1024 余量覆盖；真实用量仍以 provider 回报为准，**响应后核实**。

- `internal/lingdoc/generation/service.go:557-561`：模型失败 ⇒ `Repository.Fail(...)` ⇒ **`return failed, nil`** ⇒ handler 看不到 error。
- `internal/lingdoc/generation/tasks.go:130-146`：handler 只在 `err != nil` 时才考虑重试；`err == nil` ⇒ 直接 ACK（`return nil`）。

## 8.5 三个未决事项：是否构成**当前实现的硬依赖**

| 未决事项 | 是不是当前实现的硬依赖 | 理由 |
|---|---|---|
| **`SYSTEM_AES_KEY` 轮换策略** | **不是**（可独立处理） | 实现的代码只要求一件事：**当前这把 key 能解开那一行密文**。轮换的**策略**（多久轮一次、要不要重加密旧密文、换钥匙的操作流程）属于运维约定，代码里没有、也不需要它。本轮顺带把「解不开」从「静默置空」改成「构造客户端前 fail closed」（`internal/application/service/model.go:642`），所以**轮换期间的行为是失败而不是带空 key 出网** —— 这是安全方向的改变，不是对轮换策略的依赖。⇒ **单独记录，不做部署变更。** 现场只需确认「这一行的密文能被当前 key 解开」（只读探针，§11）。 |
| **4xx/5xx 落库区分** | **不是**（可独立处理） | 本实现对失败的处理只依赖一件事：**调用失败 ⇒ 运行失败 ⇒ 不重试 ⇒ 证据留账**（`service.go:561` 返回 `(failed,nil)`；账本记 `outcome_unknown` 并 blocked；DB 行 `status=failed`）。这与「这次是 4xx 还是 5xx」无关。4xx/5xx 的**落库粒度**是另一件事（更细的失败分类要落到库里供对账用），可以单独做，不影响本实现的任何断言。⚠️ 现状提示：`taskFailureRetryable`（`internal/lingdoc/generation/tasks.go:79`）是从**错误消息文本**里正则出 HTTP 状态码的（既有实现，PR #521），不是从库里读的 —— 所以 4xx/5xx 落库区分**不会**改变现在的重试判定。 |
| **全局默认模型选择（`is_default`）** | **不是**（本实现已绕开） | 受控路径在 `generation.go:438-441` 用 **profile 的显式选择**覆盖了 `defaultGenerationModel`（`generation.go:629`），**不读、也不改**默认位；Qwen 行不存在就 fail closed，不回落默认模型（§1.4 + 2 个测试）。⇒ **本实现不需要动 `is_default`；本轮也没动。** 「是否要动默认位」作为开放问题记录在 §1.4：若将来有人要动，影响范围已列出，需要单独裁定 + 单独票。 |

⇒ 三项**都不构成本实现的硬依赖**，本轮**不做任何部署/配置变更**，只在此记录。

## 12. 真实调用的授权边界与停止条件（用户预授权原文要点）

**授权范围**

模型选择不符、凭据异常、非预期出网、闸门失效、意外第二次请求、请求失败 ⇒ **立即停止，不重试、不切 provider、不追加调用**。

- **不得为补齐用量而自动发起第二次真实请求**；
