## 统一接线

Service 装配字段为 `impactRules`、`impactPreflight`、`runtimeRecovery`、`runtimeMode`。提供相应 setter；没有实际规则、Preflight 或恢复 checker 时阻断动作，不能由请求参数自称 PASS。

ChangeSet 创建/重评保存 `AssessChangeImpact`；apply 写前执行 `ValidateChangeImpactAssessment`，写后在同一事务执行 `CommitChangeImpactTasks`。审计、任务、revision、handoff 和 replay record 的任一持久化失败必须整笔回滚。

`G3SourceSensitiveOperation` 和 `G3OperationSourceIDs` 供现有统一 operation 使用：策略 IO 在事务外，最终事务重读项目和 exact source IDs / assessment basis。普通无来源动作不触发该 helper，也不递归调用领域动作。

`RuntimeGate` 必须同时用于工作区新写、生成、交付检查、冻结、导出和下载。事件应来自 `RecordRuntimeOperationContext` / `ObserveRuntime`，携带真实 correlation / causation / request / task / version / runtime mode；手工上报的 `origin=reported` 不能成为真实试用事件，也不触发自动暂停。

`AcknowledgeImpactPreflight` 的公开输入是 `proof_id`。实际 checker 重读服务端 check receipt（`ProofKind=check_receipt`）或仍当前的已存在 snapshot。检查回执放 `lingdoc_g6_records`、`kind=preflight_check`、`record_key=checkID`，必须含 `source_ids`。实际流程为：交付检查 → 回执闭环 → 稳定化 → 冻结 → 导出。旧快照不能因为操作回退而被强改为 current。

纯控制和任务处置使用各自 record.Version 的 CAS。统一装配必须防止这些元数据动作推进正式版本后，使刚生成的检查回执或恢复使用的快照立即失效而形成循环。

## 2026-10-18 G3-198.1（#199）版本化 DependencyEdge 与 confirmed 影响解析

上文 2026-10-14 的记录保留原样，本节只描述本批增量。

### 依赖边生命周期与人工结论

`DependencyEdge` 持久化 source/target（`ObjectVersionRef`，含 kind 与版本坐标）、relation、action、origin、reason、可选 confidence、actor_id、version 与 created_at/updated_at。`origin` 决定初始状态：`ai` 落为 `suggested`，`user`/`rule` 直接落为 `confirmed`；两者都由服务端决定，客户端不再本地推断。

候选关系支持三种人工决定，`DependencyDecisionInput` 增加三个**可选**字段 `relation`/`action`/`confidence`（指针 + `omitempty`，旧的 confirm/reject 请求体逐字节兼容）：

- `confirm` → `confirmed`，`version+1`；
- `reject` → `rejected`，`version+1`；
- `modify` → 仍为 `confirmed`，改写 relation/action/confidence 并记录被替换掉的旧元组到 `superseded_relation`/`superseded_action`，`version+1`，审计 `dependency.modify`。

`modify` 必须至少给出一个字段，否则 `ErrInvalidRequest`；`confirm`/`reject` 携带这些字段同样 `ErrInvalidRequest`。决定只接受 `status == "suggested"` 的边，否则 `ErrInvalidState`；`expected_version` 不匹配返回 `ErrVersionConflict`。机器主体对非 `ai` 建边和任何决定都返回 `ErrHumanDecisionRequired`。

**人工结论不得被后续 AI 运行覆盖**，且这一条按"覆盖"而不是"同源对再加一条候选"定义：AI 复用同 (source,target,relation,action) 元组时返回既有边；AI 重新提出被 `modify` 替换掉的旧元组时返回 `ErrDependencyDecided`（HTTP 409 `dependency_decided`）；对同一对引入不同 action 的新候选仍然允许，这与既有的多动作图行为一致。

### suggested 与 confirmed 的语义

`suggested` 边在影响解析中只产生 `certainty="possible"`，不入队继续遍历、不进 `requiredObjects`，因此不能独立阻断或放行交付；`confirmed` 边产生 `definite` 并参与 BFS 多跳传播。循环由 `visited` 集合截断，同一 (target,action,certainty) 合并为一条 impact 并保留全部 causes。

### 授权覆盖范围修正

`GetImpactAssessment` 原先只对 `result.Objects` 做来源复核，而 `Edges`/`Impacts` 会引用不在 `Objects` 内的对象（suggested 边的目标按设计就不是 required object）。这构成真实泄露：受限对象不出现在 `Objects`，却仍由 `Edges` 与 `Impacts` 的 ref 与 cause 暴露。现在复核覆盖响应暴露的**全部** ref（Objects、Edges 两端、Impacts 目标与 causes 来源）。回归证据见 `TestImpactAssessmentHidesUnauthorizedEdgeEndpoints`：临时移除该修复时该用例失败，并打印出被撤销来源章节的 ID。

### 契约与客户端

`contracts/openapi.json` 补齐 `/projects/{projectId}/dependencies`（GET/POST）与 `/projects/{projectId}/dependencies/{edgeId}/decision`（POST），以及 `ObjectVersionRef`、`DependencyEdge`、`DependencyEdgeInput`、`DependencyDecisionInput` 四个 schema，并在 `status` 上写明"由服务端决定、suggested 不进入 required objects"。前端 `mainlineChanges.ts` 抽出 `DependencyOrigin`/`DependencyStatus`/`DependencyDecision`，`decideDependency` 改用 `DependencyDecisionInput`，补上时间戳与 superseded 字段。
