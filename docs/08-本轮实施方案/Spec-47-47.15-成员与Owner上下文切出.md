### Q1 — membership 怎么跑操作管道？ → **甲：导出通用机制口**

**框架依据**
- **ch06 通用机制优先**：管道是工作区**所有**写操作的通用机制（53 个调用点、20+ 操作名），不是成员操作的专用件。段三已建的 36 个**上下文**窄口切的是「哪些用例」；再切一个「成员专用 runner」等于同一机制出现两个抽象层级，ch17 一致性不成立。
- **ch04 深度 = 功能收益/接口成本**：1 个方法隐藏幂等 + 哈希 + 重放 + 授权 + 审计 + 事务 + G1 溯源 + 人类决策门 + 幂等记录。
- **ch07 层次**：membership 是高层用户语义，管道是低层机制。高层拿到 13 个接缝自己拼 = ch04 反模式「透传方法」。
- **ch11 两次设计**：甲/乙/丙按「变化扩散」比较——甲 0 份管道知识，丙每切一个上下文多一份，乙 2 份。

**配套条件**
1. 导出口必须**非泛型**（Go 接口不能有泛型方法）。
2. 泛型不丢：导出 `core.MutationPort[T]`（泛型**函数**可导出，只有泛型*方法*不行），错误语义 `ErrInvalidState` 逐字不变。
3. 读路径另配 `core.WorkspaceAuthorizer`（2 方法）；`core.Repository`（已导出，1 方法）负责开事务。
4. 管道协议词汇必须导出：操作名常量、输出种类、`operationStatus`、`AuthorizationRequest` 构造器。

**残留风险 / 变化炸弹**
- **炸弹 1（已排除）**：`operationResult[T].Value` 擦成 `any` 是否安全。**已实测**：`operationcore` 的接缝签名**本来就是 `any`**——`Write func(...) (value any, output string, status int, err error)`，下游 `StoreReverseSources` / `StoreProvenance` / `AfterWrite` 全收 `any`，管道对 value **只做 `json.Marshal`**，无类型分派。⇒ 擦除零成本，JSON 逐字不变。
- **炸弹 2**：`OperationRunner` 成了 workspacecore 的长期公共承诺，未来每个上下文都要用。必须用**现有 53 个调用点**检验通用性（ch06），不能只按成员操作设计。
- **炸弹 3**：新口叫 `WorkspaceAuthorizer`，与段三已有的 `core.ProjectAuthorizer` / `core.CapabilityAuthorizer` 名字相近但语义不同（ch14 精确命名风险），必须区分命名。

### 接口声明（先写接口，评论先于实现）

```go
// OperationRunner runs one workspace operation under the shared pipeline.
//
// The pipeline owns the order of the steps: identity and request hash, the
// idempotency ledger, replay, authorization, source recheck, the human
// decision gate, the transaction, the write, provenance, and projection. A
// caller supplies only what it knows: which operation this is, and what to
// write.
//
// The runner is the single copy of that wiring. A caller that assembled the
// steps itself would hold a second copy, and every change to the pipeline
// would then have to be made twice.
type OperationRunner interface {
    Run(ctx context.Context, actor Actor, spec OperationSpec, write OperationWrite) (json.RawMessage, int, bool, error)
}
```

```go
// OperationSpec describes one operation to run.
//
// Body is the request body the pipeline hashes for idempotency. SourceIDs is
// nil for an operation whose sources need no recheck.
type OperationSpec struct {
    Name         OperationName
    Target       string
    Key          string
    Body         any
    Request      AuthorizationRequest
    SourceIDs    func(ChapterWorkspaceTransaction, OperationResult, bool) ([]string, error)
    Output       OperationOutputKind
    CheckProject func(Project) error
}

// OperationWrite performs the mutation. It runs inside the pipeline's
// transaction, so it must not open one.
//
// The value it returns is marshaled by the pipeline exactly as the aggregate's
// own value was; its type is never inspected.
type OperationWrite func(tx Transaction, project Project) (OperationOutcome, error)

// OperationOutcome is what a write produced.
type OperationOutcome struct {
    Value  any
    Status OperationStatus
    Output OperationOutputKind
}
```

## 不可变契约

1. **端口方法集合与语义不变**：15 个端口方法的签名**逐字**等于聚合体搬走前的同名方法。
2. **管道步骤顺序与判定不变**：幂等键与请求体哈希、重放顺序、授权、审计写入、来源复核、事务边界、人类决策门——一个步骤的顺序或判定都不改。
3. **零写入保证不变**：授权失败、版本冲突、幂等冲突、人工决策缺失时，本次操作**不得留下任何业务写入**；审计记录是唯一允许的写入，且与判定同事务。
4. **授权拒绝与对象不存在对无权调用方返回同一种对外形态**，不泄露对象是否存在。
5. **成员不变量语义不变**：Owner 唯一、成员数 ≤ 20、角色与功能角色合法、邀请校验、成员状态流转（remove / restore / restore_tenant）。
6. **幂等记录格式不变**：`operationcore` 的 `Result`（BodyHash / Body / Status / Output）逐字不变。
7. **传输层零改动**：路由表、信封、状态码、错误码、文案、前端类型逐字不变。
