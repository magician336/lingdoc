# 灵档（LingDoc）产品开发规划文档集

_统一基线：2026-09-19；以当前 Tencent WeKnora 仓库、顶层产品计划和团队 PR 计划为准。_

## 定位与使用方式

本套文档把顶层产品计划、团队 PR 计划以及 A/B/C/PCC 设计合并为可实施的产品开发基线。它面向整个产品，而不只是某一功能或某一位开发者。

**基线优先级（发生冲突时按此裁决）**：当前 WeKnora 仓库与 [`DEVELOPMENT_PLAN.md`](../DEVELOPMENT_PLAN.md) 定义平台边界；[`PROJECT_TOP_LEVEL_DEVELOPMENT_PLAN.md`](../PROJECT_TOP_LEVEL_DEVELOPMENT_PLAN.md) 定义产品范围；[`TEAM_DEVELOPMENT_TASKS.md`](../TEAM_DEVELOPMENT_TASKS.md) 定义交付顺序；本目录定义灵档领域的详细设计。若本目录与前三者冲突，以前三者为准，并在本目录同步修订。

产品不是“自动写标书”工具；它是面向科研项目申报的、以**证据关联、变更影响检查、版本确认和可编辑交付**为核心的协作工作台。研究判断、证据适用性判断与最终提交始终由人负责。

## 统一设计基线

| 决策项   | 当前基线                                                                     | 不再采用                                              |
| ----- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| 产品边界  | LingDoc 是 WeKnora 之上的科研项目工作台；项目、证据、协作和交付是新增领域能力                          | 把 WeKnora 知识库或通用聊天直接当作项目系统                        |
| 项目实体  | 领域统一称 `Project`；实现文件/表可使用 `research_project`                             | 在 `Project`、`ResearchProject`、`Workspace` 之间互换含义  |
| 项目资料  | 领域统一称 `ProjectAsset`；其中可包含 WeKnora 受控资料、外部来源和对话摘录                        | 将 `Material`、`ProjectAsset`、Knowledge Base 当作同一对象 |
| 证据    | 用户可见对象统一称 `EvidenceCard`；内部可保留支持关系字段                                     | 以 `EvidenceRelation` 作为用户主对象                      |
| 主张与版本 | `ResearchClaim`、`Chapter`、`ChapterVersion` / `ResearchClaimVersion` 分别表示论断、章节和版本 | 用 `Claim`、`ContentVersion` 或“章节版本”指代多个不同对象             |
| 外部调研  | 学术来源仅接入已批准的目录；联网检索复用 WeKnora 的 `web_search` / `web_fetch` 作为**发现层**；检索结果和 AI 回答只能进入候选队列并带层级标记 | 承诺联网结果或 AI 回答自动成为正式证据；LingDoc 自建第二套搜索引擎 |
| 建项结构  | 三步：创建记录 → 草稿阶段（可选、可停留、即可协作）→ 立项确认；`Revision 0` 是草稿期空基线，确认时生成章节骨架与 `Revision 1` | 把建项当成一次性表单；让草稿期出现章节、`ChangeSet` 或 `EvidenceCard` |
| 阶段    | P0–P5 是本目录的执行编号；P0–P3 为构建阶段，P4 交付首个对外版本 Beta，P5 是 Beta 之后的生产增强              | 把 P2 调研或 PCC 描述成当前已实现能力；把 Beta 描述成已交付版本           |
| 权限    | WeKnora 提供租户/知识库上限，LingDoc 提供项目角色与 capability，最终权限取交集                    | 新建第二套登录、租户或绕过项目检查的 Agent                          |
| 模板与规则 | 模板是代码与 AI 的共用合同；规则按判定方分 `computed`（规则求值）与 `model`（模型判定），两类进入同一问题清单、同等可推翻；模板检查与预检是同一套规则的两次求值 | 把模板当成给模型的提示词；让规则寄居在提示词里；实现成两套并行的检查体系 |
| 管理台  | RuoYi 作为 root 控制平面，通过私网 Admin BFF 治理组织、用量与审计；具体版本/部署待 P0 确认 | 让 RuoYi 直连 WeKnora 业务表或进入研究者主路径 |

### 术语迁移表

旧文档中的名称仍可在历史记录、事件兼容层或代码迁移中出现，但新接口、页面和验收文档使用右列名称。

| 旧称 | 统一称 | 备注 |
|---|---|---|
| `ResearchProject` / `Project` | `Project` | 代码可保留 `research_project` 文件名 |
| `Material` | `ProjectAsset` | `AssetRevision` 表示资料处理谱系 |
| `EvidenceRelation` | `EvidenceCard` | 卡片中保留 `support_type`、`claim_refs` 等关系字段 |
| `Claim` | `ResearchClaim` | 避免与通用模型 claim 混淆 |
| `ContentVersion` | `ChapterVersion`（章节）或 `ResearchClaimVersion`（主张） | `ContentVersion` 作为兼容统称 |
| `ExternalSource` | `AcademicSource` | 仅指经目录批准的外部学术来源；网页元数据仍可作为其字段 |

## 已确认的架构立场

```text
WeKnora：知识与 Agent 数据平面（文档处理、检索、引用、Agent 与流式交互）
LingDoc：面向研究项目的产品层与领域层
RuoYi：root 级运营/治理控制平面，通过 Admin BFF 访问，不进入研究者主工作流

A Evidence   ：Source Truth
B Workspace  ：Project Truth + PCC Core
C Delivery   ：Delivery Truth
PCC          ：让三种 Truth 在每次实质修改后收敛至同一 Context Revision
```

`PCC` 为 **Project Change Coordinator**，产品中文名采用“关联变更协调机制”。它协调而不替代领域判断：A 判断证据是否仍可用，B 判断项目内容与确认状态，C 判断交付是否可放行。

## 阅读与实施约定

- 本文中的“应”“必须”是目标设计或验收约束，不表示当前 WeKnora 已实现。
- 当前 WeKnora 可复用的事实基础包括：异步文档处理、分块/向量化/索引、检索问答、引用输出、Agent 工具、流式会话以及租户/知识库权限。项目工作台、ProjectAsset—EvidenceCard—ResearchClaim 模型、PCC、确认链路和申报 DOCX 预检均应作为 LingDoc 新领域能力交付。
- 任何跨域互动只走明确 API、命令或事件；禁止跨域直接写对方数据库表或依赖 WeKnora 的短生命周期内部对象（如 chunk ID）。
- 优先验证一个完整的真实任务：固定资料集 → 章节草稿 → 一次研究条件变更 → 影响处置 → 人工确认 → 可编辑文件导出。

## 非目标

- 不承诺自动判断研究价值、学术正确性或申报结果。
- 不把所有资料都复制进“统一知识库”，也不把全项目文本塞进每一次模型调用。
- 不将论文写作、行政业务、未批准学术数据库或多申报类别自动纳入同一工作流。联网检索能力复用 WeKnora 并在产品中保留，但它只作为**发现层**：检索到的结果不自动成为正式证据，搜索摘要（未读原文）不具备可重定位的原文位置，因此不能作为引用依据（见 [`10-调研智能体与知识沉淀规划`](10-调研智能体与知识沉淀规划.md) 第 5 节）。
- 不把 RuoYi 和 WeKnora 两套用户、权限、前端或数据库硬拼为一个产品核心。
