# 模板与规则系统设计

> **后续设计参考**：本文保留完整产品方案；本轮范围见[实施方案](../08-本轮实施方案/01-范围与任务流程.md)，领取以[任务池](../TEAM_DEVELOPMENT_TASKS.md)为准。A/B/C 仅指领域，不分配人员。完整 PCC、复杂权限等不自动成为本轮前置条件。

> 面向对象：产品、架构与实现三方共同使用。  
> 解决的问题：模板系统在整个产品中承担什么职责，规则由谁定义、由谁执行、出问题谁负责，以及 AI 在其中可以做什么、不可以做什么。  
> 与顶层计划的关系：本文是 [顶层开发计划](../PROJECT_TOP_LEVEL_DEVELOPMENT_PLAN.md) 第 7 节的展开；产品范围与验收仍以顶层计划为准，本文不重新定义产品能力。

> **核心判断**
>
> **模板不是给 AI 的提示词，而是代码与 AI 的共用合同。** 它同时是确定性规则的来源和 AI 判断的输入声明；两者通过同一个问题实体汇合，因此交付契约不依赖任何模型的表现。

---

## 1. 定位与边界

### 1.1 模板要解决的真实问题

申报材料的合格与否，传统上依赖两种情况之一：**专家人工核对**，或**笼统的格式工具**。前者的成本无法摊薄，后者只能看见版式、看不见内容。

模板系统的目标是把"这份材料合规吗"从专家经验中尽可能多地剥离出来，变成**可复算、可审计、可版本化**的判定。做不到的部分（语义判断、学术裁量）明确标记为判断而非规则，并交给可被推翻的流程。

### 1.2 本文覆盖与不覆盖

| 本文定义 | 本文不定义 |
|---|---|
| 模板的职责边界与信息组成 | 模板的具体章节清单与字数（属申报类别配置） |
| 规则的三分工与版本化约束 | 单条规则的完整清单（随申报类别演进而增加） |
| 规则集的结构与求值契约 | 规则编辑器的界面形态 |
| 问题实体的统一身份 | 具体章节编辑器的交互细节 |
| AI 参与模板系统的约束 | 模型选型、提示词措辞与推理参数 |
| 规则与模板的演进与治理路径 | 机构模板的商务与授权流程 |

### 1.3 一处需要先对齐的口径

顶层计划正文使用通用产品语言（"研究主张""证据卡""章节"）；本文使用可对应到数据实体的术语（`TemplateProfile`、`ValidationIssue`、`EvidenceCard`）。两者不是两套东西，只是抽象层级不同：**顶层计划说产品能力，本文说系统契约**。实现时以本文的实体命名为准，产品范围以顶层计划为准。

## 2. 模板的本质

### 2.1 模板是合同，不是提示词

`TemplateProfile`（模板档案）是**按申报类别与年度版本化的规则包**，包含四类信息：

```text
TemplateProfile
  ├── sections          章节结构
  ├── required_fields   必要字段
  ├── ruleset_id        指向规则集（独立实体，不是模板的内联字段）
  ├── ruleset_hash      该规则集的内容指纹（发布时冗余一份，供导出审计与回放）
  └── grant_category / year / version   适用范围与版本
```

规则集是独立于模板结构版本化的实体，模板只持有它的引用与一份发布时复制的指纹——这样规则收紧不必改动章节结构，而导出记录仍能回答「这一次用的是哪一套规则」。

这四类信息恰好对应两种消费者：

| 消费者 | 消费什么 | 怎么消费 |
|---|---|---|
| 代码 | `sections`、`required_fields`、`ruleset_id`（据此加载规则集）、`ruleset_hash` | 直接执行确定性判定与结构生成 |
| AI | `TemplateProfile` 整体 + 规则版本 | 作为上下文切片的输入声明，约束它能看见什么、该判什么 |

**同一份内容、同一个规则版本，代码必须算出同一个结论**。这是模板能成为交付放行依据的前提，也是规则不能寄居在提示词里的根本原因——提示词的任何措辞变化都会导致判定漂移，而判定漂移会让"导出放行"失去意义。

### 2.2 模板被"哈希"意味着什么

`ruleset_hash` 这个字段名本身就是一条设计约束。规则被哈希，意味着：

1. **规则集是可寻址的稳定对象**——同一个人查看同一条问题，能回到产生它的规则；
2. **规则版本会被写入交付记录**——导出时固定的是"哪一套规则下的结论"，而非"当时模型说了什么"；
3. **规则可以独立于模板演进**——模板结构不变而规则收紧，是可表达的。

> **常见混淆**
>
> `TemplateVersion`（模板版本）标识**一套模板的整体版本**；`ruleset_hash` 标识**规则集的内容**。两者不是同一个东西：规则集可以在模板版本号不变的情况下被修订（收紧一条规则），此时模板版本需随之升级；反过来，模板版本的升级也可能只含结构变化而不含规则变化。实现时必须分开记录，导出记录两者都要。

### 2.3 模板不承担什么

- **不承担学术判断**。模板判定"样本范围是否说明"，不判定"这个样本范围是否合理"。
- **不承担内容修改权**。模板可以指出缺口，但不能改写正文；任何内容变化必须由人发起。
- **不承担例外裁定**。规则命中只产生问题，是否接受由人决定（见第 5 节）。

## 3. 规则与 AI 的三分工

这是本文最核心的一节。规则系统如何在"确定性"与"表达能力"之间取舍，全部体现在这张分工表上。

### 3.1 分工表

| 判断类型 | 归属 | 判定性质 | 典型例子 | 出错的后果 |
|---|---|---|---|---|
| 结构、字段、字数、标题层级、版本、可计算格式 | **规则（代码）** | 可复算，同一输入必得同一结论 | 缺必要字段、标题层级不符、字数超限 | 规则写错了 → 修规则，重跑即修正 |
| 术语一致性、结论与证据是否匹配、论证链条是否断裂 | **模型（AI）** | 语义判断，可能出错 | 术语前后不一致、某论断只有背景材料 | 模型判错 → 人推翻，不需改代码 |
| 例外是否可接受、学术价值是否成立 | **人工** | 价值裁量，不可自动化 | 有理由地接受一条警告、判定某条为误报 | 人担责，记录理由与审计 |

**分界线是"能否复算"，不是"难不难"。** 一条判断只要能保证相同输入得到相同输出，就应该下沉到规则；只要它依赖语义理解，就必须留在模型层，并接受被推翻。

### 3.2 为什么不让 AI 做全部，或不让规则做全部

**全部交给 AI** 的代价：判定漂移。同一个项目内容，今天跑出 3 条问题、明天跑出 5 条，用户无法判断是内容变了还是模型变了。"导出放行"失去依据，审计也答不出"当时为什么放它过"。

**全部交给规则** 的代价：规则永远追不上语义。术语一致性、证据充分性这类判断写成规则会立刻退化成关键词匹配，漏报率极高，反而让用户失去信任。

因此两者**必须并存**，且必须在同一个流程里被同等处置——这正是第 5 节要解决的问题。

### 3.3 三分工的实现约束

| 约束        | 要求                               |
| --------- | -------------------------------- |
| 规则不依赖模型   | 规则求值必须能在模型不可用时独立完成并给出完整结果        |
| 模型不依赖规则措辞 | 模型检查项的判定依据来自模板声明，而不是硬编码在提示词里     |
| 人工处置可审计   | 每一次推翻都必须记录人、理由、规则标识与目标对象版本       |
| 三方结论不互相覆盖 | 模型不能"修好"规则报出的问题；规则不能"关闭"人工标记的待核项 |

## 4. 规则体系

### 4.1 规则集结构

规则集是模板携带的、可独立版本化的判定清单。每条规则的最小形态：

```text
Rule
  rule_id        唯一标识，跨版本稳定（问题身份的一部分）
  kind           computed | model        判定方
  severity       blocking | warning | info
  target         选择器：作用于章节 / 主张 / 字段 / 交付项
  evaluator      kind=computed → 规则实现；kind=model → 检查项声明
  params         阈值、术语表引用、允许值域等参数
  version        随规则集整体版本化
```

`kind` 字段是整个设计的关键：**它把"谁来判"变成数据，而不是藏在代码的分支里**。这样，两级求值（见 4.3）可以无差别地对待两类规则；模型更换或检查项调整也不需要改动求值流程。

### 4.2 规则分类

| 类别 | 判定方 | 是否可自动修复 | 处置方式 |
|---|---|---|---|
| 结构完整性（章节是否存在、必要字段是否齐备） | computed | 部分（补结构） | 修复或关闭 |
| 格式与计量（标题层级、字数、编号、图表题注） | computed | 可（支持一键修复预览） | 修复或关闭 |
| 版本一致性（引用版本、确认版本、快照版本） | computed | 可（提示重新绑定） | 修复或关闭 |
| 术语一致性（术语是否与项目条件的写法统一） | model | 否，只能给建议 | 人工接受或关闭 |
| 证据充分性（论断是否有可支撑的证据层级） | model | 否，只能给建议 | 人工接受或关闭 |
| 论证一致性（研究问题—方法—创新点—预期成果是否互相呼应） | model | 否，只能给建议 | 人工接受或关闭 |
| 交付完整性（附件、材料清单、可打开性） | computed | 否 | 修复后才能放行 |

> **可自动修复的判据**
>
> 一条问题能被"一键修复"，当且仅当修复方案可以被程序确定地写出。格式类问题满足（缩进、编号、字数压缩有确定解法）；语义类问题不满足（术语不一致往哪边统一，是研究决策，不是排版决策）。

### 4.3 求值契约：同一套规则，两次求值

规则集只有一套，但对**两类对象**求值：

| 求值级别 | 对象 | 触发时机 | 结果去向 |
|---|---|---|---|
| `content`（写作期检查） | 项目当前内容 | 写作过程中随时可跑 | 只落在工作台界面；不改变交付状态，不产生跨域事件 |
| `release`（导出前检查） | 一个冻结的交付快照 | 内容变化、模板变更或确认失效时 | 交付放行的唯一依据 |

```text
RunTemplateCheck(project_or_snapshot, ruleset, level) -> ValidationIssue[]

level = content  →  对项目当前内容求值
level = release  →  对指定交付快照求值
```

**为什么必须两级而不是一级**：

- 只有 `release`：格式与字段缺口会被推迟到交付前才暴露，写作期看不到，返工成本最高；
- 只有 `content`：答不出"这一个快照到底能不能导"——当前内容合规不等于某个冻结版本合规。

两级共用规则集、严重度与处置方式，区别只在求值对象。由此产生一条必须显式处理的语义（见 5.3）：**同一条规则在两级各产生一条问题，它们必须能互相寻址**。

### 4.4 规则的执行约束

| 约束 | 要求 |
|---|---|
| 可独立运行 | 规则求值在模型不可用时仍能完成并给出结果；模型类规则此时标为"未求值"，而非默认为通过 |
| 可复算 | 同一输入 + 同一规则集版本 → 同一结论；不确定的规则不得进入 `computed` |
| 可定位 | 每条问题必须指向具体的对象与版本，不允许产生"整个项目有问题"这种无定位的条目 |
| 可解释 | 每条问题展示对应的规则说明，用户能理解"为什么系统认为这里不对" |

## 5. 问题的统一出口

### 5.1 统一问题实体

不管问题来自规则还是模型，都以同一个实体产出：

```text
ValidationIssue
  rule_id          产生它的规则（模型类规则同样有稳定标识）
  kind             computed | model
  severity         blocking | warning | info
  target_ref       作用对象
  target_version   作用对象版本
  check_level      content | release
  status           OPEN | RESOLVED | DISMISSED
  evidence         触发理由、建议动作、规则说明
```

**问题的身份是 `rule_id + target_ref + target_version`**，与 `check_level` 无关。这条设计让两级求值共享同一套问题身份，是 5.3 能成立的基础。

### 5.2 为什么统一出口是必要的

如果规则问题和模型问题走两条管道，会产生三个立即出现的问题：

1. **界面要分两次渲染**，用户面对两套语义、两套严重度、两套处置按钮；
2. **处置记录无法互认**——在写作期推翻了某条模型误判，导出前必须再推翻一次；
3. **交付放行的依据会分裂**——放行需要同时检查两套状态，漏掉任一套都会出错。

统一出口之后，模型更换、提示词迭代、规则增删都不会改变交付契约的形态。这是本设计中最有价值的一条约束：**AI 的能力被使用，但交付契约不依赖 AI 的表现。**

### 5.3 处置的两种语义（不可混用）

| 处置 | 语义 | 适用严重度 | 必须记录 |
|---|---|---|---|
| **误报删除**（`DISMISSED`） | 这条问题本不该存在——规则或模型判错了 | **任一严重度，含阻断级** | 删除人、理由、`rule_id`、目标版本 |
| **豁免**（`Waiver`） | 问题真实存在，但本次接受 | **仅警告与提示级** | 负责人、理由、风险清单 |

两条边界必须守住：

- **阻断级永不豁免，但永远可被判误报。** 这个组合是刻意的：不让人把真实缺口放过去，但必须让人能推翻系统的错误判断。系统判错的可能性是设计的既有前提，不是需要靠提示词工程消除的缺陷。
- **删除的作用域跨求值级别。** 在写作期被判定误报的问题，导出前只要目标对象版本未变就不再报出；反之亦然。目标对象产生新版本后删除失效，问题在下次求值重新出现——**不得成为永久静音**。

### 5.4 模型类问题的额外约束

模型类规则产生的问题，除上述统一要求外还需满足：

| 约束 | 要求 |
|---|---|
| 必须给出定位 | 指出具体段落、论断或字段，不接受"全文可能有问题" |
| 必须给出可读理由 | 用户要能判断这是不是误报；理由不可读的模型问题等同于噪音 |
| 不得自动关闭 | 模型不能在下一次求值时"自动确认已修复"，关闭动作由人或由内容变化触发 |
| 不得降级严重度 | 模型不能自行把阻断级判为警告级；严重度由规则集的 `severity` 决定 |

## 6. AI 在模板系统中的参与方式

### 6.1 上下文切片约束

AI 参与模板检查时，能看见什么由任务声明决定，不由调用方临时拼接：

| 任务 | 允许输入 |
|---|---|
| 写作期模板检查 | 当前章节与主张的版本集合、`TemplateProfile`、规则版本 |
| 导出前检查 | 交付快照、`TemplateProfile`、确认汇总、规则版本 |
| 章节候选稿生成 | 项目条件、当前章节、相邻章节摘要、已确认/待核证据、未解决影响 |
| 字段候选值生成 | 用户选定的资料轮次范围、`TemplateProfile` 的必要字段清单 |

**约束**：切片必须携带资料授权范围与当前修订号；未授权原文、已撤销资料或过期上下文不得进入模型调用。模板属交付域，AI 能力属知识域——**交付域不直接持有资料授权，必须通过知识域的受控接口获取内容**，这是权限边界，不是实现偏好。

### 6.2 AI 产出的形态约束

AI 在本系统中的产出**只有三种形态，没有第四种**：

| 形态 | 用途 | 落地要求 |
|---|---|---|
| 候选值 | 填充字段、生成章节稿 | 默认 `待确认`；必须携带来源（会话、轮次范围、采用的原文片段） |
| 候选问题 | 模板检查与一致性检查的输出 | 进入统一问题实体，带 `rule_id` 与严重度 |
| 候选关系 | 发现的内容依赖关系 | 标记为模型建议来源，不直接成为不可撤销的业务事实 |

**AI 不能生产事实。** 任何 AI 产出在被人工确认前都是候选，这个约束在产品层面表现为"待确认"状态的可见性，在系统层面表现为状态机的入口限制。

### 6.3 填写与质疑必须分离

一项容易被设计遗漏的要求：**系统对自己填出的值，仍必须提出问题**。

AI 按模板必要字段填出"研究对象：某类学生"之后，系统仍应指出"样本边界不够具体"这类缺口。如果这项能力被省略，实际效果是 AI 的自产物获得了一条免检通道——填得越顺，质疑越少，与"证据驱动"的定位直接冲突。

实现上，这意味着**字段生成任务与检查任务是两个独立任务**，不得因为字段由 AI 生成而在检查时豁免。

## 7. 模板与规则的演进

### 7.1 模板变更的影响

模板版本升级时：

| 对象          | 行为                                                   |
| ----------- | ---------------------------------------------------- |
| 已确认的正文内容    | **不自动改写**。内容修改权始终在人                                  |
| 写作期检查       | 按新规则重跑，产生新问题                                         |
| 既有交付快照的检查结论 | 失效——快照绑定的旧规则结论不再代表当前判定                               |
| 字段集变化       | 同名字段按名保留；原模板独有的字段标为"模板不再需要"（可见状态，非删除）；新模板需要的字段标为"待填" |

**不得因换模板清空已填字段**——已填字段可能带有用户确认过的来源依据，静默清空等于抹掉依据链。

### 7.2 新增一条规则的门槛

规则集是交付放行的依据，因此新增或收紧规则需要满足：

1. 有可复现的样例（能触发该规则的脱敏样本）；
2. 明确 `kind`（能否复算）与 `severity`（阻断是否恰当）；
3. 有过误报评估——阻断级规则的误报会让整个团队停摆，宁可先设为警告；
4. 规则标识稳定，且本次变更使 `ruleset_hash` 变化。

### 7.3 治理边界

- **规则的领域定义与实现归产品交付侧**；发布与生效的治理流程走机构管理台；
- **机构管理台不写模板业务记录**——它负责发布、审阅、撤销与版本管理，不直接修改规则内容；
- **模板发布与生效的治理流程需要内容负责人、审核人、版本与废止机制**，与顶层计划的运营治理要求一致。

## 8. 落地路径

### 8.1 分批交付

| 阶段 | 模板系统相关交付 | 判据 |
|---|---|---|
| 阶段一（可信知识与辅助写作闭环） | 模板的章节结构与必要字段（单类申报）；写作期检查的最小规则集（结构完整性 + 格式） | 用户能从模板生成章节树，并看到结构与字段缺口 |
| 阶段二（完整申报协作与可控 Agent） | 完整的规则集与 `kind` 区分；两级求值；统一问题实体与两种处置语义；模型类检查项 | 固定样例完成完整闭环，交付前无阻断问题导出 |
| 阶段三（机构知识资产与领域扩展） | 模板与规则的多类别扩展、发布与废止治理、规则误报评估机制 | 新模板可在不改变核心产品行为的前提下发布、审阅和撤销 |

**始终只为一类申报模板做端到端实现，再扩展**——规则的专家知识成本是这套设计的主要成本，多类别并行的代价远超预期。

### 8.2 与本设计相关的关键风险

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 规则维护成本失控 | 多类别并行、每条规则都要专家参与 | 严格按 7.2 的门槛准入；先做单类别端到端 |
| 模型类规则误报率高 | 检查项声明过于宽泛 | 模型类规则默认警告级，达到误报评估门槛后再考虑阻断 |
| 用户滥用误报删除 | 删除门槛过低 | 删除必须填理由并进审计；阻断级删除需复核判定 |
| 两级求值结论不一致 | 问题身份未包含版本 | 严格实现 5.1 的身份定义；`target_version` 必填 |
| 规则与模板版本漂移 | 两者独立变更未联动 | 按 2.2 的约束，规则集变更必须使模板版本升级；导出同时记录两者 |
