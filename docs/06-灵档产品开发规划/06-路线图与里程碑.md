# 按交接结果推进的路线图

本轮按依赖推进，不按日期把三个人排满，任务均待领取。完整 Beta、生产治理和多模板扩展另行规划。当前任务编号以 v0.5 的 T01–T16 为准；v0.4 的独立前端 T15–T18 已并入对应 T07–T14，原 T19/T20 分别重编号为 T15/T16。

| 结果 | 对应任务 | 可以提前并行什么 |
|---|---|---|
| 主要技术未知有真实结果 | T01–T05 | 检索/生成、持久化/并发、DOCX 分别验证，代码可直接演进为功能 |
| 消费者可以独立开工 | T02、T06 及各提供方 | 模板/上下文/候选/交付输入先给固定实现，不等全部 HTTP 定稿 |
| 项目可建立并持续编辑 | T07、T08 | 对应界面切片先接 Mock；最小接口达到约定即可提前接真 |
| AI 候选进入真实章节 | T09–T11 | 资料、生成、Candidate、采纳逐段接真；采纳可先用固定候选验证版本与幂等 |
| 已确认内容可冻结并导出 | T12–T14 | 固定输入先验证检查与 DOCX；最终验收接真实快照 |
| 失败后仍可恢复工作 | T15 + T07–T14 | F02–F21 随已就绪领域功能逐项接真，不把修复责任集中到测试任务 |
| 完整连续闭环通过 | T16 | 提前组合可挂载界面切片并逐段替换 Mock，最终在真实测试环境跑 F01 |

真实依赖：生成需要 T08 上下文和 T09 来源；采纳需要 T10 候选和 T08 写入；冻结需要 T12 输入和 T09 当前来源检查；导出需要 T13 快照。它们是**接真的依赖**，不要求等待整个提供任务完成；满足约定的最小接口应尽早交给消费者。

UI 可演示、最小接口可消费、真实接口可用、跨任务交接通过、完整流程通过分别记录。每次完成一个可描述的用户结果，不把三个局部演示合称闭环，也不把“父任务尚未完成”误作下游等待理由。
