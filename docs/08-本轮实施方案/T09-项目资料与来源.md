## 3. 设计

### 3.1 资料版本：从可观测信号自维护（契约 §10）

契约 §4 要求 `asset_revision` 在「内容或解析定位改变时」变化。底座没有版本号，只有下列可观测信号：

| 信号 | 底座位置 | 说明 |
|---|---|---|
| `FileHash` | `types.Knowledge.FileHash` | 内容指纹，**最强信号** |
| `FileSize` | `types.Knowledge.FileSize` | 缺失（0）与空文件在这里不可区分，取更保守的一侧 |
| `ProcessedAt` | `types.Knowledge.ProcessedAt` | 该次解析完成时刻；重解析会变 |
| `ParseStatus` | `types.Knowledge.ParseStatus` | **不进指纹**，只映射 `processing_state`（理由见下） |

`FingerprintOf` 把**可得**的信号做规范化拼接后取 sha256，并**记录依据**（`basis`，落地在 `lingdoc_asset_revisions.metadata_json`），使得「这次用了哪几个信号」可被报告与人工复核，而不是一个看不出成分的哈希。

- **刻意不吃 `ParseStatus`**：它翻转只是处理进度，把它算进内容指纹会造出契约没要求的版本递增（`processing→completed` 会让 `asset_revision` 平白 +1）。
- **刻意不吃 `UpdatedAt`**：底座任何一次行更新（含状态翻转）都会改它，同上。
- 一个内容信号都拿不到时，指纹落在**固定哨兵** `no_content_signal`，而不是每次现算：现算会让每次观测都判成「变了」，版本自己往上跑；空串更不行——空串在存储里表示「还没观测过」。此路径由 `TestFingerprintWithoutContentSignalsIsStableSentinel` 钉住（§6.4 登记其区分度风险）。
- **退化不改变判据方向**：指纹只用来回答「与上次观测是否相同」。同输入必同输出，所以信号缺失**不会**导致每次都判定为变化。
- 观测到指纹变化 → `asset_revision + 1`，旧修订行标 `superseded`，并新建一条修订行。这正是契约 §4 末行「检测到重解析则要求重新选择资料」的落地：消费者按版本比较发现自己持有的 `asset_revision` 已过期。
- **首次观测只建立基线、不递增**（`Observe` 在 `prev.Fingerprint` 为空时直接返回）：还没有任何东西基于旧版本产出，递增只会平白作废消费者的工作。

`processing_state` 由 `ParseStatus` 映射，**只有 `completed` 映射为 `ready`**（fail-closed）：

| ParseStatus | processing_state | 说明 |
|---|---|---|
| `pending` | `pending` | |
| `processing` / `finalizing` | `processing` | 主解析完成但富化未完成，仍不算就绪 |
| `completed` | `ready` | 唯一可进入允许集合的值 |
| `failed` | `failed` | |
| `cancelled` | `failed` | 契约枚举里没有 `cancelled`；取消后既无可用产物、也不会自行恢复，故并入 `failed`（提示需重解析），而不是 `pending`（会暗示还在排队） |
| `deleting` | `replaced` | 资料正在被删除，绑定不再指向可用内容 |
| `unprocessed` / `""` / 未知值 | `pending` | DDL 默认值里有 `unprocessed` 而 Go 常量里没有；不认识就不当就绪，不给它放行 |

映射表由 `TestProcessingStateOfIsFailClosed` 逐值钉住（含 `cancelled`、`unprocessed`、未知值），断言「恰好一个值映射成 `ready`」。

### 3.2 原文落点：本轮的可诚实上限（T03 §6.5 的缺口）

T03 §3.3 的强档要求「原始资料可直读」。全量解析产物没有落库，`Knowledge.FilePath` 指向原始文件。T09 交出 `NewOriginReader`（`origin.go`），判据是**可证明的字节同一性**，不是「看起来像文本」。

**先查清楚了真链路**（这是本节与初稿最大的差别，初稿的两条结论是错的）：

| 环节 | 实际行为 | 出处 |
|---|---|---|
| Go 侧简单格式读取 | `md`/`markdown`/`txt`/`text` **原样返回文件字节**，不过 Python 解析服务 | `docparser/builtin_converter.go:57-60` |
| 同处的转换格式 | `csv`→`csvToMarkdown`、`json`→`jsonToMarkdown` **明确改写** | 同文件 `:61-72` |
| 切分前的清洗 | `CleanInvalidUTF8` 丢掉非法 UTF-8 字节与 NUL | `common/tools.go:189-210` |
| 切分前的归一 | `NormalizeLineEndings` 把 `\r\n` 与 `\r` 统一成 `\n` | `infra/chunker/strategy.go:207-213` |
| 切分前的图片处理 | 图片引用被改写成对象存储地址 | `docparser/image_resolver.go` |

**所以强档的成立条件被精确化成**：读到的字节经过上述几步改写之后**没有变化**。逐条排除：

| 情况 | 结论 | 理由 |
|---|---|---|
| `txt`/`text`/`md`/`markdown` 且文件干净 | **强档 `ok=true`** | 字节同一，rune 偏移可比对 |
| `csv`/`json` | 降弱档 | 解析侧明确改写，偏移不可证 |
| PDF/DOCX/HTML/图片等 | 降弱档 | 走 Python 解析，产物与文件无逐字关系 |
| 文件含 `\r`（CRLF 或裸 CR） | 降弱档 | 切分用的是归一后的文本，硬claim会产出**假的 `stale`** |
| 文件含 NUL、或非法 UTF-8 | 降弱档 | `CleanInvalidUTF8` 会丢字节 |
| 文件含图片引用（`![`/`<img`/`data:image/`） | 降弱档 | 图片解析会改写这串字节 |
| 带 UTF-8 BOM | **仍算强档** | U+FEFF 是合法 rune、不是 NUL，上面两步都不动它，两侧一致（初稿判错，已由 `TestOriginAcceptsBOMBecausePipelineKeepsIt` 钉住） |
| 文件缺失/目录/空文件/超 8 MiB | 降弱档 | 读不出可比对的正文；**不是错误**——底座真故障才报错（`TestOriginSeparatesWeakTierFromFailure`） |
| 该文件类型被 KB 规则改派给别的引擎 | 降弱档 | 见下「第二道前提」 |

**第二道前提：没有别的引擎经手**（代码评审补上的一处假强档）。上面那句「`md`/`txt` 原样返回字节」只在**默认路由**下成立：`eff.ChunkingConfig.ResolveParserEngine(fileType)`（`knowledge_process.go:3771`）允许 KB 级 `parser_engine_rules` 把 txt/md 改派出去，那时切分吃的是引擎产出的 markdown，与文件字节不再逐字相等，而 `origin.go` 仍会发强档 → 又是一批假的 `stale`。空串即内置路由（`types/knowledgebase.go:305`）。

判据因此要求调用方回答一个事实：`KnowledgeReader.UsesBuiltinConverter(ctx, knowledgeID)`。实现方在接线处取上面那个函数，**判不定返回 false**——保守一侧是降档，不是失败。`TestOriginDeclinesWhenAnotherEngineParsesTheContent` 钉住三条：改派降档、判定故障如实报错、手工资料不受引擎路由影响（它走另一条链路，直接进 Go 分块器）。

**手工资料的强档同样要按链路走，不能靠「手工写的」这个身份**（代码评审补上的另一处假强档）。它的正文在 `metadata.content` 里（`types.ManualKnowledgeMetadata`，见 `types/knowledge.go:322`），但进切分前有**四步改写**（`knowledge_create.go:1237-1274`），而分块器切的是改写之后的文本——chunk 的 rune 偏移是相对改写结果，不是相对 metadata 里的原文：

| 步骤 | 处理 | 出处 |
|---|---|---|
| 1. `clean := strings.TrimSpace(content)` | **纯函数——这里照样做一遍**，取回的字串就与切分输入对齐 | `:1237` |
| 2. data-URI 图片解析成存储地址 | **排除**：读文件系统/存储，重建不出同结果 | `:1241` |
| 3. 远程 http(s) 图片解析成存储地址 | **排除**：要联网 | `:1249` |
| 4. `chunker.NormalizeLineEndings(clean)` | **排除**：手工输入的 CRLF 是常态（该行注释自认） | `:1274` |

镜像第 1 步比降档更对：首尾空白是最常见的情况，而分块器看到的就是 `TrimSpace` 之后的那一串，取回它偏移才对齐（否则块尾的偏移会越界）。后三步只能排除。`TestOriginDeclinesManualContentThePipelineRewrites` 两边都钉：CRLF/图片降档，首尾空白取回对齐后的字串。

- 降弱档不是失败：调用方落到 T03 已有的 `quoteBySelfConsistency`，引用仍可用，只是强度不同。
- **不新增解析产物落点**：那是底座（docreader/解析链路）的职责，且「重解析」会引入新的失效面（解析器版本、模型版本）而本轮无法验证。本轮如实声明上限，把「解析产物落库」登记为欠账（§6.3）。
- 维护提示：上面几处改写只要有一处变了（例如新增加一道清洗），`verbatimOrigin` 的判据就必须跟着改。这是**有意写死的耦合**——判据依赖的是底座的实现细节，而它没有稳定的公开契约。

### 3.3 授权接缝：消费既有权限体系，不自建（B2）

`evidence.Authorizer` 是 T03 留下的消费点。T09 交出 `NewFixedAuthorizer`（`authz.go`），它**只回答资料级当前授权**：

```
FixedAuthorizer.CanAccessAsset = ScopeReader.AssetScope(projectID, assetID) → KBReadChecker.CanReadKB(actor, kbID, ownerTenant)
```

- `ScopeReader` 由 `Bindings` 直接满足：判权要知道「这份资料属于哪个知识库、那个库属于哪个租户」，而契约的 `Asset` 是 `additionalProperties: false`，加不了这两个字段；回存储取是对的落点。
- **`AssetScope` 按（项目, 资料）双键收敛**（代码评审修正）：早先只按 `assetID` 查，注释却声称「与 `ObserveAsset` 一样按 projectID 收敛」——承诺由调用方保证，而不是本方法保证，于是它成了一个跨项目探测的口子。现在项目不对就返回 `ErrAssetNotFound`，与「不存在」不可分辨（`TestBindingsAssetScope` 钉住）。`CanAccessAsset` 的参数 `projectID` 早先是 `_`，现在真的用上了。
- `KBReadChecker` 是**缝**：实现在应用层（`internal/application/access` 的 `KBPermissions.Check(kbID, ownerTenantID, OrgRoleViewer)`），由接线处注入。本包不反向依赖应用层——那会把 `types.Caller` 这类运行上下文语义带进资料域。**该适配器随 S4 一起落**（S4 才有 ctx 里的 `types.Caller`）。
- 判权**每次现查、不缓存、不落库**（B5，`TestFixedAuthorizerAsksEveryTime` / `TestGatewayDeniesAfterRevocation`）。**不写** `lingdoc_asset_revisions.status = 'revoked'`：那是把授权状态存成标志位，撤权后再授权就会留下一个过期的 `revoked`。授权是「此刻能不能读」的问答，不是资料自身的属性。

**初稿在这里判错了一半**，修正如下：项目可见性**不放在** `Authorizer` 里。

- 端口只能回 true/false，而「不可见」在 HTTP 上必须与「不存在」收敛成同一个答案（`02-接口与Mock约定.md` §8 末句）。若由这里把不可见答成 `not_authorized`，就变成「403 说明这个项目存在」——**泄露存在性**。
- 且 `02-接口与Mock约定.md` §2 要求资料服务「校验资料不能再调用已经包含来源检查的总入口」：项目可见性是工作区服务（T07 的 ProjectAccess）的事。
- 所以它是 **S4 接线时的前置条件**，由 HTTP 层先判、不可见即 404，且必须现查。这一点在 `NewFixedAuthorizer` 的文档注释里写死，避免接线的人漏掉。

### 3.4 拒绝原因与「请求 ID 集合 vs 返回 ID 集合」

契约 §8 要求资料服务比较请求 ID 与返回 ID，不能把「返回无错误」当成全部授权成功。T03 的 `ResolveResult{Requested, Allowed, Denied}` 已承载这个语义，T09 的责任是：**用真实存储与真实授权把三条路径都跑到**（未就绪/未授权/不存在），并断言 `Requested` 逐项出现在 `Allowed ∪ Denied` 中——缺项即失败。

跨项目 ID 与不存在的 ID 收敛为同一个 `not_found`（不泄露存在性）。

### 3.5 仓储与迁移

- `Bindings`（`binding.go`）是绑定存储，GORM 模型 `ProjectAsset` / `ProjectAssetRevision` 对应设计表 `lingdoc_project_assets` / `lingdoc_asset_revisions`；`Asset`（契约形状）仍由 T03 的 `asset.go` 承载，**序列化边界不变**。
- 迁移：`migrations/versioned/000098_lingdoc_evidence_assets.*.sql` + `migrations/sqlite/000019_lingdoc_evidence_assets.*.sql`。
  **版本号取 98/19 而不是 97/18**：PR #4（未合入）已占用 `000097_lingdoc_workspace` / `000018_lingdoc_workspace`。设计文档 §6.1 要求「不复用已经占用的版本号；合并分支前重新检查最大版本号」——本条即为那一步的结论。
- 迁移只建结构/索引/约束，不写业务数据（设计文档 §6.1）。`internal/database` 的双库对照测试已登记新表并把 `expectedSQLiteMigrationVersion` 提到 19。

**与设计表 §4.2 逐条的差别（不是遗漏，是决定）**：

| 设计列 | 本轮处理 | 理由 |
|---|---|---|
| `origin` | **落**，`Bind` 恒写 `weknora` | 绑的是底座的一份知识，来源是事实不是猜测；`academic`/`conversation`/`upload` 留在 CHECK 里等各自的写入方 |
| `title` | **落**，绑定时快照 | 设计表没有这一列，但契约 `Asset` 把 `title` 标成**必填**。底座改名不产生任何事件，所以它只能如实是「绑定时叫什么」（§8 Q3 登记） |
| `external_ref` / `authorization_scope` | **不落** | 本轮没有能写或读它们的代码；列跟着第一个需要它的任务走 |
| `processing_run_ref`（修订表） | **不落** | 同上 |
| 修订表 `status` 的 `failed`/`revoked` | CHECK 里保留，**只写 `active`/`superseded`** | `revoked` 会与 B5 冲突（见 §3.3）；CHECK 取设计表的全集，免得为别人的取值再改一次表 |
| 至少一个 `knowledge_id`/`external_ref` | 收紧为 `knowledge_id NOT NULL` | 本轮只有 `weknora` 来源，`external_ref` 不存在，收紧后的不变量更简单也更强 |

**模型与迁移必须逐列一致**，这条由 `TestSQLiteMigrationSchemaSupportsBindings` 守住：它把 `000019` 的 DDL 原样执行，再在真实表上跑绑定/观测/唯一约束/CHECK。`AutoMigrate` 建的表只能证明模型自洽，证明不了 `migrations/` 里的那一份，而线上跑的是后者。

**该测试在本轮补了一段：索引也要对齐**（代码评审发现的漏洞）。早先它只看表名与 CHECK，于是漏掉过一类漂移——模型上的 `gorm:"index"` 与迁移里的 `CREATE INDEX` 是两处独立声明，谁多一条少一条都不会让上面那些断言变红，而测试库（AutoMigrate）与线上 DDL 就此分叉。现在它用 `PRAGMA index_list` + `index_info` 比**索引形状**（唯一与否 + 列序列，排序后比较），刻意不比名字：迁移里用表级 `UNIQUE` 声明的那两条，SQLite 建出来叫 `sqlite_autoindex_*`，而 `uniqueIndex` 建出来是带名字的索引，比名字只会造出假的红。

这一段补上当天就抓出两处真实漂移：

| 漂移 | 谁对 | 处理 |
|---|---|---|
| 模型把 `idx_lingdoc_project_assets_scope` 只声明在 `tenant_id` 一列上，迁移是 `(tenant_id, project_id)` | 迁移 | 模型给 `ProjectID` 补上 `index:...,priority:2` |
| 迁移多一条 `idx_lingdoc_asset_revisions_asset (asset_id, revision_no DESC)` | 模型 | 删掉这条冗余索引：同列的 `UNIQUE (asset_id, revision_no)` 就是 btree，本域的查询（精确查某一版、按 `asset_id` 取全部修订）都走它，`DESC` 只对谁都没做的「最新优先扫描」有用 |

另外 `ProjectAsset.DeletedAt` 去掉了 `gorm:"index"`：本域没有一个查询按 `deleted_at` 过滤，建一条用不上的索引只会多一处可以漂移的地方。`migrations/versioned/000098` 与 `migrations/sqlite/000019` 两份对称，两份都在真实 Postgres 容器上实跑过（见 §7）。

### 3.6 来源复核 `SourcePolicy.Validate`（契约 §2，评审点名的缺项）

契约 §2 的签名是 `SourcePolicy.Validate(projectID, actor, sourceRefs)`，只说清它管四件事：**当前授权、引用存在性、定位、资料版本**（返回形状未定义，与 T03 遇到的情况相同）。T09 §5 答应过要补这个薄封装，本轮补上（`policy.go`）。下面四条判据里的**归位**是「定位」那一项里评审补上的一步：坐标先要落在这份资料**此刻**的正文上，才谈得上比对。

`Resolve` 与 `Validate` 看着重叠，实际是两个时点上的两个问题：`Resolve` 拿一份 `Asset` 与一批检索命中，**产出**来源（`Source` 的坐标只能在这一刻确定，`ContentRevision`/`ContentRewritten` 是 `json:"-"`，跨进程就丢了）；`Validate` 拿一批**已产出**的 `Source`，回答「此刻还能不能当证据」。后者的判据必须包含**当下的**资料状态——`Resolve` 的入参里没有、也不可能有它（它连项目都见不到），所以 §5 里那句「转调 `Resolve`」在实现时改成了**复用它的判据**：定位那一层抽成 `quoteAt`/`selfConsistentAt`（`source.go`），产出与复核调用同一对函数，`Resolve` 的两个原函数退化成取 `hit` 字段的薄壳。两个时点若各写一套判据，「可用」的定义会各自演化而测试双双是绿的。

资料层的两条（存在性、当前授权）**不另写一套**，组合本领域的 `AssetGateway.ResolveAllowed`：它已经在做「还在不在本项目、就绪没有、还授不授权」，且每次现查。契约 §2 禁止的是「再调用已经包含来源检查的总入口」——那是跨域循环（工作区服务的基础授权）；这里是本领域内部的单向组合。

结论分**两层作答**，不互相顶替：

| 层 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 资料层 | `AssetDeny` | `not_found`/`not_ready`/`not_authorized`（复用 `DenyReason`） | 非空时坐标层**留空**：资料都不能用了，坐标是否对得上已无意义，再报一个 `stale` 只会误导 |
| 坐标层 | `Status` | `stale`/`unavailable`（复用 `SourceStatus`） | 资料层放行后才作答 |

两层的补充说明走 `Detail`（散文，给人看；机器判两层字段，别解析 `Detail`）——与 `DeniedAsset.Reason` 的枚举语义刻意分开，代码评审时按这条改过字段名。

返回值沿用 `ResolveResult` 的三段式（`Requested`/`Usable`/`Unusable`），理由相同（契约 §8）：只交可用的那部分，调用方就会把「没被复核」当成「复核通过」。集合收敛**不是一个平行实现**：`ID` 与 `AssetID` 都经网关那个 `normalizeKey`（`gateway.go`）——`normalizeIDs` 也调它。两边各写一套时（初稿就是这样）同一个 ID 在复核里是一种、在网关里是另一种，而两边的报错都说得通：`AssetID` 尤其危险，网关按修剪后的 ID 回答了，复核按原样去查，会得出「网关一条都没答」的**假故障**。

一条 `AssetID` 为空的来源**照答**（判 `not_found`，`Detail` 说明「没有指向任何资料」）而不是让整批报错——那是能逐项说清的事，不该污染一批（§8）。整批报错只留给真的坏掉的协作方：网关对某个请求 ID **既不在允许集合也不在拒绝集合**（`ResolveResult` 的不变量被破坏，`silentGateway` 用例钉着）。编一个原因出来会让调用方按错误的理由丢弃引用。

四条判据决定「不可用」，顺序即优先级：

1. **失效标记**：`ContentRewritten` 或 `ContentRevision != 0` → `stale`。与 `Resolve` 同一条规矩（术语表 §2 默认拒绝）：坐标被记录过变更，即便此刻仍对得上也不采信。
2. **资料版本**：`Source.AssetRevision != 当前 AssetRevision` → `stale`。指纹变了版本才递增（§3.1），所以版本前进**就是**「所引正文被改过」的事实。这里刻意**不**去比坐标：「原件没动、坐标也还对得上」恰恰是最容易蒙过复核的一类，而复核比产出更松是不可接受的。调用方想拿到当前版本的新引用应当走 `Resolve`，不是让复核宽免旧引用。
3. **归位**：坐标要回原文，而「哪一份知识是这份资料此刻的正文」必须由资料侧说了算。不校验的话，一条锚点指向**另一份文档**、坐标又恰好对得上的来源会被判 `available`（评审前的探针实测过：`err=<nil> usable=1`）——产出侧的 `Resolve` 有同义守卫（`ErrAssetKnowledgeMismatch`），复核不重做它等于自己拆掉那道守卫。
   判据取**修订行**（`RevisionReader.KnowledgeOfRevision` → `ProjectAssetRevision.KnowledgeID`）而非资料行：重解析后资料行上的 `knowledge_id` 仍是**绑定时**那一份（它是绑定的身份，`findBinding` 按它查），新知识 ID 只记在修订行上（见 §8 Q5）。修订行缺失（基线没补上的历史数据）时退回 `asset.KnowledgeID`——那与产出侧的守卫**逐字同源**，不会造出产出侧认不下的结论；存储故障则如实报错，不静默降级（降级等于无声地拆掉这道守卫）。
4. **定位**：归位过了才比坐标。取得到原文（强档）就逐字比对坐标指向的那一段；取不到（弱档）退回坐标自洽——与产出时同一档，也就是复核不会声称比产出更强的证据。

`stale` 这一档因此覆盖四种「坐标已不可信」（被标过重写、资料版本前进、锚点不属于这份资料、坐标取回的字串对不上），它们的区别只在 `Detail`。契约 §2 的 `Source.status` 只有 `available`/`stale`/`unavailable` 三个取值，复核不另造词汇——否则消费者要为同一个概念写两套映射。

上游故障（原文读取、授权判定、归位存储、网关自己坏掉）**如实返回 error**，不退化成「这条来源不可用」：那会把一次故障说成一批引用失效，调用方据此删掉的是好数据。

### 3.7 「回到原文」的形态：同页展开，不是跳转（S5）

界面切片那条验收写的是「定位可回到原文」。可选的形态有两种，本轮选了后者：

| 形态 | 为什么不是它 |
|---|---|
| 跳转到知识库文档页 | 那条路要 `kbId`，而 `Asset` 与 `Source` 在契约里都是 `additionalProperties: false`，**带不了它**（加字段是一次契约变化，要实际消费者评审，而 T09 没有评审人——§1）。且跳转会把「复核一条已产出的引用」变成「重新去检索一次」，两件事在术语上就不同：来源是**已产出**的证据，不是一次查询 |
| **工作台内联展开**（本轮） | 不离开当前上下文、不重新检索、也不需要知识库 ID；展开的边界由服务端一次答清 |

`GET /projects/{projectId}/sources/{sourceId}/context`（契约 `getSourceContext`）：

- **判定链与 `getSource` 逐字一致**，两步共用 `readSource`（`source_policy.go`）：身份 → `Authorize` → 按 `sourceId` 查 `types.Chunk` → `AssetForKnowledge` 反查资产 → `ResolveAllowed` 要求恰好一条 → `SourceResolver` + `SourcePolicy.Validate` 复核。**窗口必须在允许集合确认之后才读**，否则这个端点就是一条绕过 `ResolveAllowed` 读全文的旁路。抽成一个函数而不是照着抄一遍，理由是把「判据只有一份，两条路才有同一个答案」变成结构上的事实——两处各写一套时，将来改一处就会造出「取来源说不可用、展开上下文却看得到原文」的自我矛盾。
- **展开的是分块表里的文本（`chunks.content`），不是重新解析原文件得到的逐字原文**。后者没有落库（[ADR-0001](../adr/0001-source-anchor-uses-repo-offsets.md) 第二条后果），强档校对只在 `origin` 那条路上做（§3.2），两者不是一回事。所以 `segment.verbatim` 说的是「这段文字此刻逐字等于原文坐标上的那一段」，也只有拿得到原文（强档）才可能为真；拿不到原文时它**照样给正文**，代价是那段正文无法被原文证明。两种 `false` 在界面上的措辞不同（`sourceContext.ts` 的 `UNPROVEN_TEXT_NOTE` / `MISSING_TEXT_NOTE`），不能混成一句「原文」。
- **窗口只在引用块自己那一族里扫**（`chunk_type` 相同）。`text` 与 `parent_text` **各有独立且稠密的 `chunk_index` 空间**（子块另起序号），混进同一个窗口会让同一段文字出现两次——父块一次、子块一次。派生块（`summary`/`image_ocr`/`entity`/`wiki_page`…，`types/chunk.go` 共 12 个取值）没有指向原文的坐标，一律不可展开；判据是**白名单**（`expandableChunkType`）而非黑名单，底座将来加了新类型默认落在「不可展开」这一侧。
- **取邻居按索引位取（`<` / `>` 加 LIMIT），不是 `chunk_index` 的算术区间**：那个区间把「第几段」当成稠密整数，而 `chunk_index` 有空隙（软删的块留下空洞、别的族也占着同一片号码），算术区间会**静默少给**几段，让人以为是文档到头了。
- **不看 `is_enabled`**：停用是「不参与检索」，不是「不在原文里」。窗口跳过它，前后两段看上去就挨着了——那是这个端点最不该给的一种错觉。反过来，软删（`gorm.DeletedAt`）的块确实不在原文里，跳过它、**留下号码空洞**才是如实的。
- 窗口大小写死成 Go 常量 `contextWindow = 1`，不做请求参数：本轮界面只用一种窗口，暴露参数就要在契约里定义取值域与上限，而多出来的自由度没有消费者。单段正文有 4096 rune 上限，超了**只给位置不给正文**（降档而不报错，与 `origin.go` 的 `maxOriginBytes` 同一条政策）。
- 不设 `context_available` 之外的降级字段：引用失效的信息已经由 `source.status` 承载（那是 `SourcePolicy.Validate` 的结论），这里不再发明一个判据。`context_available=false` 只在两种情况下出现——引用块是派生块（`status` 仍是 `available`），或者它此刻指不回原文（`status` 非 `available`）。**界面的两种措辞就挂在这上面**，所以「展不开」不等于「这条引用坏了」。

**本轮的边界（写进界面文案的同一句话）**：命中那一段**不在** `segments` 里——它是 `source.quoted_text`，窗口只给前后邻居。所以「引用跨块」在界面上没有高亮可言：跨出去的部分既不在窗口里，也没有被标出来。窗口给的是「这道引用周围长什么样」，不是「这段引用覆盖了原文的哪些字节」。

### 6.2 幂等的落点（本轮查清了，初稿的前提是错的）

契约 §6 要求有副作用的请求带 `Idempotency-Key`，`bindAsset` 的该头是 **required**。初稿写「仓库没有任何幂等实现」——**不准确**：未合入的 PR #4 已经实现了完整的一套：

- 表 `lingdoc_operations(tenant_id, user_id, operation, target, key, body_hash, response_json, response_code)`，主键就是这五元组；
- `internal/lingdoc/workspacecore/service.go:140` 的 `operation()` 助手：授权 → 键查询（同 `body_hash` 重放 `replayed=true`；不同则 `ErrIdempotencyConflict`）→ 条件写入，与 `02-接口与Mock约定.md` §6 的顺序一致；并发撞键翻成 `ErrRequestInProgress`。

**所以 T09 的 S4 应当复用它，而不是新落一张 `lingdoc_idempotency_keys`。** 需要处理的只是：它现在住在工作区域（`internal/lingdoc/workspacecore`），资料服务要用得先抽成共用组件（或由 T07/T08 导出）。

**顺带发现一处文档互相打架**（不属 T09 范围，登记给设计文档维护者）：设计文档 §4.5 的 `lingdoc_idempotency_keys` 唯一约束是 `(tenant_id, actor_id, idempotency_key, command_type)`——**没有 `target`**；而 `02-接口与Mock约定.md` §6 说的作用域含「目标资源路径」，PR #4 也按后者实现（主键里有 `target`）。同一个键作用在两个目标资源上时，前者会误判成冲突，后者才对。

### 6.3 解析产物没有落点（承 T03 §6.5）

§3.2 的决定意味着：真实 PDF/DOCX 上「指回原文」只有弱档。要提升，需要在底座落解析产物（或按 `FilePath` 重解析并固定解析器版本）。**登记为欠账**，不在本任务内解决。

### 6.4 未测风险

- `FileHash` 在部分资料类型上可能为空；退化到只剩 `FileSize` 时指纹区分度低（同大小改内容检测不出来），只剩 `no_content_signal` 时**完全不检测**。这条路径有测试钉住行为，但**没有真实资料样本可验证它的实际发生率**——不知道线上有多少资料落在这一档。
- 强档判据依赖底座的实现细节（§3.2 两张表 + 引擎路由）。它们没有稳定的公开契约，改动不会让 T09 的测试失败，只会让强档**静默失真**。缓解只有注释里的出处引用，没有自动化守卫。代码评审后判据更严了（多两条排除），但**守卫方式没变**。
- 授权链路的替身：`KBReadChecker` 的应用层适配器**已落**（`kbReadChecker` → `access.NewKBPermissions`，2026-09-26 更新；原文写的是「随 S4 落」，那一步已经做完）。但**它并没有被真正跑到过**：集成测试的固定装置是同租户，而 `KBPermissions.Check` 在同租户 + Viewer 时直接放行、根本不查 shares——所以 `shares` 的真实实现在这条路上从未执行。T09 能保证的是「每次现查、不缓存、fail-closed」这三条，至于权限体系本身判得对不对是 T07 的事。见 §7 末表与 §6.5。
- **新增依赖**：`KnowledgeReader.UsesBuiltinConverter` 是本轮为「引擎改派」那个假强档加的端口方法。**已实现**（`dbKnowledgeReader.UsesBuiltinConverter`，2026-09-26 更新；原文写的是「S4 之前没有实现」），且集成测试走的就是这个生产实现，所以「txt 直读 → `ResolveParserEngine == ""` → 强档」这条链是真跑过的（`getSourceContext 展开同族邻居` 断言 `verbatim=true`）。它仍然是一条**便宜的旁路**：判不定时返回 false（降档），所以「不实现它强档等于没开」这条设计意图没有变，只是现在确实开了。
- Postgres 侧迁移（`000098`）本轮**在真实容器上手跑过**（见 §7），SQLite 那份由 `TestSQLiteMigrationSchemaSupportsBindings` 真实执行。但**仓库仍没有 PG 迁移的自动化测试**，且上面那次是 `psql` 直接执行 DDL，走的不是 `golang-migrate` 的 runner；runner 路径（版本表登记、`up`/`down` 顺序）依旧未被任何测试覆盖。

### 6.5 S5 的诚实边界（2026-09-26 登记）

- **界面没有在浏览器里连真后端跑过**。本机没有 T07–T12 需要的那套运行环境，所以那三条界面验收（只显示允许集合、拒绝越权/未就绪、定位可回到原文）**只到「代码这样写、纯逻辑这样判」为止**。本轮前端补的是抽出来的纯逻辑单测（`sourceContext.test.ts`/`sourceNotices.test.ts`，`node:test`）加**源码级**回归断言——仓库没有 vitest/jsdom/@vue/test-utils，组件「测试」是读 `.vue` 源码做字符串匹配，它证明的是**接线还在**，不是**渲染正确**。验证报告里 S5 因此仍是 `not_run`，不因为多了单测就上调；`vue-tsc --build` 通过、`vite build` 通过，都不是界面验收。
- **被拒明细只给得出 `asset_id`，给不出资料标题**。`listAssets`（`http.go:364`）只回 `resolved.Allowed`，丢掉了 `resolved.Denied`——被拒的那一份在界面上没有痕迹，也就没有它的标题可显示。契约 `Asset.title` 是必填，所以这不是「懒得查」，而是**没有合法的查询入口**。「只显示允许集合」本身是验收要求，本轮不改 `AssetListResponse`；这条属 F07 的另一刀（T15）。界面的做法是如实显示 ID，并写明为什么只有 ID。
- **「查看原文」展开的是分块表文本**，不是重新解析原文件得到的逐字原文（§3.7）。这一条同时写在界面文案里，不让它只活在文档里。
- 前端单测跑的是 `tsx --test`（`node:test`），**没有 DOM 环境**：`sourceContext.ts`/`sourceNotices.ts` 的存在本身就是为了让判定与文案能在没有浏览器的情况下被钉住，渲染那一层只能靠源码级断言。
