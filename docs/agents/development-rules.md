# 快速交付开发规则

> 本文件是所有 G1–G7 Spec 开发的详细执行细则。调用项目级 [`lingdoc-development-gates`](../../.agents/skills/lingdoc-development-gates/SKILL.md) 时读取本文件；`AGENTS.md` 只保留必须遵守的硬门槛。任务地图和 Issue 对应关系仍以 [`docs/TEAM_DEVELOPMENT_TASKS.md`](../TEAM_DEVELOPMENT_TASKS.md) 为准。

## 目标和适用范围

规则的目标是减少“实现一部分、评审才发现交付边界、再反复补齐”的循环。所有带有 Spec、数据库、权限、跨模块、并发、审计或真实适配器变化的 Issue/PR 都执行两道门：

1. **代码前门**：验收矩阵、范围、依赖和不可变契约已经明确；
2. **评审前门**：当前 head 的实现、测试、集成证据和文档已经闭环。

纯文字、换行、单文件机械重命名可以跳过完整矩阵，但仍必须说明影响范围并通过现有 CI。

### 文档提交的 CI 边界

门禁的**验证单元**是 (被测面内容, 基线内容)：被测面内容变了，或者基线在 PR 底下移动了，就要重测；两者都没变，就不重测。判定只读 Git（贡献面、树哈希、合并基点），判定器是 `scripts/ci/lingdoc_gate_decision.py`，工作流级与 PR gate 都从它取决策。**判定层只有这一个入口**：范围计算、改动文件、被测面推导、门禁面分类与格式快判都在这个模块里，没有第二个脚本能回答「跑不跑」。

- **被测面**来自 PR 自己的贡献（`base...head`）：Go 侧到**包**级，前端侧到目录。判定与执行都在合并后的树上进行，所以「贡献在新 main 上还成立吗」被正面覆盖。
- **推送被测面**是这次推送自己的 diff（`before...after`），基线是推送开始前的那个提交（创建分支时是 `after` 的父提交）。push 没有 PR 贡献面，它按自己的范围判定；验证单元仍是 (被测面内容, 基线内容)。
- 纯文档/证据提交：贡献面内容没变 → 保留快速门禁与文档契约校验，跳过 Go、前端、lint、mock、并发和真实接口集成矩阵。
- **基线合并**（把 main 并进分支或变基）：贡献面内容没变，基线变了 → 仓库级矩阵不重跑（main 的代码由 main 自己的 CI 负责），但 PR 贡献触及的包会在新基线上重测；贡献未触及前端时前端步骤跳过，并在门禁产物里写明理由。
- **改动判定脚本或门禁工作流本身时不得缩面**：裁判必须由全量门禁来验。
- 贡献包含代码、迁移、契约或工作流变更时，照常运行相关检查。首次打开、重新打开或手动 dispatch 按完整范围运行。
- 判定失败一律回退到全量：门禁的目的是不漏，不是卡人。

**门禁始终出现**：PR 上的必需检查必须有一个稳定的名字，否则 ruleset 要么永远等一个 Pending 的检查，要么在某次无关改动上突然失去它。所以 PR gate 的 job 不用顶层路径过滤把自己藏起来——**门禁 job 永远创建，跑不跑由 job 条件决定**；工作流级门禁同理，它们的触发器不按 PR 路径过滤，缩面发生在 job 条件里。被跳过的步骤给出 skipped 状态与理由，而不是让检查变成 Pending。

被跳过的 job 必须通过 job-level `if` 产生成功的 skipped 状态，不能用顶层路径过滤制造必需检查的 Pending 状态。门禁产物必须写明这次测了什么面（`surface`）、为什么是这个面（`reason`）、以及所依据的基线（`base`）——「Skipped means NOT RUN, not passed」，跳过必须带可解释的理由。

决策与理由见 [ADR 0006](../adr/0006-gate-surface-by-contribution.md)，判定层的结构见 [ADR 0007](../adr/0007-gate-decision-deep-module.md)：0005 处理「只重排版的推送」，0006 处理「基线合并」，0007 处理「判定这件事由谁做、结论以什么形状存在」。

### 门禁触发说明

八个门禁（七个门禁级工作流与 PR gate）遵守同一条触发纪律，各个工作流只在 `on:` 段留一行指向这里：

- **门禁始终创建**：门禁 job 永远创建，跑不跑由 job 条件决定。顶层 `paths:` 过滤会让工作流根本不启动，必需检查永远 Pending，门禁连结论都没有地方发布——所以触发器不按 PR 路径过滤，缩面发生在 job 条件里。被跳过的步骤给出 skipped 状态与理由，而不是让检查变成 Pending。
- **路径归属只登记一次**：门禁看的路径写在门禁面清单 `scripts/ci/lingdoc_gate_surfaces.py` 里，工作流不再带路径表。工作流级门禁的 `push:` 触发器保留一份静态镜像（GitHub 不能动态生成 `paths:`），镜像由手工维护：改清单就要同时改这份镜像。
- **判定只有一个入口**：跑不跑由判定模块 `scripts/ci/lingdoc_gate_decision.py` 判定，工作流只读它的结论。
- **结论一律发布**：每个门禁都发布同样的三个字段（`surface` / `reason` / `base`），每个没跑的检查都写明理由。

### 纯格式提交的 CI 边界

路径判定回答不了「这次改动碰了代码路径，但只是把代码重新排版」。工作流因此在 `synchronize` 事件上再问一次**内容**：本次更新是否只重排版、不改语义？这条内容判据由判定模块自己实现（`scripts/ci/lingdoc_gate_decision.py` 内的格式快判），判定层没有第二个入口。它接受两个判据：

- **gofmt 等价**：改动后的文件正是 `gofmt` 对改动前的文件会产出的结果。
- **只改注释与空白**：去掉注释、去掉字符串字面量之外的空白之后，两版的 token 序列逐行相同。

判定为纯格式提交时，**测试类** job（Go 测试、前端测试、integration、workspace-concurrency、mock、镜像构建、PR gate 里的 provider tests 与 frontend 步骤）以 job-level `if` 产生 skipped 状态。**lint 不跳**——它就是格式的裁判；contracts 校验、diff 空白检查与检查边界发布也不跳。判定模块把这条快判**折进**它给出的那一个布尔量：工作流的 `if:` 只读判定结果，不再自己组合「跑不跑」与「是不是格式改动」。

边界：

- 只覆盖 Go 文件。仓库没有前端格式化器，用「忽略空白」的弱判定会把字符串字面量里的空白变化误判成格式改动，那会改变行为。
- 含编译期指令（`//go:`、`//line`）的文件永远不算格式改动。
- 判不出来（范围解析不了、gofmt 不可用、文件增删或改名字）一律**不算**格式提交，照常跑全量。
- 首次打开、重新打开、手动 dispatch 与 push 到 main **不走**这条快门禁：PR 第一次被人看到时，整套矩阵必须跑。
- 判定结论与理由随检查边界一起发布，可复核。

接线纪律（2026-10-20 线上验证 #288 补记）：**job 的 outputs 是显式白名单**。step 往 `GITHUB_OUTPUT` 写了键，不等于下游 job 读得到——漏声明时下游取到**空字符串**，于是 `'' != 'true'` 恒成立、跳过条件静默失效且不报错。跨 job 引用必须在该 job 的 `outputs:` 里显式声明；**step 级引用**（`steps.<id>.outputs.<name>`）不需要声明。给工作流加门禁条件时，用守护测试断言「工作流声明的 outputs」与「判定模块写出的键」一致（`scripts/ci/test_lingdoc_workflow_wiring.py::GateStepWiringTests`、`scripts/ci/test_lingdoc_gate_contracts.py::WiringTriadTests`），只测脚本输出不够——本地求值不会模拟这层白名单。守护测试本身也必须有工作流在跑：PR gate 的「Test CI scope scripts」步骤无条件执行整个 `scripts/ci` 测试套件（`test_lingdoc_*.py`）。判定语义的用例只在 `scripts/ci/test_lingdoc_gate_decision.py` 这一个 seam 上——判定模块的公开接口；接线与文档的守护测试各自成文件。

## 默认运行模式：Agent 先完成，人审结果

这套规则默认把执行工作交给 Agent，把人的参与收敛到不可推断的信息、明确授权和最终审查。Agent 不得因为缺少偏好就暂停；先从 Issue、Spec、代码、CI 和环境推导事实，缺少事实时使用可复现的本地或 staging 替代，并在证据中标明边界。

### Agent 的责任

- 自动读取任务地图、Issue、Spec、迁移、OpenAPI、CI 和当前工作区，生成范围、依赖、真实消费者和验收矩阵；
- 自动创建测试账号、合成数据、临时数据库、浏览器运行时和失败注入夹具；
- 自动执行定向测试、application/HTTP 验收、浏览器 E2E、真实适配器、迁移、重启读回、并发和恢复验证；真实服务链路若不属于当前 PR，转为独立验收 Issue 并在当前矩阵跟踪。
- 在用户提供了授权的供应商/API Key 后，自行完成受控的真实模型调用、限流和用量记录；
- 自动更新验收证据、健康评分、PR body、Issue 状态和 Draft/Ready 建议；
- 对不能执行的项目记录 `NOT RUN`、`N/A` 或 `WARNING`，给出事实、影响和解除条件，不用猜测填成已实测 `PASS`。

### 人只需提供的输入

仅当下列信息不能从仓库或上下文推断时才询问：

- 外部模型供应商、模型名、endpoint 和 API Key；
- 外部 URL、SSO 测试账号或第三方服务的访问方式；
- 未定义的业务阈值、用户可见取舍和不可逆决策；
- 付费调用、生产写入、发布、转 Ready 或合并的明确授权。

API Key 只能放在环境变量、Secret store 或 CI Secret，不能粘贴到聊天、Issue、PR 或提交中。没有生产数据库时，Agent 自动创建生产同构的 SQLite/PostgreSQL staging 演练；验收报告必须明确这是 staging 证据，并将真实生产迁移/回滚标为 `N/A`，因为当前没有生产验收目标。

### 门禁状态和例外语义

- `PASS`：当前 head 有可复核证据，满足本次交付要求。
- `PASS (follow-up)`：当前 PR 接受该项不阻塞；真实服务验收事项必须链接到独立 GitHub Issue，不能把未运行写成已实测。
- `N/A`：验收前提在当前目标中不存在，例如没有真实生产数据库；该项不计入当前 PR 的必需矩阵。
- `WARNING`：宿主环境有局部限制，但等价的 WSL2、CI 或 staging 路径已通过；警告保留在报告中，不阻塞放行。
- `NOT RUN`/`BLOCKED`：仅对当前 PR 必需范围内的项目阻塞 Ready。外部真实服务链路可以转移到独立 Issue，当前矩阵使用 `PASS (follow-up)`。

### 最小输入门

Agent 开工后先把依赖分类为：

- `[DERIVED]`：仓库、Issue、Spec 或 CI 已给出的事实，直接采用；
- `[GENERATED]`：Agent 可以创建的夹具、账号、合成数据、临时数据库和浏览器；
- `[REQUIRED]`：必须由用户提供的供应商、密钥、外部地址或账号；
- `[APPROVAL]`：涉及费用、生产写入、发布或合并的授权。

只有存在 `[REQUIRED]` 或 `[APPROVAL]` 时才发起一次合并提问，并给出推荐默认值。收到答案后继续执行，不逐项回问。缺少某个外部输入时，只阻塞相关矩阵行，其余本地、合成和 CI 验证继续完成。

## 一、代码前门：先锁定目的地

### 1. 明确单一交付目的地

开发卡片必须只对应一个主要 Issue 和一个 Spec，并明确：

- 本次交付的用户可见结果；
- 明确在范围内和明确不在范围内的内容；
- 前置 Issue、阻塞依赖和可并行工作；
- 真实消费者：领域服务、application port、HTTP、前端或导出入口。

如果“完整 Spec”仍依赖未决定的业务规则，先创建决策记录或 Issue，不要用代码猜测并把未决内容写成已完成。

### 2. 创建验收矩阵

矩阵放在开发计划或 PR 描述中，至少包含以下列：

| 验收项 | 用户可见入口 | 领域不变量/事务边界 | 成功 | 失败/权限/恢复 | 持久化与并发 | 测试或运行证据 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 每个 User Story、失败场景和恢复场景一行 | API、application seam、UI 或导出 | 身份、版本、哈希、幂等、锁和审计要求 | 预期结果 | 拒绝、回滚、重试和隔离 | 迁移、重启读回、竞态和无部分写入 | 命令、CI、运行报告或人工验收 | TODO/PASS/PASS (follow-up)/N/A/WARNING/NOT RUN/BLOCKED |

当前交付范围内的矩阵出现 `TODO`、`NOT RUN` 或 `BLOCKED` 时，PR 不能放行；`N/A`、`WARNING` 和已链接验收 Issue 的 `PASS (follow-up)` 不阻塞，但必须说明边界，环境限制必须和产品断言分开记录。

### 3. 先写不可变契约

写代码前先决定并写下：

- 哪个模块拥有身份、版本、有效配置和哈希的真相；
- 哪个事务同时保护读取、校验、写入和审计；
- 哪些 reader/writer port 是必需的，替代组合根缺少能力时如何 fail-closed；
- 失败时哪些对象必须保持零写入，重试如何幂等；
- 审计记录如何被生产 application/HTTP seam 读取，而不是只在 store 测试中可见。

跨模块任务先画调用路径和数据边界，再拆实现提交。已有领域服务或 port 能承载契约时，复用它，不新建平行治理框架。

### 4. 记录风险和健康度

开发计划完成后运行一次 `lingdoc-health-scoring`，记录高风险维度、拟采取的措施和未验证证据。使用 Wayfinder 时，把未决规则拆成决策票；票未解决前保持 Draft，不把推测当实现任务。

## 二、实现门：沿验收矩阵形成垂直切片

- 每个提交有一个可验证目的：契约、实现、测试、适配器或证据同步，不把换行清理和业务修复混在一起。
- 先覆盖领域不变量和失败路径，再接 HTTP、前端和导出；每条用户路径至少覆盖成功、失败/权限和恢复。
- 涉及持久化、并发或审计时，同时补迁移、重启读回、幂等重试、竞态和无部分写入证据。
- 真实适配器和生产 seam 是交付的一部分。直接调用内存 store 或内部函数只能作为定向单元测试，不能替代 HTTP/application 验收。
- 代码、迁移、OpenAPI、Spec、PR body 和测试名称使用同一术语；发现术语冲突时先修正契约或记录决策。

## 三、评审前门：只用当前 head 的证据

Agent 在请求人工审查前完成以下清单：

- [ ] PR 关联一个 Issue 和一个 Spec，范围和 out-of-scope 与代码一致；
- [ ] 验收矩阵每一行都有当前 head 的实现位置和证据；
- [ ] 定向测试、构建、lint 和相关集成测试已运行，命令和 PASS/FAIL/PASS (follow-up)/N/A/WARNING/NOT RUN 已记录；
- [ ] 数据库变化覆盖 SQLite/PostgreSQL（适用时），并验证迁移、重启读回和失败回滚；
- [ ] 关键行为经过 application/HTTP 或真实交付 seam；若真实服务链路移交独立验收 Issue，矩阵须有链接和 `PASS (follow-up)` 记录；
- [ ] 并发、幂等、权限、审计和恢复场景已逐项检查；
- [ ] PR body 的 SHA、CI 链接和结论都指向当前 head，没有沿用历史提交的证据；
- [ ] `lingdoc-health-scoring` 已完成合并前复评，低分项有风险和处理计划。

只要当前交付范围内的必需项未完成，PR 保持 Draft。`N/A`、`WARNING` 和已链接的 `PASS (follow-up)` 不算未完成。转为 Ready 的条件是“当前范围矩阵已闭环”，不是“代码暂时能编译”或“通用 CI 已变绿”。

Agent 不应把常规测试、日志整理、证据汇总、本地依赖准备或 staging 演练交给用户。只有环境不可访问、外部凭据缺失或需要业务决策时，才向用户提出一项精确请求。

## 四、评审反馈和返工边界

Reviewer 使用三类结论：

- **Blocker**：违反 Spec、事务/权限/数据一致性或当前 head 无法证明，必须修复；
- **Required**：本轮应完成的契约、测试或文档同步，修复后复审；
- **Suggestion**：不影响本次目的地，记录为后续 Issue。

若评审发现新的不变量，先把它加入验收矩阵并说明来源，再修改代码。连续两轮出现新的 Blocker 时，停止继续堆补丁，重新切分 Spec、补决策记录或拆 PR；这样让下一轮评审面对稳定目的地。

代码修改后只重跑受影响的定向检查；若改变公共契约、迁移、事务边界或 base，则重新执行完整门禁。所有结果必须写回当前 head 的 PR body。

## 五、合并和关闭 Issue

合并前确认 PR 非 Draft、评审状态已解决、当前 head 的必需 CI 全部通过。合并后确认 `main` 的 CI 和关键验收证据；只有最后一个交付切片完成全部矩阵项时，才关闭对应 Issue。

人工审查接收的是结果包，而不是待执行清单。结果包至少包含当前 head、矩阵状态、验证命令和结果、失败证据、环境限制、健康评分、剩余决策和 Draft/Ready/合并建议。人负责审查代码与证据，并作最终 Ready、合并或风险接受决定。

```text

定向验证：命令 + 结果
集成验证：命令或 CI 链接 + 结果
环境限制：
未覆盖风险：
```
