# T15-读回式副作用断言

对应 issue #33。F11 和 F21 从各自声明的 S1 起点构造有效章节与已确认版本，再通过真实 HTTP 请求验证快照过期和历史标签刷新。

## 契约写法

需要观察某次写入的后置状态时，在后续读取步骤上声明 `readback_of`，并在该步骤的 `checks` 中写出 JSON Pointer、期望值和意图。例如：

```json
{
  "id": "F11-09",
  "operation_id": "getRelease",
  "request": {
    "path_params": {"projectId": "{{project.id}}", "snapshotId": "{{f11.snapshot_id}}"},
    "headers": {},
    "json": null
  },
  "readback_of": "F11-08",
  "checks": [
    {"path": "/data/is_current", "equals": false, "intent": "章节编辑后读回快照为历史版本"}
  ]
}
```

静态校验与执行器都要求读回步骤使用 GET、声明至少一条可求值检查，并引用前面已执行的写步骤。执行器在发出第一条请求前检查整条读回关系；读回检查只比较该 GET 响应中的实际值。

## 报告来源

读回步骤及其每条检查均记录 `observation`：`kind` 为 `readback`，并带有读取步骤、被观察写入步骤和 operation ID。报告中的 `actual` 因而能追溯到一次后续 GET 响应，不是从写入响应或界面状态推断出来的。

机制默认是黑盒 HTTP 观察。当前 F11/F21 都能经 `getRelease` / `getExport` 直接读回，因此没有使用数据库探针或白盒断言。

## 两条真实场景

- F11 先保存并确认两章、准备通过检查的快照，再编辑章节；随后 GET 快照并检查 `is_current=false`，最后确认 `startExport` 返回 `stale_input`。
- F21 提交导出并轮询到 `verified`，读取编辑前的当前标签，保存新章节后重新 GET 导出和快照；报告分别记录仍为 `verified` 和 `is_current=false`。

2026-09-27 修复版本机服务真实 HTTP 实跑通过：F11 的 10 个步骤、F21 的 13 个步骤全部通过。F11 编辑后读回 `/data/is_current=false`，导出请求返回 `409 stale_input`；F21 编辑前读回 `is_current=true`，编辑后读回导出仍为 `verified`、快照标签为 `is_current=false`。逐步实际值与观察来源见 `T15-S7-验证报告.json`，修复版二进制哈希、报告哈希和代码提交见 `T15-S7-证据.json`。本次只选择运行 F11/F21，其余 20 个场景没有执行。

HTTP 状态和响应检查能证明服务通过对应读取端点返回了这些值；它不单独证明 DOCX 可由桌面 Office 软件打开。
