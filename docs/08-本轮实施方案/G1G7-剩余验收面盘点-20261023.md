## 0. 口径与已知空白

- **验收点计数单位 = US**（User Stories 编号条目）。19 张 Spec 票正文**没有 `AC-xx` 编号**（`ACtoks=0`），统一结构是 `## User Stories` + `## Implementation Decisions` + `## Testing Decisions`。下文 US = User Stories 条数，IMPL / TEST 单列。
- **没有逐条 PASS 表**：仓内 `docs/06-灵档产品开发规划/*.md` 搜 `US-\d+` 零命中 ⇒ 「某条 US 已被交付」没有权威来源，本文只能按「登记处 summary + 已合并 PR + 文件:行」做**逐条映射**，属**推断层**；只有 #127 / #143 的 4 条映射有票面原文直接支撑。
- **「主链已落地」是静态存在性判定**（grep / 文件树 / 路由 / 迁移），路径图自述「未运行 `go test` / `npm test`」⇒ **不等于验收通过**。
- **推断标注纪律**（#437 明文要求「推断项标注 `（推断）`」）：本文凡属推断层的结论都逐条标 `（推断）`，主要是**「某条 US 已被交付」的映射**——交付记录写的是**子面**（「研究提案契约」「告警接线 + 两个版本字段」「模板升级的冻结」「立项确认的冻结」等），子面 → 具体 US 编号的对应关系**任何一处都没有被写下来**，因此 §1 表的「本轮已交付」列整体是推断层映射；只有 #127 的 US6 / US7 / US12 与 #143 的 US34 有票面原文直接支撑（未标推断）。**逐条 PASS 表仍缺**（见 §5）。
- **两代票的验收段落粒度不同**（影响「TEST 段条数」的横向比较，不影响以 US 为主的统计）：#123 #124 #125 #126 #127 #128 #129 #130 #133 九张的 `## Testing Decisions` 每条是一句单独可核验的要求；#135 #136 #137 #138 #139 #141 #142 #143 #145 #146 十张则出现「（必验成功）/（必验失败）」或英文 `Must pass: / Must fail:` 的**聚合条目**，一条里塞了十几个场景。按条数计时这十张的 TEST 段会**被低估**（例如 #143 的两条聚合条目展开后是 36+28 条）。本文的统计一律以 **US** 为单位，聚合条目不影响结论。

### PG 条件面（对应票面第 3 问）

显式含 PG 验收条款的有 **6 张票各 1 条**（#138 #139 #142 #143 #145 #146）；另 #130 的 US8 是**反向**的一条（只在 SQLite 成立，PG 上 fail-open 崩，#387）。**合计 7 条 PG 条件面**，且因 #360，这 7 条在 CI 上**没有回归证据**：`lingdoc-interface-integration.yml:64-78` 有 PG service + DSN，但 `:98`/`:100` 只跑 `./internal/router` 与 `./internal/container`，`app.yml` 无 PG service。

> **票面第 3 问的字面答案与精确口径**（本轮独立复核补记）：票面问「多少**只在 PG 上成立**」。**字面答案是 0** —— 19 张票的正文里**没有一条**把验收点写成「只有 PostgreSQL 能验、SQLite 验不了」；平台相关的写法一律是**「SQLite 与 PostgreSQL 要分别验证」**（两边都算，缺一边就不算完），#138 的 TD-05 更是条件句（「需要真实 WeKnora、PostgreSQL 和真实模型时单独记录 real 验收」，未提 SQLite）。所以那 7 条的准确分类是：
> - **5 条双边要求**（#139 #142 #143 #145 #146：SQLite/PG 各验一次，两边都算数）；
> - **1 条条件要求**（#138：PG 与真实模型侧单独记 real 验收，不含 SQLite）；
> - **1 条反向**（#130 US8：fail-open **只在 SQLite 成立**，PG 上不成立 ⇒ 它不是「只在 PG 上成立」，而是「PG 上过不了」，SQLite 上的绿不能算数）。
