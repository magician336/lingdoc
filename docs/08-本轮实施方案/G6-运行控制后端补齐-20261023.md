## 1. 为什么三票合一个面

三张票都改同一个文件 `internal/lingdoc/workspacecore/runtime_control.go`（改后名 `runtime_control.go`）。施工并行面登记处是「谁可以碰哪些路径」的唯一可校验权威，**任何两个面的路径集重叠都会被 loader 拒绝加载**。

上一轮 PF-1 收口时的裁决是 **#382 → #327 → #383** 顺序执行（依据是语义依赖，不是抢锁）。既然三张票串行落在同一个面上，就合并为一次交付、一次 PR，避免三个 PR 反复争同一段代码、反复触发基线合并。

## 4. 口径与不可变契约

### 4.1 #382-A 告警规则可读回

- `Service.ListRuntimeAlertRules(ctx, actor, projectID) ([]RuntimeAlertRule, error)`：只读事务 + 项目 read 授权 + `ListRuntimeRecords(tenant, projectID, "alert_rule")`，逐条反序列化。
- HTTP：`GET /api/v1/lingdoc/projects/:projectId/runtime/alert-rules`（`impactRouteRead`）。
- 返回的规则必须带出**状态**与**版本**。

### 4.2 #382-B 告警规则可停用 / 可更新

- `RuntimeAlertRule` 增加 `Version int64`（json `version`）与 `Status string`（json `status`，取值 `ACTIVE` / `DISABLED`）；新建时 `Status=ACTIVE`、`Version=1`。
- 新增 `RuntimeAlertRuleActionInput{ExpectedVersion, Operation, Reason, Signal?, Severity?, Disposition?, ResponsibleID?, Scope?}`。`Operation` ∈ `disable` | `enable` | `update`。**处置动作字段叫 `disposition` 而不是 `action`**——规则的 `Action` 是处置动作，语义会撞车。
- `disable` → `DISABLED`；已停用再 `disable` → `ErrInvalidState`。`enable` → `ACTIVE`；已启用再 `enable` → `ErrInvalidState`。`update` 改 `signal/severity/disposition/responsible_id/scope`，**未提供的字段保持原值**。
- `reason` 非空否则 `ErrInvalidRequest`；`expected_version` 不符 → `ErrVersionConflict`。
- `signal` / `severity` / `disposition` / `responsible_id` 的合法值**复用 `SaveRuntimeAlertRule` 的同一套校验**，不复制第二份规则表。
- `responsible_id` 仍须对项目有 manage 权。
- CAS 用 `CompareAndSwapRuntimeRecord(tenant, projectID, "alert_rule", ruleID, expectedVersion, next)`，`next.Version = expectedVersion + 1`。
- HTTP：`POST /api/v1/lingdoc/projects/:projectId/runtime/alert-rules/:ruleId/actions`（`impactRouteWrite(h, true, ...)`）。
- **`applyRuntimeAlerts` 必须跳过 `Status == "DISABLED"` 的规则**——这是本规格的核心行为，必须有测试证明。

### 4.3 #382-C 授权判定可观测

- **只记拒绝（deny），不记放行（allow）**。理由：放行是常态且每次读请求都会发生，记下来会淹没运行事件流、让 `GET /runtime/events` 的全量返回变成性能问题；拒绝才是需要值班响应的信号。放行侧由既有的 `request/success` 事件覆盖。
- **判定结果必须在不会被回滚的事务上下文里写**。operation 路径的授权拒绝会让写事务回滚 ⇒ 写在同事务里的事件会一起消失；而 operation 写路径恰恰是最需要观测的。
- **不能在 `authorizeProject` / `authorizeTenant` 里另开事务写事件**：`service_facade.go:449-451` 记录了「SQLite 单连接下写事务进行中另开 store 会死锁」。
- ⇒ **上下文 holder 方案**：`workspacecore` 导出 `RuntimeObservationHolder` 与 ctx 存取函数（holder 是可变指针）；`authorizeProject` / `authorizeTenant` 在拒绝时往 holder 写 `{capability, decision:"deny", reason}`；判定结果由 **holder 携带**，在**事务结束后**由一个**独立事务**写成运行事件（`category="permission"`, `status="deny"`, `error_code=<拒绝错误码>`，另带 `capability` 字段）。事件写入失败必须被忽略（`_ =`）。
- **holder 装在哪**：装在**服务方法**上（G6 运行时方法、四个 fail-open 访问审计路径、`runOperation`），而不是 HTTP 适配层。这样覆盖的是**所有经过 WorkspaceCore 事务的授权判定**，包含 G6 端点组，也包含内部调用；HTTP 层因此不需要改动。
- **覆盖面如实声明**：覆盖**经 WorkspaceCore 事务发起的 capability 判定**（G6 端点组在内）；**不覆盖 `projectOwner()` 一族 Owner-only 业务前置条件**（约 13 处，在 `authorizeProject` 之外）；**不覆盖**未经 `authorizeProject` / `authorizeTenant` 的判定。
- **拒绝事件不带 project revision**（判定失败时 `Project{}` 零值，且读项目行会削弱 404 的存在性隐藏语义）。
- 观测里只有 allow/deny 二值 + `error_code`，**没有细因**（拒绝原因被刻意抹平为 `ErrNotFound`）。

### 4.4 #327 审计失败 → G6 告警事件 + AuditEvent 字段

- **硬前置**：改 `internal/container/lingdoc.go:250-256` —— 让生产 sink 的失败**能被拿到**（返回错误或增加显式失败回调）。不改这里，下面的接缝在生产是死代码。
- **fail-open / fail-closed 的界线必须落在调用点**：把 fail-open 的访问审计抽成显式独立函数，由 fail-open 调用点使用；fail-closed 的调用点（`operationcore.go:458-464`、`agent_action_service.go:201`）**不发**「审计不可用」告警——它们已经以 500 `audit_write_failed` 失败了，再发是噪音。
- 事件形状：`category="audit"`、`status="failed"`、`error_code="audit_write_failed"`（`runtimeSafeCode` 允许下划线）。告警规则配 `signal="audit/failed"` 或 `signal="audit_write_failed"` 都能命中（`runtime_control.go:482` 的三种匹配都覆盖）。
- `AuditEvent` 增加 `TargetVersion int64`（json `target_version`）与 `ProjectRevision int64`（json `project_revision`），**沿用 `details_json` 形状**（由 `RecordAudit` 并进 details，与 `Reason` 同样处理）⇒ **零迁移、零 SQLite 重建表、跨方言无风险**。
- **关键写仍然 fail-closed**：审计失败 ⇒ 业务写入也失败。本轮不得改变这一点；告警事件的写入不得改变审计错误的返回值。

### 4.5 #383 运行控制的回退端点

- **回退经既有领域入口执行**，不新造回退领域逻辑：`reverseChangeSet`（`change_inverse_operation.go:30`，HTTP `impact_routes.go:103-105`）。
- `RuntimeControlInput.Action` 加 `"rollback"`；加 `Rollback *RuntimeRollbackInput{ChangeSetID, TemplateVersion, RulesetHash}`；`RuntimeControl` 加 `RollbackTo *RuntimeRollbackTarget`。
- `rollback` 语义：① 与 `pause` 完全相同的范围校验与授权（project scope 要求 owner，其它 scope 要求 tenant-manage，跨范围 → `ErrNotFound`）；② 通过领域入口执行逆向 ChangeSet（**不直接改 revision 指针、数据库指针或发布文件**）；③ 新写入停止（状态 `PAUSED`），记录目标配置；④ 写审计 `runtime.rollback`。
- `resume` 仍要求既有复验（`snapshot_id` + `export_id` + `runtimeRecovery.Recheck`），并校验目标配置仍可读（不匹配 → `ErrRuntimeRecoveryRequired`）。
- ⚠️ **「切回已验证配置」这一半本轮不完整实现**：让后续新写入真正使用旧模板/旧规则需要领域写路径支持，不在本面范围。本轮实现的是「停止新版本写入 + 记录回退目标 + 复验后恢复」。**这一条必须如实写进票面与 PR，不得让它看起来像已经切过去了。**
