# C 工作台设计讨论

更新日期：2026-10-12。来源：PR #105 三种工作台原型评审及本次 grill-with-docs 访谈。

本文保存已确认的产品方向与待讨论问题。它不是实施规格，也不表示原型已接入正式产品；接口和任务范围仍按 docs/README.md 指定的依据执行。

## 已确认

- 目标用户是科研人员、课题组和实验室；不预设用户会写代码或熟练操作电脑。页面应易懂、易操作。
- 用户偏好 PR #105 的 C 专注写作布局，以此作为后续设计讨论基础。具体入口、按钮和引导尚未确定。
- “首次使用产品”“首次进入项目”“首次负责章节”是三个不同的进入场景，不能统一按一个“首次”处理。术语见根目录 CONTEXT.md。
- 课题组第一个使用产品的人可能从空白开始：建立项目草稿、导入已有研究材料、与 AI 对话明确方向。
- 负责编写章节的成员需要先了解申报方向，再引导 AI 起草自己负责的章节。
- 用户认可“创建项目 → 整理申报方向与研究条件 → 导入已有研究材料 → 与 AI 对话整理方向和章节结构 → 起草第一版正文”的讨论框架，并要求先与既有文档整合。该顺序尚未成为新的实施流程。
- AI 应在产品各个环节提供帮助；建项表单、资料处理、方向整理、章节起草、核查和交付都应有相应的辅助入口。
- 建项表单与 AI 对话可以并存：表单保证项目结构完整，AI 对话作为草稿阶段可随时进入的辅助工作区，不强制成为额外的阻断步骤。
- 资料入口区分“选择已有资料”和“上传新资料”，避免把两种动作混成一个不明确的“导入”。
- AI 可以提出章节结构建议，用户逐项采纳和调整；正式章节结构不被模板强制锁定，用户可以决定采用模板、修改模板或形成自己的结构，但变更应保留清晰的影响和确认边界。
- 项目创建者、研究方向整理者、资料整理者和章节起草者可以是同一个人，也可以由多个成员承担；交互不应以角色交接为前提。
- 章节负责人进入时优先看到项目简报、申报方向、负责章节、相关资料和“开始起草”入口。
- 模板不是长期产品中的强制结构；用户可以采用模板、调整模板或形成自己的章节结构。当前 Beta 仍以已验证模板为实现边界，自定义或新建申报模板暂缓。
- C 工作台正文页常驻显示“当前项目、当前章节、当前责任、当前版本、下一步动作”；详细研究条件和成员信息通过项目简报展开。
- 只有多人协作时才显示责任人、协作者和待确认人；单人连续工作时隐藏分工面板，只保留当前任务和下一步。
- 草稿项目进入“项目准备工作台”，集中提供研究条件、资料、AI 对话和立项确认进度；不显示空白章节编辑器。
- 已立项但当前用户尚未分配章节时，显示项目简报、全部章节状态以及“选择要协作的章节 / 联系负责人”入口；不显示空白编辑器或无解释的灰色按钮。
- “专注写作台”是项目工作台中的“写作”路由，不是整个产品的唯一页面；左侧导航还应提供资料知识库、AI 调研、核查与交付等路由，并在切换时保留项目和当前章节上下文。

## 已发现的文档衔接

现有一阶段流程已明确“新建项目 → 填研究条件 → 选择已有资料 → AI 起草 → 采纳和人工编辑 → 确认 → 检查 → 导出可编辑 DOCX”，见[范围与任务流程](../08-本轮实施方案/01-范围与任务流程.md)。长期建项设计进一步把前半段拆为“创建记录 → 草稿阶段 → 立项确认”，见[建项阶段设计](07-建项阶段设计.md)；草稿期可以停留、上传资料、进行对话和受控检索，立项确认后才创建正式章节骨架。

因此，用户提出的五步可以作为**面向用户的引导层**，与现有状态机整合成：

1. 创建项目草稿（对应创建记录）；
2. 整理申报方向与研究条件（对应申报类别/模板和研究条件）；
3. 选择或导入项目资料（当前正式流程的术语是“选择已有资料/资料范围”；草稿期可以上传，不能把“导入材料”理解成通用导入能力已经完成）；
4. 与 AI 对话，形成研究条件候选并讨论章节结构（长期设计支持草稿期对话和受控检索；AI 可填写研究条件候选，但章节骨架仍由模板在立项确认时生成，不能承诺由模型自由生成章节结构）；
5. 立项确认后，起草负责人章节的第一版正文。

第五步之后接回已有链路：“采纳和人工编辑 → 确认 → 检查 → 导出可编辑 DOCX”。因此“生成第一版项目草稿”应改为“立项确认后起草第一版章节正文”：既避免与“项目草稿”混称，也保留立项确认对章节骨架和正式基线的边界。

G1–G7 的主要实现线已经合入当前 `main`（当前基线 `d04ac58`），因此当前问题不是“是否已经实现 G1–G7”，而是“哪些合入能力已经通过 Beta 的真实连续验收”。第二阶段减量计划仍规定首版只放行持续写作、依据回看和最小变更复核三个连续结果；“AI 整理章节结构”以及五步向导的正式交互仍不能仅凭 PR #105 的静态原型视为已验收。见[Beta 六项缺口开发计划](18-Beta六项缺口开发计划.md)。

## 文档已回答的设计问题

- [用户界面与交互规划](09-用户界面与交互规划.md) 第 5 节已经规定：建项是四步表单，但可以中途离开和返回；草稿阶段可以聊天、检索、上传；AI 按模板必要字段填写候选值并保留溯源；成员和权限在建项向导中配置；资料范围可以选择已有资料、创建范围或稍后上传。
- 同一文件第 7 节已经规定了上下文 AI：对话工作区同时显示项目/章节上下文、资料范围、输出目标、引用、工具步骤和待确认项；任务卡约束目标、资料、输出格式、不可改变的观点、证据要求和是否允许结构改写。
- [权限设计与复用 WeKnora](08-权限设计与复用WeKnora.md) 已经规定治理角色与职能角色正交、职能角色可叠加；`Author + Reviewer` 合法，同一人可以确认自己撰写的内容。流程步骤不等于必须由不同成员承担的角色。
- [建项阶段设计](07-建项阶段设计.md) 已经规定草稿期可邀请成员、草拟研究条件、上传资料、对话和受控检索；立项确认是唯一闸门。确认页必须显示他人修改和仍由 AI 填写的字段；负责人确认后才生成章节骨架。
- [建项阶段设计](07-建项阶段设计.md) 和 [用户界面与交互规划](09-用户界面与交互规划.md) 还规定了 UI 验收：建项结束时，用户应能在 30 秒内回答当前项目、当前版本和下一步动作。

## 待确认

- 草稿项目尚未生成章节时，C 工作台如何承接“研究条件 / 资料 / AI 对话”而不误显示空章节编辑器；既有文档明确草稿期没有 `Chapter`，但没有规定 C 的建项态入口。
- C 页面中常驻的导航、保存状态、工具入口和下一步提示。
- Q2–Q4 的其他建议（固定向导、允许跳过、成员职责驱动入口）尚未获确认。
