# G4. 模板、规则与问题治理

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)  
> 相关计划：[G1. 建项语义与草稿阶段](G1-draft-baseline.md)、[G3. PCC、ChangeSet、依赖图与技术路线图](G3-pcc-change-coordination.md)、[G4. 项目级模板副本与规则编辑](G4-project-template-copy.md)  
> 前置假设：T01–T16 已完成并通过各自验收。本文件是后续开发计划，不表示功能当前已实现。

## 1. 目标和基本判断

G4 把 T02 的固定演示模板升级为可复制、可编辑、可版本化、可检查、可回放的 Beta 模板和规则系统。它解决的是“这份材料是否满足项目事先声明的结构和基本要求”，不是替评审人判断研究是否有创新、论证是否有价值或结论是否正确。

模板是 LingDoc、组织、领域专家或用户整理并发布的一组项目结构和检查配置。模板不自动代表外部主管部门的官方要求；只有模板元数据中明确写出的来源、适用范围和依据材料才具有可追溯意义。

本阶段采用两条原则：

1. **模板先复制、后编辑。** 用户从已有模板版本创建项目级副本，在自己的项目内自由调整字段、章节、术语和声明式规则。源模板的后续发布不静默改变已有项目。
2. **规则只写明确判据。** 可以稳定计算的要求可以产生确定问题；需要示例或人工判断的要求最多产生待核提示。无法举出合格/不合格例子的“创新性”“写得是否全面”等要求，不作为自动阻断规则。

## 2. 范围、边界与用户结果

### 2.1 本轮交付

- TemplateProfile、TemplateVersion、ProjectTemplateCopy、RuleSet 和 RuleDefinition 的版本与绑定；
- 从已有模板版本复制出项目级副本，并编辑字段、章节、术语和声明式规则配置；
- computed、pattern、presence、consistency、model_assisted 五类规则的统一求值契约；
- 写作期 Template Check 与导出前 Preflight；
- ValidationIssue 的发现、去重、修复、resolve、waive、dismiss、复核与审计；
- 模板/规则内容哈希、冻结输入、ReleaseSnapshot 绑定和历史回放；
- 问题中心、检查结果和最小的规则统计；
- 与 G3 `template_upgrade` ChangeSet、与 G6 导出闸门的领域交接。

### 2.2 明确不负责

G4 不负责：

- 判断研究创新性、学术价值、论证是否“充分”或结论是否正确；
- 自动生成专家规则、自动决定阻断严重度或把模型相似度当成合规事实；
- 替用户改写研究内容、补证据、选择方法或确认主张；
- 跨项目共享模板库、模板市场、通用拖拽编辑器；
- 用户上传任意代码或自定义规则执行器；
- 通过模板检查绕过 G3 的变更协调、G5 的权限或 G6 的导出授权。

### 2.3 用户应得到的结果

用户应能回答：

1. 当前项目使用的是哪一个模板副本版本和规则版本？
2. 这条问题由哪条规则、针对哪个目标版本发现？
3. 该问题是确定的结构问题、待人工核查的问题，还是学术判断？
4. 我可以修复、豁免还是仅记录误报？这些操作影响哪个版本？
5. 为什么写作期看起来通过，但导出前仍然被阻断？

## 3. 核心对象与关系

### 3.1 TemplateProfile 与 TemplateVersion

`TemplateProfile` 是模板的稳定身份，`TemplateVersion` 是不可变的具体内容。版本至少包含：

- `template_profile_id`、版本号、来源类型、名称、说明和适用范围；
- 章节定义、字段定义、术语表、规则集引用和路线图必需项定义；
- 来源材料、整理者、发布时间、废止/召回信息；
- `content_hash`、`ruleset_hash`、创建者和审计记录。

推荐的来源类型：`lingdoc_builtin`、`organization_input`、`external_reference`、`project_copy`。来源类型只说明整理来源，不等于官方认证。

已发布版本不能原地修改。修改必须生成新版本；撤回默认只阻止新项目复制，已有项目继续按自己的副本和哈希运行。若发现必须停止使用的严重错误，需产生明确的召回记录、影响范围和迁移路径，不能悄悄改写历史版本。

### 3.2 ProjectTemplateCopy

`ProjectTemplateCopy` 是项目私有的模板副本。它至少保存：复制来源、当前副本版本、状态、内容哈希和规则哈希、字段/章节/术语/规则差异、创建和修改审计，以及绑定的 Project、Context Revision 和 ReleaseSnapshot。

副本状态：

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `draft` | 草稿期可编辑副本 | 编辑、预览、迁移、绑定 |
| `bound` | 已成为项目当前基线 | 读取；active 项目只能生成新版本 |
| `superseded` | 被新副本版本替代 | 只读、回放 |
| `discarded` | 项目草稿被丢弃后的副本 | 只读审计 |

项目实际读取字段、章节和规则时，以副本版本为准；复制来源只用于追溯，不能绕过副本读取源模板的“当前内容”。

### 3.3 RuleSet、RuleDefinition 与 RuleBinding

`RuleSet` 是一组可用于某个模板版本或项目副本的规则配置。`RuleDefinition` 是系统预定义的规则类型和判定契约；`RuleBinding` 把规则绑定到具体章节、字段、术语或交付对象。

每个绑定至少包含：`rule_id`、规则版本、`origin`、目标类型和范围、参数、严重度、触发场景、正反例引用、启用状态和负责人。项目可以配置已有规则的启用、停用、适用范围和允许范围内的参数，但不能改变规则执行器的安全边界。

### 3.4 ValidationIssue

`ValidationIssue` 表示在特定规则、特定目标版本和特定输入上发现的问题。逻辑身份为：

```text
(rule_id, target_ref, target_version)
```

检查级别不进入身份；写作期和 Preflight 可以共享同一问题身份，但每次求值必须记录检查场景、输入快照、ruleset_hash、发现时间和判定依据。新目标版本或 `ruleset_hash` 变化后必须重新求值，不能沿用旧裁定。

## 4. 模板生命周期

### 4.1 发布前

模板编辑者完成字段、章节、术语和规则配置后，必须通过结构校验、规则参数校验、正反例校验、回放校验和来源校验。未通过时只能保存为编辑草稿，不能标记为可复制版本。

### 4.2 复制和草稿期编辑

创建项目时，用户选择一个可用模板版本，系统同时建立项目级副本。草稿期编辑流程为：

```text
选择模板版本 → 创建项目副本 → 编辑字段/章节/规则
            → 预览迁移和影响 → 保存副本新版本 → 立项绑定
```

副本编辑与 ProjectSpec 保存使用同一项目版本条件。并发编辑时一次成功、一次 `version_conflict`，不得静默覆盖。删除字段、改变类型、停用章节或新增必要字段必须先显示迁移预览。

### 4.3 立项绑定

G1 立项确认读取当前副本版本：副本从 `draft` 变为 `bound`；Project 进入 `active`，Context Revision 从 0 变为 1；按副本定义生成 ProjectSpec 字段集和章节骨架；绑定当时的 `content_hash` 和 `ruleset_hash`。

立项绑定本身不创建 G3 ChangeSet；它是项目从草稿进入 active 的一次基线建立。未处理的必要字段迁移、孤儿值或规则结构错误必须阻止绑定。

### 4.4 active 项目升级

active 项目不能通过普通保存修改字段、章节、术语或规则绑定。任何模板语义变化都必须走 G3 `template_upgrade` ChangeSet。评估至少列出字段迁移、章节影响、规则重算、ValidationIssue、路线图必需项、确认和快照影响。

只有 Owner 可以应用升级。应用成功后，新副本版本、项目模板引用和新的 Context Revision 原子写入；旧版本继续供历史章节和 ReleaseSnapshot 回放。应用失败时不得留下半套字段、半套规则或孤立问题。

## 5. 模板可编辑内容

### 5.1 字段

可编辑：显示名称、说明、顺序、帮助文本、是否必要、格式约束和项目自定义字段。稳定 `field_id` 不得无迁移地改变数据类型；停用字段必须保留旧值和 ProvenanceRecord，不能用删除静默丢失数据。

### 5.2 章节

可编辑：标题、说明、顺序、是否必需、固定小节、写作上下文、字数和格式约束。删除或停用已有章节必须显示受影响的正文、主张、证据、路线图和导出项。active 项目只能通过模板升级 ChangeSet 操作。

### 5.3 术语

术语表只收真正会混用且需要统一的词。每条术语至少有推荐写法、禁止或需核查写法、适用范围和说明。术语规则可以提醒不一致，但不能在用户未确认时自动替换研究概念。

### 5.4 规则配置

项目编辑者可以启用/停用已有规则、限定章节或字段范围、调整允许参数和严重度。但模型辅助或需要学术判断的规则最多为 warning/info；只有判据稳定、误报可接受的结构规则才可申请 blocking，并需要产品与领域专家留下评审记录。

## 6. 声明式规则模型

### 6.1 规则分类

| 类型 | 可检查内容 | 默认结论边界 |
|---|---|---|
| `presence` | 章节、字段、对象是否存在 | 可计算；必要项缺失可阻断 |
| `computed` | 字数、数量、层级、范围、格式 | 可计算；按严重度处置 |
| `pattern` | 标题、编号、格式、术语表匹配 | 可计算或提示 |
| `consistency` | 字段与正文、章节之间是否一致 | 常需人工核查，默认 warning |
| `model_assisted` | 覆盖提示、关联建议、语义风险 | 只能建议，不能单独阻断 |

### 6.2 统一求值契约

规则求值输入至少包括：项目、目标 revision、模板副本版本、ruleset_hash、目标对象版本、冻结/编辑中标记和授权范围。输出至少包括：`rule_id`、`target_ref/target_version`、检查场景、`PASS/ISSUE/NOT_APPLICABLE/UNKNOWN`、严重度、消息、证据引用、求值器版本和 `based_on_revision`。

同一规则对当前内容和 ReleaseSnapshot 求值时，问题身份和字段结构一致；若输入不是冻结版本或授权已失效，结果只能是 `UNKNOWN`/待复核，不能伪造通过。

### 6.3 规则编写要求

每条规则必须说明编号、名称、判定方式、严重度、适用对象、触发场景、参数、正例/反例、负责人和来源。规则应优先从 warning 起步；运行一个周期并确认误报可接受后，才可以申请升级为 blocking。

“创新性足够”“内容写得很全”不能直接作为规则。可以拆成可核对问题，例如“是否明确说明与已有研究的区别”“是否出现研究对象、问题、方法、样本和预期成果”，但这些检查通过也不能推出学术判断已经成立。

## 7. 两级检查

### 7.1 Template Check（写作期）

写作期检查服务于即时反馈：可以在内容变化、手动刷新或异步任务完成时运行。它展示当前问题、严重度、规则依据和建议下一步，但不改变项目交付状态，也不承诺导出可用。写作期允许显示 `UNKNOWN`、待人工核查和模型建议。

### 7.2 Preflight（导出前）

Preflight 是导出的唯一放行依据。它必须在冻结的 ReleaseSnapshot 输入上重新求值，不复用过期的写作期 READY 标记。至少检查必要章节/字段/路线图交付项、blocking 问题、输入对象/模板/规则/授权版本、G3 复核状态、导出格式和冻结完整性。

只有 Preflight 明确返回可导出，G6 才能继续导出；写作期检查全部通过不能单独放行。

## 8. ValidationIssue 处置语义

### 8.1 状态

推荐状态：`OPEN`、`IN_REVIEW`、`RESOLVED`、`WAIVED`、`DISMISSED`、`STALE`。`STALE` 表示输入、目标版本或规则版本已变化，不能作为当前通过依据。

### 8.2 三种处置

| 动作 | 含义 | 限制 |
|---|---|---|
| `resolve` | 内容已修复或人工核查证明问题不成立 | 必须记录依据对象版本；重新求值确认 |
| `waive` | 暂时接受 warning/info 风险 | blocking 不可 waiver；保留问题真实性 |
| `dismiss` | 当前规则/目标版本判定为误报 | 必须有理由、判定方、操作者和版本；新版本可重新出现 |

`dismiss` 不等于关闭 G3 ImpactTask；问题处置和变更任务是两条独立链。blocking 问题即使被 dismiss，若对应影响任务、确认或授权仍未完成，也不能导出。

### 8.3 去重和重算

同一 `(rule_id, target_ref, target_version)` 的重复发现合并为一个逻辑问题，保留每次求值记录。目标版本、ruleset_hash、模板副本版本或冻结输入变化时重新求值；旧问题进入历史/STALE，不得把旧的 resolve 直接套到新版本。

## 9. AI 辅助边界

G4 可以使用 AI 帮助解释问题或提出待核建议，但 AI 不是模板发布者，也不是规则裁判。AI 允许把自然语言要求整理成待编辑规则草稿、根据正反例建议适用范围或提示文本、提出语义风险候选、用通俗话解释命中原因。AI 不允许自动发布模板、改变严重度、把建议写成 blocking、自动处置问题或放行 Preflight。

AI 输出必须标记为候选/待核，记录模型运行标识、输入范围、模板/规则版本和生成时间。正式状态只由声明式求值和有权限的人确认产生。

## 10. 版本、哈希和回放不变量

- 已发布 TemplateVersion、RuleSet 和已绑定 ProjectTemplateCopy 版本不可原地修改；
- `content_hash` 覆盖字段、章节、术语和模板元数据；`ruleset_hash` 覆盖规则定义、绑定、参数和严重度；
- Project、Context Revision、ReleaseSnapshot、ValidationIssue 和 G3 ChangeSet 都引用具体模板/规则版本和哈希；
- 历史快照只读取其冻结的模板和规则，不跟随当前版本变化；
- 同一冻结输入、同一模板/规则版本重复求值，问题身份、严重度和结构结果应一致；
- 规则实现或模型版本变化必须产生新求值记录，不能修改历史结果；
- 项目副本不自动进入跨项目共享库，源模板新版本不自动迁移已有项目。

## 11. 权限与审计

| 动作 | 默认责任人 | 必须记录 |
|---|---|---|
| 复制模板 | 创建者/Owner | 来源版本、复制者、时间 |
| 编辑草稿副本 | Owner/Project Admin | 字段、章节、规则差异、版本 |
| 发布可复制模板 | 模板管理员/领域负责人 | 来源、适用范围、评审和哈希 |
| 绑定立项模板 | Owner | 副本版本、迁移结果、Context Revision |
| 应用 active 模板升级 | Owner | G3 ChangeSet、评估、目标版本 |
| 改变 blocking 严重度 | 产品+领域负责人 | 正反例、误报数据、决定理由 |
| 处置 ValidationIssue | 具备相应权限的成员 | 动作、理由、操作者、规则/目标版本 |
| 查看历史回放 | 项目可读成员 | 访问授权和读取审计 |

Owner 不可用时，不能绑定新模板基线、应用 active 模板升级或放行导出。模板副本权限不能扩大资料、章节或租户权限。

## 12. 交付切片

| 切片 | 交付物 | 完成判据 |
|---|---|---|
| G4.1 模板域 | Profile/Version/Copy、来源、发布、哈希 | 已发布不可原地修改；项目绑定明确副本版本 |
| G4.2 副本编辑 | 字段、章节、术语、规则配置和迁移预览 | 草稿可自由编辑；不静默丢值；并发写入有冲突 |
| G4.3 求值契约 | RuleDefinition、RuleSet、统一输入输出 | 同一规则可对编辑内容和冻结快照求值 |
| G4.4 问题实体 | ValidationIssue、去重、版本和证据引用 | 问题身份稳定；新版本不复用旧裁定 |
| G4.5 处置语义 | resolve/waive/dismiss、权限和审计 | blocking 不可 waiver；dismiss 有理由和版本 |
| G4.6 两级检查 | Template Check、Preflight、冻结重算 | 写作期不能放行；Preflight 是唯一导出闸门 |
| G4.7 统计和问题中心 | 误报、漏报、处置和阻断原因 | 用户能看见规则、对象、依据和下一步 |

## 13. 与其他能力线交接

### 交给 G1

- 可复制模板版本和项目级副本创建入口；
- 副本字段集、章节骨架、必要项和立项绑定条件；
- 草稿期模板编辑不产生 active ChangeSet 的边界。

### 交给 G2

- 模板字段、章节和规则对 EvidenceCard、ResearchClaim、SourceAnchor 的适用范围；
- 证据重检、来源失效和授权变化触发 Template Check/Preflight 的条件；
- G2 证据对象进入当前冻结输入所需的版本和状态。

### 交给 G3

- `template_upgrade` 的新旧副本版本、规则哈希、字段迁移和问题影响；
- 模板、规则或路线图必需项变化时的 ImpactTask 创建依据；
- G3 稳定化所需的当前 ValidationIssue、确认和冻结状态。

### 交给 G5

- 复制、编辑、发布、绑定、升级、问题处置和历史读取的权限矩阵；
- Owner 不可用、项目隔离、租户边界和审计要求。

### 交给 G6

- 模板复制—编辑—立项—升级—回放 fixture；
- 正例触发、合格反例不误报、版本陈旧、权限失败、并发冲突和导出阻断证据；
- 误报率、处置时长、规则覆盖率、阻断原因和 Preflight 失败率指标。

## 14. 验收场景

### AC-G4-01：项目级复制与编辑

用户从已有模板复制项目副本，修改字段、增加章节、调整术语和规则范围。源模板不变；草稿项目读取副本新版本。

### AC-G4-02：立项按副本生成

Owner 确认立项时，系统按当前副本字段和章节生成 ProjectSpec 与章节骨架，不读取源模板的后来版本。

### AC-G4-03：字段迁移失败

用户把文本字段改为枚举字段。系统显示旧值迁移预览；未处理值标记为 orphaned，未完成处理前不能绑定立项模板。

### AC-G4-04：规则可重复求值

同一冻结快照重复执行字数规则和必填规则，问题身份、严重度和结构结果一致；规则实现版本被记录。

### AC-G4-05：写作期与导出前分离

写作期全部通过后，Preflight 发现 ReleaseSnapshot 中存在未冻结必需 RouteNode，产生 blocking；不能导出。

### AC-G4-06：问题处置边界

用户 dismiss 一个 blocking 误报。问题从当前规则问题集合中移除，但对应 G3 ImpactTask 仍为 OPEN，导出继续阻断。

### AC-G4-07：新版本重新出现

旧规则版本的问题已 resolve；模板或 ruleset_hash 更新后重新求值，新版本重新产生问题，不沿用旧裁定。

### AC-G4-08：active 模板升级

用户尝试普通保存修改 active 项目章节，操作被拒；通过 `template_upgrade` ChangeSet 评估并应用后，新版本生效，旧快照仍可回放。

### AC-G4-09：AI 只做辅助

AI 根据编辑者描述生成规则草稿和提示文本，但必须由用户补充适用范围、严重度和正反例；AI 不得发布规则、自动阻断或处置问题。

### AC-G4-10：项目隔离

一个项目编辑自己的副本后，其他项目不发生字段、章节或规则变化；用户不能凭副本 ID 读取另一个项目的私有内容。

## 15. 验收与统计

发布前必须用固定 fixture 验证每条规则的合格样例、反例和边界值；需人工核查规则的 `UNKNOWN` 情况；新旧版本回放；并发、权限和授权失败；三种问题处置；以及 Template Check 不改变交付状态、Preflight 能阻断不完整快照。

上线后至少统计：规则触发数、误报处置数、重新出现数、平均处置时间、阻断原因、Preflight 失败率、版本陈旧率和规则覆盖范围。统计只用于改进规则，不自动把规则升级为阻断，也不能把“误报低”解释成学术质量已经合格。

## 16. 不纳入 G4

本阶段不做跨项目共享模板库、模板市场、通用拖拽编辑器、用户代码规则、自动专家规则生成、自动学术质量评分或无限制模板智能体。G4 的完成标准是：项目可以编辑自己的模板副本，规则能在明确边界内稳定检查，问题能按版本和权限处置，历史快照能回放，导出由当前 Preflight 明确放行。
