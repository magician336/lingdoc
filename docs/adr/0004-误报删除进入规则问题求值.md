# 4. 误报删除进入规则问题求值

**状态**：已采纳（2026-10-20，由 issue #254 / G3 缺口收口-5 产生）

## 背景

G3 的验收标准 AC-G3-09 有两半：

1. 阻断级规则问题可以被「误报删除」受理（不再 500）——由 #253（G3 缺口收口-4）完成。
2. 误报删除之后，**该问题不再阻断当次求值**；但对应 ImpactTask 仍为 OPEN，项目仍不能稳定——本决策处理这一半。

第 2 半此前不成立。三个来源的说法互相冲突：

| 来源 | 主张 |
| --- | --- |
| Spec AC-G3-09 与 §10.2 | 误报删除后问题**不再阻断该次求值**；但不自动关闭 ImpactTask，也不能替代对象重新确认 |
| ADR 0003 第二节 | 「能否被责任人接受」与「是否阻断稳定化」是同一件事的两面；可被接受的，本来就从未阻断 |
| 现有代码 `internal/lingdoc/delivery/rule_snapshot.go` | 「Human disposition is workflow metadata; it cannot manufacture new findings or alter an evaluator's severity, identity, evidence, or version.」 |
| 现有测试 `internal/lingdoc/workspace/delivery_http_test.go` | **主动断言**「处置不改变阻断闸门」（`disposition changed the blocking gate`） |

Spec 与 ADR 0003 是一边的，代码与测试是孤例。术语上的根子在 `GLOSSARY.md`：影响任务侧早就有「接受不处理」，规则问题侧的三个动作却**没有术语条目**，于是「处置只是元数据」这句话在两套语义之间被各说各话。本决策同时补上三个术语条目（见 `GLOSSARY.md`）。

## 决策

### 一、两阶段求值：`Evaluate` 保持纯函数，处置在应用层合入

| 阶段 | 责任 | 契约 |
| --- | --- | --- |
| 阶段一：求值 | `delivery.Evaluate(input)` | **纯函数**：只产出 issues，不读处置、不读审计 |
| 阶段二：处置合入 | 应用层（`workspace`）读出当前绑定的处置 | 把处置贴回 issues → 交给**一个**阻断集判定函数 → 得到最终阻断集与状态 |

不采用单阶段（把处置塞进 `DeliveryInput`，让 `Evaluate` 内部合并），理由有两条：

- 求值器一旦依赖审计读取，就有两个求值器（`delivery.Evaluate` 与 `TemplateGovernanceRuntime.Check`）各合并一次，同一条知识必然漂移。
- 处置绑定需要**当次求值产出**的 issue id、规则、目标与版本，才能保证「同一规则版本、同一目标版本」下才生效，因此压不成单次传参（鸡生蛋）。

### 二、阻断集判定只有一处：`delivery.BlockingIssues`

「这条规则问题是否还阻断」此前同时存在于 `delivery.Evaluate`（`snapshot.go`）与 `TemplateGovernanceRuntime.Check`（`template_governance_runtime.go`）——这是计划文档点名的信息泄漏点。本决策把它收敛到 `internal/lingdoc/delivery/blocking.go` 的一个函数里，两个求值器与稳定化聚合器都走它。

判定规则只有一条：**阻断级问题被「误报删除」后不再阻断当次求值；「修正」与「豁免」不解除阻断。** 后者保持不变——判断依然成立，该由谁处置仍由谁处置；「豁免」对阻断级仍按语义被拒（400）。

### 三、误报删除的边界

- **只解除该问题对求值的阻断**：不关闭 ImpactTask、不解除稳定化阻断（挡住项目的是仍然 OPEN 的任务）、不替代对象的重新确认。
- **绑定完全匹配才生效**：规则、规则集摘要、目标、目标版本、项目版本全部一致。版本一变，处置不生效，问题重新出现并再次阻断。
- **求值结果仍要写明「这条问题被误报删除了」这一事实**：被处置的问题**仍留在 issues 清单里**并带着处置记录，审计与导出口径不得静默消失。

### 四、第二个求值器按 finding 身份匹配处置

交付链给每条 finding 发布一个 issue id；模板治理求值从**同一条规则判断**得出**同一条 finding**，但它不发布那个 id——那个 id 是交付链的把手，不是 finding 本身的身份。因此第二个求值器读处置时，匹配跑在**标识 finding 本身**的字段上：规则、规则集摘要、严重度、目标、目标版本、项目版本。

这不是把绑定放松成「同一条规则就算」：版本、目标、规则集摘要、项目版本一个都不能差，差一个就重新出现。差异只在 issue id 一个字段上——被记录的处置仍带着完整绑定（含 issue id）留在审计里，审计链没有因此少记任何东西。

交付链自己的读侧（`Service.ValidationIssueDispositions`）**未改动**，仍然是完整绑定（含 issue id）匹配。

## 被否决的备选方案

**维持现状并改 Spec。** 否决理由：Spec 的两半（§10.2 与 ADR 0003 第二节）互相支持，孤例的是代码与那条主动断言旧语义的测试；改 Spec 等于让实现反向定义产品语义。

**只让稳定化聚合器读处置。** 否决理由：那样「求值」与「稳定化」会用两套判定回答同一个问题，正是本决策要消除的信息泄漏点；而且求值结论仍会撒谎（检查说 blocked，聚合器说没挡）。

**把处置塞进 `DeliveryInput`，让 `Evaluate` 内部合并。** 见第一节。

**让第二个求值器复刻交付链的 issue id 算法。** 交付链对历史规则自己算 id（`vi-` + 摘要），对模板规则用求值器发布的 id；第二个求值器要复刻它就得知道「哪条规则走哪条算法、错误码是什么」，那是把交付链的内部结构泄漏出去，而且两边一漂移就静默错配。按 finding 身份匹配没有这个问题。

## 影响

- `internal/lingdoc/delivery/blocking.go` 是「是否还阻断」的唯一判定处；两个求值器与稳定化聚合器都走它。
- `delivery.Evaluate` 仍是纯函数，求值与处置的边界没有被打破。
- 冻结（`POST /releases`）与检查（`POST /projects/{id}/checks`）发布的是同一份求值结论：误报删除过的阻断问题在两处都不再阻断。被处置的问题仍在快照的 issues 里，带着处置记录。
- 导出仍然被挡住，但原因不是规则：被误报删除的问题对应的 ImpactTask 仍 OPEN，项目不能稳定化；规则回执的重放也仍然是 fail-closed（回放不读人工处置，重放的是不可变的那份求值）。
- 术语表补三条：**误报删除**（规则问题 `dismiss`，适用于任一严重度）、**豁免**（`waive`）、**修正**（`resolve`）。影响任务侧的「接受不处理」不受影响。
