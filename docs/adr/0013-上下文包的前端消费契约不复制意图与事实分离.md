# 13. 上下文包的前端消费：契约不复制、意图与事实分离

**状态**：已采纳（2026-10-23，由 Issue [#330](https://github.com/magician336/lingdoc/issues/330)（施工并行面 PF-6）与 Spec [#431](https://github.com/magician336/lingdoc/issues/431) 产生）

**修订关系**：本决策**不修订**任何既有 ADR。它决定的是**前端如何消费**已经存在的上下文包，不改服务端契约。

## 背景

服务端的上下文包早就落地了：`AgentContextPackage` 定义在 `internal/lingdoc/workspacecore/agent_research_model.go:409`，预览端点是 `POST /projects/:projectId/agent-context`（`internal/lingdoc/workspace/agent_routes.go:190`），每轮实际用过的包也留在 turn 的回执里。

前端对它的消费**只有一处残缺**：`frontend/src/views/lingdoc/ResearchPanel.vue` 里有一份自己的 `contextInput()`（`:268`）与一行预览（`:48`），显示来源定位、资料版本、模型使用许可与输出约束——**卡片、选择理由、卡片状态三样都没有**；而且改完表单之后界面从不复述服务端的组装结果。于是「我以为带了」和「实际带了」之间没有任何一屏可以对照。

PF-6 要补一个上下文包面板。摆在面前的是两个岔路口，每一个都会决定后面所有代码的形状。

## 决策

### 决策一：契约类型**不复制**，由传输层模块独家拥有

`AgentContextPackage` / `AgentContextInput` / `VersionRef` / `AgentSourceRef` 的前端形状住在 `frontend/src/api/lingdoc/agentApi.ts`（PF-5 的路径，已在 `main` 上）。本面的上下文包模块用 `import type` 复用它们，**不重新声明**，也**不导出**它们。

理由：同一份契约知识住在两个模块就是信息泄漏。服务端加一个字段，两个模块都要跟着改，漏掉一个就开始漂移——而漂移在运行时**不会报错**，只是某个界面发错请求。静态断言守住这条（模块的导出清单里不出现契约类型本身）。

### 决策二：**意图与事实是两个不可互换的类型**

- **意图**（`ContextIntent`）是用户勾选的卡片与其余请求参数：它是**发请求的输入**。
- **事实**（`ContextFacts`）是服务端组装好的那一份上下文包：它是**这一轮实际带了什么**。

两者的字段集不相交。视图的事实区只吃事实，编辑区只吃意图。

理由：把它们合成一个类型，就等于允许「本地勾选」被当成「本轮包含」渲染——而那正是本面要消灭的错误。分开之后，这个错误在**类型层**就暴露出来，不必靠人读代码发现。

配套的一条规则：**任何增删之后必须重新预览，事实区只由预览结果刷新**。服务端上下文输入是全量替换语义——删掉一张卡就是不再提交它，服务端重新组装时可能连带去掉它依赖的来源。所以本地增删事实区里的条目在语义上就是错的。

### 决策三：上下文包模块是**用例门面**，层次单向

```
ContextPackagePanel.vue  ──值导入──>  agentContext.ts  ──值导入──>  agentApi.ts  ──>  HTTP
        （视图）                    （用例门面）              （原子客户端）
```

原子客户端（一个端点一个函数）留在传输层模块；上下文包模块负责这一用例的完整编排——从意图构造请求体、调用预览、对齐卡片状态、到分组产出可展示的事实——对外只暴露一个入口。**视图不导入传输层模块**。

理由：这一层存在的意义就是藏掉「构造 + 对齐 + 分组」这三件容易做错的事。若视图直接调传输层，它就得自己拼请求体、自己对齐状态、自己分组——那就没有这一层了。

⚠️ 本决策会引入**本仓第一个 api 模块之间的值导入**（既有先例只有 `import type`）。这是有意的取舍：值导入让「意图与事实」「构造与对齐」的知识收在一个门面里，比让每个视图各拼一次请求体更符合深模块。层次方向由静态断言守住。

## 后果

- **`agentApi.ts` 是契约类型的唯一拥有者**。本面不改它（那是 PF-5 的路径）。
- **卡片状态按 id 且 version 双重对齐**。上下文包的 `card_refs` 只有 id / version / kind，**没有业务状态**；状态要从证据卡端点取，对齐键必须是完整版本——否则一张已经翻新的卡会挂着旧卡的状态。对不上时显示「状态未知」，**不回退**到任何缓存值。
- **选择理由按服务端原文逐条展示**，不解析成「哪一条对应哪个条目」的映射。理由的结构化映射是服务端契约缺口（[#432](https://github.com/magician336/lingdoc/issues/432)），前端不代偿。
- **面板不自己判断「要不要确认」**。它用 `sensitive_context_confirmed: false` 预览，服务端返回什么授权结论就显示什么。
- **预览失败或版本冲突 ⇒ 事实区清空**。保留上一次成功的包会让人以为那就是当前范围。
- 本决策**不解决**三件已单独开票的事：研究面板里那份重复的上下文构造逻辑（[#434](https://github.com/magician336/lingdoc/issues/434)）、「低风险状态卡免额外确认」在服务端不成立（[#433](https://github.com/magician336/lingdoc/issues/433)）、前端契约类型落后于服务端两个字段（[#435](https://github.com/magician336/lingdoc/issues/435)）。
- 模块名按命名规范取：`agentContext.ts`。登记处最初留的 `g2Context.ts` 以交付批次代号开头，命名登记表把 `^[gGtT]\d` 判为编号命名——实测新增该文件会让守护测试失败。PF-1 当年也把登记的 `g6Runtime.ts` 改成了 `runtimeMetrics.ts`，是同一类修正。
