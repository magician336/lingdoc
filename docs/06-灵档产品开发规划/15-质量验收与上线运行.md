# 质量验收与上线运行

> **后续设计参考**：本文保留完整产品方案；本轮范围见[实施方案](../08-本轮实施方案/01-范围与任务流程.md)，领取以[任务池](../TEAM_DEVELOPMENT_TASKS.md)为准。A/B/C 仅指领域，不分配人员。完整 PCC、复杂权限等不自动成为本轮前置条件。

## 1. 验收哲学

灵档的质量不是“文本生成得像不像”，而是研究团队是否能更可靠地找回依据、发现变更遗漏、完成可编辑交付。所有测试都围绕可追溯性、变更一致性、权限和交付保真展开。

## 2. 验收矩阵

| 维度 | 必测场景 | 通过标准 |
|---|---|---|
| 建项与基线 | 创建记录 → 草稿期协作 → 立项确认；草稿期丢弃 | `Revision 0 → 1` 只冻结语义、不改变语义，草稿期产物不失效；草稿期不产生章节、`ChangeSet` 与 `EvidenceCard` |
| 证据可追溯 | 主张关联材料片段；材料重解析 | 用户可打开原文位置；失效锚点/旧证据不再伪装为有效 |
| 变更一致性 | 改研究对象、变量、材料或模板 | 只创建相关影响任务；任务、状态、Revision 均可解释 |
| 异步正确性 | 任务运行中连续两次修改、重复事件、重试 | 旧 Revision 结果标为 `STALE`；重复任务无重复副作用 |
| 确认有效性 | 确认后编辑内容/替换证据 | 旧确认失效；重新确认所覆盖的版本和范围明确 |
| 交付可靠性 | 预检、导出、重打开导出文件 | 阻断问题不能进入 READY；关键表格/图形/引用/分页保真或明确报告 |
| 权限与资料边界 | 跨项目、跨角色、撤销授权 | 不泄露对象存在性/原文；模型上下文不包含未授权资料 |
| 易用与可恢复 | 解析失败、证据不足、取消、网络中断 | 显示下一步和责任人；失败可重试/恢复，不静默丢失 |

## 3. 关键验收用例

### AC-01：建项与基线成立

给定一个租户 `active` 成员（角色 ≥ `Contributor`）与一类已验证模板。创建记录后项目处于 `draft`、`Context Revision 0`、没有章节；草稿期邀请一名成员，该成员接受后**立即 `active`**，其职能角色对章节对象的写权为空（待指派，不是全集）。立项确认页必须同时显示两类差异——「自上次查看以来被他人修改的字段」与「仍是 AI 填写、未经人工改动的字段」，Owner 确认后生成章节骨架 Ch1–ChN 与 `Context Revision 1`，`status` 转 `active`、交付 `NOT_READY`。不得以“填完了表单”“生成了一段完整的研究条件描述”或“骨架已渲染”作为通过。

### AC-02：草稿期边界不变量

三条边界同时受测：

- **发现层不漏水**：草稿期的联网检索结果只能进入候选池并带层级标记，不写入正式证据；搜索摘要在导入关口即被拒绝，聚合页可导入但不得直接建立 `EvidenceCard`，补足原始出处后可显式升级且升级留审计。
- **草稿期授权不被重置**：草稿期上传资料的 `authorization_scope` 在立项确认后不变宽也不变窄；草稿期授予的职能角色在立项后仍为待指派。
- **语义不失效**：候选池在立项确认后层级不变、不标 `STALE`；草稿期发起创建 `EvidenceCard` 或 `ResearchClaim` 的请求被**显式拒绝**，而不是静默失败或落成孤儿记录。

### AC-03：证据闭环

给定已授权文献和一条主张，Researcher 创建 EvidenceCard；负责人能看到原文定位、支持范围和限制并确认。若原文仅提供背景而非证明，系统必须允许/推荐 `INSUFFICIENT`，不得强制成为已确认支持。

### AC-04：变更闭环

给定 Revision 117 的两章内容和路线图，负责人应用“缩小研究对象范围”的 ChangeSet。系统创建 Revision 118，识别受影响的证据、方法章节、进度和路线图；无关章节不受影响。存在未关闭的 `BLOCKING` 问题时交付不可导出，且该阻断项不接受豁免；若判定为误报（规则误判或模型误判），`Owner` 或 `Reviewer` 可删除它，但删除须记录理由、判定方与目标版本，目标章节产生新版本后该问题重新出现。

### AC-05：陈旧任务保护

对 Revision 118 发起证据重检/章节候选稿生成，在其完成前应用 Revision 119。118 的结果返回时必须保存为可审计的陈旧结果或丢弃，绝不覆盖 119 的候选或确认状态。

### AC-06：确认失效

确认一个章节版本后，改变该章节依赖的 ProjectAsset 或 ProjectSpec。系统应将确认标为不再适用，显示原因和最小需复核范围；用户重新确认后生成新的 Confirmation 记录，而不是覆盖旧记录。

### AC-07：导出保真

在无阻断项的稳定 ReleaseSnapshot 上导出 DOCX，随后自动/人工检查：标题层级、必要字段、关键数字、表格、路线图、引用、分页及可编辑性。出现无法判断或损失时，交付记录必须有问题项和恢复方式。

## 4. 自动化测试分层

| 层级 | 内容 | 责任 |
|---|---|---|
| 单元测试 | 状态机、ImpactResolver、版本比较、规则计算、权限判定 | 所属领域开发者 |
| 契约测试 | 命令/事件 schema、兼容性、错误码、幂等与陈旧写入 | Shared + 生产/消费者双方 |
| 集成测试 | WeKnora Gateway、队列、Outbox/Inbox、数据库迁移、DOCX 管道 | A/B/C 协同 |
| 端到端测试 | 固定资料集完成完整闭环、导出文件检查 | QA + 产品 |
| 安全测试 | 越权、撤销授权、恶意文件、SSRF、日志/模型上下文脱敏 | 平台/安全责任人 |
| 回归评测 | 证据支持、变更影响、误报、导出损失的基准集 | 产品 + QA |

所有 fixture 应脱敏、版本化，且覆盖：资料充分、资料不足、来源替换、相互矛盾证据、模板升级、跨项目越权和异步乱序。

## 5. 运行与观测

每个请求和异步任务都应关联 `tenant_id`、`project_id`、`context_revision`、`correlation_id` 与 `causation_id`。记录结构化元数据而非不必要的研究原文或密钥。

最小运行指标：

- 材料解析成功率、耗时、失败类别、重试次数；
- 检索/重校验成功率、证据不足率、锚点失效率；
- ChangeSet 从创建到稳定的耗时、影响任务数量、陈旧结果数；
- 确认失效次数、未解决阻断项、导出通过率和导出损失；
- 模型/工具调用成本、时延、拒绝/超时和人工接管率；
- 越权拒绝、授权撤销、导出审计和异常访问告警。

## 6. 上线与回退

### 灰度顺序

1. 内部测试：固定脱敏样例、全链路自动化和故障演练；
2. **Beta（限定试点）**：单一申报模板、少数授权项目、人工高频复核；
3. 扩大试点：在指标稳定后增加团队和材料类型；
4. 标准服务：模板、支持、部署和升级路径均可复用后再对外承诺。

### 回退原则

- Feature flag 可立即关闭候选生成、PCC 自动路由、导出等高风险入口；
- 不删除已创建的审计、ChangeSet、版本或导出快照；
- 迁移采用前向兼容，出现问题可停写/双读，不破坏既有项目；
- 模型/外部服务不可用时退回到检索、人工编辑和明确失败提示，不制造“已完成”的假状态。

## 7. 产品效果评估

对同一类任务建立前后对照，而非用主观好评替代证据：

| 指标 | 定义 |
|---|---|
| 人工投入 | 从资料整理到导出的有效人工时长；包含新增确认成本 |
| 来源支撑率 | 关键主张中具有有效、可定位证据或明确待核标记的比例 |
| 变更遗漏 | 人工复核发现但 PCC 未提示的受影响内容数量/比例 |
| 误报率 | 系统提示但人工判定无需处理的影响比例；规则判定与模型判定分别统计 |
| 交付损失 | 导出后关键字段、表格、图形、引用或分页的不一致数 |
| 采用与续用 | 不同修改轮次、后续申报中实际回访和持续使用行为 |

对外陈述只报告已完成的样本、条件、方法和结果；尚未验证的能力写为研发目标，不能把方案图当成产品效果。
