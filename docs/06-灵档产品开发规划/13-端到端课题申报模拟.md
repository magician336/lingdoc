# 端到端课题申报模拟

> **后续设计参考**：本文保留完整产品方案；本轮范围见[实施方案](../08-本轮实施方案/01-范围与任务流程.md)，领取以[任务池](../TEAM_DEVELOPMENT_TASKS.md)为准。A/B/C 仅指领域，不分配人员。完整 PCC、复杂权限等不自动成为本轮前置条件。

> 本文是依据当前 LingDoc 产品开发规划制作的演练案例，不是已经完成的真实申报，也不是对当前 WeKnora 已有功能的夸大描述。文中标注“规划能力”的部分，需要按路线图继续开发后才能成为产品承诺。
>
> 本文走的是**从建项到导出**的完整主线：建项三步（创建记录 → 草稿阶段 → 立项确认）→ 材料与证据 → 结构与写作 → 一次实质变更 → 影响处置 → 稳定化 → 预检与导出。每一幕结束时给出该幕的项目状态，全流程汇总见第 10 节；草稿不立项而是被丢弃的那条出口见第 15 节。
>
> 同一课题与团队的权限操作演练见 [`14-权限管理操作模拟`](14-权限管理操作模拟.md)：本文演示业务闭环，12 号演示支撑它的权限闭环。

## 1. 模拟任务

### 1.1 课题

**课题名称：数字化平台赋能高校创新创业教育对本科生创业意向的影响机制研究**

申报类别：教育部人文社会科学青年项目（演示用模板）。

研究团队希望完成一份包含选题依据、国内外研究现状、研究目标与内容、研究方法、创新点、技术路线、进度和预期成果的申请书。

### 1.2 团队与权限

| 人员 | 治理角色 | 职能角色 | 本次任务 |
|---|---|---|---|
| 李老师 | Owner | —（顶点，含全部职能） | 确认研究条件、应用变更、确认关键内容和放行导出 |
| 王同学 | Member | Author | 建项、草拟研究条件、负责选题依据与文献综述章节 |
| 陈同学 | Member | Researcher | 接入 ProjectAsset、制作候选 EvidenceCard、整理待补材料 |
| 赵老师 | Admin | Author | 管理项目配置与任务分派；协作技术路线章节、检查材料完整性，但不替代学术确认 |

两点值得先说明，它们在后面的流程里都会兑现：

- **李老师的 `Owner` 由建项产生，不由邀请产生**。邀请弹窗的治理角色只能给到 `Admin` / `Member`——`Owner` 只能走所有权转让（见 2.1）。
- **赵老师是“职责超出预设”的例子**：她的四项职责（管理模板、分派任务、检查材料完整性、协作 Chapter 6）对应 `Admin + Author`——预设之外的组合可直接在邀请弹窗里表达，不需要新增第六种核心项目角色（见 [`14-权限管理操作模拟`](14-权限管理操作模拟.md) 2.3）。她仍然拿不到 `evidence.confirm`、`content.confirm`、`changeset.apply` 和 `delivery.export`——行政支持不越位成学术裁定。

### 1.3 已有材料

```text
M-01 团队既有“创新创业教育”研究论文（已公开）
M-02 前期调研问卷与统计摘要（团队内部，项目可用）
M-03 上一年度项目申请书（仅作结构参考）
M-04 教育部项目申报通知与模板（本年度）
M-05 外部检索得到的数字教育文献（待筛选）
```

开始前，负责人确认 M-02 只可在本项目内使用，不进入其他项目或模型训练范围。

## 2. 第一幕：建项三步

### 2.1 ① 创建记录：一次轻量写入

动手建项目的不是负责人，而是王同学——真实课题组里这很常见。他在项目列表页点“新建项目”，进入建项向导。

**Step 1 选申报类别与模板**：`教育部人文社科青年项目-2026-v1`（`TemplateProfile`，C 域对象）。选定模板即确定两件事：研究条件的**字段集**（模板的必要字段）和立项确认时要生成的章节骨架。此刻骨架**尚未生成**。

**创建记录**落下的东西只有这么多：

```text
Project          status = draft
                 current_context_revision = 0
                 template_profile_id = 教育部人文社科青年项目-2026-v1
ProjectMember    王同学（创建者，临时 Owner）
章节             无
ChangeSet        无
交付对象          无
```

创建记录不写章节骨架、不产生 `Context Revision 1`、不涉及模板以外的任何交付对象。

**同一屏上还要定清两件事**，否则项目会一开局就错位：

```text
指定负责人：李老师
声明创建者自己的职能角色：王同学 = Author
```

系统据此自动发起一次所有权转让——**复用既有转让机制，不新增机制**。在李老师确认之前，王同学临时持有 `Owner`，项目任何时候都不出现零 Owner：

```text
转让前   王同学  governance_role = owner（临时）   李老师  尚未成为成员
转让后   李老师  governance_role = owner          职能轴恒为空
         王同学  governance_role = member         function_scopes = [author]
```

如果不声明创建者自己的职能角色，转让会让他按“未指定职能”处理，直接变成只读——而草稿期最想干活的人恰恰是他。

### 2.2 ② 草稿阶段：可以停在半途

草稿阶段**不是一组新增页面**，它就是“向导可以停在半途”这件事本身。王同学可以先走完四步直接立项，也可以在此停留任意时长。它可选、非必经，也不做默认着陆页。

#### 一起理思路

**李老师邀请陈同学加入**——`project.members.manage` 由 `Owner` 与 `Admin` 持有，王同学是 `Member + Author`，手里没有这项能力（见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 4 节）。治理角色 `Member`、职能角色 `Researcher`。**陈同学接受后立即 `active`**，不挂在 `invited` 上等立项——真实的实验室从草稿期就开始协作。此处与前不同的两点：

- **草稿期授予的是不带章节 scope 的角色**。章节尚未生成，所以陈同学此刻对章节对象的写权为**空**（待指派），不是全集——这是默认拒绝的直接应用，见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 3.2 节。
- 草稿项目只对创建者与被邀请成员出现；对非成员一律 `404 project not found`，不泄露对象存在性。

**会话是各聊各的**。WeKnora 的会话所有权是 per-user 的，LingDoc 不改造它，也不做“团队共享对话”。草稿期真正**共享**的是对象：`ProjectSpec` 草稿、项目资料、调研候选池。

#### 受控检索与候选池

陈同学在研究条件页打开调研智能体。上下文退化为项目自身（没有章节可以关联）：

```text
项目：数字平台课题（草稿）
关联章节：—
Context Revision：0（尚未立项）
已允许资料：M-01、M-02
来源：租户已配置的搜索能力与学术来源目录（目录版本：……）
```

他先写调研任务卡，不立即搜索：

```text
研究想法：家庭资源可能影响创业教育与创业意向的关系
问题：定义和测量方式？是否存在调节效应研究？本项目是否适用？
范围：中文/英文；2015—2026；论文和政策材料
排除：无作者、无出处、无法定位原文
输出：候选来源 + 比较表 + 待验证问题
```

检索走的是 WeKnora 既有的 `web_search` / `web_fetch`（**发现层**，LingDoc 不建第二套搜索引擎）。结果分三档落位：

```text
R-01  期刊论文《Family Support and Entrepreneurial Intention》
      作者、机构、年份、DOI 齐全，有可核验的原文位置          → 候选证据层
R-02  某学会年度综述的转载聚合页，无原始出处                 → 背景线索层
R-03  搜索引擎返回的一段摘要，未读原文                       → 仅作发现入口
```

**层级决定的是“它能否支撑证据”，不是“它能否被导入”**，三条动作的实际结果因此不同：

| 结果 | 导入项目资料 | 建立 `EvidenceCard` | 本幕实际发生的事 |
|---|---|---|---|
| R-01 | 可以 | 可以 | 用户选择片段 → `ImportCandidate` → 确认权限与范围 → `ProjectAsset` |
| R-02 | 可以（背景线索层） | 不可以 | 陈同学先以背景线索层导入；后来补上原始出处，**显式升级**为候选证据层，升级留审计 |
| R-03 | **不可以** | 不可以 | **在导入关口即被拒绝**，提示“该结果没有可重定位的原文位置，无法建立来源锚点，请打开原文后再选择片段” |

R-03 这条不是政策而是**结构结论**：只拿到摘要意味着没有可重定位的原文位置，而 [`03-数据模型与接口契约`](03-数据模型与接口契约.md) 第 2 节的 `SourceAnchor` 要求 `locator` 与 `quoted_text_hash`、`EvidenceCard` 以 `anchor_id` 为必填——锚点无从建立，证据卡在数据模型上就构造不出来。

**一次越界尝试**：陈同学试图把 R-02 直接变成一张证据卡。系统**显式拒绝**并说明原因——草稿期没有 `ResearchClaim` 可以关联，没有主张可以关联的证据卡就是孤儿记录。拒绝是显式的，不是静默失败，也不留半成品。

#### 资料与授权范围

陈同学上传 M-01、M-02，把 M-03、M-04 从租户已有资料关联进本项目——`asset.import` 归 `Owner`、`Admin` 与 `Member + Researcher`，它和“章节由谁来写”是两条不同的能力，并不因为王同学建了项目就归他：

```text
M-01 PROCESSING → READY
M-02 PROCESSING → READY（authorization_scope：本项目）
M-03 READY（只读参考）
M-04 READY（模板依据）
```

M-02 的授权范围在这一步就写死：不进其他项目、不进模型训练范围。**这条范围在立项确认后不变宽也不变窄**。

#### 研究条件与 AI 填写

王同学按模板必要字段逐项草拟。其中「拟用方法」「核心变量」他不想手敲，于是选择一段会话的**轮次范围**作为上下文，交给 AI 填写：

```text
研究对象：普通本科生
研究场景：高校创新创业教育
核心目标：解释数字化平台、创业教育与创业意向之间的作用机制
拟用方法：问卷调查 + 访谈 + 结构方程模型        [AI 填写 · 待确认]
           溯源：会话 S-12，第 12—18 轮，采用片段 3 处
核心变量：数字平台使用、创业教育获得、创业意向    [AI 填写 · 待确认]
           溯源：会话 S-12，第 12—18 轮，采用片段 2 处
已有资源：前期问卷、团队论文、合作高校样本渠道
当前限制：样本范围、因果解释、访谈伦理审批仍需确认
```

三条硬约束在这段里同时成立：

1. **AI 产出的值默认 `待确认`，绝不默认已确认。** 系统允许生成候选值，但不允许把模型推断写成项目事实。
2. **每个 AI 产出的字段值都带溯源**——会话、轮次范围、实际采用的原文片段，可以回看。否则 `Context Revision 1` 从第一天起就含有无法回答“基于什么”的项目事实。
3. **上下文粒度是轮次范围，不是整段会话。** 用户可跨多个会话多选，但系统不提供“把整段对话当依据”的按钮。

#### 换模板（草稿期自由，但不清空）

李老师换了一次模板——`template_profile_id` 属于项目设置，走 `project.settings.edit`，归 `Owner` 与 `Admin`。草稿期换模板是自由的（骨架尚未生成），但字段集由模板的必要字段决定，所以换模板会改变字段集，处置规则是：

```text
研究对象      两模板同名            → 按名匹配保留，溯源一并保留
研究场景      原模板有、新模板没有    → 标为“模板不再需要”（可见状态，不是删除）
预期成果      新模板需要、尚未填      → 标为“待填”
```

**不得因换模板清空已填字段**——那些字段可能带着用户选过的溯源，静默销毁等于抹掉依据。

### 2.3 系统对草稿值的质疑

填写与质疑是两条独立通道。系统填完之后，仍然必须对它**自己填出的值**提出问题：

- “普通本科生”的样本边界还不够具体：是否包含不同年级、不同专业和不同地区？
- “数字平台使用”需要说明平台类型和测量方式。
- 结构方程模型需要样本量和量表依据；当前缺少支撑材料。
- 因果关系表述可能超出横截面问卷能够支持的范围。

这些是待确认问题，不应由模型直接补成确定事实。

### 2.4 ③ 立项确认：全流程唯一的闸门

整条建项链路上只有一个闸门。其余步骤都是为这个确认准备输入，或为确认后的协作准备边界。

**确认页必须显示两类差异**：

```text
自你上次查看以来，被他人修改的字段：
  研究对象      李老师 → 王同学（3 天前）
  核心变量      + 家庭资源（王同学，2 天前）

仍是 AI 填写、未经人工改动的字段：
  拟用方法      会话 S-12 第 12—18 轮（3 天前）      [查看溯源]
```

草稿期没有 `ChangeSet`，因此**确认页是唯一的可见性关口**，不能省略。

第一类差异防的是“别人改了研究对象、Owner 没看见就点了确认”。第二类差异防的是另一半，也是这一幕最容易漏掉的地方：「拟用方法」从头到尾没有任何人碰过——它是 §2.2 里 AI 从会话 S-12 第 12—18 轮填出来的，一直挂着 `待确认`。如果确认页只列“他人修改”，这个字段就会被整体确认顺带冻结进基线，而李老师从未看过它。它不阻止确认（李老师的确认本身就是那道人工闸门），但必须被看见，点 `[查看溯源]` 能回到当初的会话与轮次。

确认同时**不抹掉来源**：字段的**来源**（人工填写 / AI 填写 / AI 填写后人工改动）与字段的**状态**（草稿 / 待确认 / 已确认）是两个正交的维度，确认只推进状态。因此 `Revision 1` 之后仍然回答得出“这个值当初是 AI 根据哪几轮对话填的”——这正是“哪些内容基于什么”在项目第一天的兑现。

李老师确认的是**整个研究条件草稿**，不是逐字段重新点一遍。确认后：

```text
Context Revision 1
Project Status:   active
Delivery Status:  NOT_READY
章节骨架           Ch1–ChN（依所选 TemplateProfile 生成）
```

**`Context Revision 0 → 1` 是 `ContextRevision` 序列里唯一一次不改变语义的递增**。它把 `Revision 0` 的内容冻结为正式基线，而不是修改项目语义。由此两件事在本幕同时成立，也是后面 PCC 不会误判的前提：

- 建项是**唯一不经 `ChangeSet` 产生 Revision 的入口**——首版基线没有可比的既有语义，所以由 Owner 一次性确认，而不是“对一个空基线做变更”。
- **基于 `Revision 0` 的产物在立项确认时不失效**。防陈旧规则是机械比较 `based_on_revision == current_context_revision`，在这里会误判：草稿期检索出的候选池，其依据的语义内容**等于** `Revision 1` 的内容，因此继续有效，**不标 `STALE`**。真正按机械比较处理的是 `117 → 118` 那种实质变更。

立项确认还同时兑现三件事：

```text
草稿期上传资料的 authorization_scope   不变宽，也不变窄
草稿期授予的职能角色                    进入“待指派”：对章节写权为空，直到被指派 scope
草稿期检索出的候选池                    层级不变，一条都不标 STALE，也不进入 Revision 1
```

基线成立后，**研究条件不能再被直接编辑**。任何实质修改都必须走 `ChangeSet` 的评估—应用两阶段，系统不提供绕过入口。

### 2.5 本幕状态

```text
项目状态        draft → active
Context Revision 0 → 1
交付状态        无对象 → NOT_READY
章节             无 → Ch1–Ch6（骨架，无版本）
候选池          R-01 候选证据层、R-02 背景线索层（已升级）、R-03 已在导入关口拒绝
```

## 3. 第二幕：材料接入与证据整理

立项确认之后，草稿期收进来的材料继续有效——授权范围没变，处理状态也没丢。陈同学现在才开始做**证据**这一步，因为直到这一刻才有了可以关联的对象。

### 3.1 材料处理

M-01 ~ M-04 已在草稿期完成接入与解析，授权范围与处理状态都原样带过立项确认。本幕复核全部状态，并继续把 R-01 那条外部来源沉淀为项目资料。当前 WeKnora 可复用的部分负责文件保存、异步解析、分块、向量化、索引和处理状态展示；LingDoc A 域负责把它们映射为项目级 `ProjectAsset` 和 `SourceAnchor`。

```text
M-01 READY
M-02 READY（权限：本项目）
M-03 READY（只读参考）
M-04 READY（模板依据）
R-01 PROCESSING → READY（外部来源，候选证据层）
```

如果 M-02 解析失败，系统应显示失败原因并建立待处理任务，而不是让模型假装已经读到它。

### 3.2 证据卡示例

#### 证据卡 E-01：团队前期结果

```text
来源：M-02，问卷统计摘要，第 4 页表 2
支持主张：团队已有样本中，数字平台使用与创业意向存在统计相关
支持范围：当前样本、当前测量工具和当前分析方法
限制：不能单凭该结果证明普遍因果关系
状态：CANDIDATE
```

李老师确认其可以作为“前期基础”使用后：

```text
EvidenceCard E-01 → CONFIRMED
```

#### 证据卡 E-02：外部研究

```text
来源：M-01，第 8 页
支持主张：创新创业教育与创业意向之间存在理论和经验研究联系
支持范围：该论文研究对象和方法条件
限制：研究场景与本项目拟定样本并不完全相同
状态：CANDIDATE
```

#### 证据卡 E-03：不足证据

```text
待支持主张：数字化平台如何改变创业教育作用机制
当前结果：已有材料只说明相关概念，缺少直接机制证据
状态：INSUFFICIENT
补充任务：检索机制研究；由负责人判断理论路径
```

产品在此处不能把“相关主题的论文”自动升级成“直接证明机制的证据”。

**草稿期导入的来源不会被浪费**：R-01《Family Support and Entrepreneurial Intention》是草稿阶段检索到、并按候选证据层导入的。它在草稿期什么也做不了——没有主张可以关联，`EvidenceCard` 建不出来；立项确认后它仍是候选证据层、没被标 `STALE`，于是此刻可以直接被选为证据基础，不必重新检索一遍。这正是 `Revision 0 → 1` 不使草稿期产物失效的实际价值。

## 5. 第四幕：分章节生成与人工编辑

王同学在“章节候选稿”任务中选择：

```text
目标章节：Chapter 2
资料范围：M-01、M-03、已确认 E-01、候选 E-02
不允许使用：其他项目资料、未授权全文
输出要求：按理论脉络组织，不扩大因果结论
```

Context Assembler 只拼接本任务所需的 ProjectSpec、章节草稿、EvidenceCard 和待核问题。WeKnora 的检索和生成能力返回带引用的候选稿：

```text
段落 P-12：引用 E-02，状态 AI_DRAFT
段落 P-13：发现“机制”证据不足，标记 REVIEW_REQUIRED
段落 P-14：引用 E-01，状态 AI_DRAFT
```

王同学将 P-12 改写为更谨慎的表述；陈同学补入外部候选文献 M-05——走两阶段导入，先成 `ImportCandidate`，确认权限与资料范围后才成为 `ProjectAsset`。P-13 指出的机制证据缺口转成一条待办任务。随后李老师确认 Chapter 2 的 `ChapterVersion`（v2），核查范围为“理论脉络完整、引用可定位”。此处 P-12 引用的 E-02 仍为 `CANDIDATE`，即“明确标为待核”，满足“内容确认以其所引证据已有确认记录或明确标为待核为前提”的条件（见 [`08-权限设计与复用WeKnora`](08-权限设计与复用WeKnora.md) 第 3.3 节）；章节确认不因此免除证据确认——E-02 的自身状态仍需单独处理。

段落状态只说明“这一段处理到什么程度”，本身不是确认记录：`content.confirm` 的对象是 `ChapterVersion` / `ResearchClaimVersion`，绑定版本与核查范围，不按段落逐条记账。因此不能因为章节读起来完整，就把段落状态当成已确认。

写作过程中王同学随时可以跑一次**模板检查**——它不需要快照，只看项目当前内容：

```text
[阻断] Chapter 2 缺少理论框架的样本范围
[警告] 研究目标与预期成果术语不一致
```

他补上范围说明、把两处术语统一到 `ProjectSpec` 的写法，两条随即关闭。第八幕的预检会在冻结的版本集合上复跑同一套规则，不会再报出它们；但预检仍要单独跑——模板检查答的是“当前内容还缺什么”，预检答的是“这一个快照能不能导”（见 [`09-用户界面与交互规划`](09-用户界面与交互规划.md) 第 10.2、12.2 节）。


阻断项与豁免的边界在这里必须守住：**阻断级问题只能被修复、关闭或判定为误报删除，不能被豁免跳过**；只有警告/提示级问题才可由 Owner 记录理由后豁免。误报删除适用于任一严重度、也适用于规则误判与模型误判两种情况，但要填理由、记规则、判定方与目标版本，且只对当前规则与目标版本生效——目标章节一旦产生新版本，被删除的问题会重新出现。这个作用域**跨检查级别、也跨判定方**：第四章里删掉的误报，预检只要目标对象版本未变就不再报出，不会因为换成了对快照求值就复活。

```text
Delivery Status: READY → EXPORTED
```

负责人点击导出后，系统生成可编辑 DOCX，并保存：

- 导出文件和哈希；
- ReleaseSnapshot ID；
- 使用的 Context/Content/Template 版本；
- 预检结果；
- 导出时间和操作者；
- 处理前快照与恢复路径。

## 10. 全流程状态账本

把八幕的状态串起来看，`Context Revision` 只递增了两次，且第一次不改变语义：

| 幕 | 关键动作 | `Context Revision` | 项目状态 | 交付状态 | 章节 |
|---|---|---|---|---|---|
| 2.1 | 创建记录（`draft` + `Revision 0`） | `0` | `draft` | 无对象 | 无 |
| 2.2 | 草稿期协作、检索、上传、AI 填写 | `0` | `draft` | 无对象 | 无 |
| 2.4 | **立项确认（唯一闸门）** | `0 → 1` | `draft → active` | `NOT_READY` | Ch1–Ch6 骨架 |
| 3 | 材料解析、建证据卡 | `1` | `active` | `NOT_READY` | 骨架 |
| 4 | 责任人、章节 scope、依赖图 | `1` | `active` | `NOT_READY` | 骨架 + 指派 |
| 5 | 章节候选稿与确认 | `1` | `active` | `NOT_READY` | Ch2 v2 |
| 6 | **应用 CS-01** | `1 → 2` | `active` | `BLOCKED` | 待复核 |
| 7 | A/B/C 影响处置 | `2` | `active` | `BLOCKED` | `REVIEW_REQUIRED` |
| 8 | 重新确认、稳定化 | `2` | `active` | `PREFLIGHT_RUNNING` | v3 / v2 |
| 9 | RS-02 预检通过并导出 | `2` | `active` | `READY → EXPORTED` | 冻结于 RS-02 |

两处容易被做错的地方，正是这两次递增的区别：

- **`0 → 1` 不是变更。** 它只冻结语义，草稿期产物（候选池、资料授权、AI 填写的溯源）全部继续有效。按机械比较把它当变更，会在立项当天把草稿期成果一次性作废。
- **`1 → 2` 是变更。** 它使基于 `Revision 1` 的旧确认失效、旧任务标 `STALE`，并按依赖图局部重跑。

## 12. 模拟结论

这次流程的核心不是“模型写出了一份申请书”，而是：

```text
草稿期的构想可以停留，但不会偷偷变成项目事实
→ 材料有权限边界，且不因立项而改变
→ 证据能回到原文
→ 主张知道自己依据什么
→ 修改会产生可追踪影响
→ 旧确认不会误用于新版本
→ 交付快照固定了实际导出依据
→ 人最终确认并承担研究判断
```

如果当前原型只能完成“上传—检索—问答—引用”，那么它已经具备知识能力底座，但还不能宣称完成上述完整的 LingDoc 申报闭环。完整闭环必须以 P1 至 P4（Beta）的领域模型、PCC、确认和交付验收全部通过为准。

## 13. 人工复核点与干预能力

### 13.1 必须人工复核的地方

| 环节    | 必须由人判断的内容                    | 系统可以做什么                        | 复核不通过时                                  |
| ----- | ---------------------------- | ------------------------------ | --------------------------------------- |
| 建项    | 研究问题、研究对象、目标、方法和资源条件是否真实、合理  | 澄清问题、检查缺失字段、显示他人改动与 AI 未复核字段、保存版本               | 留在草稿阶段或待确认，不进入正式项目基线                      |
| 草稿期检索 | 检索结果值不值得读原文、聚合页是否补得出原始出处 | 分档、标注层级、在导入关口拒绝无锚点的摘要         | 停在候选池；层级不动，可显式升级并留审计                    |
| 材料接入  | 文件是否获授权、是否属于本项目、是否允许被模型使用    | 解析、分类、去重提示、显示处理失败              | 拒绝接入、限制范围或转人工处理                         |
| 证据整理  | 原文是否真的支持该主张、支持范围是否被夸大        | 定位片段、生成证据候选、提示冲突和不足            | 保持 `CANDIDATE`/`INSUFFICIENT`，不能进入已确认依据 |
| 结构设计  | 章节结构是否适合研究问题，研究目标与方法是否匹配     | 按模板生成骨架、检查缺章和字段                | 创建补充任务或人工改结构                            |
| 章节生成  | 候选文字是否准确、是否改变原意、是否有不当因果表述    | 基于指定资料生成草稿、显示引用和差异             | 保留草稿，人工改写或退回重新生成                        |
| 研究变更  | 是否真的要应用 ChangeSet，变更是否符合研究意图 | 预估影响、展示受影响对象、创建任务              | `ChangeSet` 保持 `DRAFT`/`REJECTED`       |
| 影响处置  | 证据是否重新有效、哪些提示需要处理、是否接受误报     | 局部失效、重检索、列出待办和依赖路径             | 保持 `REVIEW_REQUIRED`，阻断稳定化/导出           |
| 模板与预检 | 论证质量、证据适切性、规则例外是否可接受         | 检查标题、字段、字数、版本和可计算格式            | 修改内容、补证据或判定误报删除；仅警告/提示级可记录豁免，阻断级不可 |
| 最终确认  | 申请人是否认可正文、图表、数字、引用和未解决事项     | 汇总确认范围、显示差异、生成 ReleaseSnapshot | 不生成 `READY`，允许继续编辑                      |
| 导出    | 导出文件是否满足实际提交要求               | 生成可编辑文件、做结构/内容保真检查             | 修复、重新导出或保留失败文件供追踪                       |

### 13.2 是否每一步都支持人工干预？

**从产品目标看，是的；从当前原型看，不是。** 更准确地说，规划要求每个可能改变研究语义、证据可信度、确认状态或交付资格的环节，都必须有人工接管路径；但并不是每个底层机械步骤都需要用户逐项点击。

可以分成三类：

| 类型 | 例子 | 人工干预方式 |
|---|---|---|
| 自动执行、人工可停止 | 文件解析、分块、向量化、检索、预检 | 取消、重试、查看失败原因、改配置后重跑 |
| 自动建议、人工决定 | 证据候选、影响范围、章节草稿、路线图修改、AI 填写的字段值 | 接受、编辑、拒绝、标记待核、分派任务 |
| 人工闸门、系统不得越过 | 立项确认、应用 ChangeSet、确认主张、关闭阻断问题、正式导出 | 负责人确认、记录理由和版本范围 |

### 13.3 当前原型与规划能力的差距

当前 WeKnora 原型已经能支持部分“查看/控制”动作：文件上传、解析状态轮询、重解析、删除、知识库检索、引用查看、Agent 流式交互和停止请求。它还不能据此证明已经支持完整的 LingDoc 人工闭环。

以下能力仍属于 LingDoc 规划能力，需专门实现后才能称为“可人工干预”：

- 草稿态 `Project`、`Revision 0` 与立项确认差异视图；
- 对 `ProjectSpec` 的逐项状态、AI 填写溯源与逐项确认；
- 检索结果的层级标记、导入关口的锚点校验与显式升级审计；
- 对 `ResearchClaim`、`EvidenceCard` 的逐项确认与撤回；
- 对 `ChangeSet` 的预览、应用决定、拒绝和基线冲突处理；
- 对依赖图影响任务的逐项接受、忽略、转派和理由记录；
- 对确认失效、陈旧结果和阻断交付的人工处置；
- 对 `ReleaseSnapshot` 的最终审核、豁免与误报删除记录和可恢复导出。

因此，验收时不能只问“页面上有没有按钮”，还要验证：人工动作是否改变了正确的领域状态、是否绑定正确版本、是否留下审计记录，以及异步任务是否会尊重这个决定。

## 14. 初稿生成中途新增参考文献的模拟

第四幕“陈同学补入外部候选文献 M-05”的那一步，单独展开如下。假设王同学正在基于 `M-01、M-03、E-01/E-02` 生成 Chapter 2。任务开始时系统记录：

```text
run_id: WR-07
based_on_context_revision: 1
asset_scope_revision: 1
selected_assets: M-01, M-03
```

此时陈同学上传新文献 M-05。系统先处理 M-05 并显示 `PROCESSING → READY`，但不自动改变 WR-07 的上下文，也不在已显示的候选稿中插入 M-05 的内容。

负责人可以选择：

1. **继续当前初稿**：WR-07 按原快照完成，M-05 留作下一轮资料；
2. **使用新文献重生成**：创建新的 `ChapterVersion`，标明新增依据和新旧差异；
3. **先检查影响**：A 判断 M-05 是否支持、补充或反驳已有主张，B 决定是否需要让确认失效。

如果 M-05 只是候选资料，不改变研究条件，则更新资料范围版本即可；如果负责人据此修改研究对象、变量或章节结论，则创建新的 `ChangeSet` 和 `Context Revision`。原 WR-07 返回时若基于旧 Revision 或旧资料范围，只能标为 `STALE`/历史候选，不能覆盖当前章节、确认状态或交付快照。

## 15. 另一条出口：草稿被丢弃

主线之外还有一条真实的结局：构想没走通，项目从没立项。

假设王同学那条线停在了草稿阶段，两个月没有推进。系统**只做超期提醒，不自动处置**——把一个人未完成的想法悄悄冻结，会让用户回来时看到“已归档”，而不是“你上次停在哪”。

李老师可以显式丢弃它：

```text
操作：丢弃草稿
能力：project.archive（仅 Owner）
效果：写入软删除标记 discarded_at
      status 保持 draft，不置 archived
      默认不再出现在项目列表；不可写入、不可立项确认
      保留审计与可恢复入口
```

**丢弃与归档不共用一个状态**，因为语义不同：

| | 适用对象 | 写法 | 含义 |
|---|---|---|---|
| 丢弃 | 仅 `draft` | 软删除标记 `discarded_at` | 这段构想未成立 |
| 归档 | 仅 `active` | `status = archived` | 项目已结束 |

因此 `active` 项目不能丢弃，`draft` 项目不能归档。两者复用同一个 `project.archive` 能力，靠对象状态分流——草稿期不新增 capability，也就不需要第二张权限表。物理清除依资料保留策略执行；草稿期上传资料的授权范围仍然有效，不因丢弃而被放宽。
