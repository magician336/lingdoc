# G2. 证据工作台与调研智能体

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)
> 相关设计：[调研智能体与知识沉淀规划](../10-调研智能体与知识沉淀规划.md)、[领域架构与 PCC](../02-领域架构与PCC.md)、[数据模型与接口契约](../03-数据模型与接口契约.md)
> 前置假设：T01–T16 已完成并通过各自验收。本文件描述领域逻辑，不等同于当前代码已实现。

## 1. 目标和问题定义

G2 要建立一条从“发现资料”到“可审阅证据”的受控链路。搜索结果、原文资料、证据片段、研究主张和章节引用是不同对象，不能因为它们都出现在同一个工作台里就互相替代。

G2 要回答六个问题：

1. 用户在草稿期或 active 项目中，当前究竟在寻找什么？
2. 一个搜索结果什么时候只是发现入口，什么时候可以成为项目资料候选？
3. 一段资料怎样保留可回到原文的定位，而不是只保存摘要或模型转述？
4. 证据卡怎样表达“支持到哪里、限制是什么、哪里仍然不足”？
5. 谁可以创建主张、建立证据卡、确认证据和把证据交给生成上下文？
6. 来源重解析、授权撤销、项目 revision 变化或异步任务乱序时，哪些对象继续有效，哪些对象必须复核？

G2 不替用户确认研究结论。调研智能体负责发现、整理和提出候选；A Evidence 负责来源定位和证据状态；B Workspace/PCC 负责项目主张、确认和变化；最终研究判断仍由有权限的人员完成。

## 2. 阶段边界和对象边界

| 项目阶段 | 可以做什么 | 不可以做什么 |
|---|---|---|
| `draft` / Context Revision 0 | 建立调研任务、受控检索、查看来源、导入资料候选、保存对话片段和背景线索 | 创建 `ResearchClaim`、`EvidenceCard` 或正式章节引用 |
| `active` | 建立主张、把 READY 资料定位为 `SourceAnchor`、创建候选证据卡、请求确认和复核 | 把搜索摘要、AI 推断或无定位材料直接当作已确认依据 |
| `archived` | 查看项目允许范围内的历史对象和审计记录 | 新建正式主张、证据卡或改变历史确认 |

Context Revision 0→1 是草稿内容冻结为正式基线，不会机械地使草稿候选变成 `STALE`。从 1→2 等实质变化开始，证据是否陈旧按依赖关系和语义影响判断，不能只用“版本号变大”代替判断。

### 2.1 渐进式证据成熟度

G2 采用“探索低门槛、确认高门槛”的原则。系统不要求用户在第一次看到资料时就完成完整的证据整理，而是在不同动作上设置不同要求：

| 用户动作              | 允许的最低条件                         | 系统结果                                 |
| ----------------- | ------------------------------- | ------------------------------------ |
| 查看、收藏、加入调研任务      | 有效来源结果或项目内可见资料                  | 保留在调研工作区，不代表项目事实                     |
| 保存背景线索或阅读笔记       | 来源元数据和当前授权可用                    | 可进入项目资料范围，标记为背景/待核，不可作为正式证据          |
| 提升为候选证据           | 用户选择片段并填写用途                     | 进入 ImportCandidate 或候选资料，显示缺少的定位和核验项 |
| 建立候选 EvidenceCard | READY 资料和至少一处可回原文的 SourceAnchor | 形成 `CANDIDATE` 证据卡；可继续补充锚点，主张可以稍后关联  |
| 确认或进入正式生成         | 当前版本、授权、主张关联、支持范围和确认范围有效        | 才能作为已确认依据使用                          |

硬阻断只用于越权读取、来源不可用时继续使用、建立无前置条件的正式证据或把未确认材料送入正式交付。缺少定位、适用性或限制说明时，优先保存为待核对象并提示下一步，不阻断用户继续探索。

## 3. 核心对象和状态

### 3.1 调研任务和执行轮次

`ResearchTask` 是用户要解决的调研问题，包含目标、问题、范围、排除条件、期望输出、允许来源和关联项目/章节。一个任务可以有多次执行。

`ResearchRun` 是一次具体执行，保存检索计划、查询轮次、来源目录版本、提供方、执行时间、结果集合、固定的项目 revision 和授权范围。`ResearchTask` 负责用户语义，`ResearchRun` 负责一次可追溯的执行。

任务状态：

| 状态 | 含义 |
|---|---|
| `draft` | 用户仍在修改问题和范围 |
| `approved` | 用户确认可以按当前计划执行 |
| `running` | 至少一轮检索或来源读取正在进行 |
| `completed` | 本轮结果已保存，可能包含失败或待验证结果 |
| `failed` | 本轮没有形成可用结果，保留失败原因，可重试 |
| `cancelled` | 用户主动停止，已有结果仍可查看 |
| `stale` | 执行依据的项目语义或授权范围已不再适用于当前上下文 |

任务成功不等于证据成功。`ResearchRun` 返回的每一项都必须带结果层级、来源信息、检索时间和当前可用性。

### 3.2 来源、片段和导入候选

| 对象 | 领域含义 | 关键边界 |
|---|---|---|
| `AcademicSource` | 学术来源或外部来源的元数据卡 | 不等于已读原文，也不等于项目证据 |
| `ResearchExcerpt` | 用户从来源或对话中选定的片段 | 必须保存来源引用和可定位信息 |
| `ConversationExcerpt` | 选定的 AI 会话、轮次和片段 | AI 推断仍保持候选身份 |
| `ImportCandidate` | 用户明确选择、等待进入项目资料范围的候选 | 未确认权限和用途前不能成为项目资料 |
| `ProjectAsset` | 已进入项目资料范围的稳定资料引用 | 必须有授权范围和处理状态 |
| `SourceAnchor` | ProjectAsset 中可回到原文的页、段、表、图或稳定片段 | 证据卡的必要前置，不接受只有摘要文本的替代物 |

ImportCandidate 的结果层级至少分为：

- `candidate_evidence`：有作者/机构、出处、原文定位和可核验来源，可继续建立证据卡；
- `background_lead`：可作为背景线索，但出处、质量或适用性仍需确认；
- `discovery_entry`：仅帮助用户找到原始来源，不能直接建立证据卡；
- `unread_search_summary`：搜索引擎摘要或模型转述，没有稳定原文定位，只能保留为调研工作区的发现记录，不得冒充项目资料或正式证据。

层级描述“可以支撑什么”，不描述“来源是否有价值”。用户仍可以保存背景线索，但不能让它绕过原文定位和人工判断。

ImportCandidate 的处理状态至少包括：`selected`（已选择）、`awaiting_consent`（等待用途/授权确认）、`importing`（正在进入项目资料范围）、`imported`（已形成 ProjectAsset）、`rejected`（用户或规则拒绝）和 `failed`（处理失败，可重试）。结果层级与处理状态是两条不同维度：一条背景线索可以成功导入，但仍不能作为正式证据。

### 3.3 主张和证据卡

`ResearchClaim` 是项目中需要证据支撑、反驳或限定的具体研究主张。它属于 active 项目语义，由 B 域创建和版本化。主张可以是待验证、已确认、存在争议或已取代，但不能因为关联了一张来源卡就自动变成成立。支持与反对材料可以同时保留；是否接受哪种解释由用户判断，系统不能自动替用户裁决。

`EvidenceCard` 是用户可审阅的证据载体。创建候选卡时只要求最小字段；其余字段按确认阶段逐步补齐：

- 创建候选卡必填：至少一个 `SourceAnchor`（可随后添加更多锚点）、选定片段；创建者和 `based_on_revision` 由系统记录；
- 确认前必填：至少一个 `claim_ref`、`support_type` 和 `scope`；
- `limitations`、`gaps`、替代解释和适用性说明默认是提示项，可以暂时留空，但界面要明确显示“尚未补充”；
- 当前状态、版本和审阅记录由系统保存，不能由用户省略。

一张卡允许关联多个 `SourceAnchor`，可以来自同一资料的不同片段，也可以来自不同资料。卡片应显示每个锚点各自支持、限制或反驳的内容，整体 `scope` 只表达这些片段共同支持到的范围；不能因为多放了几个片段就自动扩大结论。对同一主张也可以保留多张立场不同的证据卡。添加、移除或替换锚点会形成新的卡片版本，原有确认不能直接沿用。

EvidenceCard 状态：

| 状态 | 含义 |
|---|---|
| `CANDIDATE` | 已有可定位资料，等待补充主张或人工审阅；可以暂时没有 `claim_ref` |
| `CONFIRMED` | 有权限的确认人已确认该卡在指定范围内可作为证据 |
| `NEEDS_REVIEW` | 来源、主张、项目条件或授权发生变化，需要重新检查 |
| `INSUFFICIENT` | 资料仍存在，但不足以支撑当前主张或范围 |
| `STALE` | 该卡基于旧 revision/旧资料版本，不能直接进入当前生成上下文 |
| `SUPERSEDED` | 新版本证据卡替代了旧卡，旧卡保留用于历史回放 |

`INSUFFICIENT` 不是删除，`NEEDS_REVIEW` 也不是自动否定。两者都必须保留原因和下一步处理建议。

证据卡的主要状态转移为：

```text
CANDIDATE
  ├─ 补充主张与支持范围 → 等待确认
  ├─ 确认支持成立       → CONFIRMED
  ├─ 确认支持不足       → INSUFFICIENT
  └─ 来源/主张/版本变化  → NEEDS_REVIEW 或 STALE

CONFIRMED / INSUFFICIENT
  └─ 新版本或授权变化    → NEEDS_REVIEW / STALE

NEEDS_REVIEW / STALE
  ├─ 重新核验通过        → CONFIRMED
  ├─ 重新核验不足        → INSUFFICIENT
  └─ 新证据卡替代         → SUPERSEDED
```

## 4. 调研任务流程

调研智能体先帮助用户把想法变成任务卡，再按任务卡执行，不直接把自由对话写进项目事实。

任务卡至少包含：

```text
目标：要澄清什么研究问题
问题：需要定义、测量、反例还是适用性比较
范围：语言、时间、来源类型、研究对象和允许资料
排除：无作者、无出处、无法定位原文或超出授权范围的结果
输出：候选来源、比较表、待验证问题或变量定义
```

用户可以修改任务卡、暂停、取消或重新执行。每次执行保留：

1. 每轮查询词、同义词、排除词和用户修改；
2. 来源目录、提供方和授权配置版本；
3. 结果去重、排序和分层依据；
4. 检索时间、获取时间和工具；
5. 该轮固定的 Context Revision、asset scope 和成员权限。

来源通道分为三类：租户批准的学术来源、一般网页发现层和项目内已授权资料。学术来源保留目录版本与许可说明；一般网页结果默认只能作为发现入口或背景线索；项目内资料只在当前成员和项目授权范围内可检索。G2 复用已有来源提供方和 WeKnora 检索能力，不另设一套绕过租户策略的项目级联网开关。

搜索摘要、模型生成的比较结论和来源推荐只能作为发现层输出。用户必须打开并选择有稳定出处的原文片段，才能进入 `ImportCandidate` 的证据候选层。

### 4.1 G2 调研助手的辅助职责

G2 的调研助手用于降低检索、阅读和证据整理的操作成本。它可以：

- 把用户的自然语言问题整理成可编辑的 ResearchTask 草稿；
- 扩展同义词、检索词和排除词，解释每轮检索的变化；
- 推荐可能相关的来源、章节、表格或片段，并提示来源层级；
- 在用户打开原文后，建议可能的 SourceAnchor 范围、章节和段落位置；
- 根据用户选定的片段生成 EvidenceCard 候选和主张关联草稿；
- 提示支持范围、限制、反例、争议材料和仍未覆盖的问题；
- 在资料重解析、授权变化或项目 revision 变化后，提醒用户哪些证据需要复核。

上述结果都属于候选或提醒。调研助手不能把搜索摘要、模型转述或自身推断直接写成 `SourceAnchor`、`EvidenceCard.CONFIRMED` 或 `ResearchClaim`；用户必须打开原文、选择片段并由有权限的人确认。助手使用的上下文受当前项目授权、资料范围和 revision 限制，所有模型运行记录其输入范围、模型/工具、时间和输出版本。

## 5. 导入和来源定位

### 5.1 两阶段导入

```text
ResearchRun 结果
  → 用户选择来源与片段
  → ImportCandidate
  → 用户确认用途、资料范围和授权
  → KnowledgeGateway / WeKnora 处理与索引
  → ProjectAsset PROCESSING
  → ProjectAsset READY
  → SourceAnchor
  → EvidenceCard 候选
```

创建 ImportCandidate 只表示用户选择了候选，不表示已经同意全文保存，也不表示它已经可以支撑主张。用户可以先保存为背景线索或待核候选，系统在后续升级为证据卡时再要求补齐原文定位和主张关联。确认导入时，用户至少要决定：

- 保存全文、链接加摘录，还是只保存元数据；
- 进入项目资料范围、团队共享范围，还是仅个人草稿；
- 是否允许后续模型检索；
- 是背景线索、候选证据还是待补出处任务；
- 是否需要脱敏或排除特定片段。

用户确认导入后，系统通过现有 `KnowledgeGateway` 复用 WeKnora 的上传、解析、分块、索引和检索能力，形成当前项目授权范围内的 `ProjectAsset`。这里的“进入知识库”指进入项目资料/知识库视图，不表示进入全租户公共知识库，也不表示自动成为 `EvidenceCard` 或已确认事实。项目资料仍由 LingDoc 保存项目归属、授权范围、版本和来源谱系，不能直接把 WeKnora 的 chunk ID 当作业务真相。

导入事务必须同时写入候选来源、用途、授权范围和审计记录。处理失败时保留 `ImportCandidate` 及失败原因，不产生可被误用的 READY ProjectAsset。

### 5.2 SourceAnchor 的最低条件

SourceAnchor 不是一条 PDF 文件链接，而是“某个来源版本中的一段可重新找到的内容”。它必须包含来源版本、定位器、选中原文的哈希和可重新打开的定位信息。定位粒度按资料类型递进：

| 资料类型 | 推荐定位层级 | 最低可接受定位 |
|---|---|---|
| 论文 PDF | 文档 → 页码 → 章节/小节 → 段落或句子 | 页码 + 选中文本 + 文本哈希 |
| 书籍 PDF | 书籍/版本 → 章节 → 小节 → 页码范围 → 段落 | 章节 + 页码范围 + 选中文本 + 文本哈希 |
| 表格或图片 | 文档 → 页码 → 表/图编号 → 标题或区域 | 页码 + 表/图编号 + 选中区域/说明 |
| 扫描 PDF | 文档版本 → 页码 → OCR 文本区块 → 页面坐标 | 页码 + 坐标 + OCR 文本哈希，并标记 OCR 风险 |

用户在 PDF 预览器中选中文本、表格或图注后，系统自动生成上述定位信息；用户不需要手工填写一串锚点。系统同时保存便于回看原文的可读位置，例如“第 4 页，研究方法，小节 2，第二段”，以及复核用的页码、文本哈希、段落序号或页面坐标。本阶段只处理内容定位，不扩展最终申报书的引文格式。

只有搜索摘要、无出处的模型回答或不能重新定位的文本不能建立正式 SourceAnchor。整篇论文或整本书可以作为 `ProjectAsset` 保存和检索，但不能仅凭“这篇论文/这本书”建立一张覆盖全文的证据卡；证据卡必须指向具体片段。

对于一本十万字的书，系统不要求用户先通读或手工标注全书。用户可以先导入整本书作为项目资料，再按“章节 → 小节 → 页码范围 → 片段”逐步创建多个 SourceAnchor。一张证据卡可以关联其中多个片段，也可以与其他资料的片段放在同一张卡中；每个片段仍须可单独回到原文。书籍级元数据可复用，但不能代替片段定位。本阶段不另行处理不同版次、印刷页码与 PDF 页码的换算问题。

每个锚点还要记录定位置信度：原生文本、可靠 OCR、低置信 OCR 或人工修正。低置信 OCR 可以保存为候选资料，但在确认或正式生成前必须人工复核原页；系统不能把 OCR 结果无提示地当成原文。

人工修正 OCR 时，保留“原始页面位置 → 原始 OCR 文本 → 人工修正文本 → 核对结果”的谱系，记录修正者、修正时间、修正前后差异和是否已对照原页。修正文本不能覆盖原始 OCR；用户确认的是已对照原页的内容，而不是把自己的转录自动当成原文。修正或重新解析导致锚点内容变化时，引用该锚点的证据卡进入待复核；只改显示方式、原文和定位未变时保留原确认。

来源页面可以变化，但系统不能静默把锚点替换到新的文本。重解析、URL 变化、原文消失、摘要与原文不一致时，发布来源变化事件，相关证据卡进入 `NEEDS_REVIEW` 或 `STALE`，由人决定是否建立新的锚点。

### 5.3 对话片段

对话导入必须保存会话、轮次范围、选定片段、生成时间、模型/工具（可用时）、引用来源、导入者和导入时 revision。可导入形式包括研究笔记、来源清单和待核证据候选。

AI 推断必须标为 `AI_GENERATED_CANDIDATE`，不能因为用户导入了对话就成为 `EvidenceCard.CONFIRMED`。要成为证据，仍需回到可定位的原始来源并由有权限的人确认。

## 6. 证据卡与主张的建立

正式证据的领域顺序固定为：

```text
ImportCandidate
  → READY ProjectAsset
  → 至少一个当前版本 SourceAnchor
  → EvidenceCard.CANDIDATE（可暂不关联主张）
  → active 项目 ResearchClaim + 支持范围
  → 有权限人员确认
  → EvidenceCard.CONFIRMED / INSUFFICIENT
```

建立候选 EvidenceCard 前只必须满足：

- 项目为 active；
- ProjectAsset 在项目允许的资料范围内且状态为 READY；
- 至少一个 SourceAnchor 属于当前可用的 ProjectAsset 版本并可定位；增加其他锚点时，每个锚点分别满足同样条件；
- 创建者具备证据卡创建能力。

缺少来源或定位时，系统不创建 EvidenceCard，但应保留 ImportCandidate 或 ProjectAsset，并明确显示缺少的条件和补齐入口。候选卡可以暂时没有主张关联；尝试确认或送入正式生成时，必须补齐主张和支持范围，并逐一核验卡上全部锚点。重复提交使用相同幂等键时返回原卡，不重复产生审计事件。

同一主张出现支持与反对证据时，工作台并列呈现两方来源、支持范围和限制，并提示用户判断；用户可以将主张保留为“存在争议”，写明自己的解释或暂不下结论。确认某张证据卡只表示该来源片段在约定范围内被核对过，不表示主张已经被证明，也不要求用户删除相反证据。

界面必须把“候选 EvidenceCard”和“已确认依据”明确分开显示。候选卡可以用于个人整理和带标记的待核草稿，但任何“已确认证据”查询都必须同时满足有效状态、主张关联、当前版本和 Confirmation；不能因为对象名称叫 EvidenceCard 就默认它已经是正式证据。

候选卡在列表、详情、检索结果和生成上下文中都必须显示“待核候选”标记；已确认依据必须显示确认人、确认范围和所依据的对象版本。系统提供“只看已确认依据”和“只看待核候选”两个明确过滤入口，不能用颜色或折叠状态代替文字语义。

证据卡只能表达“这段来源对这条主张支持到什么程度”。它不能自动把“有文献”变成“主张成立”，不能自动替用户补出样本适用性，也不能把背景线索升级为直接支持。

## 7. 确认、权限和审计

| 动作 | 默认能力 | 领域约束 |
|---|---|---|
| 创建 ResearchTask/ResearchRun | 项目成员中的 Researcher、Author、Owner | 受项目资料和来源目录权限限制 |
| 创建 ImportCandidate | 有项目资料写入能力的成员 | 必须选择来源、片段和用途 |
| 确认导入 ProjectAsset | 有资料管理能力的成员 | 不能扩大租户或来源授权 |
| 创建 ResearchClaim | Owner 或有项目研究编辑能力的成员 | 仅 active 项目，主张必须版本化 |
| 创建候选 EvidenceCard | 有证据整理能力的成员 | 必须满足 READY + 至少一个 Anchor；Claim 可稍后关联 |
| 确认 EvidenceCard | Owner 或明确的 Reviewer/证据确认能力 | 逐一核对关联锚点，绑定卡版本、锚点集合、主张版本、项目 revision 和确认范围 |
| 关闭/标记不足 | 证据确认能力或被委派的 Reviewer | 记录理由，不删除来源和历史卡 |

Research Agent、A Evidence 无权代替 B 写入 ResearchClaim 或 Confirmation。A 可以发布资料处理、锚点和证据状态事件；B 负责主张、确认及项目语义；G5 负责实际能力判断。

所有导入、定位、证据建立、确认、撤销和复核都记录操作者、时间、来源版本、项目 revision、资料版本、授权范围和审计理由。同一个来源片段同时被 ProjectSpec 和 ProjectAsset 引用时，两条用途必须分别记录，撤权时分别传播失效。

## 8. 失效、陈旧和复核

### 8.1 触发来源

以下变化可以触发局部复核：

- ProjectAsset 重解析、替换、删除或处理失败；
- SourceAnchor 无法重新定位、原文或 URL 变化；
- 资料授权范围收窄、成员被移除或租户身份失效；
- ResearchClaim 版本变化或项目 Context Revision 实质变化；
- 模板或规则改变了证据适用章节和必要范围；
- 异步任务返回时，其 basis 已落后于当前项目。

### 8.2 局部传播规则

来源变化先影响直接引用它的 SourceAnchor 和 EvidenceCard，再沿显式 DependencyEdge 影响主张、章节和交付。没有依赖关系的证据、章节和资料保持原状态，不能全项目“一键陈旧”。

| 场景 | 证据结果 | 后续动作 |
|---|---|---|
| 资料重解析但原文定位不变 | 暂不自动否定；保留版本差异 | 重新核对锚点哈希 |
| 某一锚点定位失效、OCR 修正或原文变化 | 引用该锚点的卡 `NEEDS_REVIEW` | 核对受影响片段及整卡支持范围；其他卡保持原状态 |
| 授权撤销 | 不再向无权用户返回原文 | 相关卡待复核，导出重新鉴权 |
| 项目 0→1 | 草稿候选保持原层级 | active 后重新关联 Claim/Anchor |
| 项目 1→N 实质变更 | 受影响卡 `NEEDS_REVIEW` 或 `STALE` | PCC 创建复核任务 |
| 异步结果 basis 落后 | 结果 `STALE` | 保留历史，不能覆盖当前对象 |

`STALE` 描述“不能直接用于当前上下文”，不等于资料已经错误；`NEEDS_REVIEW` 描述“需要人重新核对”。只有确认人重新检查当前版本后，证据才可恢复为 `CONFIRMED`。

## 9. 生成上下文和交接

生成任务只消费明确允许的证据集合，并固定：

- Context Revision；
- ProjectAsset 及其版本；
- SourceAnchor 和 EvidenceCard 版本；
- 证据状态和确认范围；
- 项目资料授权范围；
- 章节、主张和模板版本。

上下文中必须显示证据层级：已确认、候选、待复核、证据不足、AI 生成候选。候选证据可以用于提出带“待核”标记的草稿；只有满足当前版本、授权、主张关联和 Confirmation 的卡片才能进入正式生成上下文。`STALE`、无权或超出适用范围的证据不得进入正式生成上下文。

正式生成在建立上下文时重新过滤证据：必须同时满足 `status=CONFIRMED`、存在当前版本 `claim_ref`、确认范围覆盖目标章节，以及卡上全部 SourceAnchor 和相应 ProjectAsset 仍可访问且版本匹配。任一锚点失效时，整卡不能继续作为已确认依据；用户可以移除失效锚点并重新确认新版本卡。候选、`NEEDS_REVIEW`、`INSUFFICIENT`、`STALE`、无主张卡片和超出授权范围的资料只能作为待核提示，不能进入正式依据集合。主张处于“存在争议”时，已确认的支持与反对证据均可按各自范围呈现，不自动合并成单一结论。

同一来源片段的重复导入按来源身份和片段定位进行去重。相同 `source_version + locator + quoted_text_hash` 的候选默认合并到同一来源片段，并保留不同导入者、用途、授权和审计记录；如果用户明确选择不同用途或不同项目范围，可以建立不同的 ImportCandidate，但不能重复生成相同的 ProjectAsset 版本。片段相同但主张、支持范围或限制不同，应复用同一 SourceAnchor，建立不同的 EvidenceCard 或关联关系；同一张卡也可以复用多个既有锚点。来源版本或原文哈希变化时，不做静默合并，进入新的资料/锚点版本并触发复核。

生成任务运行期间导入的新资料不自动混入。用户可以保留当前结果、以新资料重新生成或先发起证据影响检查。旧任务返回时只保存为历史候选，并显示其 basis 与当前版本差异，不能覆盖当前章节或 ReleaseSnapshot。

## 10. 并发、失败和恢复语义

| 场景 | 必须发生 | 不能发生 |
|---|---|---|
| 同一任务重复提交 | 幂等键返回原任务/结果 | 重复扣配额或生成重复来源 |
| 同一来源片段重复导入 | 复用相同 ProjectAsset/SourceAnchor，保留用途和审计差异 | 重复生成相同资料版本 |
| 两人同时确认导入 | 一次成功，一次版本冲突 | 产生两个 ProjectAsset 版本 |
| ProjectAsset 仍在 PROCESSING | EvidenceCard 创建被拒绝 | 先建空卡等异步结果 |
| 新增锚点与资料版本不匹配 | 拒绝本次关联并保留原卡；确认前逐一复核全部锚点 | 用旧定位伪装当前原文或破坏原卡 |
| 缺少 ResearchClaim | 候选卡可以保存；确认或正式生成被拒绝并提示补充 | 把无主张候选卡当作已确认依据 |
| 来源撤权 | 读取和生成按当前权限拒绝 | 从缓存返回原文摘录 |
| 来源重解析失败 | 保留旧版本和失败原因，相关卡待复核 | 覆盖旧资料或静默使用半成品 |
| 异步任务落后于当前 revision | 标记 STALE，允许比较 | 覆盖新版本结果 |
| 草稿项目尝试建 Claim/Card | 显式拒绝 | 因创建候选而自动立项 |
| Owner/Reviewer 失效 | 确认入口重新检查能力 | 沿用旧会话授权确认 |

任何失败事务都不能留下半张 EvidenceCard、无 Anchor 的确认、超出授权的 ProjectAsset 或可下载的伪导出文件。

## 12. 领域验收场景

### AC-G2-01：草稿期检索

用户在 draft 项目中创建调研任务，执行三轮搜索。结果进入候选池并带层级标记；项目仍为 draft，不产生 ResearchClaim 或 EvidenceCard。

### AC-G2-02：搜索摘要边界

用户选择一个只有搜索摘要、没有原文定位的结果。系统允许查看和保存发现入口，但拒绝将其作为正式导入或建立 SourceAnchor。

### AC-G2-03：原文片段导入

用户从可访问来源中选取两个带页码和段落定位的片段，确认用途和资料范围。系统建立 ImportCandidate，处理完成后生成 READY ProjectAsset 和 SourceAnchor。

### AC-G2-04：论文 PDF 精细定位

用户打开一篇论文 PDF，在第 4 页“研究方法”小节中选中一个段落。系统自动保存论文版本、页码、章节标题、段落序号、选中文本和文本哈希，并生成可回到原页的 SourceAnchor。用户不需要手工输入定位字符串。

### AC-G2-05：长书分层定位与多锚点证据卡

用户导入一本十万字的书作为 ProjectAsset，先按章节和关键词定位，再从第 3 章第 2 节的若干页中选择具体段落。系统允许建立多张 SourceAnchor，并把其中多处片段关联到同一张 EvidenceCard；每个片段都能单独回到原文，整卡支持范围由用户说明，不能用整本书作为一张无范围证据。

### AC-G2-06：扫描 PDF 和 OCR

用户从扫描 PDF 中选择一段 OCR 文本。系统保存页码、页面坐标、OCR 文本哈希并标记 OCR 风险；低置信 OCR 可以保存为候选，但确认或正式生成前要求人工对照原页。

### AC-G2-07：OCR 人工修正谱系

用户发现 OCR 将一个数字识别错误，核对原页后修改转录。系统保留页面位置、原始 OCR、修正文本、差异、修正者和核对记录；引用该锚点的已确认卡进入待复核，未引用该锚点的卡保持原状态。

### AC-G2-08：对话导入

用户只导入 AI 对话中的来源清单。AI 推断标为 `AI_GENERATED_CANDIDATE`，不能直接成为 EvidenceCard.CONFIRMED；来源清单中的每个出处仍需单独核验。

### AC-G2-09：证据卡分阶段填写

active 项目中，用户从 READY ProjectAsset 的 SourceAnchor 创建候选 EvidenceCard，只选择至少一个片段即可保存；随后可继续添加锚点，并在确认或生成前补充 ResearchClaim、支持类型和支持范围。ProjectAsset 尚未 READY 或没有 SourceAnchor 时不能建卡，但原 ImportCandidate/ProjectAsset 必须保留，不能让用户已经保存的资料消失。

### AC-G2-10：支持范围和不足

用户建立一张只支持“家庭支持定义”、但不能支持“调节效应成立”的证据卡。卡片保存部分支持、适用范围、限制和不足，不能被系统改写成完整支持。

### AC-G2-11：争议证据并存

两张卡分别支持和反对同一主张。系统并列展示来源和各自范围；用户可以将主张保留为“存在争议”，并记录解释，不自动选择一方，也不因一张卡确认而删除另一张。

### AC-G2-12：多锚点局部失效

一张已确认卡关联论文的两个 SourceAnchor，其中一个原文变化。整卡不再作为已确认依据进入正式生成；用户可核对变化，或移除失效锚点形成新版本并重新确认。只引用另一锚点的其他卡不受影响。

### AC-G2-13：证据确认权限

只有 Owner 或被授予证据确认能力的 Reviewer 能确认卡片。Author 可以整理候选和补充说明，但不能代行确认。

### AC-G2-14：候选卡显示和正式生成过滤

候选 EvidenceCard 在列表和详情中明确显示“待核候选”。用户可以将它用于带标记的草稿，但正式生成只读取当前版本、当前授权范围内且已确认的 EvidenceCard；没有主张、待复核或证据不足的卡片不会混入正式依据集合。

### AC-G2-15：同源片段去重

用户两次导入同一来源版本的同一页/段片段。系统复用同一 ProjectAsset/SourceAnchor，不产生重复资料版本；不同主张可以建立不同 EvidenceCard，但都指向同一锚点。来源版本或原文哈希变化时，系统建立新版本并触发复核，而不是静默合并。

### AC-G2-16：来源变化

来源重解析后选定片段的哈希变化。相关 SourceAnchor 和 EvidenceCard 进入 NEEDS_REVIEW；没有引用该片段的证据卡保持有效。

### AC-G2-17：撤权传播

成员或来源授权被撤销后，原文和摘录不再返回给无权用户；相关证据和后续导出进入待复核，其他成员按自身权限继续访问。

### AC-G2-18：异步乱序

旧 revision 的重解析任务在新 revision 产生后返回。结果标记 STALE，保留审计和比较入口，不覆盖当前 EvidenceCard 或章节。

### AC-G2-19：生成快照

生成任务固定资料和证据版本。任务执行期间新增资料不自动混入；用户选择重生成后才建立新的候选结果。

### AC-G2-20：调研助手辅助整理

用户输入“寻找创业教育对本科生创新能力影响的实证研究”。调研助手生成可编辑任务卡、扩展检索词并推荐若干来源；用户打开其中一篇论文后，助手建议方法章节中的片段作为 SourceAnchor，并生成一张待核 EvidenceCard 候选。用户未选择原文片段或未完成确认前，系统不建立已确认锚点、不确认主张，也不把候选送入正式生成上下文。

## 13. 与其他能力线的交接

### 交给 G1

- 草稿期调研任务、结果层级和候选池；
- 0→1 后候选不机械陈旧的语义；
- 草稿资料授权和 ProvenanceRecord 的用途。

### 交给 G3

- EvidenceCard、ResearchClaim、ProjectAsset、SourceAnchor 的显式依赖；
- 证据/来源变化触发的复核动作和目标 revision；
- 异步结果 `STALE` 与当前版本隔离规则。

### 交给 G4

- 证据层级、支持范围和不足可作为模板检查/生成提示的输入；
- 模板规则不能把模型建议当成证据确认；
- 交付前对证据状态和必要引用的检查入口。

### 交给 G5

- Researcher、Author、Reviewer、Owner 的调研、资料、证据和确认能力矩阵；
- 来源目录、资料范围、原文摘录和撤权后的读取边界。

### 交给 G6

- 搜索、导入、解析、锚点、确认、撤权、重试和陈旧 fixture；
- 真实用户从调研问题到证据卡确认的耗时、失败和人工复核记录。

## 14. 不纳入 G2

- 自动确认文献、主张或证据卡；
- 把搜索摘要、AI 回答或无定位材料直接写成正式证据；
- 自动判断研究创新性、论证充分性或最终结论正确性；
- 绕过版权、来源授权、个人信息和网络出口策略；
- 建设通用聊天平台或第二套搜索/RAG 引擎；
- 草稿期创建正式 ResearchClaim、EvidenceCard 或章节确认；
- 不同版次、印刷页码与 PDF 页码的自动换算，以及最终申报书的引文格式；
- 通过后台静默替换来源、锚点、资料版本或证据卡历史。

G2 完成的标准不是“搜索结果很多”，而是每一条进入项目的证据都能回答：它来自哪里、用户选择了什么、能支持哪条主张、不能支持什么、谁确认过、基于哪个版本，以及来源发生变化后下一步该由谁处理。
