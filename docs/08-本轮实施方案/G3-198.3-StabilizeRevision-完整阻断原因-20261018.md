# G3-198.3 StabilizeRevision 与完整阻断原因

票据 #201。承接 #199（依赖边 modify 决策）、#200（影响任务 STALE 语义）、#202（交付闸门 `AssertRevisionStabilized`）。
本票只做一件事：把 `StabilizeRevision` 的稳定化判定补完整，并让阻断原因在服务端、契约与客户端类型三层完全一致。

## 一、开工前核对的既有实现

合入集成分支后先逐条核对验收标准，而不是默认「已实现即已满足」。结论：

| 验收项 | 开工前状态 | 证据 |
| --- | --- | --- |
| 读写前重读域真相 | 已实现 | `checkedImpactWrite` 先只读事务取 basis，写事务内比对 `ProjectVersion` 与每个 ref 的 `hashImpactValue` |
| BLOCK_RELEASE 回执复核 | 已实现 | 顶部预扫描 DONE 任务 closure evidence，逐个 `recheckImpactPreflight`，写事务内 `validImpactPreflight` 校验 |
| 未闭环 blocking 任务 | 已实现 | `impact_task_open` |
| RECOMPUTE/RETRIEVE 回执过期 | 已实现 | `result_receipt_stale` |
| 闭环证据已变化 | 已实现 | `closure_stale`，并把任务显式转 STALE |
| route-node / 模板 / RuleSet | 已实现 | `RouteStabilizationBlockers`、`template_unbound`、`impactRules.Check` |
| **受影响对象的当前确认** | **缺失** | 见下 |

## 二、本票修复的真实缺陷

### 缺陷：`StabilizeRevision` 从不读取该变更集持久化的 `ImpactAssessment`

开工前的稳定化只复核 **DONE 任务的 closure evidence**。`ImpactAssessment.Objects` 里记录的受影响对象从未被重读。

两处放大后果：

1. **STALE 任务彻底脱钩。** #200 明确 STALE 既不是阻断原因（依据已消失，无人能够再履行）也不算闭环。于是 STALE 任务对应的受影响对象变成**没有任何义务挂靠**：既不阻断，也无人检查。受影响章节可以处于未确认状态，而稳定化依然返回 `STABILIZED`。
2. **契约与真实负载不一致。** `StabilizationResult` 在 OpenAPI 中是 `additionalProperties: false`，但服务端实际会发送 `stale_task_ids`（#200 加入），契约里却没有该字段。契约在拒绝自己服务的真实响应。

### 修复

新增 `impactConfirmationBlockers`：读取该变更集的 `ImpactAssessment`，逐个重读其记录对象的**当前**确认状态，并给出结构化阻断码。

两个刻意的边界，都是实测得出的，不是推测：

- **STALE 仍然不是阻断原因。** 让 STALE 阻断会制造无人能够解除的死锁；修复补的是「对象当前确认」这一条被漏掉的事实，不是改变 #200 的语义。
- **已由 DONE 任务闭环证据覆盖的对象跳过。** complete 本就会把任务重定向到新版本，此时被评估的版本理应过期，由该任务自己的闭环检查负责，不能重复阻断。
- **`ProjectSpec` 按当前 spec 修订判定。** 实测：评估时记录 `ProjectSpec@1`，而 apply 该变更集本身就会推进 spec 修订到 2。把这一步预期漂移当成阻断会让**每一次**稳定化都失败，因此 spec 根改为按当前修订判定。
- 章节类对象解析为**当前**版本后再判定，使「重新保存并重新确认」这一真实修复路径能够真正通过。

新增阻断码：

| 码 | 含义 |
| --- | --- |
| `impact_object_unconfirmed` | 受影响对象的当前确认已失效，需重新确认 |
| `impact_object_stale` | 受影响对象的版本已被替换，需重新评估影响 |

### 阻断与错误的边界（本票明确下来）

`checkedImpactWrite` 在前置校验失败时返回 error 而非 `StabilizationResult`，这本身是对的，但边界此前没有被测试固定：

- **阻断 = 200 + `status=BLOCKED` + 完整 blockers**：域真相可被 Owner 修复。失败**不**创建新 revision、**不**覆盖历史、**不**把 ChangeSet 标记为 `STABILIZED`。
- **错误 = 4xx/5xx**：调用本身不被解释（未知 ChangeSet、非 Owner、修订/状态机位置不符）。

每个 blocker 都必须同时带机器可读 `code` 与人类可读 `reason`。

## 三、契约与客户端同步

- `openapi.json`：`StabilizationResult` 补 `stale_task_ids`（并列入 required），修复契约拒绝自身真实响应的问题。
- `openapi.json`：补齐此前完全缺失的 `ImpactTask` / `ImpactTaskListResponse` / `ImpactTaskResponse` schema，以及 `/impact-tasks` GET 与 `/impact-tasks/{taskId}/actions` POST 两条路径——路由早已存在，契约却既没有路径也没有 schema。`stale_reason` 明确列出三个原因码。
- `mainlineChanges.ts`：`StabilizationResult` 补 `checked_at`（服务端与契约都有，客户端类型此前缺失）。
- `G3OpsPanel.vue`：展示 `checked_at` 与 `stale_task_ids`，使 UI 与契约字段对齐。

### RED 验证方式

修复不是「先写实现再补测试」。核心测试在实现缺失时确认失败：

```
--- FAIL: TestG3201StabilizeRechecksImpactedObjectsWithNoCoveringTask
    expected: "BLOCKED"
    actual  : "STABILIZED"
    Messages: an impacted object left unconfirmed must still block: []
```

随后把 `impactConfirmationBlockers` 调用临时摘除再跑一次，确认同一失败复现，验证测试确实咬住该缺陷而非其他原因。

两个契约测试同样在原始契约上确认 RED：

```
Messages: the server sends "stale_task_ids" but the contract does not describe it
Messages: contract is missing the /projects/{projectId}/impact-tasks operation
```

### 踩坑记录（供后续票据参考）

操作幂等键有 **8 字符**下限（`runOperation` 的 `len(key) < 8`）。调试期用了 7 字符的键，表现为 `invalid_request`，与真实缺陷无关，浪费两轮定位。
