受控执行路径已经落地并且**在离线测试里真实生效**：Qwen 专用 profile 用 token 与调用次数做闸门，闸门真的走在生成调用路径上，账本记 provider 实测 token、没有 usage 就记 `unavailable`（**不可核实**）、费用列记「不适用」而不是 0，失败即停不重试。**但今天还不能直接执行一次真实的受控 Qwen 调用** —— 还差 4 项现场条件（见 §11.3），其中**前置条件第一条是「必须显式设置 profile」**（默认未设 profile ⇒ **完全不受控**），另有 1 项**语义缺口另开票**（DB 账本没有 `cost_basis` 列，§10 第 1b 条）。管理会话复核后**批准并已实施**的那 1 行 L5 改动（`generation.go:405` 的预留额改成 profile 感知）已不再是阻塞项。

**能力口径（按「请求前可强制 / 只能响应后核实」分列）**：

- **已完成且已离线验证（请求前拦截，provider 请求数 = 0 为断言）**：模型白名单、输入上界、输出上限（请求参数）、外部请求次数。

- 不要求 DeepSeek 的 provider 白名单（`provider == "generic"`）；

⚠️ **明确声明**：**响应后的检查不能阻止已经发生的超额调用。** 响应后能做的只有两件事：把记录标成 `limit_violation`、冻结账本。真正的拦截全部发生在**请求发出之前**（上表前四行），证据是「provider 请求数 = 0 / 仍为 1」的断言，而不是「事后拒绝记账」。

⚠️ **输入上界的量纲与偏差方向（不是精确 token 计数）**：

- **量纲是 UTF-8 字节**，不是 token。`acceptanceInputUpperBound` = `len(json.Marshal(messages)) + 1024`（`generation_acceptance_budget.go`）。
- **不变式**：UTF-8 下一个 token 至少占 1 字节 ⇒ **字节数 ≥ token 数**，恒成立。所以这个上界**永远不会低估** token 数 ⇒ 请求前闸门**不可能放行一个超限请求**；代价是它**可能拒掉一个其实装得下的请求**。
- **偏差方向按语言**（以 16,000 的上限为例）：
  - **中文**：1 字 ≈ 3 字节，token 数 ≈ 字数 ⇒ 字节上界约为 token 数的 **3 倍** ⇒ 实际允许的输入约 **5,300 字**（比「16,000 token」严）。
  - **英文**：1 token ≈ 4 字符 ≈ 4 字节 ⇒ 字节上界约为 token 数的 **4 倍** ⇒ 实际允许的输入约 **4,000 token**（比「16,000 token」严）。
  - ⇒ **两种语言都偏严（保守），不存在「偏松」的方向**：用字节数当 token 上界只会把闸门收紧。⚠️ 若把「16,000」理解为「16,000 **token**」，当前实现的实际允许量明显更小；这是**口径声明**问题，不是安全漏洞（安全侧）。**请裁定「16,000」到底指 token 还是字节**（见 §11.3 第 6 条）。
- **替代口径与代价（若要精确 token）**：本仓**没有** Qwen 分词器；引入本地 tokenizer 需要 ① 新增依赖（如 `tiktoken`，但它**不是** Qwen 的分词器，对 `qwen3.8-flash` 的计数只是近似）② 附带模型分词器文件（数 MB）③ 进程启动/首次调用的一次性加载成本 ⇒ **本轮不引入**（不报告就加依赖是不允许的）。当前选择的理由：**请求前用保守上界拦、请求后用 provider 回报的真实 usage 对账**（`usage_status=reported`），两头互补。
- **provider 侧看不见的部分**：字节数看不到 provider 自己加的 chat template 与控制 token，由固定的 1024 余量覆盖；真实用量仍以 provider 回报为准，**响应后核实**。

### 4.2 「没有 usage 就记 unavailable（不可核实），不推算冒充」

- 生成路径判定：`internal/lingdoc/workspace/generation.go:558` —— 无 usage ⇒ `reservation.unknown("usage_unknown")`。

### 4.3 费用列的口径（不伪造、不冒充「费用为零」）

- Qwen profile：`cost_basis = "not_applicable"`，费用列写 0，**含义是「没有计价口径 ⇒ 未核算」**；`pricing_basis` 写成一句人话「No price basis: this profile controls tokens and call count, and no money amount is computed.」（`internal/lingdoc/workspace/generation_qwen_acceptance_budget.go:138`）。

- DeepSeek profile：口径与数值**逐字不变**（`cost_basis = "deepseek_peak_usd_2026_09_29"`），旧账本没有该字段时按同一口径读（`internal/models/acceptancebudget/ledger.go:569` `validLedgerCostBasis`）。

- **核心指标不依赖费用**：请求次数 / 输入 token / 输出 token / 总 token / 是否发生额外调用（§3.5 的强制时点表）；费用**不是**放行条件。

## 8.5 三个未决事项：是否构成**当前实现的硬依赖**

| 未决事项 | 是不是当前实现的硬依赖 | 理由 |
|---|---|---|
| **`SYSTEM_AES_KEY` 轮换策略** | **不是**（可独立处理） | 实现的代码只要求一件事：**当前这把 key 能解开那一行密文**。轮换的**策略**（多久轮一次、要不要重加密旧密文、换钥匙的操作流程）属于运维约定，代码里没有、也不需要它。本轮顺带把「解不开」从「静默置空」改成「构造客户端前 fail closed」（`internal/application/service/model.go:642`），所以**轮换期间的行为是失败而不是带空 key 出网** —— 这是安全方向的改变，不是对轮换策略的依赖。⇒ **单独记录，不做部署变更。** 现场只需确认「这一行的密文能被当前 key 解开」（只读探针，§11）。 |
| **4xx/5xx 落库区分** | **不是**（可独立处理） | 本实现对失败的处理只依赖一件事：**调用失败 ⇒ 运行失败 ⇒ 不重试 ⇒ 证据留账**（`service.go:561` 返回 `(failed,nil)`；账本记 `outcome_unknown` 并 blocked；DB 行 `status=failed`）。这与「这次是 4xx 还是 5xx」无关。4xx/5xx 的**落库粒度**是另一件事（更细的失败分类要落到库里供对账用），可以单独做，不影响本实现的任何断言。⚠️ 现状提示：`taskFailureRetryable`（`internal/lingdoc/generation/tasks.go:79`）是从**错误消息文本**里正则出 HTTP 状态码的（既有实现，PR #521），不是从库里读的 —— 所以 4xx/5xx 落库区分**不会**改变现在的重试判定。 |
| **全局默认模型选择（`is_default`）** | **不是**（本实现已绕开） | 受控路径在 `generation.go:431-438` 用 **profile 的显式选择**覆盖了 `defaultGenerationModel`（`generation.go:622`），**不读、也不改**默认位；Qwen 行不存在就 fail closed，不回落默认模型（§1.4 + 2 个测试）。⇒ **本实现不需要动 `is_default`；本轮也没动。** 「是否要动默认位」作为开放问题记录在 §1.4：若将来有人要动，影响范围已列出，需要单独裁定 + 单独票。 |
