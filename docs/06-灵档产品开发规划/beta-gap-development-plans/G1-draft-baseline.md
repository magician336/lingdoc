# G1. 建项语义与草稿阶段

> 父计划：[Beta 六项缺口开发计划](../18-Beta六项缺口开发计划.md)
> 对照设计：[07-建项阶段设计](../07-建项阶段设计.md)、[03-数据模型与接口契约](../03-数据模型与接口契约.md)、[08-权限设计与复用WeKnora](../08-权限设计与复用WeKnora.md)
> 前置假设：T01–T16 已完成并通过各自验收。本文件描述领域逻辑，不等同于当前代码已实现。

## 1. 目标和问题定义

G1 要解决的不是“再做一个项目创建表单”，而是把一个尚未成形的研究构想，经过可停留、可协作、可追溯的过程，变成第一个可被系统引用的正式项目基线。

建项必须回答四个问题：

1. 这个项目现在只是构想，还是已经成立的项目？
2. 当前研究条件是人工填写、AI 建议，还是已经由负责人确认？
3. 其他成员在项目成立前能做什么，项目成立后还需要补什么授权？
4. 项目第一次成立时，哪些草稿期结果应继续有效，哪些对象根本不能在草稿期产生？

G1 的最终用户结果是：

> 课题组可以随时暂停建项并回来继续；Owner 能看见协作和 AI 的来源；确认后得到一个有版本、有章节骨架、有审计记录的 active 项目；后续实质修改不能绕过 ChangeSet。

G1 不替负责人决定研究问题、方法、变量或证据是否充分。它只负责把人的决定、AI 的候选和项目的阶段边界记录清楚。

## 2. 建项的三段语义

建项由三个阶段组成：

| 阶段 | 项目状态 | Context Revision | 允许发生的事 | 禁止发生的事 |
|---|---|---:|---|---|
| 创建记录 | draft | 0 | 建立项目、选择模板来源并创建项目级模板副本、确定初始 Owner、邀请成员 | 生成章节、正式主张、EvidenceCard、ChangeSet、交付快照 |
| 草稿协作 | draft | 0 | 保存 ProjectSpec 草稿、协作、上传资料、受控检索、AI 填写、积累候选 | 把候选直接当正式证据；给章节授予写 scope；应用 ChangeSet |
| 立项确认 | active | 1 | Owner 查看差异并确认；生成章节骨架；开始正式写作 | 以普通保存直接修改已确认研究条件 |

草稿阶段是可选的持久化中间态。用户可以创建后直接确认，也可以停留数天或数周。系统不能因为停留时间长而自动归档或丢弃草稿。

Context Revision 0 不是“没有版本”，而是一个明确的空基线：草稿期的研究条件、候选池和资料操作都以 revision 0 为上下文，但 revision 0 尚未成为正式项目语义。

### 2.1 状态转移和唯一入口

| 当前状态 | 动作 | 成功后的状态 | 允许的发起者 | 失败时保持 |
|---|---|---|---|---|
| 不存在 | 创建项目 | `draft`、`current_context_revision=0` | 租户 active Contributor 及以上 | 不产生半成品项目 |
| `draft` | 保存 ProjectSpec、候选或副本编辑 | `draft` | 有对应项目写权限的成员 | 原 `project_version` 和内容 |
| `draft` | 立项确认 | `active`、`current_context_revision=1` | 当前 Owner | `draft`、revision 0 |
| `draft` | 丢弃 | `draft + discarded_at` | 当前 Owner | 原 draft |
| `draft + discarded_at` | 恢复 | `draft`、revision 0 | 有恢复权限且仍可见的成员 | 丢弃状态 |
| `active` | 普通 ProjectSpec 保存 | 拒绝 | 无 | 原 active 基线 |

每个动作只能通过一个领域入口改变状态；接口重试必须携带创建或写入幂等键。相同幂等键返回第一次成功结果，不得重复创建项目、模板副本、Owner 转让或审计事件。

## 3. 核心对象的逻辑含义

### 3.1 Project

Project 表示课题组正在组织的研究项目，而不是 WeKnora 知识库或聊天会话。

Project 在建项期至少有租户归属、项目名称、当前模板版本、当前项目状态、当前 Context Revision、当前 Owner、是否被显式丢弃、创建者和时间。

Project 的三个主要状态：

- draft：项目尚未成立，Context Revision 必须为 0；
- active：已经完成立项确认，可以产生章节、主张、证据和正式变更；
- archived：active 项目结束后的只读状态。

discarded_at 是 draft 项目的软删除标记，不是第四种 Project 状态。丢弃表示“这段构想没有成立”；归档表示“已经成立的项目结束”。两者不能共用一个按钮或一个用户含义。

owner_unavailable 也不是 Project 状态，而是由当前 Owner 的租户身份失效派生出的限制。项目仍然是 draft 或 active；draft 项目的立项确认，以及 active 项目的变更应用、正式导出和归档能力被冻结，直到 Owner 恢复或完成所有权转让。

### 3.2 ProjectSpec

ProjectSpec 是结构化研究条件，不是永久有效的自由提示词。它包含模板要求的字段、每个字段的当前值、字段值的版本、字段值的状态、字段值的来源类型、字段值的 ProvenanceRecord、最近修改者和修改时间，以及确认页上的两类差异标记。

字段值的来源和状态是两个正交维度：

| 来源 | 说明 |
|---|---|
| human | 用户直接输入 |
| ai_generated | AI 产生候选值，尚未被人改写 |
| ai_assisted_human | AI 提供候选后由人修改 |

| 状态 | 说明 |
|---|---|
| draft | 尚在草稿期，未成为正式基线 |
| pending_confirmation | AI 或协作值需要 Owner 在立项确认时看到 |
| confirmed | 已随 Context Revision 1 进入项目基线 |
| superseded | 被新的项目 revision 取代，保留历史 |

Owner 的整体确认不会抹掉字段来源。一个 confirmed 字段仍必须回答“它最初来自哪里、谁修改过、基于哪段 AI 对话或资料”。

### 3.3 ProvenanceRecord

ProvenanceRecord 是所有“这个值基于什么”的统一引用。它至少表达来源类型、来源对象及其版本、选中的对话/轮次/文本片段或资料锚点、使用目的、授权范围、建立者和建立时间、当前是否仍可访问和是否需要复核。

同一个对话片段可以同时被 ProjectSpec 字段和项目资料导入引用，但这是两条用途不同的引用。撤权、删除、来源替换或重解析时，系统必须沿反向引用检查两条链，不能只失效其中一条。

ProvenanceRecord 证明的是来源和使用关系，不证明研究结论正确。AI 值即使有完整溯源，也仍然可能需要人工修改或质疑。

### 3.4 草稿候选池

草稿期的检索结果、对话片段和资料导入候选属于候选池，不是正式项目语义。

候选池中的结果可以有层级：

- 候选证据：有作者、出处、原文定位，可以在 active 后继续转为 EvidenceCard 候选；
- 背景线索：可以保存，但仍缺少支撑主张的条件；
- 发现入口：只能帮助用户找到原始来源；
- 未读搜索摘要：没有稳定原文定位，不能成为 ProjectAsset 或 EvidenceCard。

立项确认不会把候选池自动变成正式证据，也不会因为 revision 从 0 变为 1 而机械地把候选标记为 STALE。候选仍需在 active 项目中经过 Claim、SourceAnchor 和证据状态流程。

## 4. 第一步：创建记录

### 4.1 创建者和租户前置

创建者必须是当前租户的 active 成员，租户角色至少为 Contributor。创建者提交创建时，系统先建立一个唯一的临时 Owner。

创建记录的最小结果：

- Project.status = draft；
- current_context_revision = 0；
- 已选定一个可用的 LingDoc 模板版本，并创建项目级模板副本；
- 创建者成为 ProjectMember Owner；
- 没有章节；
- 没有 ResearchClaim；
- 没有 EvidenceCard；
- 没有 ChangeSet；
- 没有交付对象。

创建项目的请求可以重放，但不能产生第二个项目。创建失败时，不应留下只有 Project 没有 Owner 的半成品。

### 4.2 指定负责人

创建者可以指定另一位课题负责人。此时系统创建待接受的所有权转让，而不是直接把 Owner 写给尚未接受的人：

1. 创建者暂时保持唯一 Owner；
2. 指定负责人收到转让请求；
3. 指定负责人必须是租户 active 成员；
4. 指定负责人接受后，Owner 转移和创建者降级在一次事务中完成；
5. 转让前后项目都不能出现零 Owner 或双 Owner。

创建者如果要在转让后继续编辑草稿，必须同时声明自己的职能角色。Owner 转为 Member 后，未声明职能的默认写作用域是空集，不应因为“他曾经创建项目”而自动获得全部章节权限。

### 4.3 项目可见性

draft 项目只对创建者、当前成员和拥有明确项目读取权限的人可见。非成员访问时返回统一的不可见结果，不泄露项目是否存在、名称、资料标题或 Owner。

项目可见不等于资料可读。成员关系、租户身份和资料授权仍需分别检查。

## 5. 第二步：草稿期协作

### 5.1 草稿期可以邀请谁

草稿期可以邀请成员。被邀请人接受后立即成为 active 项目成员，不必等项目立项。

草稿期授予的是不带章节 scope 的治理和职能角色：

- Researcher 可以整理资料和调研候选；
- Author 可以编辑被允许的研究条件草稿；
- Reviewer 可以参与审阅可见草稿，但没有章节对象可确认；
- Admin 可以管理成员和项目配置；
- Owner 仍是唯一能完成立项确认的人。

由于章节尚未生成，非 Owner 的职能 scope 为空表示“尚未指派”，不是“全部章节”。立项后必须显式为需要写作的成员分配章节范围。

### 5.2 草稿协作的共享对象

团队共享的是 ProjectSpec 草稿、项目资料关联、候选池和审计记录，不是 WeKnora 的个人聊天会话。

每个成员可以使用自己的 AI 会话。用户选择部分轮次或片段后，才能把它作为 ProjectSpec 的溯源或项目资料候选。系统不提供“一键共享整段会话作为项目事实”的路径。

### 5.3 草稿期保存

保存草稿是可重复的。保存操作必须说明操作基于哪个 project_version、当前字段的旧值和新值、修改者、是否由 AI 产生、是否有 ProvenanceRecord、是否仍处于 pending_confirmation。

两个成员基于同一版本同时保存时，只能有一个条件写入成功。失败的一方应重新读取并让用户决定如何合并；系统不能静默覆盖，也不能把一次重试当成新的语义确认。

草稿期保存不产生 Context Revision，也不创建 ChangeSet，但必须区分工作区版本和研究条件版本：

- `project_version` 递增，表示项目工作区发生了一次条件写入；
- `spec_revision` 递增，表示研究条件发生了一次实质保存，包括草稿期；
- `current_context_revision` 保持为 `0`，因为项目尚未建立正式研究基线；
- 同一次保存的字段值、来源、溯源和审计记录必须绑定到成功写入后的版本。

因此，`project_version` / `spec_revision` 的递增不能被误读为 Context Revision 的推进。前两者记录草稿的可并发读写历史，后者只表示已经应用到项目语义的正式基线。

## 6. AI 填写和质疑

### 6.1 AI 填写的边界

AI 可以根据用户选定的会话或允许资料，为模板字段提供候选值。AI 不能自动确认字段、自动改变项目状态、自动生成正式章节、自动创建 ResearchClaim 或 EvidenceCard、自动扩大资料授权范围，或将推断写成没有来源的项目事实。

AI 填写值默认是 pending_confirmation。即便值看起来完整，仍必须在立项确认页作为“仍是 AI 填写且未经人工修改”的项目显示给 Owner。

### 6.2 AI 填写和系统质疑分开

填写是产生候选值；质疑是要求人检查值是否足够明确。两者不能因为同一次模型调用而合并。

例如 AI 填写“普通本科生”和“结构方程模型”后，系统仍应要求用户考虑样本边界、研究对象的纳入/排除条件、样本量和量表依据、伦理审批，以及因果措辞是否超出研究设计能够支持的范围。

系统可以提出问题，但不能替用户回答并把回答默认为 confirmed。

### 6.3 溯源不可用时

如果 AI 值没有可访问的 ProvenanceRecord，用户仍可以把它作为草稿文本暂存，但字段必须保持 pending_confirmation，确认页必须明确标示溯源缺失。如果模板规定该字段必须有来源，立项被阻断；如果模板未规定来源，Owner 可以在看到风险后整体确认，但审计中必须记录“无可回溯来源”。

## 7. 草稿期换模板

### 7.1 允许条件

draft 项目可以从当前模板副本切换到另一个可用的 LingDoc 模板版本，系统为项目生成新的副本并预览字段迁移；因为章节骨架尚未生成，也没有正式交付版本，换模板不是内容确认，也不产生 ChangeSet 或 Context Revision。

active 项目不能使用这个入口换模板；active 项目换模板必须由 G3 的 template_upgrade ChangeSet 处理。

### 7.2 字段迁移规则

字段不能只靠显示名称匹配。每个模板字段有稳定 field_id，并声明数据类型、必要性、可迁移关系和适用范围。

换模板时：

- 稳定 field_id 且类型兼容：保留值、字段状态、来源和修改历史；
- 旧模板存在、新模板删除：进入 orphaned，原值和溯源仍可查看，不能静默删除；
- 新模板新增字段：进入 missing；
- 同名但 field_id 不同：视为两个字段，不能自动合并；
- 类型不兼容：旧值进入 orphaned，新字段进入 missing；
- 新模板的必要字段未填：立项确认时阻断；
- 用户取消换模板：不产生任何字段或模板变化。

换模板预览必须同时显示字段、值、来源、状态和处理结果。迁移写入和审计记录必须在同一条件操作中完成。

### 7.3 换模板与候选池

换模板不会删除草稿候选池。候选来源仍可保留，但其适用模板字段可能需要重新标记。候选不因此变成正式证据，也不因此自动失效。

## 8. 第三步：立项确认闸门

### 8.1 立项前条件

ConfirmProjectBaseline 只能由当前 Owner 发起。系统至少检查：

- 项目仍为 draft；
- 项目没有 discarded_at；
- Owner 的租户身份仍为 active；
- 项目当前模板副本仍可用；其来源模板版本普通撤回只禁止后续复制，不影响已有副本，只有明确标记为禁止继续使用的强制禁用/安全召回才阻断立项；
- 草稿字段迁移没有未处理的 orphaned 必要字段；
- 模板必要字段满足最低要求；
- 当前项目副本启用的确定性规则已经求值；阻断级问题必须因内容修复或规则版本变化而消失，不能用 waiver/dismiss 绕过，警告和提示必须在确认页可见但不自动等同于学术判断；
- Owner 已加载当前项目并查看两类差异；
- 当前 project_version 没有被其他保存操作改变。

“最低要求”不等于研究设计已经科学成立。系统只能检查结构完整性和明确的模板规则，不替专家决定选题、方法或变量。

### 8.2 两类差异必须可见

确认页必须分开显示：

1. 自 Owner 上次查看以来被其他成员修改的字段；
2. 仍是 AI 填写且未经人工修改的字段。

每项差异都应显示当前值、修改者、时间、来源和查看溯源的入口。Owner 不必逐字段点击确认，但不能在未加载差异的情况下整体确认。

如果 Owner 查看差异后又有人保存，原确认页失效，必须重新读取。系统不能用旧页面提交一个已经过期的整体确认。

### 8.3 立项的原子结果

确认成功后在一次领域事务中完成：

- Project.status：draft → active；
- `project_version` 递增，记录立项确认这次工作区写入；
- `current_context_revision`：0 → 1；
- ProjectSpec 草稿值冻结为基线；
- 根据当前项目级模板副本生成 Ch1–ChN 章节骨架；
- Delivery 状态建立为 NOT_READY；
- 写入基线确认记录和审计；
- 草稿期候选池保留；
- 草稿期资料授权范围保留；
- 非 Owner 成员的章节 scope 仍为空，等待正式指派。

确认失败时，以上结果全部不发生。不能出现 active 项目没有章节骨架、revision 已为 1 但没有确认记录、或只生成了一部分章节的状态。

### 8.4 0→1 的特殊语义

Context Revision 0→1 是唯一不改变研究语义的 Revision 递增。它表示“把草稿期内容冻结为正式基线”，不是一次修改研究条件的 ChangeSet。

因此：

- 草稿期候选的语义基础与 revision 1 相同，不自动标记 STALE；
- 草稿期候选不会自动成为正式证据；
- 立项确认不会创建 ChangeSet；
- 立项确认不把草稿内容重新计为一次 `spec_revision`；当前 `spec_revision` 被绑定到新建立的正式基线；
- 立项确认后才存在可供后续 ChangeSet 比较的正式基线；
- 117→118 这类实质变化仍按普通陈旧规则处理。

## 9. 立项后的边界

### 9.1 研究条件

active 项目的研究条件不能再通过普通草稿保存直接改变。实质修改必须创建 ChangeSet、指定 base_revision、经过影响评估、由 Owner 应用、生成新的 Context Revision，并让受影响确认、证据、章节、路线图和交付进入相应待处理状态。

纯粹的显示排序或未改变语义的界面偏好，可按产品规则作为普通对象编辑，但不得借此绕过实质变更判断。

### 9.2 成员 scope

草稿期没有章节，因此不能授予 Ch1、Ch2 等章节写 scope。立项生成骨架后，Owner 或有成员管理能力的 Admin 才能为 Author、Reviewer 等分配章节范围。

“职能已授予”与“对象范围已授予”是两步：

- 有 Author 但没有章节 scope：可以看到协作入口，但不能写任何章节；
- 有 Reviewer 但没有章节 scope：不能确认任何章节或证据；
- Owner 不使用职能 scope，Owner 的能力来自治理角色全集。

### 9.3 丢弃和恢复

只有 draft 项目可以被显式丢弃。丢弃后不显示在普通项目列表，不能保存 ProjectSpec、邀请成员、继续检索或导入、立项确认；保留必要的审计和恢复入口。

恢复后仍是 draft/revision 0，需要重新走确认。恢复不扩大任何资料授权，也不恢复已经撤销的租户成员权限。非成员不能通过恢复入口判断项目是否存在。active 项目不能使用丢弃，只能由 Owner 归档。

### 9.4 Owner 失效

Owner 租户身份 suspended 时：

- Project.status 不变；
- owner_unavailable 派生标记为 true；
- 普通成员仍可进行被授权的读取、评论、资料整理和草稿编辑；
- draft 项目的立项确认、active 项目的 changeset.apply、delivery.export、project.archive 被冻结；
- access-status 只返回访问状态和合法恢复动作；
- 不返回旧正文、研究条件或资料标题给已失效成员。

Owner 恢复后，下一个请求重新检查租户身份并解除冻结。所有权转让是另一条恢复路径，必须经过受让人确认和条件写入。

如果 Owner 无法恢复，`owner_unavailable` 下允许租户 Owner 或平台管理员指定受让人并发起所有权转让；这条旁路只解决发起权，不直接授予项目所有权。受让人接受后，必须在同一事务中完成 Owner 转移、原 Owner 降级和项目版本条件写入，项目始终保持唯一 Owner。转移完成前，草稿可以继续协作但不能立项确认；转移完成后，新 Owner 必须重新加载当前项目和两类差异，不能复用失效 Owner 的旧确认页。

## 10. 失败和竞态规则

| 场景 | 必须发生 | 不能发生 |
|---|---|---|
| 两人同时保存同一草稿 | 一次成功，一次 version conflict | 后写入覆盖前写入 |
| Owner 查看确认页后别人修改 | 确认页失效，要求重新读取 | 旧页面冻结新修改 |
| 创建请求重试 | 返回原 Project | 产生两个项目或两个 Owner |
| 转让同时接受两次 | 一次成功，一次冲突 | 双 Owner |
| Owner 恢复与转让并发 | 按 project_version 决定一个成功顺序 | 零 Owner 或两条有效转让 |
| 草稿换模板失败 | 字段和模板保持原状态 | 一半字段迁移、一半旧模板 |
| AI 溯源被撤权 | 相关字段和导入候选待复核 | 继续把失效来源当有效依据 |
| 草稿候选跨 0→1 | 保留并标明仍是候选 | 机械标 STALE 或自动成为证据 |
| draft 被丢弃后写入 | 拒绝并返回可执行恢复提示 | 静默写入或恢复为 active |
| active 研究条件普通保存 | 拒绝并引导 ChangeSet | 绕过影响评估直接递增 revision |

## 11. G1 交付切片

| 切片 | 逻辑交付 | 完成判据 |
|---|---|---|
| G1.1 阶段与对象 | draft/active/discarded/owner_unavailable 语义 | 状态转移表和失败边界可由测试逐项复现 |
| G1.2 草稿协作 | 字段来源、状态、版本、差异和保存冲突 | 两人协作不会覆盖；AI 值可回看溯源 |
| G1.3 Owner 生命周期 | 临时 Owner、指定负责人、接受/转让/恢复 | 并发操作始终保留唯一持久 Owner |
| G1.4 模板迁移 | field_id、orphaned、missing、预览和取消 | 不静默丢值；active 换模板必须走 ChangeSet |
| G1.5 立项确认 | 两类差异、0→1、章节骨架和确认审计 | 成功是原子的，失败无半完成状态 |
| G1.6 候选和溯源 | ProvenanceRecord 与草稿候选保留 | 0→1 不误陈旧；撤权传播到所有用途 |
| G1.7 丢弃恢复 | draft 软删除和最小恢复入口 | 丢弃不可写；恢复不越权、不自动立项 |

## 13. 领域验收场景

### AC-G1-01：直接立项

用户选择一个可用模板并立即确认。系统先建立项目级模板副本，再生成 active 项目、revision 1 和章节骨架；没有草稿候选也不应被迫进入调研页面。

### AC-G1-02：草稿停留和恢复

用户只填写部分条件后离开，重启服务再回来。项目仍是 draft/revision 0，字段、来源、候选池和成员不丢失。

### AC-G1-03：AI 值可追溯

AI 根据用户选择的会话轮次填写字段。确认页显示该字段仍是 AI 填写，点击溯源可回到轮次；AI 值没有自动变为人工事实。

### AC-G1-04：草稿换模板

用户切换模板，看到保留、orphaned、missing 三类结果；取消切换不改状态；确认切换后未处理必要字段不能立项。

### AC-G1-05：证据边界

草稿期可以积累候选来源，但创建 ResearchClaim 或 EvidenceCard 被显式拒绝；active 后按 G2 顺序创建，不产生孤儿证据卡。

### AC-G1-06：立项差异

Owner 未加载确认页差异时不能确认；其他成员在加载后修改字段时，旧确认页失效。

### AC-G1-07：0→1 陈旧例外

草稿期调研候选 based_on_revision=0。立项后候选仍保留原层级和来源，不自动标 STALE，也不自动变成 confirmed evidence。

### AC-G1-08：指定负责人并发接受

创建者指定负责人，负责人重复接受或与另一位负责人竞争接受。只有一个接受成功，项目始终有唯一 Owner。

### AC-G1-09：丢弃与恢复

Owner 丢弃草稿后，成员保存、邀请、检索和立项都失败；恢复后仍是 draft/revision 0，需要重新走确认。

### AC-G1-10：Owner 失效

Owner 被租户停用。普通成员可继续合法的读取、资料整理和草稿编辑，但 draft 不能立项、active 不能应用 ChangeSet 或导出；租户 Owner 或平台管理员指定的受让人接受转让后，唯一 Owner 在同一事务中恢复，且新 Owner 必须重新加载确认差异。Owner 恢复后能力重新可用。

### AC-G1-11：active 绕过保存

active 项目直接提交 ProjectSpec 普通保存。系统拒绝并提示创建 ChangeSet；不产生新 revision、不覆盖确认。

### AC-G1-12：权限交接

草稿期 Researcher 接受成员邀请后可导入资料但没有章节写权；立项后被显式分配章节 scope 才能执行相应写操作。

## 14. 不纳入 G1

- 自动替用户决定选题、方法、变量或研究结论；
- 自动把 AI 输出标记为已确认；
- 草稿期正式章节编辑；
- 草稿期正式 ResearchClaim 或 EvidenceCard；
- 自动归档或自动丢弃长期未立项草稿；
- 完整组织审批流；
- 实时多人协同编辑；
- active 项目的模板直接替换；
- 通过解除资料绑定来恢复撤权后的旧派生正文。

G1 完成的标准不是“表单能提交”，而是任何用户动作都能明确回答：当前项目处于哪一阶段、该值从哪里来、谁有权继续、失败后哪些状态没有改变。
