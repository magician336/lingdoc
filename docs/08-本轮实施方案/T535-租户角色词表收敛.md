# T535 租户角色词表收敛（第一段）

> 票：#535《收敛 governance.Actor.Role 的角色词表 —— 一处定义、一处校验、审计列语义写清》
> 本文件只覆盖票的**第一段**。第二段（跨面契约变更）不在本票内，见文末「第二段需要谁裁定什么」。

## 一句话

`governance.Actor.Role`（= `rulesetstore.Actor.Role`）承载的是**租户角色**。这个词表现在只有一个拥有者、只有一个判定入口，三个写入方都受它守护。

## 唯一权威位置

| 事实 | 位置 |
| --- | --- |
| 词表成员（四个） | `internal/types/tenant_member.go:21`、`:25`、`:29`、`:32`（`TenantRoleOwner` / `TenantRoleAdmin` / `TenantRoleContributor` / `TenantRoleViewer`） |
| 词表的取值集合 | `internal/types/tenant_member.go:38`（`tenantRoleLevel`，同时承载权限层级） |
| **唯一判定入口** | `internal/types/tenant_member.go:46`（`TenantRole.IsValid`） |

`internal/types` 拥有这份词表。它不是三套角色词表里的一份，而是**租户角色**这一概念的权威；成员记录上的项目角色、治理角色、职能角色，以及跨租户共享用的 `OrgMemberRole`（`internal/types/organization.go`），都是**不同的概念**，各有各的定义，不并入这份词表。

## 审计列的语义

`actor_role` 这一列只有一个意思：

> **操作者在那个租户里当时的角色**（tenant role，取自上面那份词表）。

它**不是**项目角色、**不是**治理角色、**不是**职能角色，也不是「这条操作被允许了」的判定结果。这三件事容易被混起来，因为它们在同一个租户里同时存在：一个人可以既是租户 owner，又是某个项目的 member，还是该项目的 author。

具体到落库：

| 列 | 写入方 | 代码位置 |
| --- | --- | --- |
| `audit_logs.actor_role` | `rulesetstore` | `internal/lingdoc/rulesetstore/store.go`（`recordAudit`） |
| `audit_logs.actor_role` | `templategovernance` | `internal/lingdoc/templategovernance/storage.go`（`recordAuditOutcome`） |
| `lingdoc_ruleset_use_audits.actor_role` | `delivery` → `rulesetstore` | `internal/lingdoc/delivery/export.go`（`RuleSetUseAuditEvent.ActorRole`）、`internal/lingdoc/template/ruleset_use_audit.go` |
| `lingdoc_ruleset_use_audits.actor_role` | `rulesetstore` | `internal/lingdoc/rulesetstore/use_audit.go`（`ruleSetUseAuditRow.ActorRole`） |

读这一列的人现在不需要知道「是哪一面写的」就能解释它——因为只有一份词表。

## 判定规则：拒绝，不是归一

词表外的角色**被拒绝**，不做归一映射。依据：

1. **既有实践已经是拒绝。** 模板治理的应用层对同一个字段早就用 `types.TenantRole.IsValid()` 判过（`internal/lingdoc/workspace/template_governance_runtime.go:187`）。本票做的是把同一判定补在它原本就缺的那一层，不是新增一条策略。
2. **归一会发明语义。** 把一个词表外的词映射到某个词表内的词，等于替写入方决定「它本来是什么意思」。漂移正是要消灭的东西，归一只是把漂移藏起来。
3. **既有可接受集合未变。** 生产侧所有填充点本来就只产生词表内的值（`internal/container/lingdoc.go:226`、`internal/container/lingdoc.go:182`、`internal/lingdoc/workspace/template_governance_runtime.go:174`），所以收紧之后被拒的只有**生产上不可能产生**的值。

各面的拒绝形态：

| 面 | 词表外的角色 | 形态 |
| --- | --- | --- |
| `rulesetstore` | `ErrActorRoleInvalid`（401 `unauthenticated`） | 与「没有 actor」（`ErrActorRequired`）区分开：前者是角色不可解释，后者是身份缺失 |
| `templategovernance` | **应用层**给形态：`errors.Join(core.ErrNotFound, ErrUnverifiedActor)` | 见下方「为什么 templategovernance 不在 ready() 里抢先拒绝」 |
| `delivery` | `ErrExportUnavailable` | 既有行为，本票只补守护断言 |

### 为什么 `templategovernance` 不在 `ready()` 里抢先拒绝

票面建议把 `ready()` 从「非空」升级为「在词表内」。直接照做会**改变既有错误形态**，所以本票没有照做。

既有契约由 `internal/lingdoc/workspace/template_governance_routes_test.go` 的
`TestTemplateGovernanceRejectsArbitraryRoleClaimWithoutAuthoringReceipt` 钉住：
一个词表外的角色声明（`Role = "not-a-tenant-role"`）必须被当作**身份无法归属**
拒绝，形态是 `errors.Join(core.ErrNotFound, governance.ErrUnverifiedActor)`
（再被 `AuthorizeTemplate` 包成 `ErrPermissionDenied`），并且**不能**留下回执。

那个形态只能由应用层给出：`workspacecore` import `templategovernance`，
反向引用会成环，所以 `templategovernance` 这一层**无法**产出 `core.ErrNotFound`
（它是 `*clienterror.Error` 指针，没有按 Code 匹配的 `Is` 方法）。

⇒ 如果 `ready()` 抢先拒绝，对外形态会从「身份无法归属 + 不可枚举」变成
「授权不可用（403）」。那是契约变更，属于第二段。

⇒ 本票的落点：

- `ready()` 保持「非空」判定，注释写清「角色判定归应用层」；
- **写侧**守住审计列（`recordAuditOutcome` 在 INSERT 前查词表）—— 词表外的
  角色进不了 `audit_logs.actor_role`；
- 读侧「在词表内」的判定由应用层 `freshActor` 完成（`types.TenantRole.IsValid`，
  同一份词表），既有测试钉住其形态，本票不改它。

## 写入方守护

「写不进审计列」这件事不依赖调用方记得先校验：每个写入点自己都有最后一道门。

| 写入点 | 守护位置 |
| --- | --- |
| `rulesetstore` 读侧 | `validateActor`、`GetVersionForBinding` |
| `rulesetstore` 写侧（直写 SQL） | `recordAudit` |
| `templategovernance` 读侧 | 应用层 `freshActor`（`types.TenantRole.IsValid`，既有行为与形态，本票不改） |
| `templategovernance` 写侧（直写 SQL） | `recordAuditOutcome` |
| `delivery` 写侧 | `export.go` 已有的 `actor.Role.IsValid()` |

守护测试：

- `internal/types/tenant_role_vocabulary_guard_test.go`：词表成员与取值固定；成员标识符在 `internal/types` 之外只允许带限定符引用；仓内没有第二份字面量清单；持有 `Actor.Role` 的两个面不拿字面量判角色。
- `internal/lingdoc/rulesetstore/actor_role_vocabulary_guard_test.go`：读侧与写侧都拒绝词表外的角色，且审计表里不留下任何行；词表内的角色照旧写入并被原样读回。
- `internal/lingdoc/templategovernance/actor_role_vocabulary_guard_test.go`：`ready` 不抢先改形态（归应用层）；直写 SQL 的 `recordAuditOutcome` 拒绝词表外的角色；一次真实治理操作在词表外角色下失败且审计表零行。
- `internal/lingdoc/delivery/actor_role_vocabulary_guard_test.go`：词表外的角色导不出，两个写入点都不留下记录；词表内的角色照旧被记录。
