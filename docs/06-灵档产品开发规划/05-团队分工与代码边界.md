# 团队分工与代码边界

## 1. 分工原则

三人以领域所有权分工，而不是以页面、数据库或“谁方便谁改”分工。允许状态影响，禁止跨域写入；允许共享契约，禁止共享内部模型。

| 开发流 | 领域所有权 | 主要交付 | PCC 中的责任 |
|---|---|---|---|
| A | Evidence / Source Truth | 项目资料接入适配、来源锚点、证据卡、受控检索与重校验 | `KnowledgeImpactHandler` |
| B | Workspace / Project Truth | 项目条件、主张、章节、版本、确认、PCC | `ChangeCoordinatorCore` |
| C | Delivery / Delivery Truth | 模板、路线图、预检、导出与交付快照 | `DeliveryImpactHandler` |
| Shared | Contract / Platform | 事件信封、错误语义、上下文快照、测试 fixture | 审核和演进契约 |

## 2. 推荐代码组织

不改动 WeKnora 核心领域的内部实现来“塞入” LingDoc 规则。新增模块应位于独立命名空间（下列为建议路径，落地前随当前仓库约定校准）：

```text
WeKnora/internal/lingdoc/
  evidence/       # A：Gateway、ProjectAsset、Anchor、EvidenceCard
  workspace/      # B：Project、Spec、ResearchClaim、Chapter、Confirmation
  pcc/             # B：ChangeSet、Dependency、Impact、outbox
  delivery/        # C：Template、Route、Preflight、Export
  contract/        # Shared：事件、DTO、错误码
  api/             # BFF/HTTP handler，仅编排本领域服务
WeKnora/migrations/lingdoc/
WeKnora/testdata/lingdoc/
WeKnora/frontend/src/features/lingdoc/
```

若最终决定独立 LingDoc 服务，上述边界应转为独立服务/API，而非改变职责。无论单体模块还是服务化，禁止 A/B/C 直接访问彼此 repository 或表。

## 3. 各流工作包

### A：Evidence

- 封装 WeKnora 文档入库、处理状态、混合检索和引用定位为 `KnowledgeGateway`。
- 建立 `ProjectAsset`、`SourceAnchor`、`EvidenceCard` 与授权范围；重解析时维持可追踪谱系。
- 实现候选证据、证据重校验和缺口报告；只发布证据事实/候选，不更改项目主张或确认。
- 为材料替换、锚点丢失、权限撤销和检索不足提供可测试事件。

### B：Workspace 与 PCC

- 建项三步：创建记录得到草稿态 `Project`（`Revision 0`）→ 草稿期协作（邀请成员立即生效、模板驱动的 `ProjectSpec` 字段集与逐项状态/溯源、AI 填写与溯源）→ 立项确认生成章节骨架与 `Revision 1`；以及草稿丢弃的软删除标记。
- 建立主张、章节、内容版本、评论/任务和确认。
- 实现 ChangeSet → 影响评估 → 应用 Revision → 领域任务 → 稳定化状态机。
- 维护 DependencyRegistry、ImpactResolver、任务路由、Outbox/Inbox 与上下文快照。
- 所有项目写入、确认失效和导出放行均经过 B 的领域服务；禁止管理台直写。

### C：Delivery

- 建立按申报类别/年度版本化的 `TemplateProfile` 和规则集（领域定义与规则实现归 C；模板发布与生效的治理流程走 RuoYi 管理台，不写 C 的业务表）。规则按判定方分工：`computed` 由 C 求值，`model` 由 C 声明检查项、经 A 的受控通道调用模型执行——**C 不直接持有资料授权，模型类检查的输入必须经 A 获得**。
- 实现可编辑技术路线图表示、正文—图形关联、模板检查（对当前内容）与交付预检（对快照）、ReleaseSnapshot 与 DOCX 导出。模板检查与预检是**同一套规则集对两类对象的两次求值**，不得实现成两套并行规则。
- 对 `workspace.release_snapshot_changed.v1` 与确认失效执行预检，发出 `delivery.issue_detected.v1` / `delivery.release_ready.v1`；模板版本变更时重跑模板检查，并使既有快照的预检结果失效。
- 不修改章节或研究条件；需要修复时创建影响任务并返回 B。

## 4. 共享文件与评审规则

下列变化必须由至少 A/B/C 中两位（其中一位为 B）评审：

- `contract/` 中的事件 schema、DTO、状态枚举与错误语义；
- 任何数据库迁移、授权中间件、Outbox/Inbox、Revision 或 ReleaseSnapshot 变更；
- 任何从 WeKnora 回传的引用/定位信息映射；
- 跨域 API，或会改变导出是否可放行的规则；
- Feature flag、数据保留策略、审计字段和脱敏行为。

共享不等于谁都能随手改。契约先以小 PR 固定，再由各域实现消费；新增可选字段优先于修改已有语义。

## 5. 交付节奏与 PR 纪律

1. **契约先行**：先合并数据/事件 schema、fixture 和空实现，再并行开发 A/B/C。
2. **纵向小切片**：一个 PR 只实现一个用户可验证动作，例如“资料重解析使 EvidenceCard 进入待核”，不在同一 PR 同时改 Agent、模板和权限。
3. **迁移前向兼容**：先加字段/表与双读，再切换写入，最后在单独版本清理旧路径；不覆盖既有用户资料。
4. **测试随 PR 提交**：领域单测、契约测试和至少一个 fixture 验收案例；跨域 PR 必须验证重复事件和陈旧结果。
5. **功能开关**：`lingdoc_evidence`、`lingdoc_workspace`、`lingdoc_pcc`、`lingdoc_delivery` 等按域独立开启，便于灰度、回退和隔离。

## 6. 冲突预防清单

| 高风险点 | 统一规则 |
|---|---|
| 用户/权限 | WeKnora 提供租户/知识库上限，LingDoc 提供项目 capability；最终权限取交集，不建立第二套身份真相。 |
| Workspace 命名 | `Project` 不等于 WeKnora tenant/workspace/knowledge base。 |
| 材料引用 | B/C 只保存 `ProjectAssetRef/SourceAnchorRef`，绝不保存裸 `chunk_id`。 |
| 版本 | 严格区分 Asset/Context/Chapter/Template/Release 版本。 |
| 草稿态与基线 | `Revision 0` 是草稿期空基线，语义上**等于** `Revision 1` 的内容：草稿期不产生 `ChangeSet`，`0 → 1` 只冻结语义、不使草稿期产物失效（`117 → 118` 才按机械比较）。两侧判错会让草稿期功能与 PCC 对“什么算变更”得出不同结论——这也是 P0 的并发禁区。 |
| 状态互相覆盖 | 通过事件+Revision；消费者拒绝陈旧写入。 |
| 提示词/模型规则 | 证据判定归 A，项目影响与确认归 B，交付判定归 C；同一业务事实不能有三套 prompt 裁决。 |
| 缓存/队列 | 使用独立 namespace、事件幂等和可观测的任务状态；不以缓存充当权威状态。 |
| 管理端 | 管理动作走 Admin API 和审计，不直连数据表或任务 worker。 |

## 7. 工作量平衡

B 因 PCC 会成为新增业务最重的一域，这是合理的：WeKnora 已提供了大量 A 的知识基础能力，而 B 是当前没有的项目运行时；建项三步（草稿态、协作与 AI 填写、立项确认）同样落在 B。为平衡实现量，可让 A 实现 `Context Assembler` 的资料/证据部分，让 C 实现依赖图的只读可视化和交付侧测试 fixture；但建项三步、Project Truth、ChangeSet、Revision、确认与稳定化的业务所有权始终留在 B。
