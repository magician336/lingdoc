# LingDoc 项目健康度评分与重构诊断

使用本 Skill 时，先读取仓库根目录的 [项目健康度评分协议](../../../docs/项目健康度评分协议.md)。它是权重、评分等级、评分时点和当前基线的唯一依据。

本 Skill 的交付物是“哪里做得不够好、应该怎样重构”，不是健康项清单。评分必须由结构性缺陷和可复核证据驱动；测试、文档或 CI 通过只能证明某条路径被验证，不能替代模块深度、信息隐藏或变化放大的判断。

## 适用范围

- 用户要求评估 LingDoc、某个 Spec 或 PR 的设计健康度、维护风险或仓库集成程度。
- 用户要求给出 `H_L`、`F_R`、0–100 分或 A/B/C 置信度。
- 用户要求比较 Spec 完成时和 PR 合并前的评分变化。

不要把 `F_R` 解释为整个 WeKnora 仓库的质量分数；它只表示 LingDoc 与宿主仓库的契合度。

## 工作流程

1. 确认 Git 根目录、当前 SHA、目标 Spec 或 PR，以及评分阶段。
2. 按项目 `AGENTS.md` 使用 CodeGraph 理解代码；必要时先确认 `.codegraph/` 已初始化并保持索引最新。
3. 阅读当前 Spec、`CONTEXT.md`、`GLOSSARY.md`、相关接口契约、测试、CI 和验收材料。区分当前依据、历史记录和设计意图。
4. 分别计算 `H_L` 和 `F_R`。两者使用相同六维权重，但 `H_L` 观察 LingDoc 内部，`F_R` 观察 LingDoc 与宿主仓库的边界。
5. 先找缺陷再打分：对每个二级指标记录“变化会在哪里放大、哪些知识泄漏、哪个边界浅或错位、调用者承担了什么本应由模块隐藏的规则”。每个二级指标给 0–5 分，并记录证据路径、验证命令、置信度和模块级重构方向。不要用文件数、代码行数或测试数量直接代替复杂性判断。
6. Spec 阶段把尚未实现的代码证据标记为待验证；PR 阶段重新检查真实代码、失败/权限/恢复路径、CI 和文档同步，并记录 `ΔH_L`、`ΔF_R`。
7. 报告健康等级、结构性不足、重构顺序、关键阻断项和未覆盖风险。若关键维度低于 2/5，单独列为阻断风险。

## 反通胀评分规则

“低分”不是失败测试的同义词，而是代码在变化、理解或恢复上已经产生结构性成本。按以下锚点评分，3/5 表示“能工作但有明显债务”，不是健康默认值：

- **5**：模块深、知识集中、变化局部；有持续度量、复盘和自动约束证明这一状态。
- **4**：边界和约定系统化，常见变化可以局部完成；仍有少量已知债务。
- **3**：主路径可用，但存在重复规则、人工协调、浅接口或未收敛的跨模块依赖。
- **2（低分）**：已观察到结构性放大：同一规则在多个模块重复、调用链透传实现细节、一个小改动需要多处同步，或失败/权限语义由多个层共同决定；只能靠人工记忆或局部补丁维持。
- **1（严重低分）**：边界基本失效，调用者必须理解内部机制才能正确使用；关键变化无法局部实施，或恢复路径依赖临时操作。
- **0**：缺失、互相矛盾，或无法提供可信证据。

出现以下证据时不得给 4–5 分：没有定位到具体模块的泛泛描述；只有单元测试通过而没有边界/调用路径证据；设计意图与真实代码不一致；同一知识在两个以上层级重复表达；大量 pass-through 方法、特殊分支或隐藏副作用；关键失败只能靠重跑或人工修复。关键维度低于 3/5 时必须给出重构方向；低于 2/5 时必须标为阻断风险。

## 结构诊断与重构方向

用 Ousterhout 的复杂性、深模块和信息隐藏原则解释缺陷，优先回答：

1. 哪个变化会牵动最多模块，为什么这是变化放大而不是单纯工作量？
2. 哪个设计知识（权限、状态、格式、并发、恢复或供应商策略）泄漏到了多个模块？
3. 哪个接口只是转发参数或暴露内部数据结构，应该合并、下沉或改成更深的接口？
4. 哪些特殊情况可以被统一语义、空对象、聚合错误或单一恢复机制消除？

每个低分项至少给一条可执行建议，格式为：

`模块/边界 → 结构问题 → 重构动作 → 预期减少的变化放大或认知负荷 → 回归门槛`

重构动作应指向模块合并/拆分、职责下沉、端口收窄、策略集中、状态机归属、错误语义统一或消除透传；不要只写“补测试”“加强文档”“重跑 CI”。测试只作为证据和回归门槛，只有当测试失败暴露结构缺陷或阻塞安全重构时，才可列入最高优先级动作。

最高优先级按“复杂性降低收益”排序：变化放大范围 × 变化频率 × 边界关键性。若没有定位到模块和重构动作，不得把该项写成最高优先级治理建议。

## 证据与环境约束

- A 级置信度需要自动化测试、CodeGraph、CI 或可复现运行结果；B 级允许代码抽样和文档证据；C 级表示主要依赖未验证假设。
- “未知的未知”不直接评分，使用未知发现速度、失败诊断、可观测性、回退和假设验证来评估。
- Go 测试优先使用项目约定的 WSL2 Ubuntu、Go 1.26 和 Linux SQLite 环境。`sqlite3.h`、cgo、CRT 或 MinGW 工具链错误先记录为环境限制，除非业务断言本身失败。
- 不要把未运行的测试写成通过；记录 PASS、FAIL、BLOCKED 或 NOT RUN 及确切命令。

## 输出要求

默认输出：

- `H_L`：LingDoc 系统健康度 /100 和置信度；
- `F_R`：LingDoc—仓库契合度 /100 和置信度；
- 六维分项表、低分二级指标和关键证据；
- 每个低分项的结构性不足与模块级重构方向；
- 与上一次评分的变化；
- 按复杂性降低收益排序的最高优先级重构动作；
- Git SHA、Spec/PR、取样范围、验证命令和未覆盖风险。

需要快速填写评分卡时，读取 [评分卡模板](references/评分卡模板.md)。
