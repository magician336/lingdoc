# G3 首版最小变更复核

## Problem Statement

现有 active 项目已经有 `current_context_revision`、项目条件、章节版本、确认、冻结和导出语义，但用户修改研究主题或研究目标后，系统还不能把这次变化作为一个可追踪的正式变更处理。用户无法可靠知道哪些已确认章节需要重新检查，也无法保证旧确认不会继续放行当前交付。

本 spec 只定义第二阶段首版的 G3 最小变更复核切片，不承诺完整 PCC、通用依赖图或自动发现所有隐含影响。

## Solution

在现有项目工作台中增加受限的 ChangeSet 流程：

1. 项目成员针对 `research_subject` 或 `research_goal` 创建变更草稿，填写旧值、新值、理由、当前基线 revision，并明确选择已登记的受影响章节。
2. 系统生成影响预览，把已登记的受影响章节与尚未核对范围分开显示；预览不会改变正式项目。
3. 当前 Owner 在仍匹配基线 revision 时应用变更。应用、递增 `current_context_revision`、保存新条件、使登记章节的旧确认失效和写审计记录必须是同一事务。
4. 变更应用后，受影响章节必须绑定当前 revision 重新复核/确认；未完成时继续阻断冻结和导出。
5. 完成复核后沿用现有确认、冻结和导出流程。旧 revision、旧章节版本、旧确认和旧快照保留为历史，不能被当作当前版本继续写入。

主要行为 seam 是现有 workspacecore 的项目/章节应用服务；通过已有 HTTP 工作区入口验证权限、状态码、幂等和交付闸门，避免新建独立 PCC 服务。前端只维护该领域的 adapter、状态和最小交互，不建立平行业务状态。

## User Stories

1. As a project member, I want to create a change proposal for the research subject, so that a semantic change is recorded before it affects delivery.
2. As a project member, I want to create a change proposal for the research goal, so that the first release has an explicit bounded field set.
3. As a project member, I want to see the current context revision when creating a change, so that I know which baseline I am changing.
4. As a project member, I want to record old and new values, so that reviewers can understand the semantic delta.
5. As a project member, I want to record a reason for the change, so that later reviewers can distinguish intentional changes from recovery actions.
6. As a project member, I want to select the chapters I know may be affected, so that the system records explicit impact instead of pretending to infer every dependency.
7. As a project member, I want to preview a change without applying it, so that I can correct the proposal before changing the project baseline.
8. As a project member, I want the preview to show affected chapters and reasons, so that I can decide whether the registered impact is complete.
9. As a project member, I want the preview to show an explicit “not yet checked” area, so that missing dependency records are not presented as proof of no impact.
10. As the project owner, I want only the current owner to apply a proposal, so that project semantics cannot be changed by an arbitrary member.
11. As the project owner, I want a proposal based on an old revision to fail safely, so that a concurrent change cannot be overwritten.
12. As the project owner, I want applying a proposal to update the project condition and context revision atomically, so that no half-applied project state is visible.
13. As the project owner, I want registered affected chapters to lose current confirmation status after application, so that old review decisions cannot authorize the new revision.
14. As a chapter reviewer, I want to review the current chapter version against the current context revision, so that the new confirmation binds to the correct baseline.
15. As a project member, I want the system to reject freezing and export while an affected chapter remains unreviewed, so that an old confirmation cannot pass the delivery gate.
16. As a project member, I want the normal freeze and export paths to continue after all affected chapters are re-confirmed, so that G3 does not create a second delivery workflow.
17. As a project member, I want repeated application with the same idempotency key to return the first result, so that a lost response does not create a second revision.
18. As an auditor, I want to see who created, applied, rejected, and reviewed a change, so that the complete decision trail is available.
19. As a second developer, I want a reproducible two-chapter flow, so that the feature boundary is demonstrated rather than inferred from unit tests.

## Implementation Decisions

- The first release supports only `research_subject` and `research_goal`.
- A ChangeSet is a project-scoped decision record after application. It stores the base context revision, field-level delta, reason, selected affected chapters, actor, status, target revision, and audit linkage.
- The initial impact model is explicit registered impact, not automatic dependency discovery. The UI and API distinguish “registered affected”, “reviewed”, and “not yet checked”.
- ChangeSet lifecycle is `assessed`, `applied`, `rejected`, and `stale`. The create-preview request persists an assessed proposal directly; there is no separately persisted draft or independent `approved` state, and owner decision and application share one conditional write.
- Applying a ChangeSet requires active project state, current owner authorization, matching base revision, valid field versions, and an idempotency key.
- The application transaction updates project fields, increments context revision by one, records application, invalidates selected chapters’ confirmations, and writes audit data together. Any failure leaves the original state unchanged.
- A stale application creates no new revision, impact rows, or field mutation. The user must deliberately create a new proposal against the current revision.
- Old revisions, chapter versions, confirmations, and release snapshots remain historical and cannot satisfy current freeze or export checks.
- Re-confirmation binds to the current context revision and current chapter version.
- Existing confirmation, release, and export services remain the delivery source of truth; G3 adds the revision/impact precondition.
- The primary implementation seam is the existing workspacecore application service, with HTTP tests for the same behavior and the existing request layer for frontend integration.
- SQLite and PostgreSQL migrations must remain symmetric and preserve old projects.
- No general DependencyRegistry, ImpactTask dispatcher, RouteNode graph, AI dependency import, or natural-language impact assistant is introduced.

## Testing Decisions

- Observe behavior through workspacecore application behavior and HTTP tests for authorization, error mapping, idempotency, and delivery blocking; do not assert private helper calls.
- Reuse existing project activation, chapter version, confirmation, release freeze, export, optimistic conflict, and idempotency test patterns.
- Success coverage includes preview, current-baseline apply, new revision, invalidated confirmation, re-confirmation, freeze, and export.
- Failure coverage includes stale revision, non-owner, inactive/discarded project, malformed delta, missing affected chapter, idempotency replay, transaction failure, concurrent chapter edit, stale confirmation, and freeze/export while review is open.
- Database tests cover migration and transaction atomicity on SQLite and PostgreSQL where supported.
- The acceptance report distinguishes `PASS`, `FAIL`, `NOT RUN`, and `BLOCKED`; mock or static checks are not real end-to-end evidence.
- Final validation uses two representative chapters on one merged SHA, service restart, stale/concurrent proposal, re-confirmation, freeze, export, and second-developer reproduction.

## Out of Scope

- Automatic discovery of all implicit dependencies, a general DependencyRegistry, AI-generated edges, or an AI impact assistant.
- Generic ImpactTask assignment, cross-domain event orchestration, distributed workflow infrastructure, RouteNode/RouteEdge roadmaps, template-upgrade ChangeSets, and complete PCC semantics.
- Automatic rewriting of chapters, claims, evidence, or research conclusions.
- Real-time collaboration, offline source caching, or a new delivery/export system.
- Treating a reason or model suggestion as evidence, confirmation, or authorization.

## Further Notes

The long G3 blueprint remains a future design reference. This issue implements only the narrow change-review result from the lean plan: record a bounded semantic change, show registered impact and uncertainty, invalidate affected confirmations, and resume delivery after current-version re-review.

The implementation is tracked by the tracer-bullet tickets: change capture/preview, atomic application/invalidation, and re-review/delivery recovery. Each ticket includes schema, API, UI state, and behavior tests for its own vertical slice; the current branch contains the first integrated slice and its focused verification.
