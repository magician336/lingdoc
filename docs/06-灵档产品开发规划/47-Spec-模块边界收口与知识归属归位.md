# Spec #47：模块边界收口与知识归属归位

> 状态：草案（2026-10-20）。本 Spec 由架构深挖循环产出，接续已关闭的横切契约 Spec [#164：LingDoc 应用层传输解耦与幂等结果边界](https://github.com/magician336/lingdoc/issues/164)，不推翻其已落地的边界。
> 配套实施与验收证据：[`../../08-本轮实施方案/Spec-47-模块边界收口与知识归属归位.md`](../../08-本轮实施方案/Spec-47-模块边界收口与知识归属归位.md)。
> 架构取证报告与逐条证据：`.scratch/lingdoc-arch-20261020/`（工作区本地，不入库）。

## Problem Statement

LingDoc 的工作区领域层是一个**单点聚合体**：一个服务结构体承担了项目、成员、章节、工作副本、模板副本、变更集、影响任务、调研、规则、运行观测等全部用例的公开方法，公开方法总数约 245，分布在 36 个文件里，最大的单个文件 3,752 行、承载 14 个互不相干的主题。

这一形状给三类人造成实际成本：

**对领域开发者**：想改一个概念，必须先知道这个概念的知识散落在哪里。变更集状态字面量出现在 9 个生产文件的 20 多处；章节"已确认"的判定有三套不同条件、失效写入有 6 处；引用标记语法有 8 处独立实现；业务错误到 HTTP 对外形态有 5 张平表、42 个分支。每加一个状态、每加一种错误、每加一个来源标记语法，都要同时改多处，且漏改不会立刻报错——它只是让某个分支不再命中。

**对评审者**：评审一个跨模块改动时，无法用"哪个模块拥有这个真相"来提问。同一知识出现在两层以上时，评审只能逐行比对字符串，而字符串比对正是最容易漏的形式。Spec #164 已经把"应用层契约不再声明 `json.RawMessage`"这条边界立起来，但只有一条传输面走了这条边界；另有 5 条传输面仍直接持有该聚合体的具体类型，因此边界在多数路径上并未真正生效。

**对发布与运行时**：组合根缺少能力时，两条互不相同的失败路径都不在启动期暴露。一条传输面在端口缺失时仍注册路由，故障以首个请求的空指针出现；另一条传输面在端口缺失时静默不注册路由，端点变成 404 而没有任何启动期信号。装配错误因此在生产启动之后才被看见。

## Solution

把"知识归属"作为本 Spec 的唯一目的地，按**先集中泄漏、再提取共享核心、最后上下文切分**三段推进，每一段都可独立验收、独立回滚：

**第一段（集中泄漏）**：为四个当前没有唯一主人的设计决策各指定唯一主人，并把散落实现收拢到主人处。这一段**只做消除，不做搬运**，是纯低风险改动：
1. 变更集与其变更影响的状态词表归位到变更集模型（与影响任务状态表同层同法）；
2. 章节"已确认"判定归位到一个谓词，失效写入归位到一个触发点；
3. 业务错误的对外形态归位到错误定义处，传输层映射器只做兜底；
4. 引用标记语法的解析与"标记数必须等于正文出现次数"这条约束归位到一处。

**第二段（提取共享核心）**：把操作管道（身份与人工决策门、幂等键与请求体哈希、重放顺序、授权、审计写入、来源复核、事务边界）从聚合体中提取为一个真正的深模块，让上层用例依赖它，而不是各自实现一份。

**第三段（上下文切分与端口收窄）**：在接缝成立的前提下，按上下文把用例实现从聚合体中切出，每切出一个上下文就带走它的端口，并把仍直接持有聚合体具体类型的传输面改为消费按上下文收窄的端口。

对用户可见的结果是：**同一类问题只有一处决定**。新增一种业务错误不需要改传输层平表；新增一种引用标记语法不需要改六个包；新增一个变更集状态不需要改九个文件；把一个上下文切出时不需要先发明新的边界。

## User Stories

### 作为领域开发者

1. 作为领域开发者，我希望**新增一个变更集状态只改一个地方**，这样我不会漏改某个分支而让该状态永远无法被读到。
2. 作为领域开发者，我希望**变更集的状态词表是显式声明的、可枚举的**，这样我能查到某个状态是否可达，而不必在 36 个文件里搜字符串。
3. 作为领域开发者，我希望**每个状态有明确的含义说明**，这样我不会把"已被取代"和"已解决"当成同一个终态。
4. 作为领域开发者，我希望**能区分"变更集已闭环"和"变更集已被取代"**，这样稳定化闸门不会把"被取代"误当作"已处理"。
5. 作为领域开发者，我希望**章节"已确认"只有一个判定入口**，这样我改判定规则时知道只有一处需要同步。
6. 作为领域开发者，我希望**确认失效只有一个写入点**，这样我不会在某条路径上漏掉失效，导致章节带着过期确认继续放行。
7. 作为领域开发者，我希望**"已确认"的判定条件在代码里是一个可读的谓词**，而不是三份各带条件的判断。
8. 作为领域开发者，我希望**交付预检与稳定化对"章节是否已确认"给出一致结论**，这样两个流程的结论可以互相解释。
9. 作为领域开发者，我希望**新增一种业务错误时只声明它的对外形态**，这样我不需要去传输层大表里加一条分支。
10. 作为领域开发者，我希望**错误自带对外形态这件事有一个统一入口**，而不是每个包各写一张映射表。
11. 作为领域开发者，我希望**同一种业务语义在所有传输面对外完全一致**，这样前端和外部集成方不需要按路由猜状态码。
12. 作为领域开发者，我希望**"调用方不必区分"的异常被屏蔽掉**，这样错误种类不会随时间无节制增长。
13. 作为领域开发者，我希望**引用标记语法只有一处解析实现**，这样我改语法时不会漏掉某个包。
14. 作为领域开发者，我希望**"正文里的标记数必须与解析出的标记数相等"这条约束只写一次**，这样不会出现一半路径校验、一半路径不校验。
15. 作为领域开发者，我希望**引用标记的 ID 字符集由一处定义**，这样加宽字符集不会导致某些路径解析失败。
16. 作为领域开发者，我希望**操作管道（幂等、重放、授权、审计、事务）只有一份实现**，这样 G2 的行为不会和其余用例天然漂移。
17. 作为领域开发者，我希望**管道是深模块**，这样我调用它时不需要知道它内部有几个阶段。
18. 作为领域开发者，我希望**上层用例依赖管道这个接缝，而不是依赖聚合体的内部字段**，这样我替换管道实现时不用改所有用例。
19. 作为领域开发者，我希望**每次改动都小到能单独验证**，这样重构失败时我能立刻定位到是哪一步。

### 作为评审者

20. 作为评审者，我希望**每个设计决策都能指到唯一主人**，这样我能用"这个知识属于谁"提问，而不必逐行比对字符串。
21. 作为评审者，我希望**新增一个状态或一种错误时，diff 里能看到它只加在一个地方**，这样"漏改"从评审负担变成评审可见。
22. 作为评审者，我希望**能看到词表被测试逐态断言**，这样词表和实际可达状态不会各说各话。
23. 作为评审者，我希望**对外契约（错误码、状态码、文案）在重构前后逐字不变**，这样我可以只审结构而不审行为。
24. 作为评审者，我希望**重构提交自带行为基线**（重构前后同一条命令的结果），这样我能判断这是结构调整还是行为改变。
25. 作为评审者，我希望**每个阶段可以独立回滚**，这样某一段不成立时不需要推翻全部。
26. 作为评审者，我希望**术语与实现一致**，这样代码里的"已确认""已闭环""已取代"指的是产品文档里的同一件事。

### 作为发布与运行时维护者

27. 作为运行时维护者，我希望**组合根缺少必需能力时在启动期报错**，这样我不会在生产上收到一个空指针堆栈。
28. 作为运行时维护者，我希望**端口缺失不会静默变成 404**，这样端点消失是一件启动期就会说出口的事。
29. 作为运行时维护者，我希望**每条传输面只依赖它需要的端口**，这样新增一个端口不会波及所有面。
30. 作为运行时维护者，我希望**一个端口的缺失只影响它自己**，这样故障范围可以预期。
31. 作为运行时维护者，我希望**组合根不需要在多个位置推断同一个能力**，这样我不会读到一段"为什么这里又要判一次 nil"的代码。

### 作为前端与外部集成方

32. 作为前端开发者，我希望**同一业务错误在所有路由上返回相同的状态码与错误码**，这样我不需要为每个路由写分支。
33. 作为前端开发者，我希望**错误文案在同类错误间保持一致**，这样我可以直接展示而不必重写。
34. 作为前端开发者，我希望**"可重试"标记在同类错误间一致**，这样我才能正确决定是否自动重试。
35. 作为前端开发者，我希望**契约里出现全部可达状态**，这样我不会在渲染一个从未被文档描述过的状态。
36. 作为外部集成方，我希望**重构不改变任何 wire 行为**，这样我的集成不受影响。

### 作为 AI 编码代理

37. 作为 AI 编码代理，我希望**改一个概念时目标文件是可预测的**，这样我不会在错误的文件里加分支。
38. 作为 AI 编码代理，我希望**接口注释说明调用契约、错误语义和不变量**，这样我能正确使用而不必读实现。
39. 作为 AI 编码代理，我希望**状态与错误词表是单一可检索的声明**，这样我能查到合法取值而不必猜。

## Implementation Decisions

### 一、总体原则

1. **先消除，再隐藏。** 四个"变化炸弹"先各自归位，再谈模块边界。理由：当前"窄端口"只覆盖了六条传输面中的一条，在接缝真正成立之前搬运实现只会把泄漏搬到新位置。
2. **知识归属，而非执行时间或文件命名。** 拆分的判据是"边界隐藏的知识 > 边界收费"，不是文件大小、不是名词切分。
3. **每段可独立验收、独立回滚。** 三段之间不共享未提交的中间状态。
4. **对外契约逐字不变。** 路由、成功与错误信封、状态码、错误码、文案、重放元数据、数据库 schema、持久化的幂等记录格式在本 Spec 全程保持不变。已冻结的对外错误码不得因内部归位而改变。

### 二、第一段：集中泄漏（四个炸弹各一个主人）

#### 2.1 变更集与变更影响的状态词表

5. **主人**：变更集模型所在的领域模块。影响任务的状态表已是同层同法（一份可达状态列表、一份闭环状态子集、各带设计说明与逐态断言），变更集照此办理即可，不发明新范式。
6. **词表**：变更集状态共七个取值——`draft`、`assessed`、`applied`、`stabilized`、`rejected`、`stale`、`satisfied`。变更影响状态至少包含 `open`。**取值集合以「契约中已声明的状态」与「变更集相关代码路径中实际可达的状态」两者的并集为准**，并由测试逐态断言二者一致。
7. **契约并无缺口，缺的是 Go 侧的声明。** 已核实：对外契约的变更集状态枚举、数据库的取值约束、前端的状态类型与中文标签表**三处已经一致**地覆盖上述七个取值。真正的缺口是 **Go 侧没有这份声明**——七个取值以裸字符串分布在 9 个以上生产文件。因此本项的交付不是补契约，而是：建立唯一的 Go 词表声明，并增加**漂移断言**，让契约枚举、数据库约束、前端类型与 Go 词表四者在测试中互相比对，任一处改动而其余未跟随时测试失败。
8. **状态含义与闭环子集必须写进词表声明**：变更集状态的**闭环子集是 `applied` 与 `stabilized`**（当前稳定化闸门与反向变更的准入都按这两态判定）。必须区分的是：`stale`（依据已被取代或失效，**不算闭环**）、`satisfied`（本次变更已无待办语义工作）、`rejected`（人工驳回，**不是闭环**）。稳定化闸门只承认闭环子集，不得把"被取代"或"已驳回"读成"已处理"。这与影响任务表「可达状态列表 + 闭环状态子集」的做法一致。
9. **合法迁移集中判定**：合法状态迁移由词表所在模块判定，其他模块不得自行拼装迁移条件。

#### 2.2 章节"已确认"判定

10. **主人**：一个显式谓词，表达"某章节版本当前是否处于已确认状态"。
11. **谓词条件为现有三套条件的并集**：存在一条有效的确认记录，且其章节标识、章节版本标识、研究条件修订、模板版本、确认人、确认时间全部与当前状态一致。取并集而非交集，是因为并集才是三套条件里最强的一套；较弱的一套之所以弱，是因为它拿不到判定所需的事实，而不是因为那些事实不重要。
12. **失效写入只有一个触发点**：章节正文被改写、工作副本被提交、正式依据变更导致确认不再成立时，由该触发点统一把确认置为失效。当前这些写入散落在多处。
13. **三个消费者共用这一个谓词**：稳定化的影响解析、规则治理的影响阻断判定、交付预检。三处当前各自判定，其中一处因数据形状所限**在结构上看不到确认已失效**，只能靠研究条件修订相等间接挡住。
14. **已裁定（DR-47-01）：章节标识不允许为空。** 确认记录的章节标识必须存在且与目标章节一致。裁定已核实可行：确认记录表的章节标识在两个数据库上都是非空且带外键，"允许为空"只存在于规则治理运行时的一处宽松判定，不是数据形状允许，收口时只需收紧该判定、**不需要数据迁移**。必须区分的两件事：「确认记录存在但章节标识为空或与目标章节不符」属非法，该确认不成立；「章节没有确认记录」是交付侧当前有意使用的表达（空章节或未确认章节必须到达交付环节并持久化一份可处理的阻断快照），**该行为保持不变**。收紧后携带空标识或错配标识的历史记录将不再被判为有效，开票前须核查现网是否存在此类记录。
15. **交付侧的数据形状必须补齐**：交付的确认快照结构当前没有"是否有效"字段，因此该路径**无法**表达失效。这是数据形状缺口，必须补上，否则谓词无法在交付侧落地。

#### 2.3 业务错误的对外形态

16. **主人**：错误定义处。错误在定义时同时声明状态码、错误码、文案与是否可重试；传输层映射器只保留兜底分支。**本方向是既有决策的延续，不是新决策**——ADR-0003 第六节已裁定"错误自带对外形态、映射器只做兜底"，并显式把"现有错误暂不迁移"列为推迟项。本段执行那项推迟。
17. **不一对一搬迁**：不得把 42 个分支逐一翻译成 42 种形态。先按语义归并：把当前散落在多张表里、语义相同但状态码或文案不同的错误**合并为同一形态**，再让每一类语义只声明一次。
18. **必须先消解的对外分歧（收口后必须一致，且与收口前的多数口径一致）**：
    - 规则集"非草稿/非发布态"：当前一条传输面答 409 `invalid_state`、另一条答 409 `state_conflict`、第三条把同类错误答 422 `invalid_state`。
    - 规则集"版本已存在/状态冲突"：当前一条传输面答 409 `version_conflict`、另一条答 409 `state_conflict`。
    - 不可重试标记：当前一条传输面对 5xx 判不可重试，另两条判可重试；治理面走另一条发送路径，其 503 恒为不可重试，与规则集面的 503 可重试相反。
    - 同错误码不同文案："内容已变化，请先读取当前版本。" 与 "输入版本已变化，请重新读取。" 指向同一事实。
19. **502 只在一处出现**：模型输出不合规当前答 502，是全套对外形态中唯一的孤例。归位时保留该状态码与错误码，但必须进入统一语义表，不再由个别传输面私有。
20. **屏蔽调用方不必区分的异常**：调用方无法据以采取不同动作的差异，不进入对外形态。归位过程中若发现两个分支调用方行为完全相同，应合并为一种形态而不是保留两种。
21. **已裁定（DR-47-02）：以各路由多数口径为准，少数口径的变更逐条列出并记录理由；收口后对外错误码清单冻结。** 归并后规则集状态类错误只有两类语义：「状态不允许该操作」→ 409 `invalid_state`；「版本或基线已变化」→ 409 `version_conflict`。状态码两边本就一致为 409，不变。少数口径变更为三项：规则集存储路由的 `state_conflict` 拆入上述两类；对外错误码 `state_conflict` 退役。该变更影响规则集相关在途票 #187、#193，需在其验收证据中同步。除上述已裁定的变更外，对外错误码集合与文案逐字不变；收口过程中新发现的少数口径变更，必须先登记为决策记录并经产品语义确认，不得在实现中顺手改掉。

#### 2.4 引用标记语法

22. **主人**：一个解析实现，负责三件事——识别标记、抽取标记携带的标识、校验"正文中的标记出现次数必须等于解析出的标记数"。今天这三件事在 8 处独立实现：4 处使用逐字节相同的正则、3 处手写字符串扫描、1 处只做计数校验。
23. **标识字符集由主人定义**：当前所有正则使用同一字符集，但手写解析处的边界判定方式不同。合并后以正则所声明的字符集为准，并保留一处显式定义。
24. **计数不变量的唯一性**：计数校验与解析必须同处一地；调用方不得只做计数而自行解析。
25. **跨包依赖方向**：解析实现必须放在被依赖方向的下层。当前跨包手写解析分散在候选采纳、交付、生成、文档渲染、选区改写与工作区核心之间；归位后不得出现下层包反向依赖上层包。

### 三、第二段：提取共享核心

26. **主人**：一个独立的操作管道深模块，公开接口小、实现有力，把下列知识一次性收拢：操作身份与人工决策门、幂等键与请求体哈希、幂等冲突判定、重放顺序与重放位、授权判定、审计写入、来源复核前置、读写事务边界与锁策略。
27. **上层用例依赖接缝**：用例只声明"我要做什么操作"，不自己实现幂等、重放、授权或审计。当前调研域另写了一套与主管道并行的幂等/重放/审计实现，必须并入同一条管道。
28. **管道不改语义**：并入后调研域的幂等键冲突、请求体哈希、重放顺序、来源重查、人类决策门五处行为必须逐条证明与并入前等价，并保留对照测试。
29. **不可变契约（执行前先写下）**：
    - **身份与版本真相**：操作身份、幂等键、请求体哈希由管道唯一拥有；上层不得另算。
    - **事务边界**：授权判定、审计写入、幂等记录与业务写入在**同一个事务**内；来源复核在**只读事务**内完成且不得跨事务持有连接。
    - **零写入保证**：授权失败、版本冲突、幂等冲突、人工决策缺失时，本次操作**不得留下任何业务写入**；审计记录是唯一允许的写入，且须与判定同事务。
    - **失败语义**：授权拒绝与对象不存在对无权调用方返回同一种对外形态，不泄露对象是否存在。
30. **管道不引入第二个真相**：管道不得复制上层用例已经拥有的领域规则；上层也不得复制管道已经拥有的机制。

### 四、第三段：上下文切分与端口收窄

31. **前提**：前两段完成后才开始。第三段不得与前两段并行。
32. **一个上下文一个主人**：切出某个上下文时，该上下文的端口、实现与不变量一并迁出；聚合体不再实现该端口。
33. **端口归属随上下文迁移**：端口当前声明在消费方。按既有层次原则，端口应当由它所描述的那门语言的拥有者声明，因此在上下文被切出时，端口随实现一起迁移到拥有它的模块。切分过程中端口的**方法集合与语义不变**。
34. **端口按上下文收窄**：一个上下文一个窄口，只含该上下文用到的操作。当前存在的宽口（一个覆盖三十余个操作的应用口、一个覆盖三十余个操作的遗留兼容口）必须被按上下文收窄的口取代，遗留兼容口在全部调用方迁移后移除。
35. **消除直连**：传输层不得再持有聚合体的具体类型。当前六条传输面中除一条外的全部都直接持有该具体类型，且一个实例被多个面与运行时共同持有，任一面可调用任一方法——这是"后门泄漏"，收窄端口正是它的关闭方式。
36. **组合根 fail-closed**：组合根缺少某条传输面必需的端口时，必须在**启动期**返回明确错误，不得留下空端口让故障推迟到首个请求，也不得静默不注册路由。允许省略的端口（可选扩展）必须在接口上显式标注为可选，并由组合根在装配时记录该选择。
37. **组合根不再做多重推断**：同一项能力不得在多处被推断。当前组合根有一段一百二十余行的依赖解析级联，同时存在遗留适配器与按上下文拆分适配器两套并存的转发层。收口后每项能力只有一个注入位。

## Testing Decisions

1. **只测外部行为**：断言端口与 HTTP 的可观察结果（状态码、错误码、文案、信封、持久化后的事实），不断言内部调用次数、内部结构或私有函数。每个阶段配一条**结构断言**（例如"传输层不出现聚合体具体类型"）用于守住接缝本身。
2. **接缝高度**：最高可用接缝是 HTTP 传输面。行为证据走传输面 + 真实存储；端口级测试只覆盖契约形状与失败语义，不承担行为证明。这与既有规则一致：直接调用存储的测试不单独构成完整交付证据。
3. **行为基线先于改动**：每段开工前先在同一 head 上跑出基线（定向测试 + 契约快照），改动后用同一命令对照，差异必须为零。结构重构与行为改变不得混在同一次提交里。
4. **优先复用既有测试形态**：
   - 状态词表逐态断言：复用影响任务状态表已有的逐态断言形态。
   - 跨面一致性：复用既有 HTTP 契约测试与多路由回归测试的形态。
   - 事务与幂等：复用既有操作管道回归测试与重放/恢复测试的形态。
   - 组合根：复用既有组合根装配测试与集成测试的手工装配场景，但**改为从组合根装配**，消除测试里重复的迁移清单。
5. **不新增测试接缝**：本 Spec 不引入新的测试专用接口。确需在传输层与领域之间加端口时，该端口必须同时是生产端口。
6. **等价性必须有对照**：并入主管道这类改动，不能只跑新测试，必须保留并入前后的同场景对照断言。
7. **失败路径优先**：每个阶段先写失败/权限/恢复用例，再补成功路径。

## Out of Scope

1. **不改变任何对外行为**：路由、成功与错误信封、状态码、错误码、文案、重放元数据、数据库 schema、持久化的幂等记录格式。
2. **不新增功能**：本 Spec 不引入任何新的用户可见能力。
3. **不实现尚未落地的能力**：影响中心渲染、规则建议、调研等既有 Spec 的功能缺口不在本 Spec 范围内；本 Spec 只处理它们共享的边界与知识归属。
4. **不合并上下文**：第一段与第二段不涉及上下文切分；第三段只切出端口已就位、证据已闭环的上下文，不做一次性大拆分。
5. **不治理与本 Spec 无关的平行框架**：规则集生命周期在治理域与存储域各有一套实现、规则目录有两条传输面——这是独立候选，需与在途票对齐后再决定是否单开，不在本 Spec 内解决。
6. **不改组合根的其它职责**：组合根同时是依赖注入清单、适配器选择器、迁移脚本与生命周期管理器；本 Spec 只处理"能力缺失时是否 fail-closed"与"同一能力是否多处推断"，不重排其余职责。
7. **不动前端交互与视觉**：前端只跟随契约同步状态与错误码，不做界面改造。
8. **不合并历史兼容行为**：遗留兼容口在全部调用方迁移后移除；本 Spec 不保留"永远不删"的兼容层。

## Further Notes

1. **本 Spec 的来源**：架构深挖循环对仓库的取证报告（CodeGraph 索引 + 四路并行静态取证 + 人工复核）。结论与逐条证据保存在工作区本地 `.scratch/lingdoc-arch-20261020/`，含候选清单、依赖图、端口足迹、错误映射对照与泄漏清单脚本。该目录不入库。
2. **与既有决策的关系**：
   - ADR-0002（Spec 交付的两道门）适用于本 Spec：第一段与第二段开工前必须有验收矩阵与不可变契约，交付前必须用当前 head 的证据闭环。
   - ADR-0003 第六节的"错误自带对外形态"方向在本 Spec 第二段被真正执行；其"现有错误暂不迁移"的推迟项在本 Spec 结束时应关闭。ADR-0003 第八节要求的"未知动作按阻断处理"这类 fail-closed 原则同样适用于本 Spec 的错误归位。
   - ADR-0001（来源定位以仓库字符区间为准）不直接涉及本 Spec，但引用标记的标识抽取不得改变来源定位的判定方式。
3. **与 Spec #164 的关系**：#164 已把"应用层契约不再声明 `json.RawMessage`"立在一条传输面上，其余五条传输面仍直连聚合体具体类型。本 Spec 不推翻 #164 已落地的边界；#164 的未完成部分正是本 Spec 第三段要关闭的缺口。
4. **已裁定的产品决定（2026-10-20）**：
   - **DR-47-01**：章节确认**不允许**章节标识为空，确认记录的章节标识必须与目标章节一致。裁定已核实无需数据迁移：确认记录表的章节标识在两个数据库上都是非空且带外键，"允许为空"只存在于规则治理运行时的一处宽松判定。同时必须区分「确认存在但标识不符」（非法）与「章节没有确认记录」（交付侧有意表达，保持不变）。
   - **DR-47-02**：规则集状态类错误**以各路由多数口径为准**，少数口径变更逐条列出并记录理由。归并后为 409 `invalid_state`（状态不允许该操作）与 409 `version_conflict`（版本或基线已变化）两类；对外错误码 `state_conflict` 退役。该变更需在规则集相关在途票 #187、#193 的验收证据中同步。
   - **DR-47-03（已裁定 2026-10-22）**：5xx 的「可重试」标记在收口时发现存在分歧，段二先按「4xx 不可重试、5xx 可重试」的暂定口径执行，并把确认单独成票（[#292](https://github.com/magician336/lingdoc/issues/292)，挂在 #259 下）。**裁定结果**：原则不变，但**尚未配置**类的 503 是例外——规则治理面的 503「目录或规则建议服务尚未配置」判为**不可重试**，因为服务不存在时重试也不会变好；治理面其余 5xx（502 `invalid_model_output`）、候选采纳面与工作区主路由的 5xx 仍可重试。落地见 `docs/08-本轮实施方案/Spec-47-段二-错误形态跨面归并与共享核心提取.md` 的 D-47-05 一节与 `docs/08-本轮实施方案/47.06-错误形态对照表.md`。
5. **本 Spec 的三段对应到票**：票粒度与垂直切片由后续票据步骤确定；每张票必须能独立验收、独立回滚，且不跨段。
