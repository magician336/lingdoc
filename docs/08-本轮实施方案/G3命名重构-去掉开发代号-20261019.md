# 命名重构：去掉 G3 开发代号（2026-10-19）

## 背景

G1–G7 是团队的**文档层级叫法**，用于组织规格、验收与交接说明，本文件继续沿用。
但在代码里，`g3_` 文件前缀和 `g3*` 标识符带来三个实际问题：

1. **零信息量**。这些文件全部位于 `internal/lingdoc/workspacecore` 与 `internal/lingdoc/workspace`，
   包名已经限定了范围，`g3_` 前缀不给读者任何额外信号，只增加打字成本。
2. **按交付批次而非知识归属切分**。文件是按「G3 这一批交付了什么」划分的，而不是按
   「哪一块知识住在这里」划分的。读者要判断一个改动该改哪个文件，只能通读全部内容。
3. **代号会渗透到用户可见文案**。开发代号本不该出现在终端用户读到的字符串里。

同时 `workspacecore` 包内本来就并存另一套命名：`working_copy.go`、`change_inverse_operation.go`、
`membership.go`、`review_anchor.go`、`human_decision.go`、`source_policy.go`。本次改动是
**回归到包内已有的语义命名约定**，不是引入新约定。

## 标识符重命名

| 旧名 | 新名 | 理由 |
| --- | --- | --- |
| `g3Audit` | `recordAuditEvent` | 它被 G2、G5、G6 的服务共同调用，从来就不是「G3 的审计」，而是项目的审计写入。旧名与实际用法矛盾。 |
| `g3RecordRow` | `versionedRecordRow` | 描述行本身：一个带版本号的记录行。 |
| `g3Read` / `g3Insert` / `g3CAS` / `g3List` | `readVersionedRecord` / `insertVersionedRecord` / `compareAndSwapVersionedRecord` / `listVersionedRecords` | 动词化，说明做什么而非属于哪个批次。 |
| `G3OperationSourceIDs` | `OperationSourceIDs` | 导出的 API 名不应携带代号。 |
| `G3SourceSensitiveOperation` | `SourceSensitiveOperation` | 同上。 |
| `RegisterG3G6FullRoutes` | `RegisterImpactRoutes` | 该函数注册的是影响相关的路由族。 |

测试辅助函数同步改为语义名（`materializeChapterVersions`、`tasksInProject`、`contractOperation` 等），
测试函数名去掉票据号（`TestG3202FreezeAndExportRequireCurrentStabilization` →
`TestDeliveryGateFreezeAndExportRequireStabilization`）。

## 用户可见文案

这是本次最实质的一类修复——开发代号出现在终端用户读到的字符串里：

- `workspace/g2_full_http.go`：「请在"正式变更"中建立 **G3** 草稿」→ 去掉「G3」。
- `workspacecore/evidence_card_delta.go`：`ErrFormalChangeRequired` 的错误文案
  「requires a **G3** ChangeSet」→「requires a formal ChangeSet」。
- `templategovernance/upgrade_impact.go`：交付阻断原因
  「requires **G3** stabilization」→「requires Owner stabilization」。

## 保留未改

- **`lingdoc_g3_records` 表名**：这是 SQLite 与 PostgreSQL 两套迁移共用的物理表名，
  改名属于 schema 迁移而非代码重命名，需要配套的数据迁移与回滚验证，不在本次范围内。
  Go 侧的 `versionedRecordRow` 已不再携带代号，物理名字留待专门的迁移票处理。
- **G2/G4/G5/G6 的 `gN_` 文件**：本票只处理 G3。其余前缀同样应改，但属于独立的重构范围，
  建议单独开票，避免与 Spec #198 的验收证据混在一起。
