### 3.2 接口形状

契约 `02-接口与Mock约定.md §2` 只给了两个方法签名（`AssetGateway.ResolveAllowed(projectID, actor, assetIDs)`、`SourcePolicy.Validate(projectID, actor, sourceRefs)`），**没有规定返回值如何承载被拒项**。

这是 T03 必须自己定义的部分，也是本任务最该交给 T09 的东西：

```go
// ResolveResult 一次性说清"请求了什么、允许了什么、拒绝了什么"。
// 三个字段缺一不可：只返回 Allowed 就是契约里那句被禁止的"静默当全部成功"。
type ResolveResult struct {
    Requested []string      // 回显请求集合，供消费者逐项比对
    Allowed   []Asset       // 绑定且就绪且当前可访问
    Denied    []DeniedAsset // 含原因：未授权 / 未就绪 / 不存在
}

type AssetGateway interface {
    ResolveAllowed(ctx context.Context, projectID string, actor Actor, assetIDs []string) (*ResolveResult, error)
}
```

`Source` 按契约字段构造，另挂一个**不序列化**的仓库锚点。实现即此（`internal/evidence/source.go`）：

```go
type Source struct {
    ID             string       `json:"id"`
    ProjectID      string       `json:"project_id"`
    AssetID        string       `json:"asset_id"`
    AssetRevision  int          `json:"asset_revision"`   // 契约是 integer，见下
    Locator        string       `json:"locator"`
    QuotedText     string       `json:"quoted_text"`
    QuotedTextHash string       `json:"quoted_text_hash"`
    Status         SourceStatus `json:"status"`           // available | stale | unavailable

    Anchor Anchor `json:"-"`   // KnowledgeID/ChunkID/ChunkIndex/StartAt/EndAt/ContentRevision/ContentRewritten
}
```

`json:"-"` 不是风格问题：契约里 `Source` 是 `additionalProperties: false`，内部锚点漏出去即违规。已用测试钉住（去掉 tag 会报「多出契约没有的字段 Anchor」）。

**两处偏离契约 §2，需 T09 评审：**

1. **`SourcePolicy.Validate(projectID, actor, sourceRefs)` 未按签名实现，改为 `SourceResolver.Resolve(ctx, asset, hits)`。** 原因是 §2 的签名收 `sourceRefs`（已产出的引用），而坐标只存在于检索命中里——**定位判据必须在产出 `Source` 的那一刻执行**，否则没有任何东西可校验。且 `ContentRevision`/`ContentRewritten` 是 `json:"-"`（ADR-0001），跨进程传进来的 `sourceRefs` 已丢失失效信息，`Validate` 在那种输入上做不出 §3.3 的判定。若 T09 仍需要独立的 `Validate`，它应当是 `Resolve` 的薄封装而非替身。
2. **`AssetRevision` 是 `int` 而非 `string`。** 契约 `Asset`/`Source`/`AssetVersion`/`FrozenSource` 四个 schema 里都是 `{"type": "integer", "minimum": 1}`；初版写成 `string`，是查契约时才发现的类型漂移。

### 3.3 来源定位与失效检测

术语表 §2 已定义「来源锚点 `SourceAnchor`：能回到材料中具体页、段、表、图或**字符区间**的位置描述；应支持**重定位和失效检测**。**不应混同为 WeKnora 的裸 `chunk_id`**」。

仓库的 `types.SearchResult`（`internal/types/search.go:151-227`）已提供 `StartAt`/`EndAt`（原文字符区间）、`ChunkIndex`、`KnowledgeID`、`ID`，并有失效钩子 `ContentRevision` / `ContentRewritten`。**但这两个字段是 `json:"-"`，序列化即丢失**——所以失效检测必须在同一进程内完成，不能靠回读持久化 JSON 补判。

**偏移的单位是 rune。** 依据：`chat_pipeline/merge_overlap.go:98` 已有的不变量 `runeLen(Content) == EndAt-StartAt`，以及 `chunk.go:631` 用 `len(baseRunes)` 作上界。按字节切会静默切错中文，强档断言正是用来抓这个错的。

**「原文」从哪来（2026-09-23 查证）。** 全量解析产物**没有落库**：`types.Knowledge` 只有 `FilePath`/`Metadata`/`ParseStatus`，无正文字段；`Chunk.SourceContent` 是逐块产物，不是整篇。现有代码把这对坐标当**相对量**而非绝对指针——`merge_overlap.go:41` 用 `EndAt-StartAt` 算重叠长度，`chunk.go:630` 用 `child.StartAt-parent.StartAt` 抵到父块，`knowledge_search.go:1224` 拿它当位置先验，`merge.go:270` 的注释称其为「editable StartAt/EndAt coordinates」（merge pipeline 自己会改写 `EndAt`）。

所以「能指回原文」分两档，**不可混为一谈**：

| 档 | 判据 | 适用范围 |
|---|---|---|
| **强（绝对）** | `原文[StartAt:EndAt] == QuotedText` | **仅当原始资料是可直读的纯文本**（本轮合成资料即如此）。只有这档能检出 rune/byte 混淆 |
| **弱（相对自洽）** | `runeLen(Content) == EndAt-StartAt` ∧ `ContentRevision == 0` ∧ `!ContentRewritten` | 真实资料上唯一能诚实声明的一档 |

**对 PDF/DOCX 等需重解析的格式，本轮只给弱档。** 提升到强档需要一个能拿到原文的落点（存解析产物，或按 `FilePath` 重解析）——**这是 T09 的缺口，见 §6.5**。

因此 `Status` 的取值规则是（**实现即此表**，判据照 `chunkTrusted`（`merge_overlap.go:94-99`）同构）：

| 次序 | 条件 | `Status` |
|---|---|---|
| 1 | `ContentRewritten == true` 或 `ContentRevision != 0` | `stale` |
| 2 | 强档且 `StartAt`/`EndAt` 越界或 `EndAt <= StartAt` | `unavailable` |
| 3 | 强档且 `原文[StartAt:EndAt] != Content` | `stale` |
| 4 | 弱档且 `EndAt <= StartAt` 或 `runeLen(Content) != EndAt-StartAt` | `unavailable` |
| 5 | 以上都不成立 | `available` |

两条校正（写作时未写准，实现时才查清）：

- `ContentRevision` 的判据是 **`!= 0`**，不是「与落库值不一致」——它记录的是人工编辑次数，0 表示没被编辑过，无从比对「落库值」。
- **`EndAt > StartAt` 必须单独判。** 空内容配零长区间满足长度不变量的退化形式（`runeLen("") == 0 == 0-0`），只看长度会把退化区间当作可用证据放过去。这一条是写好实现自查时发现的，已补测试。

失效标记（第 1 行）**先于内容判定**：被标过重写或编辑过的命中，即便此刻切片仍对得上也不采信——坐标已不再描述当前正文。这是术语表 §2「默认拒绝」的直接落地。

**`stale` 不是失败，是结论**：它表示「这条引用曾经可用，但坐标已不可信」，下游据此拒绝把它当作当前证据。

### 3.4 报告与运行模式

契约 §9 要求运行模式显式标 `mock` / `real_api_fake_model` / `real`。T03 的报告同时记录两个维度：

- 整体 `mode`：本次实际使用的最高保真度；
- 逐条 `status`：`passed` / `failed` / **`not_run`**（附原因）。

`not_run` 不得被算作 `passed`，也不得让整体 `mode` 升级。**没有真实模型输出时，`mode` 永远不是 `real`。**

### 6.6 跨平台行尾：历史问题与 PR #21 跟进

T03 初次查证时发现：它**被 `.gitignore` 第 2 行的 `.*` 匹配并忽略，且 `git log` 对该文件为空——从未提交过**。也就是说文件里那两条 `eol=lf` 规则（注释里写着「否则 Windows checkout 会 trip acceptance/contract envelope tests」）**只存在于作者本机**：

```
*.go text eol=lf
cli/acceptance/testdata/**/*.json text eol=lf
```

本机 `core.autocrlf=true`，所以新克隆的 Windows 环境会把这些文件检出成 CRLF。写这几条规则的人显然发现了问题，但修法没有随版本库走。

**这超出 T03 范围，未在本次改动**（改它等于替全队改仓库配置，且会牵动 T04/T05 的契约测试）。T03 的对策是让合成资料判据不依赖检出方式（读取时按行尾归一，见 §4）。建议单独立任务：要么提交 `.gitattributes`，要么在 `.gitignore` 里放行它。

**跟进（PR #21，T03 §6.6）**：配置已提交在该 PR 分支，包含 `.gitattributes` 与 `.gitignore` 放行规则，声明 Go 源码与 CLI acceptance 合约 JSON 使用 LF。截至本次修订仍待复审和合并；是否进入 main 以 PR #21 的合并状态为准，不将本分支已提交写成主线已修复。

### 6.7 为跑通 S7 顺带修的构建问题（`docker/Dockerfile.app`）
