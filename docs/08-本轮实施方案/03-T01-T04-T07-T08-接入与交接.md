# 工作区基础切片：T01 / T04 / T07 / T08

本切片接入现有 WeKnora 服务，不新增账号、服务进程或前端请求层。它提供两章**演示模板**下的项目创建、研究条件保存、立项、章节手动编辑与 `GenerationContext`。该模板不是正式申报模板；资料绑定、带来源的正文、生成、确认和导出分别等待 T02 / T09–T14。

## 接在哪里

- 后端：`internal/lingdoc/workspacecore` 是只依赖 GORM 的领域服务；`internal/lingdoc/workspace` 是 Gin 薄适配；`internal/container` 注入实例；`internal/router` 在既有认证路由组内挂 `/api/v1/lingdoc/projects`。
- 存储：PostgreSQL `migrations/versioned/000097_lingdoc_workspace.*.sql`，SQLite `migrations/sqlite/000018_lingdoc_workspace.*.sql`。两者沿用仓库的迁移入口，启动时不运行 `AutoMigrate`。
- 前端：`frontend/src/api/lingdoc/workspace.ts` 沿用当前 Axios 请求封装；`/platform/lingdoc` 挂载项目、研究条件和章节编辑切片。

## 本机复核与运行

在仓库根目录执行 `go test ./internal/lingdoc/workspacecore -count=1`，无 C 编译器的 Windows PowerShell 先设置 `$env:CGO_ENABLED='0'`；在 `frontend` 执行 `npm ci`、`npm run type-check`、`npm run build-only`。测试使用隔离的磁盘 SQLite，并执行同一份生产 SQLite 迁移 SQL；覆盖重启读回、同版本双写、响应丢失重试、非成员隐藏、成员移除后的重放拒绝。独立启动和登录沿用仓库现有说明；登录后打开 `/platform/lingdoc`。开发时可选仓库已有的 SQLite/Lite 模式，部署 PostgreSQL 时执行对应版本迁移。密钥仍按仓库原方式放在环境配置，不写入项目资料表或仓库。

Windows 宿主机若未安装 C 编译器，整个服务的 Go 构建会在仓库已有的 `pg_query` 依赖处失败；这不是本切片的测试通过证据。2026-09-23 的本机 Docker Desktop 又因 WSL 服务异常无法启动，因此本轮只验证了领域服务、真实 SQLite 迁移及前端类型/产物构建；**尚未完成整个服务启动、PostgreSQL 迁移、浏览器登录后联调**。T01 的“第二人能启动”验收要在可用开发环境补做。

## 向后续任务交什么

| 消费方 | 入口 | 约束 |
| --- | --- | --- |
| T02 | `TemplateReader.Get(id, version)` | 当前 `ContractDemoTemplate` 仅供两章演示；替换时保持项目锁定的模板版本。 |
| T09 | `Service.Authorize(ctx, actor, projectID, capability)` | 检查活跃租户成员及项目成员；来源授权由 T09 自己检查，禁止把两者递归合并。 |
| T10 | `Service.GenerationContext(ctx, actor, projectID, chapterID)` | 一次一致读返回条件、模板引用、当前章与版本；生成任务应把这些版本记入 basis。 |
| T11/T12 | `Service.SaveChapter(...)` 及 `lingdoc_chapter_versions` | 章版本不可变，手动编辑继承全部待核事项，按预期章版本与条件版本拒绝冲突；候选采纳和确认需另做服务操作。 |

`Idempotency-Key` 按操作者、操作和目标记录请求体 hash，领域写入与响应同事务保存；历史重放先检查**当前**项目权限，再返回原结果并提示刷新。前端仅能编辑无来源的章节，后端也拒绝写入或改写带来源章节；T09 接入 `SourcePolicy` 后才放开，不能仅去掉前端禁用态。`access-status` 当前只表达项目成员资格，不代表资料权限已核查，T09 接入后必须补上来源当前状态。
