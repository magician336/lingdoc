# T15-01：真实服务在本机起一次并完成真实 HTTP 往返

状态：2026-09-27 在本机（Windows 11）实测**能起来**，并完成 5 步真实 HTTP 往返。机器生成的证据在 `docs/08-本轮实施方案/T15-S1-证据.json`（请求原文、响应原文、耗时、启动采样、环境变量变体与各项探针，凭据一律打码）。

对应票 #28；是 #27（T15 错误矩阵）与 T15-02…T15-11 全部「接真」票的前提。

## 结论

`cmd/server` 在宿主机直连已在跑的 docker 依赖可以正常起来。三个前提缺一不可：

1. 二进制按本仓的 Windows 配方构建（`go run` 在本机链接不了 duckdb）；
2. **cwd 必须是仓库根**——`config/config.yaml` 与 `migrations/versioned` 都是相对路径；
3. 把 `.env` 里三个容器主机名覆盖成宿主机回环（宿主机上 `postgres` / `redis` / `docreader` 这些名字解析不了）。

## 启动（可复现）

服务端**自己不读 `.env`**（`cmd/server` 没有 godotenv），环境变量必须由启动者注入；而 `.env` 也不在仓库里——它被 `.gitignore:2` 的 `.*` 覆盖，入库的是 `.env.example`。所以第一步是把入库的那份拷出来：

```powershell
Copy-Item .env.example .env      # 已经有 .env 就跳过
```

`cp` 这份够用：`dotenv_provenance` 逐键比过，两边键值只差 `JWT_SECRET`（各自一份即可，不影响启动）与本地多出的两个模型 key（`DASHSCOPE_API_KEY` / `DEEPSEEK_API_KEY`，启动不读）。同样的环境组合实跑过：`start_from_env_example` = 1.21s 就绪。

然后**在仓库根**跑下面这段——第一段把 `.env` 读进当前进程，第二段覆盖容器主机名，最后起服务。2026-09-27 用 PowerShell 5.1 原样跑过：**1.07s 就绪**，`/health` 返回 `{"status":"ok"}`（该次复跑记在证据的 `recipe_check`）：

```powershell
# 1) 把 .env 读进当前进程（跳过注释与空行，值原样保留）
Get-Content .env | Where-Object { $_ -match '^\s*[^#\s][^=]*=' } | ForEach-Object {
    $k, $v = $_ -split '=', 2
    [Environment]::SetEnvironmentVariable($k.Trim(), $v, 'Process')
}

# 2) 容器主机名 → 宿主机回环（这三条是必须的）
$env:DB_HOST        = '127.0.0.1'
$env:REDIS_ADDR     = '127.0.0.1:6379'
$env:DOCREADER_ADDR = '127.0.0.1:50051'

# 3) 可选：把下面几项也一并覆盖，理由见环境变量表
$env:LANGFUSE_ENABLED       = 'false'
$env:OLLAMA_BASE_URL        = 'http://127.0.0.1:11434'
$env:LOCAL_STORAGE_BASE_DIR = (Join-Path $PWD '.local-data\files')

# 4) 起服务（cwd 必须是仓库根）
& 'D:\code_warehouse\Projects\lingdoc-build\WeKnora-t15.exe'
```

其余变量沿用 `.env` 即可，各变量的类别与不覆盖的后果如下表。

| 变量 | `.env` 原值 | 宿主机建议值 | 类别 | 不覆盖会怎样 |
| --- | --- | --- | --- | --- |
| `DB_HOST` | `postgres` | `127.0.0.1` | **必须** | 起不来：panic，exit 2，3.17s 后死掉（其中 2.70s 是 DNS 超时）。`lookup postgres: no such host` |
| `REDIS_ADDR` | `redis:6379` | `127.0.0.1:6379` | **必须** | 起不来：panic，exit 2，10.07s 后死掉（多次 DNS 超时）。`连接Redis失败: dial tcp: lookup redis: no such host` |
| `DOCREADER_ADDR` | `docreader:50051` | `127.0.0.1:50051` | 建议 | 能起来（1.03s）。gRPC 是懒连接，启动只打一行 `Connected to docreader in 504.3µs`；**推断**：后续真调解析会连不上（本票没调过解析接口，见 §边界 4） |
| `LANGFUSE_ENABLED` | 未设 | `false` | 建议 | 能起来（1.04s）。`.env` 里两个占位密钥非空会**自动开启** Langfuse（`internal/tracing/langfuse/config.go:81-84`），host 指向 `langfuse-web:3000`，本机解析该名要 2.71s 后失败（`gaierror: [Errno 11001] getaddrinfo failed`），**推断**：只影响追踪上报（未验证上报失败是否被吞掉） |
| `OLLAMA_BASE_URL` | `http://host.docker.internal:11434` | `http://127.0.0.1:11434` | 建议 | 能起来（1.04s）。`host.docker.internal` 在本机**秒解析**到 `10.136.95.160`（是解析成功、并非解析失败），**推断**：连过去没响应会挂到超时；因为 `OLLAMA_OPTIONAL=true` 所以不阻塞启动 |
| `LOCAL_STORAGE_BASE_DIR` | `/data/files` | `<仓库>/.local-data/files` | 建议 | 能起来（1.03s）。启动不读这个目录，写入路径用 `os.MkdirAll` 按需创建（`internal/application/service/file/local.go:65`）；不覆盖的话产物会落到 `D:\data\files`，散在仓库外 |

「能起来 + 耗时」是逐项实跑的结果（每种变体只留该变量为 `.env` 原值、其余照常覆盖），落在证据的 `env_variants` 字段里；标 **推断** 的后果是从代码与日志读出来的，本票没有实跑。本机解析各主机名的实测值见证据的 `host_resolution`。

**什么都不给起不来。** 只保留覆盖表、连 `.env` 那份都不给，启动会死在依赖连接层：`container.go:734): 连接Redis失败: NOAUTH Authentication required.`（exit 2）—— 服务端没有 `REDIS_PASSWORD` 的默认值，所以 `.env` / `.env.example` 里的密码那条是必需的，不是可选的（证据的 `start_without_dotenv`）。

**端口不受 `APP_PORT` 控制。** 监听地址来自 `config/config.yaml` 的 `server.port`（当前 `8080`）。实测：`APP_PORT=8082` 时服务端自报 `Server is running at 0.0.0.0:8080`，探 8080 通、探 8082 不通（证据的 `port_knob_probe`）。要换端口就改 `config/config.yaml`（`.env` 的 `APP_PORT` 只管 compose 的宿主端口映射）。

## 起来需要多久（后续票等它就绪）

| 场景 | 就绪耗时 | 口径 | 落地字段 |
| --- | --- | --- | --- |
| 冷启动（首次，含迁移 96→103） | **11.06s** | 首行日志 → 首个 `/health` 200 | `cold_start.seconds_first_line_to_first_health` |
| 暖启动（库已迁到 103） | **1.02–1.04s**（8 次：3 次采集 1.04 / 1.02 / 1.04，5 个环境变量变体 1.02 / 1.03 / 1.04 / 1.04 / 1.03） | 进程启动 → 首个 `/health` 200 | `startup.warm_ready_seconds_all`、`env_variants[*].ready_s` |

两个口径不一样，别混用：暖启动那个含进程引导，冷启动那个不含（日志里最早的记录就是首行日志）。冷启动若要换成同一口径，再加进程引导的 ~0.6s ≈ 11.6s。

暖启动的 1.0s 是**上界**：采集按 0.2s 间隔轮询 `/health`，记录值比真正开始监听晚 ≤0.2s（轮询间隔）+ ≤0.2s（单次请求耗时）。用日志时间戳拆开（多次一致）：

- 首行日志 → `Server is running at 0.0.0.0:8080`：0.23–0.27s
- `Server is running at` → 首个 `/health` 200：0.36–0.40s（轮询 + 观测延迟）
- 由此推得「进程启动 → 真正开始监听」≈ 0.6s（推算，非直接测量）

**建议就绪判据**：轮询 `GET /health` 直到 200，间隔 0.25s，超时给 ≥15s——冷启动 11.6s 是最坏情况，暖启动留的余量也更足。等价地，等 stdout 出现 `Server is running at 0.0.0.0:8080`（`cmd/server/main.go:132`）会比首次 200 早约 0.4s，但要按行读日志。

不要拿 `[gin] registered 0 routes`（`internal/runtime/startup.go:57`）当就绪或健康判据：release 模式下 gin 不打印路由注册，这行恒为 0，没有信息量。

## 起不来时卡在哪一层（实测）

四层都真跑过（脚本 `.scratch-t15-failures.py`，逐条进程级实跑；机器证据在 `docs/08-本轮实施方案/T15-S2-证据.json`）：

| 触发条件 | 卡在哪一层 | 表现 | 退出码 | 进程多久死掉 |
| --- | --- | --- | --- | --- |
| cwd 不是仓库根 | **配置层** | panic：`LoadConfig … error reading config file: Config File "config" Not Found in "[<cwd> <cwd>\config $HOME\.appname /etc/appname/]"` | 2 | 0.45s |
| `DB_HOST` 未覆盖 | **依赖连接层** | panic：`initDatabase … failed to connect to 'user=postgres database=WeKnora': hostname resolving error: lookup postgres: no such host` | 2 | 3.17s |
| `REDIS_ADDR` 未覆盖 | **依赖连接层** | panic：`initRedisClient … 连接Redis失败: dial tcp: lookup redis: no such host` | 2 | 10.07s |
| 8080 已被占用 | **绑定层** | `Port 0.0.0.0:8080 in use, retrying in …`（10 次尝试、9 次退避等待：0.3/0.6/1.2/2.4/3×5）→ `FATAL Failed to run application: failed to start server: listen tcp 0.0.0.0:8080: bind: …` | 1 | 20.16s |
| 迁移失败 | **不卡** | `ERROR Migration failed: …` → `WARNING Migration caused dirty state at version 1` → `INFO Attempting to recover from dirty state...` → `WARNING Database migration failed: …` → **`WARNING Continuing with application startup. Please run migrations manually if needed.`**，服务照常就绪 | 未退出 | 1.07s 就绪 |

三条要点：

- **依赖连接层为什么不是「秒失败」：** 本机解析一个不存在的短主机名每次要 **约 2.7s**（多次独立测量都在 2.68–2.71s 之间：S2 的 `dns_lookup_of_missing_short_names` 是 postgres 2.70s / redis 2.70s，S1 的 `host_resolution` 是 postgres 2.68s / langfuse-web 2.71s；失败原因都是 `gaierror: [Errno 11001] getaddrinfo failed`，即 Windows 的 DNS 搜索列表 + NetBIOS 回退在等超时）。postgres 那条 = 0.45s 启动 + 一次 DNS 超时；redis 那条 = 0.45s + 若干次 DNS 超时（go-redis 自己会重试）。**报错快慢由 DNS 超时决定，不是代码在死等。** 想立刻失败就把地址换成一个必然被拒的回环端口，而不是留容器主机名。
- **迁移层失败不阻断启动。** 实测（一次性探针库 + 仓外临时 cwd，`migrations/versioned` 里放一条语法错误的迁移）：迁移报错、走完 dirty 自动恢复、仍打出 `Container initialization completed successfully` 与 `Server is running at 0.0.0.0:8080`，并在 1.07s 内答出 `/health` 200。**所以「服务起来了」不等于「迁移跑成功了」**——后续票若要依赖某个新表，必须另外确认 `schema_migrations`。探针库跑完即删，dev 库的 `schema_migrations` 全程保持 `103/false`。
- **dig panic 最外层的函数名不是根因。** 上面几条 panic 的开头分别是 `registerModelConcurrencyLimiter` / `registerPoolCleanup` / `registerModelConcurrencyLimiter`——它们只是第一个需要那个依赖的消费者。真正的根因在每个 `received non-nil error from function …` 链尾（`initDatabase` / `initRedisClient` / `LoadConfig`）。查错直接看链尾，别追最外层。

## 边界（没验证到的，如实记下）

1. **Ctrl+C 优雅退出没测过。** 进程由脚本启动（没有控制台 stdin），停服一律用 `taskkill /F /PID <pid>`。代码里有 `signal.Notify` 与 30s `ShutdownTimeout`（`cmd/server/main.go:93-129`），但从未实跑。这对 T15-02…T15-11 的 runner 有直接影响：要么收尾用强杀，要么在 Windows 上给进程发 CTRL_C_EVENT。
2. **冷启动那次 10.68s 停顿未定位。** 日志把它夹在 `initNeo4jClient`（`internal/container/container.go:1679`，08:46:01.940）与 `sandbox.go:140 newTenantSandboxResolver`（08:46:12.618）之间——这是启动窗口内最大的一段空白，两端日志原文都在证据的 `cold_start.biggest_gap_before_listening` 里。之后 8 次暖启动采样（含 5 种环境变量变体）都没再现。已排除：Ollama 拨号超时（对照跑 1.04s）、Langfuse 上报、换路径新副本的冷文件/杀软扫描、jieba 词典。**首次启动的等待要留足 ~15s。**
3. **anydoc 引擎不可用**：`third_party/anydoc-go/lib` 不存在，涉及 anydoc 的解析路径在本机跑不了。
4. **docreader 只证明了「地址通 + 懒连接不阻塞启动」**，没有真的调过一次解析接口。
5. **没有真实模型**：本机没有在跑 Ollama，涉及模型调用的场景仍应标 `not_run`。
6. **结论只覆盖 Windows 宿主机。** Linux/macOS 上这套覆盖表要重做，至少 `OLLAMA_BASE_URL` 里的 `host.docker.internal` 语义不同。

### 证据怎么复核（脚本为什么不在仓库里）

产出上面两份证据的脚本（`.scratch-t15-capture.py`、`.scratch-t15-failures.py`、`.scratch-t15-buildprobe.py`）与原始服务日志都是仓内 `.scratch-t15-*` 文件（被 `.gitignore` 的 `.*` 覆盖），**不入库**：本票要交付的是「服务能起」这个事实和配方，把三个带本机绝对路径的一次性脚本搬进仓库只会立刻成为下一票的包袱——T15-02 要的是 `scripts/lingdoc_mock/` 下参数化的 runner（见 #27）。代价是复核者手边没有脚本，所以逐行给出手工复核办法：

| 想复核什么 | 怎么做 |
| --- | --- |
| 服务能不能起、多久就绪 | 按 §启动 的配方原样跑一遍；`/health` 首次 200 的耗时就是 `startup.ready_seconds_*` 的口径 |
| 「不覆盖会怎样」表的每一行 | 同样跑，但把表里那一项删掉（或设回 `.env` 原值）；`env_variants` 就是这么逐项做出来的 |
| 失败矩阵的每一行 | S2 每条的 `trigger` 字段写明了如何制造该条件（cwd 换成哪、哪个变量设回原值、端口被谁占着），照做即可复现；错误原文与 `root_cause` 直接对日志 |

三处都是幂等的：同一条件重跑得到同一量级结果（启动耗时是秒级量，抖动约 ±0.05s）。
